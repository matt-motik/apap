Профессиональные плееры (Foobar2000, Audirvana, VLC) работают так: GUI статичен, пока не произошло явное событие изменения данных. Никаких фоновых пересчетов "на всякий случай" или постоянных опросов файловой системы, если это явно не запрошено пользователем.
Вот формализация правильного поведения (State Machine) для приложения:
1. Состояние покоя (Idle)

    Триггер: Запуск приложения или завершение всех операций.
    Поведение:
        GUI полностью статичен.
        (если играет трек) Таймер тикает только для обновления прогресс-бара и времени (легкая операция).
        Запрещено: Пересчет ширины колонок, проверка файлов, сканирование дисков, обновление моделей списков.
        Ресурсы: CPU ~0% (кроме ожидания событий ОС).

2. Добавление треков (Add Files/Folders)

    Действие пользователя: Выбор файлов в системном диалоге -> Нажатие "Открыть".
    Логика (Background):
        Диалог закрывается.
        Запускается асинхронная задача (в отдельном потоке tokio::spawn или std::thread).
        Сканер читает метаданные файлов.
        Формируется новый список треков в памяти (буфер).
        Важно: В этот момент GUI плейлиста не меняется. Пользователь видит старый список (или пустоту). Курсор может смениться на "песочные часы" или спиннер, но интерфейс не виснет.
    Завершение (Commit):
        Сканирование завершено.
        Новый список атомарно подменяет старый в модели данных.
        Вызывается однократное обновление UI (sync_playlist_to_ui), которое перестраивает модель списка один раз для всего пакета новых треков.
        Если включено автовоспроизведение — запускается первый трек.

3. Удаление треков

    Действие: Выделение -> Delete.
    Логика:
        Удаление из внутренней структуры данных (Vec).
        Вызов метода удаления строк из UI модели (model.remove(index)), а не полная пересборка (model = new_model).
        Сохранение измененного плейлиста на диск (опционально, с debounce).

4. Сортировка и Фильтрация

    Действие: Клик по заголовку колонки или ввод в поиск.
    Логика:
        Сортировка происходит в памяти (быстро).
        UI обновляется одним вызовом model.set_vec(sorted_data) или, в идеале, перемещением строк (model.move_row), чтобы анимация была плавной.
        Никакого пересчета ширины колонок при сортировке! Ширина меняется только при явном ресайзе пользователем или первом открытии окна.

5. Настройки (Settings Dialog)

    Поведение: Как обсуждали ранее (Snapshot pattern).
    Изменения применяются только после нажатия "Сохранить".
    При сохранении темы или шрифтов — полная перерисовка окна.
    При сохранении устройства аудио — рестарт аудио-движка.

Что конкретно нужно исправить в коде прямо сейчас:

    Убрать сканирование из главного потока. Если у вас есть цикл for file in files { add_track(file); update_ui(); } — это убийца производительности. Нужно собрать Vec<Track> в фоне, потом один раз отдать в UI.
    Атомарное обновление модели. Вместо self.model.set(Vec::new()) + цикл push, делать self.model.set(new_full_vec). Slint оптимизирует замену всего вектора лучше, чем множество мелких push-операций, вызывающих перерисовку на каждом шаге.
    Исключить "шумные" события.
        Убрать вызовы save_columns_width() из каждого события Moved. Оставить таймер с интервалом 1-2 секунды, который сохраняет, только если ширина реально изменилась.
        Убрать любые проверки exists() или metadata() из цикла отрисовки или таймера.

Сравнение с Foobar2000:

    Foobar: Вы кидаете 1000 файлов -> Он думает 0.5 сек (сканирует в фоне) -> БАЦ, и список появился целиком.
    Ваш текущий код (вероятно): Вы кидаете файлы -> Список дергается, добавляя по одной строке, интерфейс фризит на 2-3 секунды.

Резюме: Да, список файлов в плейлисте перестраивается только по факту явного действия пользователя (добавление/удаление/перетащил файл в окно). Фоновое слежение за папкой (Watchdog) — это отдельная фича, которая должна быть выключена по умолчанию, так как она создает нагрузку на диск и CPU.
