Task: Implement Professional Settings Lifecycle & Robust Audio Initialization
Context
We are refactoring a Rust music player (Slint UI) to behave like professional desktop applications (e.g., VLC, Foobar2000, Audirvana). 
Current issues:

    Settings Logic: Changes apply immediately on every click, causing disk I/O spam and preventing "Cancel" functionality.
    Audio Init: Audio device validation only happens when pressing "Play", leading to delayed error messages.
    Config Access: Config is re-read or accessed inefficiently in some paths.
    UI Responsiveness: Settings window feels sluggish or unresponsive on first click due to blocking operations during initialization.

Objectives
1. Refactor Settings Window to "Edit-Commit" Pattern (Critical UX Fix)
Current Behavior: Changing a dropdown or checkbox immediately updates the global Settings struct and writes to disk (save()). This causes lag and makes "Cancel" impossible.
Required Behavior:

    On Open (open_settings): Create a local temporary copy (snapshot) of the current Settings. Populate the UI fields from this snapshot, not the live global settings.
    On Interaction: User modifications (theme change, column toggle, device selection) update only the temporary local copy. No disk I/O occurs here.
    On "Save" Click: 
        Validate the temporary settings.
        Apply them to the global Settings object.
        Serialize to disk (save()) exactly once.
        Apply side effects (e.g., switch theme, restart audio stream if device changed).
        Close the window.
    On "Cancel" / Close: Discard the temporary copy. Global settings remain unchanged.

2. Robust Audio Device Initialization at Startup
Current Behavior: App starts blindly. Errors like snd_pcm_dmix_open: unable to open slave only appear when the user tries to play a track.
Required Behavior:

    Probe on Start: Immediately after loading config, attempt to initialize the audio stream with the saved device name.
        Use a real open/play/sleep/drop cycle (~50-100ms) to verify hardware availability (catching ALSA backend errors early).
    Graceful Degradation:
        If the probe fails: 
            Set an internal audio_ready = false flag.
            Update Status Bar: "Audio device unavailable — playback disabled: <error>".
            Update Tray Tooltip: Show the error message.
            Do not crash the app. Allow the user to open Settings and fix it.
        If the probe succeeds: Proceed normally.

3. Unified Config Access (Architecture)

    Ensure Settings are loaded once at startup into a central owner (MusicApp).
    Implement a thread-safe, read-only global accessor (e.g., OnceLock<Settings>) for modules that need to read config (like tray, cover art) without passing references everywhere.
    Constraint: Only MusicApp (specifically the Settings Dialog logic) should have mutable access to write/save.

4. Settings Window Data Binding Fixes

    Device List: When the Settings window opens, the "Output Device" dropdown must be pre-populated with available devices.
        The saved device from config should be selected.
        If the saved device is invalid/missing, select a "(Select Device)" placeholder.
    Responsiveness: Ensure populating the device list or loading the settings snapshot does not block the UI thread. If scanning devices takes time, do it asynchronously or ensure it's fast enough (<16ms).

Implementation Plan
Step 1: Config & State Structure

    Modify Settings struct to support cloning (for the snapshot).
    Implement SettingsSnapshot or simply use clone() for the dialog's local state.
    Set up the global read-only accessor (e.g., static CONFIG: OnceLock<Settings>).

Step 2: Audio Probe Logic (src/audio/output.rs)

    Create pub fn probe_device(device_name: Option<&str>) -> Result<(), String>.
    Integrate this call into MusicApp::new() immediately after loading settings.
    Handle the failure case by updating UI status variables (status_text, tray_tooltip).

Step 3: Settings Dialog Refactor (src/settings.rs / app.rs)

    open_settings(): 
        Clone global settings to dialog_state.
        Bind UI inputs to dialog_state fields (two-way binding for the dialog only).
        Populate device dropdown using output::get_devices().
    on_save(): 
        Copy dialog_state -> global settings.
        Call settings.save().
        Trigger necessary restarts (audio stream, theme reload).
    on_cancel() / close: 
        Drop dialog_state. No save action.

Step 4: Verification

    Verify that clicking "Cancel" after changing themes/devices reverts changes.
    Verify that no disk writes occur while tweaking sliders/dropdowns in the settings window.
    Verify that starting the app with a broken audio config shows the error immediately in the status bar, not later.

Expected Outcome

    Snappy UI: No lag when clicking settings options (no disk I/O).
    Safety: Users can experiment with settings and cancel without side effects.
    Reliability: Audio errors are caught at boot, providing clear feedback.
    Professional Feel: Behavior matches standard desktop applications.
