## Правила пользователя (обязательны)

Пользователь долго добивался этой модели в предыдущей версии спецификации:

1. Файл конфига читается с диска один раз при запуске и хранится в одной переменной, с которой работает приложение.
2. Файл конфига меняет только сама программа. Следить за его изменениями на диске не нужно.
3. Файл конфига сохраняется при выходе из приложения.
4. Файл конфига сохраняется по кнопке «Сохранить» в окне настроек, если настройки отличаются.
5. Окно настроек работает с копией настроек. По «Сохранить» значения копии сравниваются с действующими, применяются только изменившиеся, полной переинициализации нет. По «Отмена» копия уничтожается, ничего не применяется, файл не меняется.
6. Изменение ширины колонок плейлиста не пишет файл.
7. Изменение громкости не пишет файл.
8. Перемещение ползунка позиции в треке не пишет файл.
9. Смена типа визуализации в меню не пишет файл.
10. Смена типа визуализации меняет переменную настроек (в памяти).
11. Колёсико мыши над ползунком громкости меняет громкость так же, как над иконкой в трее.
12. Горячие клавиши громкости (будущие) двигают ползунок громкости.
13. Колёсико над иконкой в трее двигает ползунок громкости.
14. Сортировка по колонке не перезаписывает файл плейлиста.
15. Плейлист перезаписывается при изменении добавление/удаление треков.
16. При смене сортировки в настройках хранится только колонка сортировки. Порядок песен в файле плейлиста не меняется.

Уточнения пользователя:

- **Окно настроек модальное.** Главное окно во время диалога недоступно.
- **Трей** в прошлой версии умел менять только громкость. В режиме bit-perfect (монопольный доступ) громкость в трее не работала. Это поведение нужно перенести на новые режимы.

## Принятые решения (пользователь согласился, их нужно оформить)

1. **ADR-19, новый пункт «Моменты записи».** `settings.toml` пишется только при выходе и по «Сохранить» в диалоге, если есть отличия. Писатель один, он пишет снимок всего `Settings`. `EngineCmd::SetModeSettings` только применяет настройки и файл не пишет. Файлы данных (`bp_tests.toml`, `track_marks.toml`, плейлист) пишутся по своим событиям. Отдельно нужно решить, как защититься от потери несохранённого состояния при сбое (см. «Задачи», п. 6).
2. **§4.2 и §6.27.** Убрать «Сохранение — через `PersistStore` в потоке движка (UI отправляет `SetModeSettings`)». Владелец `Settings` и инициатор записи — UI.
3. **§6.27, диалог.** Диалог работает с копией. Сравнение трёхстороннее (`base` при открытии, `edited`, `current`): применяются только поля, где `edited ≠ base`. «Отмена» уничтожает копию. Добавить таблицу «параметр → действие движка».
4. **ADR-15.** Порядок воспроизведения совпадает с видимым (отсортированным) порядком, сортировка стабильная. Ключ и направление сортировки хранятся в настройках. Ручное перетаскивание сбрасывает ключ сортировки и меняет исходный порядок.
5. **§6.18.** Колёсико, горячие клавиши и трей меняют громкость активного режима (громкость хранится для каждого режима отдельно, ТЗ-93). В Строгом режиме громкости нет (ТЗ-41, И-Т1): эти действия ничего не делают, ползунок неактивен.

## Найденные проблемы (проверь и уточни)

- **П-1. Запись при каждом изменении.** §4.2: движок получает `SetModeSettings` «при каждом изменении». §6.27: «Сохранение — через `PersistStore` в потоке движка (UI отправляет `SetModeSettings`)». §6.2 п. 4 повторяет «при каждом изменении». В таблице §4.2 владелец файлов — «движок (`PersistStore`)». Вместе это читается как «каждый `SetModeSettings` пишет файл». Тогда громкость (поле `CompatibleOpts`/`OptimalOpts`) и переключение режима пишут файл, что нарушает правила 3, 4, 7.
- **П-2. Два писателя одного файла.** `[playback]` пишет движок, остальные разделы (колонки, визуализация, сортировка) принадлежат UI. Это противоречит правилу 1 и грозит затиранием разделов.
- **П-3. Откат изменений, сделанных мимо диалога.** При сравнении копии с действующим конфигом (правило 5) значения, изменённые вне диалога во время его работы, откатываются. Диалог модальный, поэтому главное окно закрыто, но **трей, медиа-клавиши и MPRIS модальностью не блокируются**. Проверь, так ли это в текущем коде (см. «Задачи», п. 2).
- **П-4. «Применяются только изменившиеся» не определено.** `SetModeSettings(ModeSettings)` передаёт структуру целиком. Разница между старой и новой структурой описана только для смены режима (§6.18). Для буфера устройства §6.7/§6.18 фактически дают «применится при следующем `Open`». Нужна таблица «параметр → действие». Черновик:

  | Изменилось | Действие |
  |---|---|
  | опции неактивного режима | ничего, только память |
  | громкость, mute | атомик и новый снимок пути, без переоткрытия |
  | фильтр SRC, дизеринг, фильтр и компенсация DSD→PCM, правило частоты | переоткрыть текущий трек с позиции (или «со следующего трека» — вопрос пользователю) |
  | буфер плеера, буфер устройства | переоткрыть сессию; для буфера устройства `configure` без освобождения замка |
  | устройство | освободить и захватить новое (§6.19) |
  | `active` | «Смена режима», §6.18 |

- **П-5. Громкость в Строгом режиме.** Правила 11–13 не учитывают, что в Строгом режиме громкости нет, а в остальных она своя для каждого режима.
- **П-6. Сортировка и `Sequencer`.** ADR-15 и §6.21 говорят «следующий по порядку воспроизведения», но не определяют, видимый это порядок или исходный. При загрузке сортировку нужно применить заново по тегам. Значит, теги должны быть в файле плейлиста или в кэше, иначе на старте придётся читать все файлы.
- **П-7. Правило 15.** Плейлист — это данные, а не настройка. Проверь, что значит «при сохранении» в текущем коде: кнопка «Сохранить» в настройках, явное сохранение плейлиста, изменение состава, выход?
- **П-8. Потеря при сбое.** В релизе `panic = "abort"` (проверь в `Cargo.toml`). При панике или `SIGKILL` (ТЗ-120) путь выхода §6.28 не выполняется, и всё, что изменилось после последнего «Сохранить», теряется: громкость, режим, сортировка, ширина колонок.
- **П-9. Надёжность записи.** ADR-19: временный файл, затем `rename`, но без `fsync` временного файла (и каталога) перед `rename`. После пропадания питания возможен пустой файл.
- **П-10. Коррекция при загрузке.** `load_mode_settings` (§6.27, И-Р22) исправляет значения только в памяти. Спецификация должна прямо сказать, что исправления попадают в файл при следующем сохранении, а не сразу.

## Задачи

1. **Текущее поведение в коде.** Найди все места, где пишутся `settings.toml`, файл плейлиста и другие файлы состояния (поиск по `write`, `save`, `persist`, `rename`, `toml::to_string`, `fs::write`, `File::create`, имена менеджеров настроек, например `viz_settings_manager.rs`). Для каждого места укажи, какое событие вызывает запись. Сведи в таблицу «событие → пишет ли файл → файл:строка» и сверь с правилами 1–16. Отдельно проверь громкость, ширину колонок, сортировку, визуализацию, ползунок позиции, смену режима, выход.
2. **Модальность диалога.** Проверь, как в Slint реализован диалог настроек (отдельное `Window`, `PopupWindow`, флаг блокировки). Действительно ли он блокирует главное окно на всех платформах (Linux X11/Wayland, Windows, macOS)? Какие источники изменений остаются активными во время диалога: трей (свой поток или runtime `tokio`), медиа-клавиши, MPRIS, сигналы? Вывод: нужно ли трёхстороннее сравнение, или хватит двухстороннего с блокировкой внешних изменений на время диалога. Рекомендуемый вариант — трёхстороннее сравнение как дешёвая страховка; подтверди или опровергни.
3. **Трей и громкость.** Найди в коде прежнюю логику трея: «громкость не работает в bit-perfect». Как её перенести на новые режимы: Совместимый — есть; Оптимальный — есть (ТЗ-93, ОВ-5: по умолчанию 100 %); Строгий — нет. Сверь с ТЗ-41, ТЗ-93, ТЗ-95 и матрицей §5 ТЗ. Если ТЗ требует для Оптимального режима другого поведения, вынеси это как вопрос.
4. **Сортировка и плейлист.** Какой формат у файла плейлиста, хранит ли он теги? Где хранится текущая сортировка? Как `Sequencer` (ADR-15, §6.21) должен получать порядок: индексы видимого порядка, перестановку, `TrackId`? Что происходит с Shuffle при смене сортировки? Предложи минимальную модель: исходный порядок + `Option<SortKey>` + стабильная сортировка + сброс ключа при перетаскивании.
5. **Соответствие ТЗ.** Найди в `02_tz.md` все требования о сохранении, загрузке и применении настроек (ТЗ-19, ТЗ-45, ТЗ-93, ТЗ-97, ТЗ-106, ТЗ-120, ТЗ-124 и другие). Выпиши, какие правила пользователя ТЗ уже покрывает, какие противоречат ТЗ и какие нужно добавить в ТЗ.
6. **Сравнение с другими плеерами.** Как разделяют «конфигурацию» (меняется в диалоге) и «состояние сессии» (громкость, колонки, сортировка, позиция) и когда пишут на диск: MPD (`state_file`, `state_file_interval`), foobar2000, audrvana, hqplayer, roon открытые данные). Для каждого — источник. Цель — варианты защиты от сбоя (П-8):
   - а) принять потерю и записать это в спецификацию;

   - в) разделить `settings.toml` (только диалог и выход) и отдельный `state.toml` (громкость, колонки, сортировка, визуализация, последний трек) с отложенной записью.
   
   Для каждого варианта оцени, противоречит ли он правилам пользователя. Выбор оставь пользователю.
7. **Надёжность записи.** Порядок `write → fsync(tmp) → rename → fsync(dir)` на Linux; аналоги на Windows (`MoveFileExW` с `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`, `ReplaceFileW`) и macOS (`F_FULLFSYNC`). Нужна ли новая зависимость (например, `tempfile`, `atomicwrites`) или хватит `std` + `libc` (уже в дереве, см. шапку спецификации)?
