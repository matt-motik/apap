## 1. Цель и комплект

**Цель.** Получить факты для нормализации колёсика по решению 3 задачи 02 (`01_review.md`), ТЗ-36, НФ-2, НФ-8, ОВ-11 (`02_tz.md`), ТЗ-141 и ОВС-20 (01_audio_modes):
- все источники громкости ведут себя одинаково;
- шаг 2 % за щелчок, «вверх» — громче;
- тачпад не даёт десятков шагов за одно движение;
- системная инверсия прокрутки уважается.

**Комплект** — `tools/wheel_probe/` (самостоятельный крейт):
- `README.md` — что это, запуск вручную, формат результатов;
- `OPENCODE.md` — готовый промт для агента opencode на другой ОС;
- `src/main.rs` — мастер замера. Окно Slint с копией ползунка плеера (`ui/top_panel.slint:464-492`) и иконка трея ksni на Linux. В CSV пишутся три источника:
  - `slint` — `scroll-event` ползунка (`TouchArea`);
  - `winit` — сырой `WindowEvent::MouseWheel` всего окна (через `slint::winit_030`, feature `unstable-winit-030`): `LineDelta`/`PixelDelta` и `TouchPhase`;
  - `tray` — `ksni::Tray::scroll`: `delta`, `orientation`.
- `results/<os>_<backend>_<desktop>/` — `env.txt`, `summary.txt`, `NN_<device>_<target>_<action>.csv`.

**Шаги мастера:**
- мышь — 4 действия;
- тачпад — 6 действий, при включённой и при выключенной естественной прокрутке;
- высокоточное колесо — 4 действия;
- каждый шаг выполняется над ползунком и над треем. На Linux всего 40 шагов, на Windows и macOS — 20 (без трея).

**Проверка комплекта (Linux, KDE Plasma 6.7.4, Wayland, 2026-09-27):**
- `cargo build --release`, `cargo clippy --release --all-targets -- -D warnings` — без предупреждений; `cargo test` — 2 теста зелёные;
- пробный запуск: бэкенд окна `wayland`, StatusNotifierItem зарегистрирован;
- сборка под Windows на этой машине не проверялась; фактически комплект собран и запущен на Windows 10 (замер `windows_win32_windows`, §2.2). Под macOS не собирался.

**Особенности записи, важные для анализа** (`tools/wheel_probe/src/main.rs`):
- `winit` пишет события всего окна, `slint` — только над ползунком. Поэтому событий `winit` бывает больше, чем `slint` (указатель вышел за ползунок).
- Строка `crates:` в `env.txt` — константа в коде зонда (`main.rs`, `write_env`), а не определённые при запуске версии. Фактические версии задаёт `tools/wheel_probe/Cargo.lock`.
- «Повторить» очищает события шага и нигде не протоколируется: число повторов по данным не восстановить.
- Цель шага в имени CSV — из сценария мастера, а не из фактического источника событий. Если пользователь прокрутил не над той целью, в файле `*_tray_*` окажутся события `slint`/`winit` и наоборот (§2.2, аномалии).

## 2. Среда

**Версии** (корневой `Cargo.lock`; `tools/wheel_probe/Cargo.lock` с ними совпадает — проверено в этой сессии): `slint` 1.17.1, `i-slint-backend-winit` 1.17.1, `i-slint-core` 1.17.1, `winit` 0.30.13, `ksni` 0.3.6, `zbus` 5.19.0, `tokio` 1.53.1, `smithay-client-toolkit` 0.19.2, `wayland-client` 0.31.15. Файлы комплекта (`Cargo.toml`, `Cargo.lock`, `src/`) не менялись ни в одном коммите с результатами (`git diff 815d874 <коммит> -- tools/wheel_probe/{Cargo.toml,Cargo.lock,src}` пуст для всех шести коммитов). Расхождений версий с плеером нет.

**Как Slint 1.17.1 передаёт колёсико** (исходники в `~/.cargo/registry`):
- `i-slint-backend-winit-1.17.1/event_loop.rs:401-421`: `LineDelta(lx, ly)` → `(lx·60, ly·60)`; `PixelDelta` → логические пиксели по коэффициенту масштаба; `TouchPhase` переносится в `MouseEvent::Wheel { phase }`.
- `i-slint-core-1.17.1/items/input_items.rs:193-196`: `TouchArea` вызывает `scroll-event` с `PointerScrollEvent { delta_x, delta_y, modifiers }` — **фаза отбрасывается**, поля типа дельты нет.
- Итог: в `scroll-event` различие `LineDelta`/`PixelDelta` потеряно (`LineDelta 1` и `PixelDelta 60 px` неразличимы), фазы нет.

**Как winit 0.30.13 формирует `MouseWheel`:**

| Платформа | Источник в winit | Тип дельты | Фаза |
|---|---|---|---|
| Wayland | `platform_impl/linux/wayland/seat/pointer/mod.rs:172-215` | `LineDelta(-discrete)`, если композитор прислал `axis_discrete`; иначе `PixelDelta(-absolute)` | `Ended` по `axis_stop`; для дискретных — всегда `Moved` |
| X11 | `platform_impl/linux/x11/event_processor.rs:1079-1164` | `LineDelta`, в т.ч. дробная для гладкой прокрутки XI2 | `Moved` |
| Windows | `platform_impl/windows/event_loop.rs:1727-1760` | `LineDelta(value / 120)` из `WM_MOUSEWHEEL` | всегда `Moved` |
| macOS | `platform_impl/macos/view.rs:663-699` | `PixelDelta` при `hasPreciseScrollingDeltas`, иначе `LineDelta` | `momentumPhase`, затем `phase`; инерция отдельным признаком не помечается |

`smithay-client-toolkit` 0.19.2 привязывает `wl_seat` версий 1…7 (`seat/mod.rs:94`), значит `wl_pointer` ≤ 7 и `axis_discrete` приходит. Протокол (`wayland-client-0.31.15/wayland.xml`, `wl_pointer.axis_discrete`): «continuous scrolling devices like two-finger scrolling on touchpads do not have discrete steps and do not generate this event».

**Ползунок громкости плеера.** `ui/top_panel.slint:464` — `TouchArea` вокруг вертикального `Slider`:
- `scroll-event` (`:471`) реагирует только на `delta-y ≠ 0`;
- шаг ±0,04 за событие независимо от величины дельты, `delta-y > 0` → громче (`:473`);
- Shift и горизонтальная ось не обрабатываются.

## 4. Выводы по фактам

### 4.1. Величина одного щелчка мыши

| Платформа | Над ползунком (slint / winit) | Над треем (ksni `delta`) | Основание |
|---|---|---|---|
| KDE Wayland | 60 px / `LineDelta` 1 | 120 | KDE-1…3, шаги 01–08: единственное значение во всех событиях |
| GNOME Wayland | 60 px / `LineDelta` 1 | 1 | GNOME-1, 2, шаги 01–08 |
| Windows 10 | 60 px / `LineDelta` 1 (120 ед. `WHEEL_DELTA`) | трея нет | Windows, шаги 01–04 |

Разброса нет: медиана = min = max. Обычное колесо высокоточных значений не давало ни на одной платформе (высокоточное колесо не измерено).

### 4.2. Знак «вверх»

| Платформа | Ползунок (slint/winit) | Трей | Совпадает ли с ползунком | Текущий код плеера (`delta < 0` → громче в трее, `delta-y > 0` → громче на ползунке) |
|---|---|---|---|---|
| KDE Wayland | `+` | `+120` | да | ползунок верно; **трей инвертирован** (вверх → тише) |
| GNOME Wayland | `+` | `−1` | **нет** | ползунок верно; трей верно |
| Windows | `+` | — | — | ползунок верно |

Знак трея зависит от хоста StatusNotifierItem: KDE (Plasma) и расширение AppIndicator на GNOME присылают противоположные знаки для одного и того же направления колеса. Комментарий в коде плеера (`src/app/mod.rs:1738-1740`: «Ubuntu: ±1, KDE/4k: ±120… Negative delta = louder») верен для величин, но знак верен только для GNOME.

### 4.3. Shift и горизонтальная ось

- С зажатым Shift на всех платформах дельта остаётся вертикальной: `delta_x = 0`, `delta_y` как без Shift, модификатор `shift` приходит и в `slint`, и в `winit` (все шаги 04). Ни winit 0.30.13, ни Slint 1.17.1 не переводят Shift+колесо в горизонтальную ось на измеренных платформах. Трей с Shift: KDE `Vertical +120`, GNOME `Vertical −1` — как без Shift.
- Горизонтальных событий нет ни в одном замере (`delta_x = 0` везде, `orientation` трея — только `Vertical`). Наклон колеса и горизонтальный свайп мастером не предусмотрены — **пробел** (§7.3).

### 4.4. Быстрая прокрутка мышью

Склейки щелчков нет: в шагах 03 и 07 каждое событие равно одному делению (`±1`, `±60`, `±120`, `±1` в трее GNOME) при интервалах до 4 мс (KDE-2), 8 мс (KDE-3, GNOME-2, трей KDE-1), 16 мс (Windows). Число событий равно числу сделанных щелчков. Для эмулирующего колесо «тачпада» на KDE склейка есть (до 11 делений в одном событии, §4.5) — значит, KWin суммирует деления за кадр; для мыши при измеренной скорости это не проявилось.

### 4.5. Тачпад

**Windows 10 (настоящий тачпад с точными дельтами):**
- значения дробные, кратны 1/120 строки; в медленном свайпе медиана |delta| — 3–6 ед. `WHEEL_DELTA` (0,025–0,05 строки), интервал ≈ 12 мс (≈ 83 Гц);
- сумма на свайп: короткий — 0,7…2,2 строки (42,5…133 px); длинный медленный — 4,8…6,8 строки (288,5…408,5 px); быстрый с «броском» — 71…352 строки (4 268,5…21 135 px), почти вся сумма — инерция (§4.6);
- 5 из 2893 событий тачпада (0,17 %) — точно кратные 60 px (одна строка и более) и по отдельности неотличимы от щелчка мыши (шаги 10, 13, 16);
- в конце коротких свайпов бывают 1–5 событий обратного знака по 1 ед. `WHEEL_DELTA` (шаги 05, 11, 14) — отрыв пальцев;
- одиночные выбросы ≈ 67 строк за событие (§3.4) — в 3 из 6 шагов быстрого свайпа; причина не установлена.

**KDE и GNOME (устройство, которое композитор видит как колесо, §2.2):**
- значения целые; одно событие — 1…11 делений на KDE (ползунок и трей), над ползунком на GNOME — всегда 1 деление за событие, в трее GNOME — 1…11;
- сумма на свайп (в делениях): короткий — 1…21 (выброс 58 в KDE-3 шаг 15 — по длительности 558 мс это не короткий свайп); длинный медленный — 10…42; быстрый — 42…263;
- интервал 16–34 мс в длинных свайпах.

**Влияние «естественной прокрутки»** (знак дельты, которую видит программа):

- На GNOME и Windows ОС применяет инверсию до программы: знак меняется вместе с настройкой, одинаково над ползунком и над треем (GNOME).

Возможно, пользователь выбрал в мастере противоположное положение (формулировки Windows — «Движение вниз прокручивает вверх/вниз»); по данным не подтверждено.
- На KDE переключение не изменило знак. Вероятное объяснение — устройство для KWin было мышью, а настройка тачпада к нему не применяется; не подтверждено.

### 4.6. Инерция

- **Windows:** есть. После «броска» идёт плавно затухающий хвост 0,6–0,9 с: интервалы ≈ 16 мс (≈ 60 Гц), величины монотонно убывают до 1–4 ед. `WHEEL_DELTA` (шаг 07, свайп 1: 759, 338, … 46, 38, 32, 27, 20, 15, 11, 7, 4). Хвост приходит обычными `WM_MOUSEWHEEL`, winit — `Moved`, признака нет. В быстрых свайпах интервал ≈ 16 мс с самого начала (не только в хвосте), поэтому по интервалу палец и инерцию не разделить.
- **KDE/GNOME (эмулирующее устройство):** есть хвост по 1 делению с растущими интервалами 24 → 36 → 52 → 68 мс до 1,7 с от начала свайпа. Расписание повторяется на разных ОС: KDE-3 шаг 29 (трей) и GNOME-2 шаг 17 (трей), первый свайп — события на 988, 1024, 1060, 1096, 1148, 1202, 1270 мс от начала в обоих замерах. Значит, хвост формирует устройство до ОС. По величине от щелчка колеса не отличается.
- Отличить инерцию только по времени и величине: Windows — эвристикой «монотонное затухание при постоянном интервале», надёжность не оценена; KDE/GNOME — нельзя (значения совпадают с колесом).

### 4.7. Различия X11 и Wayland

Не измерены: X11 нет ни на KDE, ни на GNOME. По исходникам winit (§2): на X11 гладкая прокрутка XI2 даёт дробный `LineDelta` с фазой `Moved`, на Wayland настоящий тачпад даёт `PixelDelta` и `Ended` по `axis_stop`. Это не подтверждено экспериментом.

## 5. Предложение нормализации (гипотеза, не требование)

Пересмотрено в сессии C по всем измеренным платформам. Числа — только из измерений.

### 5.1. Правила модели

Модель прогнана во временном каталоге вне репозитория на всех записанных шагах (ползунок — события `slint`, переведённые в строки делением на 60; трей — `delta` ksni):

1. **Класс события.** Windows: значение, кратное целой строке, — колесо; дробное — тачпад; целое значение в пределах 200 мс после дробного — тачпад. KDE и GNOME: все измеренные события — колесо (дробных нет).
2. **Колесо:** одно деление = один щелчок (`unit`: ползунок — 1 строка; трей KDE — 120; трей GNOME — 1). Склейки нет — `k` делений в событии дают `k` щелчков.
3. **Тачпад:** знаковое накопление `acc += sign · delta`; шаги `trunc(acc / T)`; остаток переносится. Остаток сбрасывается после паузы > 300 мс (граница свайпа) — иначе он даёт отложенный шаг в начале следующего свайпа.
4. **Знак:** по таблице §5.3, без собственной инверсии — системная инверсия уже применена ОС (§4.5).
5. **Ограничение на свайп** (вариант): не более `K` шагов тачпада на свайп. Инерция отдельно не отбрасывается: по §4.6 она не отличима надёжно.

**Ожидание.** Методика (`prompt_wheel_test.md`, мастер) задаёт ожидание только для мыши: 10 одиночных щелчков → 10 шагов; быстрая прокрутка «≈10 щелчков» → ≈10. Для тачпада число шагов на свайп **не задано**; есть только условие ТЗ-36 «одно движение не даёт десятков шагов». Ниже оно проверяется как «не более 9 шагов на свайп» — это толкование этой сессии, не требование.

**Мышь (все платформы, все источники).** Результат равен числу событий: 10 во всех шагах, кроме шагов с лишними или недостающими щелчками пользователя (§2.2): GNOME-1/01 — 11, GNOME-2/04 — 12, Windows/03 — 12, Windows/04 — 11, KDE-3/07 — 8, GNOME-2/07 — 7. ## 7. Выводы для Части 3

### 7.1. Ответы на архитектурные вопросы

**1. Достаточно ли `scroll-event` Slint.**
- Вывод: на измеренных платформах и устройствах — да; в общем случае — нет, модулю ввода нужны события winit.
- Основание:
  - `PointerScrollEvent` в Slint 1.17.1 — только `delta_x, delta_y, modifiers` (`i-slint-core-1.17.1/items/input_items.rs:193-196`); фаза есть в `MouseEvent::Wheel`, но в `scroll-event` не передаётся; `LineDelta` и `PixelDelta` смешаны (`event_loop.rs:403`).
  - Во всех 5752 событиях всех замеров winit отдал только `LineDelta` с фазой `Moved`, и `slint = winit·60` без расхождений (§3.1). Для этих данных Slint не теряет ничего.
  - Различение «колесо / тачпад» по значениям: Windows — надёжно по потоку (дробные значения у тачпада; 0,17 % событий тачпада по отдельности целые — нужна память последних 200 мс); KDE и GNOME с измеренным устройством — невозможно ни на уровне Slint, ни на уровне winit (оба — целые деления).
  - Где Slint ломается: настоящий тачпад на Wayland (`PixelDelta` 60 px неотличим от `LineDelta` 1; теряется `Ended` по `axis_stop`), macOS (фазы инерции), высокоточное колесо (дробный `LineDelta` на Windows/X11 неотличим от тачпада и по winit). Не измерено.
  - Получить события ниже Slint можно: зонд использует `slint::winit_030::WinitWindowAccessor::on_winit_window_event` (feature `unstable-winit-030`) и получил события на Wayland (KDE, GNOME) и Windows.
- Уверенность: высокая для измеренного; для не измеренного — по исходникам, не подтверждено.

**2. Трей.**
- KDE Wayland: события есть. Мышь — ±120 за щелчок, `Vertical`, вверх `+`, знак совпадает с ползунком; «тачпад» (колесо для KWin) — 120·n, по одному событию на кадр. Основание: KDE-1…3, шаги 05–08, 15, 27–32. Уверенность высокая.
- GNOME Wayland с AppIndicator: события есть. Мышь — ±1, вверх `−` — **противоположно ползунку и KDE**; «тачпад» — 1…11 за событие. Основание: GNOME-1, 2, шаги 05–08, 15–20, 21, 27–32. Уверенность высокая.
- KDE X11, GNOME X11: **не измерено** (не «источника нет»); закроет замер мыши (шаги 05–08) в сеансе X11.
- Windows, macOS: **трея у плеера нет** (`src/tray.rs`, только ksni). Исход «источника нет».
- Тачпад в трее отличается от мыши только суммой делений за событие (1…11 против 1), тип по значениям не различить.

**3. Инерция тачпада.**
- Windows: есть, затухающий хвост 0,6–0,9 с при ≈ 60 Гц, без признака; отличима только эвристикой «монотонное затухание», надёжность не оценена (шаги 07, 10, 13, 16). Средняя уверенность.
- KDE/GNOME: хвост формирует устройство (одинаковое расписание на двух ОС, §4.6), по значению неотличим от колеса. Высокая уверенность в факте, причина — не подтверждена.
- macOS, настоящий тачпад Wayland: не измерено; по winit — фазы есть, признака инерции нет.

**4. Системная инверсия.**
- GNOME Wayland: ОС применяет инверсию до программы — знак меняется вместе с настройкой над ползунком и над треем (GNOME-2, шаги 09–32). Средняя уверенность: устройство для Mutter — колесо, неизвестно, какой переключатель (мыши или тачпада) применялся.
- Windows: ОС применяет инверсию до программы (шаги 05–16). Соответствие положения переключателя направлению — не подтверждено (§4.5).
- KDE Wayland: в данных знак не меняется. Применяется ли настройка тачпада к этому устройству — не подтверждено; **пробел**.
- Инверсия для мыши: не варьировалась ни в одном замере — **пробел** на всех платформах.

### 7.2. Формат данных для автотестов

Полей CSV `t_ms,source,delta_x,delta_y,orientation,modifiers` хватает для прогона нормализатора: время, тип дельты и фаза (`orientation` winit), модификаторы. Не хватает:
- в самом CSV — платформы, сеанса, устройства, источника-цели, положения инверсии: они разнесены по имени файла, `env.txt` и `summary.txt` (ответ пользователя);
- фактической цели (имя файла может не совпадать с источником, §2.2);
- ожидаемого числа шагов;
- разметки свайпов (начало, конец, «бросок»);
- типа устройства на уровне ОС (libinput `axis_source`, Windows `WM_POINTER`/HID) — без него нельзя проверить классификацию.

**Предлагаемая фикстура** (один файл на шаг, TOML-шапка + CSV):

```
[fixture]
platform = "windows"          # kde | gnome | windows | macos
session = "win32"             # wayland | x11 | win32 | appkit
device = "touchpad"           # mouse | touchpad | hires | emulated-wheel
source = "slider"             # slider | tray (фактический, по событиям)
natural_scroll = "on"         # on | off | unknown
direction = "up"              # up | down
action = "fast"               # single | fast | shift | short | long_slow
expected_steps = [5, 5, 5]    # по свайпам или щелчкам; пусто = «не задано»
origin = "wheel-results-windows-windows-win32:tools/wheel_probe/results/windows_win32_windows/07_touchpad_slider_fast_up-natural_on.csv"
---
t_ms,kind,phase,delta_x,delta_y,modifiers
```

`kind` — `line|pixel|tray`, данные — значения `winit` (для ползунка) или ksni (для трея) без пересчёта.

**В-3. Устройства, эмулирующие колесо, и «десятки шагов».** На Linux измеренный «тачпад» неотличим от мыши; одно движение даёт до 263 шагов (§5.2).
- а) Считать такое устройство мышью (правило по умолчанию: деление = щелчок); условие ТЗ-36 для тачпада проверять только на устройствах, которые ОС отдаёт как тачпад.
- б) Ограничение скорости для класса «колесо» (не более `N` шагов за интервал): ломает быструю прокрутку мышью при малом `N`.
- в) Исключить эмулирующие устройства из ТЗ-36 явно.
- Рекомендация: а) — данные не позволяют отличить устройство, а ограничение для колеса нарушает ожидание «10 щелчков → 10».
- **Решено:** см. §8.

**В-4. Порог и ограничение для тачпада Windows.**
- а) `T = 1` строка, `K = 5` на свайп: короткий свайп 0…2, длинный 4…5, быстрый 5.
- б) `T = 0,5` строки, `K = 5`: короткий 1…4, длинный и быстрый 5.
- в) `T = 1` без `K` + отбрасывание инерции эвристикой затухания: быстрый свайп зависит от надёжности эвристики (не оценена).
- Рекомендация: выбор за пользователем; а) ближе к «щелчок тачпада = щелчок мыши», б) — к заметной реакции на короткий свайп.
- **Решено:** см. §8.

**В-5. Знак трея по хосту.** KDE и AppIndicator GNOME присылают противоположные знаки (§4.2). Таблица ТЗ-36 должна различать хост трея, а не только «платформу × тип устройства».

- б) Определять знак при запуске по `XDG_CURRENT_DESKTOP`.

## 8. Решения пользователя (2026-10-01)

Решения по вопросам §7.4. Внесены в `02_tz.md` (§11, подраздел «Решения по итогам эксперимента `wheel_test.md`»).

**В-1 → трей на Windows и macOS — не в объёме задачи 02.** У плеера трей есть только на Linux (`ksni`). Трей на Windows и macOS — отдельная будущая задача. В задаче 02: для пар «Windows × над треем» и «macOS × над треем» исход ТЗ-36 — «источника нет»; правила и ручные сценарии, где участвует трей (колёсико над иконкой, команды трея, «Выход» в трее, сворачивание в трей, системное уведомление при окне, скрытом в трей), действуют и проверяются только на платформах, где у плеера есть трей (сейчас Linux). На Windows и macOS окно в трей не сворачивается; окно сообщения показывается обычным образом.

**В-2 → события winit через `on_winit_window_event`.** Модуль ввода получает события колёсика окна через `slint::winit_030::WinitWindowAccessor::on_winit_window_event` (feature `unstable-winit-030`): тип дельты (`LineDelta`/`PixelDelta`) и фазу жеста. Принадлежность события ползунку громкости определяется событием Slint `scroll-event`: событие winit сопоставляется с ним по значению (×60 для строк) и времени. Без сопоставленного события winit применяется правило по умолчанию на значениях Slint. Нестабильный API изолирован в модуле ввода (ТЗ-54); обновление Slint требует проверки модуля автотестами на записанных последовательностях. (Архитектурное решение для Части 3, ADR обязателен.)

**В-3 → класс устройства — по тому, что сообщает ОС.** Класс события (колесо / тачпад) определяется по тому, что сообщает ОС через winit (тип дельты, дробность значений, фаза). Устройство, которое ОС отдаёт как колесо, обрабатывается как колесо: одно деление — один щелчок, без ограничения скорости, даже если физически это тачпад, эмулирующий колесо. Требование ТЗ-36 «одно движение тачпада не даёт десятков шагов» проверяется на событиях класса «тачпад». Приёмка: записанные последовательности «тачпада» KDE-3 и GNOME-2 обрабатываются как колесо; быстрая прокрутка мышью 10–12 щелчков даёт 10–12 шагов.

**В-4 → тачпад Windows: T = 0,5 строки, K = 5.** Класс «тачпад» на Windows: порог одного шага T = 0,5 строки (60 ед. `WHEEL_DELTA`), накопление со знаком с переносом остатка, не более K = 5 шагов на свайп; граница свайпа — пауза больше 300 мс, после неё остаток сбрасывается. Инерция отдельно не отбрасывается — её ограничивает K. Значения T, K и паузы — данные таблицы модуля ввода (ТЗ-36). Приёмка: записанные свайпы Windows дают: короткий — 1–4 шага, длинный и быстрый — 5; выбросы ≈ 67 строк не дают больше 5 шагов на свайп.

**В-5 → знак трея по хосту.** Для источника «трей» ключ таблицы модуля ввода — хост StatusNotifierItem; знак и единица деления — данные таблицы: KDE Plasma — «вверх» = +, деление 120; GNOME с AppIndicator — «вверх» = −, деление 1. Хост определяется по процессу-владельцу службы `org.kde.StatusNotifierWatcher` на D-Bus (способ подтверждается в Части 3); запасной путь — `XDG_CURRENT_DESKTOP`. Неизвестный хост — знак как у KDE, деление — по величине первого события; исход «правило по умолчанию». Приёмка: записанные последовательности трея KDE-1…3 и GNOME-1, 2 дают одинаковое число шагов того же направления, что и ползунок; текущая инверсия трея на KDE устранена.

**Шаг громкости — подтверждение решения 3.** Шаг 2 % за щелчок одинаков для всех источников, включая трей; отдельного коэффициента для трея нет (решение 3 и НФ-2 без изменений). Различие 0,04 / 0,02 в текущем коде (ревью §3.4) — дефект, а не свойство источника.
