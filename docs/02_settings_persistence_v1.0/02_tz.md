## 1. Цель и границы

### 1.1. Цель

Сделать так, чтобы настройки, состояние сессии и плейлист APAP:

1. менялись на диске только в определённые моменты: `settings.toml` — по осознанному действию пользователя («Сохранить» в окне настроек) и при выходе; `state.toml` и `playlist.m3u` — отложенно и при выходе (решения 1, 5; У-1);
2. не портились и не пропадали молча: запись атомарна и долговечна, повреждённый файл сохраняется копией, ошибки видны пользователю, потери при сбое ограничены и описаны (решения 1, 9; ОВ-7, ОВ-8 (§11));
3. применялись без лишних переоткрытий трека, перерисовок и обращений к диску (решение 2);
4. управлялись предсказуемо: модальный диалог с копией, одинаковое поведение источников громкости, видимый порядок плейлиста совпадает с порядком воспроизведения (решения 2, 3, 5–8, 10).

### 1.2. Входит в объём

- Распределение данных между `settings.toml` и `state.toml`, их загрузка, разбор по ключам, значения по умолчанию, неразбираемые файлы; три случая чтения `playlist.m3u` (ОВ-8 (§11)).
- Единственный писатель `settings.toml`, `state.toml`, `playlist.m3u`; моменты записи и сравнение с эталонным текстом (ОВ-2 (§11)); отложенная запись (У-1); атомарная и долговечная запись на Linux, Windows, macOS; ошибки записи.
- Путь выхода (закрытие окна, «Выход» в трее (Linux, В-1 (§11)), `SIGTERM`/`SIGINT`/`SIGHUP`, завершение сеанса Windows, запрос завершения macOS) с общим пределом ожидания записи (ОВ-4, ОВ-6 (§11)) и поведение при сбое.
- Окно сообщений уровней Info / Warning / Error и системные уведомления (ОВ-7 (§11), У-2; системные уведомления — только при трее, Linux, В-1 (§11)).
- Платформенные модули с единым интерфейсом и подменной реализацией: жизненный цикл, файловая система, ввод, системные уведомления, выбор файлов (У-3).
- Неблокирующие системные диалоги выбора файлов (ОВ-9 (§11)).
- Диалог настроек: модальность, копия, сравнение, кнопка «Сохранить», формирование разницы и применение не-звуковых параметров, меню и выход при открытом диалоге; перенос «Удалить текущий трек» и «Очистить плейлист» из диалога в меню главного окна (ОВ-10 (§11)).
- Источники громкости в UI: ползунок, колёсико над ползунком, колёсико над иконкой трея (Linux, В-1 (§11)); нормализация колёсика (ОВ-11, В-2…В-5 (§11)); всплывающие подсказки у неактивных регуляторов; mute в `state.toml`.
- Плейлист: флаг «плейлист изменён», запись по отсчёту N, сортировка, её ключ и снятие ключа (ОВ-12 (§11)), правила сравнения (ОВ-13 (§11)), исходный и видимый порядок, операция ручного изменения порядка в модели (ОВ-14 (§11)), «Загрузить плейлист» с немедленным воспроизведением (ОВ-5 (§11)), экспорт «Сохранить плейлист» в расширенном M3U (ОВ-17 (§11)), фоновая загрузка с индикатором и недоступными командами (решение 10, ОВ-15 (§11)).
- Тестируемость: автотесты без файловой системы пользователя со счётчиком записей каждого файла.

## 2. Термины

Дальше в тексте термины используются только в этих значениях.

| Термин | Определение |
|---|---|
| **Настройки** | Параметры, которые редактируются в окне настроек, в том числе опции режимов (`ModeSettings` (01_audio_modes)) и интервал N. Хранятся в `settings.toml`. Меняются только через окно настроек (решение 1). |
| **Состояние сессии** | Значения, которые меняются в главном окне, трее и меню без окна настроек: активный режим; громкость и mute каждого режима, включая mute Строгого режима (`PlaybackState` (01_audio_modes)); ширины колонок; ключ сортировки (колонка и направление); тип визуализации; Repeat и Shuffle; геометрия окна (положение, размер, развёрнуто, полноэкранный режим); последний каталог. Хранится в `state.toml` (решение 1, Т-1, Т-2). |
| **Файл данных** | Файл, который не является ни настройками, ни состоянием: `playlist.m3u` (рабочий плейлист), `bp_tests.toml` и `track_marks.toml` (01_audio_modes, пишет движок), файлы тем, кэши обложек и визуализации, файл экспорта плейлиста. |
| **Сохранение** | Запись файла на диск. |
| **Применение** | Передача значения потребителю в памяти (UI, движку, воркерам) без записи файлов. Применение не выполняет сохранения (ТЗ-134 (01_audio_modes)). |
| **Копия диалога** | Экземпляр настроек, который редактирует открытое окно настроек. Создаётся при открытии, уничтожается при закрытии. |
| **Отличия** | Параметры, значение которых в копии диалога не равно значению в действующих настройках. Сравнение — по значению: изменить параметр и вернуть прежнее значение — отличий нет. |
| **Недопустимое значение** | Значение, которое не входит в допустимое множество параметра или нарушает правило согласования (например, `buffers_allowed` (01_audio_modes, И-Р22)). |
| **Действующие настройки / действующее состояние** | Экземпляры настроек и состояния в памяти, с которыми работает приложение (по одному, ТЗ-1). |
| **Эталонный текст файла** | Для `settings.toml` и `state.toml`: текст последней успешной записи файла, до неё — текст, прочитанный при запуске; для отсутствующего или неразбираемого файла эталон пуст. Файл записывается при выходе и по истечении отсчёта N, только если детерминированная сериализация (стабильный порядок ключей) действующих значений отличается от эталонного текста (ОВ-2 (§11)). |
| **Программное изменение состояния** | Значение состояния сессии, которое программа присваивает сама: восстановление геометрии, коррекции загрузки, пересчёт до первого показа главного окна. Событие окна, повторяющее только что выставленное программой значение, изменением не считается. Программное изменение меняет действующее состояние, но отсчёт N не запускает (ОВ-3 (§11)). |
| **Отложенная запись** | Запись `state.toml` и (если взведён флаг «плейлист изменён») `playlist.m3u` по истечении отсчёта N. Отсчёт запускается первым изменением состояния сессии или плейлиста после последней записи (первым незаписанным изменением), кроме программных; последующие изменения его не перезапускают. По истечении N записывается всё накопленное. Серия изменений в пределах N даёт одну запись; непрерывная серия дольше N — одну запись каждые N с (решения 1, 5; У-1). |
| **N** | Интервал отложенной записи: 10 / 30 / 60 / 120 с, по умолчанию 30 с; параметр окна настроек (решение 1). |
| **Флаг «плейлист изменён»** | Признак в памяти: состав или исходный порядок плейлиста отличаются от последней успешной записи `playlist.m3u` (решение 5). |
| **Исходный порядок** | Порядок треков в `playlist.m3u`: порядок добавления с учётом ручных изменений порядка. Сортировка его не меняет. |
| **Видимый порядок** | Порядок строк в таблице плейлиста: исходный порядок, если ключа сортировки нет; иначе — стабильная сортировка исходного порядка по ключу. Порядок воспроизведения — видимый (ТЗ-142 (01_audio_modes)); при Shuffle — перестановка видимого порядка (ТС-6 (01_audio_modes)). |
| **Ключ сортировки** | Пара «колонка, направление» или «нет ключа». Хранится в `state.toml`. |
| **Ручное изменение порядка** | Операция модели плейлиста, перемещающая строки на новые места (ТЗ-44). Интерфейс, который её вызывает (перетаскивание мышью, клавиатура), — отдельная задача (ОВ-14 (§11)). |
| **Выход** | Завершение программы по закрытию главного окна (если сворачивание в трей выключено; на Windows и macOS окно в трей не сворачивается, В-1 (§11)), «Выходу» в трее (на платформах с треем, В-1 (§11)), `SIGTERM`/`SIGINT`/`SIGHUP`, завершению сеанса Windows (`WM_ENDSESSION`), запросу завершения macOS (Cmd+Q, «Завершить» в Dock, выход из сеанса) (ОВ-6 (§11)). Закрытие окна при включённом сворачивании в трей выходом не является. |
| **Сбой** | Завершение без пути выхода: паника (`panic = "abort"`), `SIGKILL`, пропадание питания, аварийное завершение ОС. |
| **Атомарная запись** | Замена файла, после которой при сбое в любой момент на диске остаётся либо прежняя, либо новая версия целиком — не пустой и не обрезанный файл. |
| **Долговечная запись** | Атомарная запись, об успехе которой сообщается только после того, как новое содержимое и новая запись каталога сброшены на носитель (`fsync` файла и каталога на Linux, аналоги Windows и macOS — Часть 3). |
| **Неразбираемый файл** | `settings.toml` или `state.toml`, который не удаётся разобрать как TOML целиком. Отличается от файла с отдельными отсутствующими или недопустимыми ключами. Для `playlist.m3u` различаются (ОВ-8 (§11)): **повреждённый** — прочитан, но не валидный UTF-8 или содержит строку, которая не пустая, не комментарий `#…` и не абсолютный путь (путь к несуществующему файлу повреждением не считается); **нечитаемый** — ошибка ввода-вывода или нет доступа. |
| **Стартовая загрузка** | Чтение `playlist.m3u`, затем тегов всех его файлов, затем применение сохранённой сортировки, выполняемое после запуска в фоне (решение 10). |
| **Загрузка плейлиста** | Стартовая загрузка или фоновое чтение файла и тегов по команде «Загрузить плейлист» (ТЗ-13). Пока она идёт, команды ТЗ-48 недоступны (ОВ-15 (§11)). |
| **Окно сообщения** | Оверлей поверх главного окна и диалога настроек уровня Info, Warning или Error; до закрытия блокирует главное окно и открытый под ним диалог настроек (ТЗ-52). Единственный канал сообщений пользователю внутри программы; строка состояния каналом сообщений не является (ОВ-7 (§11)). |
| **Системное уведомление** | Уведомление ОС, которое показывается вместо окна сообщения, пока главное окно скрыто в трей (ТЗ-52). Только на платформах, где у плеера есть трей (сейчас Linux; В-1 (§11)); на Windows и macOS окно сообщения показывается обычным образом. |
| **Щелчок колёсика** | Нормализованная единица прокрутки: одно деление колеса мыши или эквивалентное ему накопленное смещение тачпада; пороги и знаки — таблица данных модуля ввода (ТЗ-36; решение 3; ОВ-11 (§11)). Класс устройства (колесо / тачпад) — по тому, что сообщает ОС (В-3 (§11)); для трея единица деления и знак — по хосту StatusNotifierItem (В-5 (§11)). |
| **Источник громкости** | Ползунок громкости, колёсико над ползунком, колёсико над иконкой трея (на платформах с треем, В-1 (§11)), будущие горячие клавиши (решение 3). |
| **Платформенный модуль** | Модуль, в котором сосредоточен платформенно-зависимый код одной задачи (жизненный цикл, файловая система, ввод, системные уведомления, выбор файлов), с единым интерфейсом и подменной реализацией для автотестов (У-3; ТЗ-54). |

## 3. Решения пользователя

| № | Решение (кратко) | Источник | Где применено |
|---|---|---|---|
| 1 | Два файла: `settings.toml` (параметры окна настроек; пишется по «Сохранить» с отличиями и при выходе) и `state.toml` (активный режим, громкость и mute по режимам, ширины колонок, сортировка, тип визуализации, Repeat/Shuffle, геометрия, последний каталог; пишется отложенно и при выходе). ## 4. Требования

Формат: формулировка → приоритет → обоснование → критерий приёмки → зависимости.

Приоритеты: **P0** — потеря или порча данных, паника, ложное заявление; **P1** — нарушение логики; **P2** — качество, производительность.

«Автотест» — тест, который выполняется в обычном `cargo test` без аудио-устройства, без переменных окружения и без обращения к файлам пользователя (ТЗ-49); число записей каждого файла считает подменное хранилище (ТЗ-50). Подменные часы позволяют проверять отложенную запись без ожидания; подменные реализации платформенных модулей (ТЗ-54) — выход, ошибки файловой системы, события ввода, уведомления и выбор файлов.

### 4.1. Файлы, владение и загрузка

**ТЗ-1. Один экземпляр настроек и состояния.** Каждый из файлов `settings.toml` и `state.toml` должен читаться с диска один раз при запуске; всё приложение должно работать с одним экземпляром действующих настроек и одним экземпляром действующего состояния (плюс копия диалога, пока он открыт). Изменения файлов на диске во время работы не должны подхватываться и не влияют на сравнение с эталонным текстом.

- Приоритет: P1.
- Обоснование: промт («Загрузка и владение»); решение 1; ревью §3.2; ОВ-2 (§11).
- Приёмка: автотест: запуск → по одному чтению каждого файла; изменение файла в хранилище во время работы → значения в памяти не меняются; при выходе файл записывается только если действующие значения отличаются от эталонного текста, и тогда содержит версию из памяти.
- Зависимости: ТЗ-3.

**ТЗ-2. Распределение значений по файлам.** Каждое сохраняемое значение должно принадлежать ровно одному файлу: настройки — `settings.toml`, состояние сессии — `state.toml` (перечни — §2, «Настройки», «Состояние сессии»). В частности: опции режимов и флажок фиксации громкости — `settings.toml`; активный режим, громкость и mute каждого режима — `state.toml` (ТЗ-135 (01_audio_modes)); тип визуализации и ширины колонок — `state.toml`; остальные параметры визуализации, видимость и порядок колонок, тема, N — `settings.toml` (Т-1, Т-2).

- Приоритет: P1.
- Обоснование: решение 1; Т-1, Т-2; R-12.
- Приёмка: автотест: множества ключей, записываемых в `settings.toml` и `state.toml`, не пересекаются, а их объединение покрывает перечни §2.
- Зависимости: —.

**ТЗ-3. Единственный писатель.** У `settings.toml`, `state.toml` и `playlist.m3u` должен быть один писатель. Записи одного файла не должны перекрываться во времени; каждая запись должна содержать файл целиком из снимка памяти на момент запроса записи; никакая часть приложения (в том числе движок, ТЗ-134 (01_audio_modes)) не должна записывать отдельный раздел файла.

- Приоритет: P0 (два писателя затирают разделы друг друга).
- Обоснование: промт («Загрузка и владение»); R-5, R-18; ОВС-14 (01_audio_modes).
- Приёмка: автотест: истечение отсчёта N во время записи по «Сохранить» и запрос выхода во время отложенной записи → записи каждого файла идут последовательно, итоговое содержимое каждого файла равно последнему снимку памяти. Ревью кода: вызовы записи этих файлов есть только у писателя.
- Зависимости: ТЗ-18.

**ТЗ-4. Загрузка не пишет файлы.** Запуск программы не должен записывать `settings.toml`, `state.toml` и `playlist.m3u` — ни при отсутствии файлов, ни при коррекции значений. Исправления, значения по умолчанию и удаление неизвестных ключей должны попадать в файл только при следующей записи этого файла, необходимость которой определяется сравнением с эталонным текстом (ОВ-2 (§11)): по истечении отсчёта N или при выходе (ТЗ-10, ТЗ-11). Единственное исключение — переименование повреждённого `playlist.m3u` в `playlist.m3u.bad` при запуске (ТЗ-21, ОВ-8 (§11)).

- Приоритет: P0 (вместе с R-2 запуск молча уничтожал настройки).
- Обоснование: R-3, R-23; решение 9; ТЗ-135 (01_audio_modes); ОВ-2, ОВ-8 (§11).
- Приёмка: автотест: запуск с отсутствующими файлами, с полным файлом, с файлом с недопустимыми значениями → 0 записей до первого события записи; `settings.toml` с недопустимым значением → в памяти исправленное значение, файл без изменений до «Сохранить» с отличиями или выхода; запуск с полными корректными файлами → выход → 0 записей; запуск с отсутствующими файлами → выход → по одной записи `settings.toml` и `state.toml`.
- Зависимости: ТЗ-5, ТЗ-10.

**ТЗ-5. Разбор по ключам.** `settings.toml` и `state.toml` должны разбираться по ключам: отсутствующий ключ или недопустимое значение → значение по умолчанию этого ключа (ТЗ-8) и заметка в журнал; все остальные ключи файла сохраняются. Неизвестный ключ игнорируется с заметкой и при следующей записи файла в него не попадает. Все заметки одного файла пишутся одной сводной записью журнала.

- Приоритет: P0 (одна ошибка стирала все настройки).
- Обоснование: R-2, R-10; решение 9; ОВ-1 (§11).
- Приёмка: автотест: файл, в котором у одного ключа недопустимое значение, один ключ отсутствует и один неизвестен → три соответствующих ключа имеют значения по умолчанию, все остальные — из файла; одна сводная запись журнала с тремя заметками; после выхода неизвестного ключа в файле нет.
- Зависимости: ТЗ-8.

**ТЗ-6. Неразбираемый файл.** Если `settings.toml` или `state.toml` — неразбираемый файл, все его значения должны взяться по умолчанию в памяти, а сам файл до первой записи этого файла должен быть скопирован в `settings.toml.bad` / `state.toml.bad`. Копия одна на файл: следующая копия заменяет предыдущую. Отсутствующий файл неразбираемым не считается, копия не создаётся. Для `playlist.m3u` — ТЗ-21 (ОВ-8 (§11)).

- Приоритет: P0.
- Обоснование: R-2; решение 9; ОВ-8 (§11).
- Приёмка: автотест: неразбираемый `settings.toml` → значения по умолчанию; до первой записи `settings.toml` содержимое `settings.toml.bad` побайтово равно исходному файлу; повтор с другим повреждённым содержимым → одна копия с новым содержимым. То же для `state.toml`.
- Зависимости: ТЗ-4, ТЗ-18.

**ТЗ-7. Сообщение о повреждённом файле.** Для неразбираемого `settings.toml` пользователь должен получить одно за запуск окно сообщения уровня Warning (ТЗ-52) с текстом по смыслу «Файл настроек повреждён, используются значения по умолчанию. Копия: <путь к `settings.toml.bad`>», показанное после первого показа главного окна и остающееся до закрытия пользователем; то же пишется в журнал. Для `state.toml` — только запись в журнал.

- Приоритет: P1.
- Обоснование: решение 9; У-2; ОВ-7, ОВ-16 (§11).
- Приёмка: автотест: неразбираемый `settings.toml` → одно окно Warning с путём копии после первого показа главного окна и одна запись журнала; неразбираемый `state.toml` → 0 окон, одна запись журнала. Ручной сценарий: испортить `settings.toml`, запустить → окно Warning с путём копии видно поверх главного окна до нажатия кнопки.
- Зависимости: ТЗ-6, ТЗ-52.

**ТЗ-8. Значения по умолчанию.** Значение по умолчанию каждого ключа должно быть документированным значением параметра, а не нулём типа. В частности: громкость Совместимого режима — 100 % (решение 11), Оптимального — 100 % (ОВ-5 (01_audio_modes)); mute всех режимов — выключен; активный режим — Совместимый (ТЗ-124 (01_audio_modes)); N — 30 с; флажок фиксации громкости — выключен (ТЗ-140 (01_audio_modes)); ключа сортировки нет.

- Приоритет: P1.
- Обоснование: R-10; решения 1, 11.
- Приёмка: автотест: пустой `state.toml` и пустой `settings.toml` → каждое значение равно значению из перечня по умолчанию (перечень — Часть 3); ни одно значение громкости, размера или ширины не равно 0, если 0 не является его документированным значением.
- Зависимости: ТЗ-5.

**ТЗ-9. Старый формат файла настроек.** `settings.toml` предыдущей версии должен загружаться без паники; аудио-настройки — по ТЗ-97 (01_audio_modes). Миграции ключей состояния нет: ключи, которые теперь относятся к состоянию сессии (громкость, mute, сортировка, ширины колонок, тип визуализации, Repeat, Shuffle, геометрия, последний каталог), — неизвестные ключи (ТЗ-5): игнорируются с заметкой, состояние начинается со значений по умолчанию (ТЗ-8). Их наличие даёт отличие действующих настроек от эталонного текста, поэтому при первом выходе `settings.toml` перезаписывается без них.

- Приоритет: P1.
- Обоснование: решения 1, 9; ТЗ-97 (01_audio_modes); ОВ-1, ОВ-2 (§11).
- Приёмка: автотест: старый `settings.toml` → запуск без паники → выход → в `settings.toml` нет ключей состояния; второй запуск — 0 заметок о неизвестных ключах.
- Зависимости: ТЗ-5, ТЗ-10.

### 4.2. Моменты записи

**ТЗ-10. Когда пишется `settings.toml`.** `settings.toml` должен записываться только: (а) по «Сохранить» в окне настроек, если есть отличия (ТЗ-28); (б) при выходе, если сериализованные действующие настройки отличаются от эталонного текста (ТЗ-14; ОВ-2 (§11)). Все остальные события (§5.1) не должны записывать `settings.toml`, в том числе изменение громкости и mute любым способом, ширины колонок, сортировка, смена типа визуализации в меню и клавишей V, перемещение ползунка позиции, переключение режима в главном окне, геометрия окна, смена устройства, применение настроек к движку.

- Приоритет: P1.
- Обоснование: промт («Моменты записи»); R-5, R-6; решение 1; ОВ-2 (§11).
- Приёмка: автотест на каждое событие §5.1 со значением «—» в столбце `settings.toml` → 0 записей `settings.toml` (в том числе `volume_change_does_not_write_settings`, `mode_switch_from_main_window_does_not_write_settings`); запуск с полным корректным `settings.toml` → выход → 0 записей `settings.toml`.
- Зависимости: ТЗ-50.

**ТЗ-11. Отложенная запись состояния.** Первое изменение состояния сессии или плейлиста (ТЗ-12) после последней записи должно запускать отсчёт N; последующие изменения срок не сдвигают. По истечении N `state.toml` должен записываться, если сериализованное действующее состояние отличается от эталонного текста (ОВ-2 (§11)); запись содержит всё накопленное. Серия изменений в пределах N должна давать одну запись; непрерывная серия дольше N — одну запись каждые N с. Отсчёт запускают только изменения, пришедшие из событий ввода и окна после первого показа главного окна; программные изменения состояния отсчёт не запускают и попадают в файл при следующей записи или при выходе (ОВ-3 (§11)). Отсчёт общий для `state.toml` и `playlist.m3u`. При смене N в диалоге новый срок записи — меньшее из прежнего срока и момента «Сохранить» + новое N. После неудачной записи `state.toml` запись этого файла по отсчёту прекращается до успешного «Повторить» (ТЗ-20; ОВ-7 (§11)).

- Приоритет: P1.
- Обоснование: решение 1; У-1; ОВ-2, ОВ-3, ОВ-7 (§11).
- Приёмка: автотест с подменными часами: N = 30 с, изменения в t = 0, 10, 20 с → одна запись в t = 30 с со значением из t = 20 с (`state_written_after_n_seconds_once`); изменения каждые 5 с в течение 10 мин → записи в t = 30, 60, … с, промежуток между записями не больше 30 с; N = 120 с, изменение в t = 0, в t = 100 с «Сохранить» с N = 10 с → запись в t = 110 с; изменение громкости и возврат прежнего значения до истечения N → 0 записей. Автотест: запуск с полным корректным `state.toml` без действий пользователя, ожидание 10 мин, выход → 0 записей `state.toml`; изменение размера окна пользователем → одна запись через N с.
- Зависимости: ТЗ-3, ТЗ-20.

**ТЗ-12. Флаг «плейлист изменён» и запись плейлиста.** Флаг «плейлист изменён» должен взводиться при добавлении, удалении, очистке, загрузке другого плейлиста и ручном изменении порядка и не должен взводиться сортировкой, снятием ключа сортировки, сменой текущего трека, обновлением тегов при воспроизведении. Взведение флага запускает общий отсчёт ТЗ-11, если он ещё не идёт (У-1); по его истечении, если флаг взведён, `playlist.m3u` записывается один раз. Флаг снимается только после успешной записи. `playlist.m3u` не записывается: после неудачной записи — по отсчёту до успешного «Повторить» (ТЗ-20; ОВ-7 (§11)); если при запуске файл был нечитаем или его не удалось переименовать (ТЗ-21, случай 3 ОВ-8 (§11)), — весь сеанс, ни по отсчёту, ни при выходе.

- Приоритет: P1.
- Обоснование: решение 5; R-15; У-1; ОВ-7, ОВ-8 (§11).
- Приёмка: автотест с подменными часами: добавить трек → через N с одна запись `playlist.m3u`, флаг снят (`playlist_dirty_written_by_timer`); сортировка → флаг не взведён, 0 записей плейлиста (`sort_change_does_not_write_playlist`); ошибка записи → флаг остаётся взведённым, за следующие 10 мин 0 попыток по отсчёту; нечитаемый `playlist.m3u` при запуске → добавить трек → через N с и при выходе 0 записей `playlist.m3u`.
- Зависимости: ТЗ-11, ТЗ-20, ТЗ-21.

**ТЗ-13. «Сохранить плейлист» и «Загрузить плейлист».**

(а) «Сохранить плейлист» в меню должен записывать в выбранный пользователем файл (экспорт) видимый порядок таблицы на момент экспорта; перестановка Shuffle не учитывается. Формат экспорта: UTF-8, `#EXTM3U`, `#EXTINF` (длительность, «Исполнитель — Название»), абсолютные пути; расширение по умолчанию `.m3u8`. Формат рабочего `playlist.m3u` не меняется. Рабочий `playlist.m3u` и флаг «плейлист изменён» при экспорте не меняются. Ошибка записи экспорта — отдельное окно Error на каждую неудачную попытку (ТЗ-52).

(б) «Загрузить плейлист» (Play Now) должен: читать выбранный файл и теги в фоне с тем же индикатором, что стартовая загрузка (ТЗ-47); пока идёт загрузка, прежний трек продолжает играть, недоступные команды — по ТЗ-48; по окончании загрузки — заменять рабочий плейлист, применять действующий ключ сортировки, взводить флаг «плейлист изменён», останавливать прежний трек, отменять подготовленный следующий трек прежнего плейлиста (gapless) и запускать воспроизведение первого трека видимого порядка (при Shuffle — первого трека новой перестановки) независимо от прежнего состояния (играет / пауза / стоп). Действуют текущие Repeat и Shuffle; mute сохраняется. Пустой загруженный плейлист → стоп, флаг взведён. При ошибке чтения выбранного файла рабочий плейлист и воспроизведение не меняются, флаг не взводится, показывается окно Error (ТЗ-52).

- Приоритет: P1.
- Обоснование: решение 5; R-13, R-15; ОВ-5, ОВ-7, ОВ-15, ОВ-17 (§11).
- Приёмка: автотест: ключ «Название ↑», Shuffle включён → экспорт → пути в файле в порядке видимой таблицы, у каждого `#EXTINF`; `playlist.m3u` — 0 записей, флаг не изменился; подменная ошибка записи экспорта дважды → два окна Error. Автотест: играет трек X, загрузить плейлист P при ключе «Название ↑» → до окончания загрузки играет X; после — воспроизводится первый по названию трек P, X в очереди нет, флаг взведён, через N с — запись `playlist.m3u`; то же из паузы и из стопа → воспроизведение началось; нечитаемый выбранный файл → плейлист и X без изменений, флаг не взведён, одно окно Error; пустой плейлист → стоп, флаг взведён. Замер: загрузка плейлиста из 5 000 треков → итерации цикла событий UI ≤ 50 мс (ТЗ-22).
- Зависимости: ТЗ-12, ТЗ-18, ТЗ-22, ТЗ-47, ТЗ-52.

**ТЗ-14. Путь выхода.** Все пути выхода (закрытие главного окна при выключенном сворачивании в трей, «Выход» в трее — на платформах, где у плеера есть трей (сейчас Linux; В-1 (§11)), `SIGTERM`/`SIGINT`/`SIGHUP`, завершение сеанса Windows, запрос завершения macOS) должны приходить единым запросом выхода с причиной из модуля жизненного цикла (ТЗ-54) и вести в один путь выхода. Путь выхода записывает, в этом порядке: `playlist.m3u` (если флаг взведён и запись не запрещена по случаю 3 ОВ-8 (§11)), `state.toml`, `settings.toml` (каждый — если отличается от эталонного текста, ОВ-2 (§11)). Каждый файл пишется не более одного раза и целиком; для каждого выполняется одна попытка независимо от прежних неудачных записей; её ошибка пишется только в журнал (ОВ-7 (§11)). Запись выполняется параллельно с завершением движка и не зависит от его подтверждения (ТЗ-136 (01_audio_modes)). Общий предел ожидания записи всех файлов — 5 с (НФ-9); по его истечении процесс завершается, в журнал пишется, какие файлы не записаны; незаписанные файлы остаются прежними целыми версиями (ТЗ-18). Повторный запрос выхода из окна или трея во время выхода не вызывает повторной записи; повторный сигнал завершения во время выхода завершает процесс немедленно (файлы целы по ТЗ-18).

- Приоритет: P0.
- Обоснование: R-4, R-24; решение 1; краевой случай 4 промта; ОВ-2, ОВ-4, ОВ-6, ОВ-7, ОВ-8 (§11); У-3; В-1 (§11).
- Приёмка: автотест для каждого пути выхода → по одной записи каждого файла с отличиями, файлы без отличий — 0 записей (`exit_writes_settings_once`). Автотест: подменная задержка записи 10 с → процесс завершается через 5 с ± 0,5 с, в журнале перечислены незаписанные файлы, в хранилище — прежние версии; подменная задержка записи плейлиста 4 с и `state.toml` 2 с → плейлист записан, `state.toml` не записан, в журнале это отражено; неудачная запись `state.toml` до выхода → выход → одна повторная попытка. Автотест: двойной `SIGTERM` при подменной задержке записи 10 с → процесс завершён сразу после второго сигнала, файлы — прежние целые версии; «Выход» в трее во время выхода (подменная платформа с треем) → записей не прибавилось. Ручной сценарий (Linux): во время воспроизведения `kill -TERM <pid>` → процесс завершился, `state.toml` содержит громкость, заданную перед сигналом, файлы разбираются целиком.
- Зависимости: ТЗ-3, ТЗ-15, ТЗ-18, ТЗ-54.

**ТЗ-15. Сигналы и завершение сеанса.** Должны вести в путь выхода ТЗ-14:
- Linux, macOS: `SIGTERM`, `SIGINT`, `SIGHUP`; обработчик сигналов только будит цикл событий;
- Windows: на `WM_QUERYENDSESSION` программа немедленно отвечает TRUE; на `WM_ENDSESSION` (wParam = TRUE) путь выхода выполняется синхронно в обработчике в пределах НФ-9, затем обработчик возвращает управление;
- macOS: Cmd+Q, «Завершить» в Dock и выход из сеанса (`applicationShouldTerminate:`) — путь выхода, завершение после записи; одной замены пункта меню Quit недостаточно.

Причина «Выход» в трее существует только на платформах, где у плеера есть трей (сейчас Linux; В-1 (§11)); остальные пути выхода не зависят от трея. Перехват выполняет модуль жизненного цикла (ТЗ-54); способ перехвата — Часть 3. Если на платформе способ не найден — открытый вопрос спецификации (ОВС) с описанием потерь, и подсказка параметра N их описывает (ТЗ-33).

- Приоритет: P0 (без обработки теряется всё изменённое с последней записи).
- Обоснование: R-4; решение 1; §6.28 (01_audio_modes); ОВ-6, В-1 (§11) (источники: https://github.com/rust-windowing/winit/issues/4360, https://learn.microsoft.com/en-us/windows/win32/shutdown/wm-queryendsession, https://learn.microsoft.com/en-us/windows/win32/shutdown/wm-endsession, https://github.com/qarmin/czkawka/issues/1942, https://github.com/rust-windowing/winit/pull/4692).
- Приёмка: ручной сценарий, Windows-ноутбук: изменить громкость и добавить трек, сразу «Завершение работы» → после загрузки ОС оба изменения сохранены; macOS: то же через Cmd+Q и через «Завершить» в Dock; Linux: `kill -INT`, `kill -TERM`, `kill -HUP` → в журнале путь выхода, файлы записаны. Автотест: подменный модуль жизненного цикла подаёт каждую причину выхода (для платформы без трея — без причины «Выход» в трее) → вызван тот же путь выхода, что при закрытии окна.
- Зависимости: ТЗ-14, ТЗ-54.

**ТЗ-16. Поведение при сбое.** При сбое (паника, `SIGKILL`, пропадание питания) программа не должна пытаться записывать файлы (решение 1). После сбоя каждый из трёх файлов должен быть последней успешно записанной версией. Теряется (НФ-6): изменения состояния сессии и плейлиста, не попавшие в последнюю отложенную запись, и копия открытого диалога; настройки, сохранённые по «Сохранить», не теряются. Эти потери должны быть описаны в подсказке параметра N (ТЗ-33).

- Приоритет: P1.
- Обоснование: промт («Надёжность», краевой случай 5); R-4; решение 1; У-1.
- Приёмка: автотест: изменить громкость, дождаться отложенной записи, изменить ещё раз, «сбой» (уничтожение приложения без пути выхода) → в хранилище значение первого изменения. Ручной сценарий: изменить громкость, через N + 5 с `kill -KILL` → после перезапуска громкость сохранена; изменить и сразу `kill -KILL` → громкость прежняя. Проверка: подсказка параметра N описывает потери.
- Зависимости: ТЗ-11, ТЗ-18.

**ТЗ-17. Выход во время загрузки плейлиста.** Выход до окончания стартовой загрузки не должен записывать `playlist.m3u` пустым или частичным: рабочий плейлист на диске должен остаться прежним. До окончания «Загрузить плейлист» рабочим остаётся прежний плейлист: загружаемый список не должен записываться в `playlist.m3u`, пока загрузка не завершена; флаг «плейлист изменён», взведённый до команды, продолжает действовать, и прежний рабочий плейлист записывается по обычным правилам — при выходе (ТЗ-14) и по истечении отсчёта N во время загрузки (ТЗ-11, ТЗ-12).

- Приоритет: P0 (потеря плейлиста).
- Обоснование: решение 10; R-15; ОВ-15 (§11), включая уточнение к ОВ-15.
- Приёмка: автотест: подменная стартовая загрузка «зависает» → выход → 0 записей `playlist.m3u`, содержимое прежнее. Автотест: «Загрузить плейлист» с задержкой загрузки: флаг взведён до команды → выход во время загрузки → одна запись `playlist.m3u`, содержимое — прежний рабочий плейлист; флаг не взведён → выход во время загрузки → 0 записей `playlist.m3u`, содержимое прежнее. Автотест с подменными часами: флаг взведён до команды, отсчёт N истекает во время загрузки → одна запись `playlist.m3u` прежним рабочим плейлистом; загружаемый список в файл не попадает до окончания загрузки.
- Зависимости: ТЗ-13, ТЗ-47, ТЗ-48.

### 4.3. Атомарность, долговечность, ошибки

**ТЗ-18. Атомарная запись.** Запись `settings.toml`, `state.toml`, `playlist.m3u` и файла экспорта плейлиста должна быть атомарной. Временные файлы, оставшиеся после сбоя, не должны читаться как настройки, состояние или плейлист и не должны мешать следующему запуску. Запись выполняет модуль файловой системы (ТЗ-54).

- Приоритет: P0.
- Обоснование: R-1, R-20; решение 1; промт («Надёжность»); У-3.
- Приёмка: автотест с подменной файловой системой: прерывание на каждом шаге последовательности записи → файл разбирается целиком и равен либо прежней, либо новой версии; оставшийся временный файл при следующем запуске не читается и не приводит к ошибке. Ручной сценарий (Linux): цикл записей `state.toml` (непрерывная серия изменений громкости при N = 10 с) и `kill -KILL` в случайный момент, повторить 20 раз → файл всегда разбирается целиком.
- Зависимости: ТЗ-54.

**ТЗ-19. Долговечная запись.** Запись трёх файлов ТЗ-18 должна быть долговечной на Linux (`fsync` временного файла до `rename` и `fsync` каталога после), а на Windows и macOS — выполнять аналогичные гарантии, определённые в Части 3; об успехе записи писатель сообщает только после этого.

- Приоритет: P0 (без `fsync` каталога на ext4 после пропадания питания возможен пустой файл, ревью §6).
- Обоснование: R-1, R-20; решение 1.
- Приёмка: ручной сценарий (Linux): `strace -f -e trace=fsync,fdatasync,rename,renameat2` при записи каждого файла → `fsync` временного файла, затем `rename`, затем `fsync` дескриптора каталога. Windows, macOS: ревью кода против Части 3.
- Зависимости: ТЗ-18.

**ТЗ-20. Ошибки записи не отбрасываются.** Ошибка записи (сериализации, создания каталога, записи, `fsync`, `rename`) должна:
- оставлять прежний файл на диске нетронутым, не менять значения в памяти, не снимать признаки ожидающей записи (отличие от эталонного текста, флаг «плейлист изменён»);
- записываться в журнал с видом ошибки, текстом ОС и путём;
- для рабочих файлов (`settings.toml`, `state.toml`, `playlist.m3u`) — показываться в одном окне Error (ТЗ-52) со списком файлов и классом причины («нет места на диске», «нет доступа», «файловая система только для чтения», «ошибка ввода-вывода»); новая ошибка при открытом окне добавляет файл в список; кнопки «Повторить» и «OK»;
- прекращать запись этого файла по отсчёту N после первой неудачи; «Повторить» выполняет запись всех файлов списка сразу, записанные удаляются из списка и для них запись по отсчёту возобновляется; окно закрывается, когда список пуст; при неудаче окно остаётся с обновлённой причиной;
- по «Сохранить» — диалог закрывается, настройки действуют в памяти, повтор — «Повторить» или при выходе (ОВ-2 (§11));
- для явного действия пользователя (экспорт, чтение «Загрузить плейлист») — отдельное окно Error на каждую неудачную попытку; дедупликации нет.

На пути выхода выполняется одна попытка записи каждого файла с отличиями независимо от прежних неудач (кроме случая 3 ОВ-8 (§11)); её ошибка — только в журнал (ТЗ-14).

- Приоритет: P0 (ошибки молча терялись, R-1).
- Обоснование: R-1; промт («Идиоматичный Rust»: типизированные ошибки); ОВ-7 (§11); У-3.
- Приёмка: автотест: подменное хранилище возвращает «нет места» для `state.toml` → файл прежний, одна запись журнала, одно окно Error, за следующие 10 мин 0 попыток записи по отсчёту; «Повторить» после освобождения места → запись выполнена, окно закрыто, следующее изменение записано по отсчёту; без «Повторить» место освобождено → выход → `state.toml` записан. Автотест: носитель только для чтения, изменить громкость и добавить трек → через N с одно окно со списком `state.toml`, `playlist.m3u`. Автотест: ошибка записи по «Сохранить» → диалог закрыт, новые настройки действуют, окно Error со `settings.toml`, при выходе — одна попытка записи.
- Зависимости: ТЗ-11, ТЗ-12, ТЗ-52, ТЗ-54.

**ТЗ-21. Чтение `playlist.m3u` при запуске.** Чтение рабочего плейлиста должно различать три случая:
1. файл отсутствует — пустой плейлист в памяти, без сообщений; файл создаётся при первой обычной записи;
2. файл прочитан, но повреждён (§2, «Неразбираемый файл») — частичного разбора нет: файл при запуске переименовывается в `playlist.m3u.bad` (одна копия, следующая заменяет предыдущую), плейлист пуст, окно Warning с путём копии (ТЗ-52); если переименовать не удалось — как случай 3;
3. файл не читается (ошибка ввода-вывода, нет доступа) или его не удалось переименовать — файл не трогается, плейлист пуст, окно Error; `playlist.m3u` в этом сеансе не записывается ни по отсчёту, ни при выходе; воспроизведение и работа с плейлистом в памяти доступны; при следующем запуске — новая попытка чтения.

- Приоритет: P0.
- Обоснование: решения 5, 9 (по аналогии); R-15; ОВ-8 (§11).
- Приёмка: автотест: нет файла → пустой плейлист, 0 записей до первого изменения; файл с невалидным UTF-8 → `playlist.m3u.bad` побайтово равен исходному, `playlist.m3u` отсутствует до первой записи, окно Warning; ошибка чтения → добавить трек, выход → 0 записей `playlist.m3u`, исходный файл не изменён, одно окно Error. Ручной сценарий: каталог настроек на носителе только для чтения → плеер запускается, плейлист читается и играет.
- Зависимости: ТЗ-18, ТЗ-52.

**ТЗ-22. Нет файлового ввода-вывода в UI-потоке.** В UI-потоке не должны выполняться: запись `settings.toml`, `state.toml`, `playlist.m3u`, файла экспорта; чтение и разбор плейлиста и тегов (стартовая загрузка, «Загрузить плейлист»); чтение файлов тем при открытии диалога и выборе темы; подсчёт размера кэшей (выполняется при открытии диалога и после очистки кэша, а не периодически); очистка кэшей (ТЗ-34). Системные диалоги выбора файлов — ТЗ-53. Длительность одной итерации цикла событий UI — по ТЗ-103 (01_audio_modes): ≤ 50 мс, цель ≤ 16 мс. Исключение: на пути выхода UI-поток ожидает писателя в пределах НФ-9 (ТЗ-14, ТЗ-15).

- Приоритет: P1.
- Обоснование: R-13; промт («Slint и UI-поток»); ОВ-4, ОВ-6, ОВ-9, ОВ-10 (§11).
- Приёмка: замер: инструментированный цикл событий; сценарии «запись `state.toml` при подменной задержке записи 2 с», «открытие диалога настроек при кэше из 10 000 файлов», «очистка кэша из 10 000 файлов», «Загрузить плейлист из 5 000 треков» → максимальная итерация ≤ 50 мс. Автотест: пока диалог открыт 10 с, подсчёт размера кэша выполнен 1 раз.
- Зависимости: ТЗ-103 (01_audio_modes); ТЗ-53.

### 4.4. Окно настроек

**ТЗ-23. Модальность диалога.** Пока открыт диалог настроек, главное окно должно быть недоступно: указатель, колёсико и клавиатура не должны достигать элементов главного окна (включая клавишу V); меню главного окна (в том числе «Удалить текущий трек» и «Очистить плейлист», ТЗ-34) должно быть полностью неактивно, а где пункты нельзя сделать неактивными — их обработчики ничего не делают; повторно открыть диалог (и пересоздать копию) нельзя. Тот же механизм недоступности главного окна используется, пока открыто окно сообщения (ТЗ-52) и системный диалог выбора файлов (ТЗ-53); тот же механизм недоступности отдельных команд — во время загрузки плейлиста (ТЗ-48).

- Приоритет: P1.
- Обоснование: R-11; решение 8; промт («Окно настроек»); ОВ-7, ОВ-9, ОВ-15 (§11).
- Приёмка: автотест: при открытом диалоге вызов каждого обработчика меню → 0 изменений плейлиста, настроек, состояния и копии (`menu_inactive_while_dialog_open`); то же при открытом окне сообщения. Ручной сценарий на Linux X11, Linux Wayland, Windows, macOS: при открытом диалоге щелчки по меню, таблице, ползункам, клавиша V, колёсико над ползунком громкости → ничего не происходит; пункты меню визуально неактивны (если платформа это поддерживает; иначе фиксируется в протоколе приёмки).
- Зависимости: —.

**ТЗ-24. Трей во время диалога и окна сообщения.** Пока открыт диалог или окно сообщения, трей должен работать: громкость колёсиком (по ТЗ-37), воспроизведение/пауза, стоп, предыдущий/следующий, показать/скрыть окно, «Выход» (по ТЗ-32 и ТЗ-52). Изменения, сделанные через трей, меняют действующее состояние, а не копию диалога, и не должны откатываться ни «Сохранить», ни «Отменой». Требование действует на платформах, где у плеера есть трей (сейчас Linux; В-1 (§11)).

- Приоритет: P1.
- Обоснование: решения 3, 7, 8; R-12; краевой случай 1 промта; ОВ-7, В-1 (§11).
- Приёмка (подменная платформа с треем; ручная проверка — Linux): автотест: открыть диалог, колёсиком трея +10 %, изменить фильтр SRC, «Сохранить» → громкость +10 %, фильтр применён по ТЗ-137 (01_audio_modes), одна запись `settings.toml`, громкость в `state.toml` по отложенной записи. Автотест: открыто окно сообщения, колёсико трея +2 % → громкость изменена.
- Зависимости: ТЗ-25, ТЗ-37, ТЗ-52.

**ТЗ-25. Копия содержит только параметры диалога.** Копия диалога должна содержать только настройки (§2) и значения, редактируемые в диалоге по Т-1 и Т-2 (тип визуализации, сброс ширин колонок). «Сохранить» не должен менять ни одного значения состояния сессии, которое не редактировалось в диалоге, — в том числе громкость, mute, геометрию окна (включая развёрнуто и полноэкранный режим), ширины колонок (если «Сбросить ширины» не нажималась), сортировку, Repeat, Shuffle, активный режим, последний каталог, изменённые за время открытого диалога. Тип визуализации и ширины из диалога по «Сохранить» переносятся в действующее состояние и попадают в `state.toml` отложенной записью.

- Приоритет: P1.
- Обоснование: R-12; решение 1; Т-1, Т-2.
- Приёмка: автотест: открыть диалог; изменить размер окна, развернуть окно, пересчитать ширины колонок, изменить Repeat; в диалоге изменить тему; «Сохранить» → все значения состояния равны изменённым во время диалога, тема новая. Автотест: «Сбросить ширины» в диалоге и «Сохранить» → ширины по умолчанию, `settings.toml` без ширин, `state.toml` — по отложенной записи.
- Зависимости: ТЗ-2.

**ТЗ-26. «Отмена» и Esc.** «Отмена» и Esc должны уничтожать копию: ни один параметр не применяется, ни один файл не записывается; значения, изменённые мимо диалога (ТЗ-24), сохраняются. Мгновенные действия очистки кэша (ТЗ-34) «Отменой» не отменяются.

- Приоритет: P1.
- Обоснование: промт («Окно настроек»); решение 6; ОВ-10 (§11).
- Приёмка: автотест: изменить в копии тему, фильтр SRC, N → «Отмена» → действующие настройки без изменений, 0 записей, 0 команд движку (`dialog_cancel_leaves_settings_and_file_unchanged`).
- Зависимости: ТЗ-25.

**ТЗ-27. Доступность кнопки «Сохранить».** Кнопка «Сохранить» должна быть активна тогда и только тогда, когда в копии есть отличия и нет недопустимых значений. При недопустимом значении подсказка при наведении на кнопку должна называть параметр и причину. Изменить значение и вернуть прежнее — отличий нет, кнопка неактивна.

- Приоритет: P1.
- Обоснование: R-6; решение 6; краевой случай 2 промта.
- Приёмка: автотест: открыть диалог → неактивна; изменить тему → активна; вернуть прежнюю → неактивна (`save_button_disabled_without_changes`); ввести недопустимое значение → неактивна, текст подсказки содержит имя параметра. Ручной сценарий: наведение на неактивную кнопку при недопустимом значении показывает причину.
- Зависимости: ТЗ-25.

**ТЗ-28. «Сохранить» — одна запись итоговых настроек.** По «Сохранить» `settings.toml` должен записываться ровно один раз и содержать итоговые настройки целиком, включая тему и все прочие применённые параметры. Промежуточные записи (например, при смене устройства) не допускаются. Диалог закрывается. При ошибке записи диалог всё равно закрывается, настройки действуют в памяти, ошибка показывается по ТЗ-20, повтор — «Повторить» или при выходе.

- Приоритет: P1.
- Обоснование: R-6, R-8; решения 1, 2, 6; ОВ-7 (§11).
- Приёмка: автотест: изменить тему, устройство и фильтр SRC одним «Сохранить» → одна запись `settings.toml`, в ней новая тема, новое устройство и новый фильтр. Автотест: «Сохранить» без отличий недоступен — 0 записей (`dialog_save_without_changes_does_not_write`). Автотест: подменная ошибка записи → диалог закрыт, новая тема применена, окно Error со `settings.toml`.
- Зависимости: ТЗ-3, ТЗ-20, ТЗ-27.

**ТЗ-29. Применяются только отличия.** По «Сохранить» должны применяться только отличия; применение каждого параметра — по §5.2. Не-звуковые параметры применяются сразу в UI без воздействия на воспроизведение (без переоткрытия трека, паузы, сброса позиции). Неизменённые параметры не должны вызывать чтения файла темы, перестроения модели плейлиста, перечисления устройств. Движку должна передаваться разница опций режимов (`ModeSettingsUpdate` (01_audio_modes)) только если изменился хотя бы один параметр режима; способ применения в тракте — ТЗ-137 (01_audio_modes).

- Приоритет: P1.
- Обоснование: R-7, R-19; решение 2; краевой случай 10 промта.
- Приёмка: автотест со счётчиками: изменить только тему → 1 чтение темы, 0 перестроений модели плейлиста, 0 перечислений устройств, 0 команд `SetModeSettings`, 0 переоткрытий; изменить только набор колонок → 0 чтений темы; воспроизводится DSD-трек, изменить только размер обложки → 0 переоткрытий; изменить параметр неактивного режима → одна команда с разницей из одного параметра, 0 переоткрытий (ТС-8 (01_audio_modes)) (`dialog_save_applies_only_edited_fields`).
- Зависимости: ТЗ-137 (01_audio_modes).

**ТЗ-30. Выбор режима в диалоге.** Выбор режима в диалоге должен только переключать показываемые параметры: он не должен менять активный режим, не должен считаться отличием и не должен сохраняться. Флажок bit-perfect как способ выбора режима в диалоге отсутствует.

- Приоритет: P1.
- Обоснование: решение 1; Т-4.
- Приёмка: автотест: в Совместимом режиме выбрать в диалоге Строгий, закрыть «Отменой» и повторно открыть с «Сохранить» другого параметра → активный режим Совместимый, 0 команд `SetActiveMode`; после выбора режима в диалоге без других изменений кнопка «Сохранить» неактивна.
- Зависимости: ТЗ-27.

**ТЗ-31. Скрытие отсортированной колонки.** Скрытие колонки, по которой отсортирован плейлист, не должно менять видимый порядок и ключ сортировки; стрелка не видна, пока колонка скрыта; при повторном показе колонки стрелка возвращается. Пока колонка ключа скрыта, снять ключ нельзя (ТЗ-42); щелчок по другой колонке заменяет ключ по ТЗ-42.

- Приоритет: P1.
- Обоснование: решение 2; ОВ-12 (§11).
- Приёмка: автотест: ключ «Год ↓», скрыть «Год» и «Сохранить» → видимый порядок и ключ прежние; показать «Год» → стрелка «↓» на «Год».
- Зависимости: ТЗ-40, ТЗ-42.

**ТЗ-32. Выход при открытом диалоге.** Любой выход при открытом диалоге должен работать как «Отмена»: без вопроса, копия уничтожается, отличия диалога в `settings.toml` не попадают; `state.toml` и `playlist.m3u` записываются по ТЗ-14.

- Приоритет: P1.
- Обоснование: решение 7.
- Приёмка: автотест для каждого пути выхода: открыть диалог, изменить тему, изменить громкость до открытия диалога → выход → в `settings.toml` прежняя тема, `state.toml` записан (`exit_with_open_dialog_discards_draft`).
- Зависимости: ТЗ-14, ТЗ-26.

**ТЗ-33. Параметр N.** В окне настроек должен быть параметр «интервал сохранения состояния» со значениями 10 / 30 / 60 / 120 с, по умолчанию 30 с, хранящийся в `settings.toml`; подсказка описывает потери при сбое (ТЗ-16) и, если способ перехвата завершения сеанса на платформе не найден (ТЗ-15), потери при завершении сеанса.

- Приоритет: P1.
- Обоснование: решение 1; ОВ-6 (§11).
- Приёмка: автотест: значение 45 в файле → 30 и заметка (ТЗ-5). Ручной сценарий: параметр виден, четыре значения, подсказка есть.
- Зависимости: ТЗ-5, ТЗ-11.

**ТЗ-34. Действия с плейлистом и кэшем.** «Удалить текущий трек» и «Очистить плейлист» должны отсутствовать в диалоге настроек и находиться в меню главного окна, в котором находятся «Добавить файлы» и «Добавить папку»; они выполняются сразу, без подтверждения, по общим правилам команд плейлиста (флаг «плейлист изменён», ТЗ-12; недоступность во время загрузки плейлиста, ТЗ-48). Кнопки очистки кэшей (визуализации, обложек, всех) остаются в диалоге как мгновенные действия вне модели копии; на вкладке рядом с ними виден постоянный текст о том, что очистка выполняется сразу и не отменяется кнопкой «Отмена». Очистка выполняется вне UI-потока, после неё обновляется показанный размер кэша, сообщений нет.

- Приоритет: P1.
- Обоснование: промт («Окно работает с копией… „Отмена“ — ничего не применяется»); R-7, §3.3 ревью; код `src/app/mod.rs:1444-1553`; ОВ-10 (§11).
- Приёмка: автотест: очистить кэш обложек, затем «Отмена» → кэш пуст, настройки без изменений, 0 записей `settings.toml`, 0 окон сообщений; «Очистить плейлист» из меню → плейлист пуст, флаг взведён, через N с одна запись `playlist.m3u`. Ручной сценарий: в диалоге нет кнопок «Удалить текущий трек» и «Очистить плейлист»; текст о неотменяемости виден на вкладке кэша без наведения.
- Зависимости: ТЗ-12, ТЗ-22, ТЗ-26, ТЗ-48.

### 4.5. Громкость и mute в UI

Правило источников громкости и их поведение в тракте по режимам — ТЗ-141 (01_audio_modes); здесь — UI и хранение.

**ТЗ-35. Ползунок отражает громкость активного режима.** Ползунок громкости главного окна должен показывать громкость активного режима после изменения любым источником, в том числе после того, как пользователь перетаскивал ползунок, и после переключения режима.

- Приоритет: P1.
- Обоснование: промт («Громкость»: трей и горячие клавиши двигают ползунок); ревью §3.4 (предположение о разрыве привязки); В-1 (§11).
- Приёмка: ручной сценарий (Linux): перетащить ползунок на 40 %, затем колёсиком трея +3 щелчка → ползунок 46 %; переключить режим → ползунок показывает громкость другого режима.
- Зависимости: ТЗ-37.

**ТЗ-36. Нормализация колёсика.** Колёсико над ползунком громкости и над иконкой трея (трей — на платформах, где у плеера есть трей (сейчас Linux; В-1 (§11))) должны давать одинаковый результат: один щелчок колёсика → изменение громкости на 2 % (решение 3; шаг одинаков для всех источников, включая трей, отдельного коэффициента для трея нет), «вверх» — громче с учётом системной инверсии прокрутки. Нормализация выполняется в модуле ввода (ТЗ-54):

1. **События** (В-2 (§11)). Модуль получает события колёсика окна через `slint::winit_030::WinitWindowAccessor::on_winit_window_event` (feature `unstable-winit-030`): тип дельты (`LineDelta`/`PixelDelta`) и фазу жеста. Принадлежность события ползунку громкости определяется событием Slint `scroll-event`: событие winit сопоставляется с ним по значению (×60 для строк) и времени. Без сопоставленного события winit применяется правило по умолчанию на значениях Slint. Трей — `delta` и `orientation` ksni.
2. **Класс устройства** (В-3 (§11)) — колесо или тачпад — по тому, что сообщает ОС через winit (тип дельты, дробность значений, фаза). Устройство, которое ОС отдаёт как колесо, обрабатывается как колесо: одно деление — один щелчок, без ограничения скорости, даже если физически это тачпад, эмулирующий колесо. Для класса «тачпад» смещения накапливаются со знаком до порога щелчка с переносом остатка; одно движение не даёт десятков шагов — проверяется на событиях класса «тачпад».
3. **Таблица данных** (не код). Ключ для ползунка — «платформа × класс устройства»; для трея — хост StatusNotifierItem (В-5 (§11)). Хост определяется по процессу-владельцу службы `org.kde.StatusNotifierWatcher` на D-Bus (способ подтверждается в Части 3), запасной путь — `XDG_CURRENT_DESKTOP`; неизвестный хост — знак как у KDE, деление — по величине первого события, исход «правило по умолчанию».

Данные таблицы:
- колесо над ползунком — одно деление (`LineDelta` 1, 60 логических px Slint) = один щелчок, знак как пришёл; KDE, GNOME, Windows — по эксперименту `wheel_test.md` (§5.3);
- тачпад Windows — порог одного шага T = 0,5 строки (60 ед. `WHEEL_DELTA`), накопление со знаком с переносом остатка, не более K = 5 шагов на свайп; граница свайпа — пауза больше 300 мс, после неё остаток сбрасывается; инерция отдельно не отбрасывается — её ограничивает K (В-4 (§11));
- трей: KDE Plasma — «вверх» = +, деление 120; GNOME с AppIndicator — «вверх» = −, деление 1 (В-5 (§11));
- платформы, сеансы и классы устройств без данных эксперимента (KDE X11, GNOME X11, тачпад с точными дельтами на Linux) — правило по умолчанию;
- macOS до эксперимента — по API платформы: тип устройства по признаку точных дельт, направление с учётом системной инверсии, инерционные события после окончания жеста игнорируются; порог тачпада — значение по умолчанию; пометка «не подтверждено экспериментом»; после эксперимента меняются только данные таблицы.

Эксперимент записал тип дельты и фазу жеста на уровне winit и значения Slint; признака инерции winit не передаёт (`wheel_test.md` §2, §4.6). Записи — данные автотестов. Нестабильный API `unstable-winit-030` изолирован в модуле ввода; обновление Slint требует проверки модуля автотестами на записанных последовательностях (В-2 (§11)).

Для каждой из восьми пар «платформа (GNOME, KDE, Windows, macOS) × источник (над ползунком, над треем)» протокол приёмки фиксирует исход: подтверждено экспериментом / по документации платформы / правило по умолчанию (событие колеса мыши — один щелчок, пиксельные дельты накапливаются до порога, знак по системной настройке) / источника нет (не дефект; глобальный перехват мыши в объём не входит). Исходы по таблице «Исходы восьми пар» `wheel_test.md` §6 с учётом В-1 (§11):

| Платформа | Над ползунком | Над треем |
|---|---|---|
| GNOME | подтверждено экспериментом (Wayland, мышь); X11 и тачпад с точными дельтами — правило по умолчанию | подтверждено экспериментом (AppIndicator, Wayland, мышь) |
| KDE | подтверждено экспериментом (Wayland, мышь); X11 и тачпад с точными дельтами — правило по умолчанию | подтверждено экспериментом (Wayland, мышь) |
| Windows | подтверждено экспериментом (мышь, тачпад) | источника нет: трея у плеера нет (В-1 (§11)) |
| macOS | по документации платформы | источника нет: трея у плеера нет (В-1 (§11)) |

- Приоритет: P1.
- Обоснование: решение 3; R-22; ревью §3.4 (шаг 0,04 против 0,02, противоположные знаки); ОВ-11 (§11); У-3; В-1…В-5 (§11); `wheel_test.md` §5.3, §6, §8.
- Приёмка:
  - автотест на записанных последовательностях GNOME, KDE, Windows (мышь, тачпад) → число шагов громкости равно ожидаемому по протоколу эксперимента (`wheel_test.md` §5.2);
  - автотест (В-3): последовательности «тачпада» KDE-3 и GNOME-2 обрабатываются как колесо — одно деление = один шаг; быстрая прокрутка мышью 10–12 щелчков → 10–12 шагов;
  - автотест (В-4): записанные свайпы тачпада Windows → короткий — 1–4 шага, длинный и быстрый — 5; свайпы с выбросами ≈ 67 строк — не более 5 шагов на свайп;
  - автотест (В-5): записанные последовательности трея KDE-1…3 и GNOME-1, 2 → то же число шагов и то же направление, что у последовательностей ползунка того же замера; щелчок вверх в трее KDE → громче (текущая инверсия трея на KDE устранена);
  - автотест (В-2): событие Slint `scroll-event` без сопоставленного события winit → правило по умолчанию (60 px = один щелчок); событие winit без сопоставленного `scroll-event` (указатель вне ползунка) → громкость не меняется;
  - автотест: одинаковые последовательности над ползунком и над треем дают одинаковый результат (подменная платформа с треем);
  - автотест macOS на синтетической последовательности «жест + инерция» → инерционные события не меняют громкость;
  - протокол приёмки содержит исход для всех восьми пар;
  - ручной сценарий на каждой платформе с исходом «подтверждено экспериментом»: 5 щелчков мыши вверх над ползунком → +10 %; над иконкой трея → +10 % — только на Linux (KDE, GNOME).
- Зависимости: ТЗ-141 (01_audio_modes); ТЗ-54.

**ТЗ-37. Источники громкости без громкости.** В Строгом режиме и в Оптимальном с фиксацией громкости ползунок, колёсико над ползунком, колёсико над иконкой трея и горячие клавиши не должны менять ни громкость, ни положение ползунка, ни состояние сессии и не должны запускать отсчёт N; mute должен работать.

- Приоритет: P1.
- Обоснование: решение 3; ТЗ-41, ТЗ-140, ТЗ-141 (01_audio_modes); краевой случай 9 промта.
- Приёмка: автотест: Строгий режим и Оптимальный с фиксацией, команды громкости от каждого источника → громкость, состояние и отсчёт N без изменений; mute переключается (`strict_mode_wheel_and_hotkeys_do_not_change_volume`, `optimal_volume_lock_ignores_all_sources`).
- Зависимости: ТЗ-11.

**ТЗ-38. Mute в состоянии сессии.** Переключение mute любым способом должно менять mute активного режима в действующем состоянии, запускать отсчёт N (если он не идёт) и восстанавливаться после перезапуска для каждого режима отдельно, включая Строгий.

- Приоритет: P1.
- Обоснование: R-9; решения 1, 3; ТЗ-138 (01_audio_modes); У-1.
- Приёмка: автотест: mute в Строгом, без mute в Совместимом → выход → перезапуск → значения каждого режима восстановлены.
- Зависимости: ТЗ-11.

**ТЗ-39. Подсказки у неактивных регуляторов.** Неактивный ползунок громкости и неактивная кнопка должны показывать причину во всплывающей подсказке при наведении (например, «Громкость недоступна в Строгом режиме», «Громкость зафиксирована на 100 % в настройках Оптимального режима»). Новых элементов интерфейса не добавляется. Кнопка «перейти к настройке» — только внутри подсказки и только если Slint это позволяет; иначе подсказка — только текст (определяется в Части 3).

- Приоритет: P2.
- Обоснование: решение 3; ТЗ-41 (01_audio_modes).
- Приёмка: ручной сценарий: в Строгом режиме и в Оптимальном с фиксацией наведение на ползунок → подсказка с причиной.
- Зависимости: —.

### 4.6. Плейлист, сортировка, порядок

Выбор следующего трека по видимому порядку, стабильность сортировки и сброс ключа при ручном изменении порядка в тракте — ТЗ-142 (01_audio_modes); здесь — хранение, UI и модель порядка.

**ТЗ-40. Сортировка не меняет исходный порядок.** Сортировка по колонке и снятие ключа должны менять только видимый порядок и ключ сортировки в действующем состоянии; исходный порядок, `playlist.m3u` и флаг «плейлист изменён» не меняются. Ключ сортировки восстанавливается после перезапуска.

- Приоритет: P1.
- Обоснование: промт («Плейлист и сортировка»); решения 1, 5; ОВС-21 (01_audio_modes); ОВ-12 (§11).
- Приёмка: автотест: сортировка «Исполнитель ↑» → флаг не взведён, 0 записей `playlist.m3u`, `state.toml` по отложенной записи содержит ключ; перезапуск → видимый порядок тот же.
- Зависимости: ТЗ-11, ТЗ-12.

**ТЗ-41. Видимый порядок соответствует ключу.** При активном ключе сортировки добавленные треки (из меню, сканирования каталога) должны занимать места по ключу, а не в конце списка; в исходном порядке они добавляются в конец.

- Приоритет: P1.
- Обоснование: ревью §3.6 (результаты сканирования добавляются в конец отсортированного списка).
- Приёмка: автотест: ключ «Название ↑», добавить трек «A…» → он первый в видимом порядке и последний в исходном.
- Зависимости: ТЗ-40.

**ТЗ-42. Снятие ключа сортировки.** Щелчки по заголовку колонки должны циклически переключать ключ: по возрастанию → по убыванию → без сортировки; щелчок по другой колонке начинает с «по возрастанию». Без сортировки видимый порядок равен исходному, стрелки нет. Снятие ключа меняет состояние (запускает отсчёт N, ключ «нет» в `state.toml`), флаг «плейлист изменён» не взводит, воспроизведение не прерывает; следующий трек — по новому видимому порядку (при Shuffle — ТЗ-45). Если колонка ключа скрыта (ТЗ-31), ключ снимается только после её показа; отдельного пункта меню нет.

- Приоритет: P1 (от снятия ключа зависят ТЗ-12, ТЗ-31, ТЗ-40, ТЗ-45).
- Обоснование: ревью §3.6 (нет возврата к исходному порядку); ОВ-12 (§11).
- Приёмка: автотест: три щелчка по «Название» → ключ «↑», «↓», «нет»; после третьего видимый порядок равен исходному, 0 записей `playlist.m3u`, через N с `state.toml` с ключом «нет»; щелчок по «Году» при ключе «Название ↓» → «Год ↑».
- Зависимости: ТЗ-40.

**ТЗ-43. Правила сравнения при сортировке.** Текст должен сравниваться без учёта регистра, после приведения к одной форме Unicode; последовательности цифр внутри текста — как числа («No. 9» < «No. 10»). Год, номер трека и номер диска сравниваются как числа. Пустые значения — в конце при любом направлении. Вторичные ключи (всегда по возрастанию, независимо от направления главного): Исполнитель → год → альбом → диск → трек; Альбом → диск → трек; Год → альбом → диск → трек; остальные колонки — без вторичных ключей. При полном равенстве — исходный порядок (стабильная сортировка, ТЗ-142 (01_audio_modes)). Колонка «Сейчас играет» не сортируется: щелчок ничего не делает, стрелки нет.

- Приоритет: P2.
- Обоснование: ревью §3.6 (побайтовое регистрозависимое сравнение, год строкой, номер диска игнорируется, колонка «Сейчас играет» переключает стрелку без сортировки); ОВ-13 (§11).
- Приёмка: автотест на наборе с регистром «beatles»/«Zappa», годами «999»/«2001», дисками 1/2 одного альбома, названиями «No. 9»/«No. 10», одним названием в двух формах Unicode и пустым годом → ожидаемый порядок для каждой колонки в обоих направлениях; щелчок по колонке «Сейчас играет» → ключ и стрелка без изменений.
- Зависимости: ТЗ-40.

**ТЗ-44. Ручное изменение порядка.** Операция ручного изменения порядка в модели плейлиста должна: сохранять видимый порядок, который видел пользователь, с учётом перемещения; при активном ключе — снимать ключ (стрелка исчезает) и делать исходный порядок равным новому видимому; взводить флаг «плейлист изменён». В задаче 02 реализуется только эта операция; интерфейс (перетаскивание мышью, клавиатура) — отдельная задача, он вызывает ту же операцию.

- Приоритет: P1.
- Обоснование: промт («Плейлист и сортировка»); решение 5; ТЗ-142 (01_audio_modes); краевой случай 8 промта; ОВ-14 (§11).
- Приёмка: автотест на операции модели: ключ «Название ↑», переместить 3-ю строку на 1-е место → ключ «нет», видимый и исходный порядок равны отсортированному с перемещённой строкой, флаг взведён (`drag_reorder_clears_sort_key`).
- Зависимости: ТЗ-12, ТЗ-40.

**ТЗ-45. Shuffle и изменения плейлиста.** Смена сортировки, снятие ключа, добавление и удаление треков при Shuffle не должны менять текущий трек и прерывать воспроизведение; треки, уже сыгранные в текущем проходе перестановки, не должны повторяться раньше несыгранных (при Repeat Off каждый трек плейлиста играет один раз). Смена сортировки, снятие ключа, добавление и удаление — действия пользователя в смысле термина «Серия пропусков» (01_audio_modes).

- Приоритет: P1.
- Обоснование: ревью §3.6 (перестановка пересоздаётся с потерей истории); краевой случай 7 промта; ТС-6 (01_audio_modes); ОВ-12 (§11).
- Приёмка: автотест: Shuffle, Repeat Off, 10 треков, сыграно 4 → смена сортировки и добавление 2 треков → до остановки сыграны все 12, каждый один раз, текущий трек не сменился в момент изменения.
- Зависимости: ТЗ-40.

**ТЗ-46. «Далее» без текущего трека.** «Далее», когда текущего трека нет, должно начинать воспроизведение с первого трека видимого порядка (при Shuffle — первого в перестановке).

- Приоритет: P1.
- Обоснование: ревью §3.6, §9 (играет индекс 1; тест `advance_index_clamps_without_repeat` подлежит переписыванию).
- Приёмка: автотест: плейлист без текущего трека, «Далее» → воспроизводится первый трек видимого порядка.
- Зависимости: —.

**ТЗ-47. Стартовая загрузка в фоне с индикатором.** Стартовая загрузка должна выполняться вне UI-потока в порядке: чтение `playlist.m3u` (по ТЗ-21) → чтение тегов всех файлов → применение сохранённого ключа сортировки. Главное окно должно появляться, не дожидаясь загрузки; пока она идёт, виден индикатор загрузки; плейлист показывается только целиком, уже отсортированным. Кэша тегов нет.

- Приоритет: P1.
- Обоснование: R-14; решение 10.
- Приёмка: замер: плейлист из 5 000 треков, подменная задержка чтения тегов → первый кадр окна не позже, чем без плейлиста, + 50 мс; итерации цикла событий UI ≤ 50 мс; до окончания виден индикатор, таблица не показывает частичный список; после — список сразу в сохранённом порядке сортировки.
- Зависимости: ТЗ-21, ТЗ-22; ТЗ-104 (01_audio_modes).

**ТЗ-48. Команды во время загрузки плейлиста.** Пока идёт загрузка плейлиста (стартовая или «Загрузить плейлист»), должны быть недоступны: «Добавить файлы», «Добавить папку», «Загрузить плейлист», «Удалить текущий трек», «Очистить плейлист», «Сохранить плейлист», сортировка по заголовку и перенос файлов в окно; подсказка «Идёт загрузка плейлиста». Во время «Загрузить плейлист» прежний трек играет; пауза, стоп, перемотка, громкость и mute работают; «Далее» и «Назад» недоступны; по окончании загрузки новый плейлист начинает воспроизводиться независимо от состояния, в том числе если во время загрузки нажат «Стоп» (ТЗ-13). До окончания «Загрузить плейлист» рабочим остаётся прежний плейлист; флаг «плейлист изменён», взведённый до команды, продолжает действовать, прежний плейлист записывается по отсчёту N и при выходе, загружаемый список не пишется (ТЗ-17).

- Приоритет: P0 (добавленные треки пропадали, R-15).
- Обоснование: R-15 (`drain_startup_tracks` перезаписывает `tracks`, `disk_tracks`, `known_paths`, `src/app/mod.rs:1670-1672`); решение 10; ОВ-5, ОВ-15 (§11).
- Приёмка: автотест: подменная загрузка задерживается → каждая перечисленная команда недоступна и не меняет плейлист; после окончания — доступна; «Загрузить плейлист», «Стоп» во время загрузки → после загрузки воспроизводится первый трек нового плейлиста; выход во время «Загрузить плейлист» при невзведённом флаге → 0 записей `playlist.m3u` (при взведённом — ТЗ-17).
- Зависимости: ТЗ-13, ТЗ-23, ТЗ-47.

### 4.7. Тестируемость

**ТЗ-49. Тесты не трогают файлы пользователя.** Ни один тест не должен читать или писать файлы в каталоге настроек пользователя, создавать файлы тем, запускать трей или поток стартовой загрузки пользователя.

- Приоритет: P0 (каждый `cargo test` перезаписывал `settings.toml` пользователя).
- Обоснование: R-16.
- Приёмка: `cargo test` с каталогом настроек, недоступным на запись (или подменённым `XDG_CONFIG_HOME` на пустой каталог только для проверки) → все тесты проходят, каталог пуст и не изменён.
- Зависимости: ТЗ-50.

**ТЗ-50. Счётчик записей каждого файла.** Все события матрицы §5.1 должны проверяться автотестами, которые считают записи `settings.toml`, `state.toml`, `playlist.m3u` по отдельности, без файловой системы пользователя и без аудио-устройства.

- Приоритет: P1 (предпосылка приёмки ТЗ-3…ТЗ-17).
- Обоснование: промт (критерий «Тестируемость»); ТЗ-114 (01_audio_modes).
- Приёмка: для каждой строки §5.1 есть автотест; перечень тестов — Часть 3.
- Зависимости: ТЗ-54.

**ТЗ-51. Переписать тесты, закрепляющие неверное поведение.** Тесты, закрепляющие поведение, противоречащее этому ТЗ, должны быть переписаны или удалены: как минимум `advance_index_clamps_without_repeat` (`src/playlist.rs:366-371`, ТЗ-46) и `bp_report_marks_volume_issue` (`src/app/bp_report.rs:205-207`, ТЗ-49); полный перечень — Часть 3.

- Приоритет: P1.
- Обоснование: промт («существующие тесты не источник требований»); ревью §9.
- Приёмка: ревью: для каждой строки перечня Части 3 указан новый тест или причина удаления и ТЗ-N.
- Зависимости: ТЗ-49.

### 4.8. Сообщения, выбор файлов, платформенные модули

**ТЗ-52. Окно сообщений.** Сообщения пользователю должны передаваться по трём каналам:
1. окно сообщения — оверлей поверх главного окна и диалога настроек; уровни Info / Warning / Error с разными значками и цветом заголовка; до закрытия блокирует по механизму ТЗ-23 главное окно и открытый под ним диалог настроек; любой выход при открытом окне сообщения закрывает его без вопроса, запись — по ТЗ-14 (одна попытка на файл); воспроизведение и трей (на платформах с треем) работают (ТЗ-24); Enter — основная кнопка, Esc — закрыть; сообщения, возникшие до первого показа главного окна, показываются после него; несколько сообщений — очередью по одному;
2. системное уведомление — если главное окно скрыто в трей; окно сообщения показывается при открытии плеера. Канал есть только на платформах, где у плеера есть трей (сейчас Linux; В-1 (§11)); на Windows и macOS окно в трей не сворачивается, сообщение показывается окном сообщения;
3. журнал.

Правило выбора канала: окно — если данные пользователя под угрозой или его явное действие не выполнено; успешное действие, результат которого виден в интерфейсе, сообщения не порождает; остальное — журнал. Строка состояния каналом сообщений не является. Уровень Info в текущем объёме не используется. Раскладка:
- ошибка записи `settings.toml`, `state.toml`, `playlist.m3u` → одно окно Error со списком (ТЗ-20);
- ошибка записи файла экспорта, ошибка чтения файла «Загрузить плейлист» → окно Error на каждую попытку (ТЗ-13, ТЗ-20);
- `playlist.m3u` повреждён / нечитаем при запуске → окно Warning / Error (ТЗ-21);
- повреждённый `settings.toml` → окно Warning с путём копии `*.bad` (ТЗ-7);
- повреждённый `state.toml`, отдельные недопустимые и неизвестные ключи, ошибка записи на пути выхода → только журнал.

Системные уведомления выдаёт платформенный модуль (ТЗ-54) на платформах с треем (В-1 (§11)).

- Приоритет: P1.
- Обоснование: ОВ-7, ОВ-16 (§11); У-2, У-3; R-1, R-2; В-1 (§11).
- Приёмка: автотест: два сообщения до первого показа окна → после показа первое окно, после его закрытия — второе; при открытом окне сообщения вызов обработчиков меню → 0 изменений; подменная платформа с треем: окно скрыто в трей, ошибка записи `state.toml` → одно системное уведомление, при открытии плеера — окно Error; подменная платформа без трея: ошибка записи `state.toml` → окно Error, 0 системных уведомлений; успешный экспорт → 0 окон; повреждённый `state.toml` → 0 окон; открыто окно Error с `state.toml` в списке → «Выход» в трее (подменная платформа с треем) → окно закрыто без вопроса, одна попытка записи `state.toml`. Ручной сценарий (Linux, Windows): окна Warning и Error различимы по значку и цвету заголовка; Enter нажимает основную кнопку, Esc закрывает; на Linux, кроме того, при открытом окне колёсико трея меняет громкость.
- Зависимости: ТЗ-14, ТЗ-23, ТЗ-54.

**ТЗ-53. Неблокирующий выбор файлов.** Системные диалоги выбора файлов (добавить файлы, добавить каталог, загрузить плейлист, сохранить плейлист, выбор файла темы) не должны блокировать цикл событий UI: пока диалог открыт, работают трей (на платформах, где у плеера есть трей (сейчас Linux; В-1 (§11))), отсчёт N и обновление ползунков. Главное окно на это время недоступно по механизму ТЗ-23; повторно открыть выбор файла нельзя. Выбор файла выполняет платформенный модуль (ТЗ-54). Если на платформе неблокирующий вызов невозможен, там используется блокирующий, и это фиксируется в протоколе приёмки.

- Приоритет: P1.
- Обоснование: R-13; ОВ-9 (§11); У-3; В-1 (§11).
- Приёмка: замер: открыт диалог «Добавить каталог» 30 с → максимальная итерация цикла событий UI ≤ 50 мс; на Linux, кроме того, громкость колёсиком трея меняется. Ручной сценарий на Linux, Windows, macOS: при открытом выборе файла главное окно не реагирует на щелчки и клавиши; на Linux, кроме того, трей работает.
- Зависимости: ТЗ-22, ТЗ-23, ТЗ-54.

**ТЗ-54. Платформенные модули.** Платформенно-зависимый код должен быть сосредоточен в отдельных модулях с единым интерфейсом и подменной реализацией для автотестов:
1. жизненный цикл — события завершения (закрытие окна, «Выход» в трее — на платформах с треем, `SIGTERM`/`SIGINT`/`SIGHUP`, завершение сеанса Windows, запрос завершения macOS); остальной код получает единый запрос выхода с причиной и сообщает модулю об окончании записи; ожидание, которого требует ОС, выполняет модуль;
2. файловая система — атомарная долговечная запись (ТЗ-18, ТЗ-19) и классификация ошибок записи (ТЗ-20);
3. ввод — нормализация колёсика (ТЗ-36): события колёсика окна winit через `on_winit_window_event` (feature `unstable-winit-030`) с сопоставлением со `scroll-event` Slint (В-2 (§11)); определение хоста StatusNotifierItem для трея (В-5 (§11)); нестабильный API используется только внутри модуля;
4. системные уведомления (ТЗ-52) — на платформах, где у плеера есть трей (сейчас Linux; В-1 (§11));
5. выбор файлов (ТЗ-53).

Выбор реализации — при компиляции (`cfg` по ОС) и, где нужно, при запуске, только внутри модуля. Вне этих модулей `#[cfg(target_os = …)]` для этих задач не используется. Для Части 3 по этому требованию обязателен ADR.

- Приоритет: P1.
- Обоснование: У-3; ОВ-6, ОВ-7, ОВ-9, ОВ-11 (§11); В-1, В-2, В-5 (§11).
- Приёмка: ревью кода: поиск `cfg(target_os` вне пяти модулей не находит мест, относящихся к этим задачам; автотесты ТЗ-14, ТЗ-15, ТЗ-18, ТЗ-20, ТЗ-36, ТЗ-52, ТЗ-53 используют подменные реализации модулей и выполняются на любой ОС; ревью кода: `on_winit_window_event` и типы `slint::winit_030` используются только в модуле ввода.
- Зависимости: —.

## 10. Открытые вопросы

### ОВ-1. Ключи состояния в `settings.toml` предыдущей версии

- **Контекст.** ТЗ-9. Решение 1 переносит громкость, mute, сортировку, ширины колонок, тип визуализации, Repeat, Shuffle, геометрию и последний каталог в `state.toml`. В текущем `settings.toml` пользователя эти ключи есть. ОВ-27 (01_audio_modes) отменил миграцию аудио-настроек, а С4 (01_audio_modes) требует удалить файл настроек перед первым запуском.
- **Варианты.**
  - а) Миграции нет: ключи состояния в `settings.toml` — неизвестные ключи (игнорируются с заметкой, ТЗ-5) и исчезают при следующей записи `settings.toml`; состояние начинается со значений по умолчанию.
  - б) Однократный перенос: если `state.toml` нет, ключи состояния берутся из `settings.toml` (с разбором по ключам); из `settings.toml` они исчезают при следующей записи.
  - в) Как а), но с тем же «Действием пользователя», что в С4 (01_audio_modes): удалить оба файла перед первым запуском.
- **Рекомендация: а).** Совпадает с ОВ-27 (01_audio_modes): единственный пользователь — автор, файл настроек и так удаляется перед С4; перенос — код, который выполнится один раз. Потеря — ширины колонок, геометрия, сортировка, громкость, всё восстанавливается за минуту.
- **Закрыт: см. §11.**

### ОВ-2. Запись при выходе: всегда или только при отличии

- **Контекст.** ТЗ-10, ТЗ-14. Решение 1: `settings.toml` и `state.toml` пишутся «при выходе». `settings.toml` меняется только по «Сохранить», которое пишет сразу, поэтому при выходе отличие от диска бывает только после коррекций загрузки (ТЗ-4) или после неудачной записи (ТЗ-20).
- **Варианты.**
  - а) Всегда: при каждом выходе оба файла пишутся.
  - б) Только если содержимое в памяти отличается от последней прочитанной или записанной версии файла; коррекции загрузки, значения по умолчанию при отсутствующем или неразбираемом файле и неудачная запись считаются отличием.
- **Рекомендация: б).** Та же гарантия (всё, что в памяти, оказывается на диске), но без записи при каждом выходе, в том числе без лишнего `fsync`; согласуется с «только если есть отличия» для «Сохранить» (решение 6) и с практикой DeaDBeeF/Audacious (ревью §6). Проверяется тем же счётчиком: выход без изменений → 0 записей.
- **Закрыт: см. §11.**

### ОВ-3. Изменения состояния без действия пользователя

- **Контекст.** ТЗ-11, §5.1. Часть значений состояния меняет сама программа: ширины колонок пересчитываются при изменении размера окна (`src/app/mod.rs:1614-1627`), при первом запуске окно получает начальную геометрию (R-5), коррекции загрузки (ТЗ-4). Решение 9: коррекции сразу в файл не пишутся.
- **Варианты.**
  - а) Любое изменение значения состояния запускает отсчёт N.
  - б) Отсчёт запускают только изменения, вызванные действием пользователя (включая изменение размера окна пользователем и следующий за ним пересчёт ширин); изменения программы (начальная геометрия, коррекции, пересчёт при запуске) попадают в файл со следующей записью или при выходе.
- **Рекомендация: б).** Иначе каждый запуск даёт запись `state.toml` через N с без действий пользователя, что противоречит духу решения 9 («файл сразу не переписывается»); по б) запуск без действий и выход по ОВ-2 б) дают 0 записей.
- **Закрыт: см. §11.**

### ОВ-4. Предел ожидания записи при выходе

- **Контекст.** ТЗ-14. Процесс завершается после записи файлов. Запись с `fsync` на нагруженном HDD, сетевом или засыпающем USB-носителе может длиться секунды; движку при выходе отведено 2 с (§6.28 (01_audio_modes)), но запись файлов от него не зависит (ТЗ-136 (01_audio_modes)). Числа пользователь не задавал.
- **Варианты.**
  - а) Без предела: процесс ждёт окончания записи.
  - б) Не более 2 с (как таймаут движка), затем выход с записью в журнал.
  - в) Не более 5 с, затем выход с записью в журнал.
- **Рекомендация: в).** Атомарность (ТЗ-18) гарантирует, что прерванная запись не портит файл — теряется только последнее изменение; 5 с покрывают `fsync` на медленном носителе, но не дают процессу зависнуть при выходе из сеанса ОС, где менеджер сеанса ждёт ограниченное время (конкретные таймауты менеджеров сеанса — не подтверждено).
- **Закрыт: см. §11.**

### ОВ-5. Текущий трек при «Загрузить плейлист»

- **Контекст.** ТЗ-13; R-15: сейчас текущий трек сбрасывается (`current = None`) без остановки плеера — трек играет, но не отмечен, «Далее» ведёт неизвестно куда (ТЗ-46).
- **Варианты.**

  - б) Воспроизведение останавливается, текущего трека нет.
  - в) Воспроизведение продолжается до конца трека, затем остановка.
- **Рекомендация: а).** Загрузка плейлиста не прерывает музыку (как добавление треков); правило однозначно и проверяемо, совпадает с «Далее без текущего трека» (ТЗ-46).

### ОВ-6. Завершение сеанса ОС на Windows и macOS

- **Контекст.** ТЗ-15. Решение 1 называет `SIGTERM`/`SIGINT`. - **Варианты.**
  - а) Входит в объём: завершение сеанса Windows и запрос завершения macOS ведут в путь выхода ТЗ-14; если Часть 3 не найдёт доступного API — ОВС с описанием потерь.
  - б) Не входит: при выходе из сеанса Windows/macOS теряются изменения за последние N с (НФ-6), это описывается в подсказке N.
- **Рекомендация: а).** Выключение ноутбука с открытым плеером — обычный сценарий на машине пользователя; без обработки он всегда теряет последние N с состояния и грязный плейлист.

## 11. Решения по открытым вопросам

Решения пользователя от 2026-09-29. Обязательны; при противоречии с текстом требований действуют эти решения. Внесены в §1–§9 (обновление 2026-09-29 в шапке).

### Уточнения решений из `01_review.md`

**У-1. Уточнение решения 1 и ТЗ-11: отсчёт от первого незаписанного изменения.** Отсчёт N запускается первым изменением состояния сессии или плейлиста после последней записи; последующие изменения его не перезапускают. По истечении N записывается всё накопленное. Серия изменений в пределах N даёт одну запись; непрерывная серия дольше N — одну запись каждые N с. НФ-6 (потери не более N плюс время записи) выполняется без изменений. При смене N в диалоге новый срок записи — меньшее из прежнего срока и момента «Сохранить» + новое N. Приёмка ТЗ-11: N = 30 с, изменения в t = 0, 10, 20 с → одна запись в t = 30 с со значением из t = 20 с; изменения каждые 5 с в течение 10 мин → записи в t = 30, 60, …, промежуток между записями не больше 30 с; N = 120 с, изменение в t = 0, в t = 100 с «Сохранить» с N = 10 → запись в t = 110 с.

**У-2. Уточнение решения 9: канал уведомления о повреждённом `settings.toml`.** Вместо «уведомления в существующей области уведомлений» — окно сообщения уровня Warning (ОВ-7). Остальное решение 9 без изменений.

**У-3. Архитектурное решение (для Части 3, ADR обязателен).** Платформенно-зависимый код сосредоточен в отдельных модулях с единым интерфейсом и подменной реализацией для автотестов: (1) жизненный цикл — события завершения (закрытие окна, «Выход» в трее, `SIGTERM`/`SIGINT`/`SIGHUP`, завершение сеанса Windows, запрос завершения macOS); остальной код получает единый запрос выхода с причиной и сообщает модулю об окончании записи, ожидание, которого требует ОС, выполняет модуль; (2) файловая система — атомарная долговечная запись (ТЗ-18, ТЗ-19) и классификация ошибок записи (ОВ-7); (3) ввод — нормализация колёсика (ТЗ-36, ОВ-11); (4) системные уведомления (ОВ-7); (5) выбор файлов (ОВ-9). Выбор реализации — при компиляции (`cfg` по ОС) и, где нужно, при запуске, только внутри модуля. Вне этих модулей `#[cfg(target_os = …)]` для этих задач не используется. Проверка: ревью кода. (Внесено как ТЗ-54.)

### Решения по открытым вопросам

**ОВ-1 → а).** Миграции ключей состояния нет. Ключи состояния в `settings.toml` предыдущей версии — неизвестные ключи (ТЗ-5): игнорируются с заметкой, состояние начинается со значений по умолчанию (ТЗ-8). Наличие неизвестных ключей в прочитанном `settings.toml` считается отличием от версии на диске (ОВ-2): файл перезаписывается без них при первом выходе. Приёмка: старый `settings.toml` → запуск → выход → в `settings.toml` нет ключей состояния; второй запуск — 0 заметок о неизвестных ключах.

**ОВ-2 → б).** При выходе `settings.toml` и `state.toml` записываются, только если сериализованные действующие значения отличаются от эталонного текста файла. Эталон — текст последней успешной записи, до неё — текст, прочитанный при запуске; для отсутствующего или неразбираемого файла эталон пуст. Тем же сравнением определяется необходимость записи `state.toml` по истечении отсчёта N (ТЗ-11). Сериализация детерминирована (стабильный порядок ключей). Приёмка: запуск с полными корректными файлами → выход → 0 записей; запуск с отсутствующими файлами → выход → по одной записи; неудачная запись `state.toml` → выход → одна повторная попытка.

**ОВ-3 → б).** Отсчёт N запускают изменения состояния, пришедшие из событий ввода и окна после первого показа главного окна. Значения, которые программа присваивает сама (восстановление геометрии, коррекции загрузки, пересчёт до первого показа), меняют действующее состояние без запуска отсчёта и записываются при следующей записи или при выходе по ОВ-2. Событие окна, повторяющее только что выставленное программой значение, изменением не считается. Приёмка: запуск без действий пользователя, ожидание 10 мин, выход → 0 записей `state.toml`, если файл был полным и корректным; изменение размера окна пользователем → одна запись через N с.

**ОВ-4 → в).** Общий предел ожидания записи файлов на пути выхода — 5 с на все файлы вместе. Порядок записи: `playlist.m3u` (если флаг взведён и запись не запрещена по ОВ-8), `state.toml`, `settings.toml` (каждый по ОВ-2). Запись выполняется параллельно с завершением движка (ТЗ-136 (01_audio_modes)). По истечении предела процесс завершается, в журнал пишется, какие файлы не записаны; незаписанные файлы остаются прежними целыми версиями (ТЗ-18). Приёмка: автотест с подменной задержкой записи 10 с → процесс завершается через 5 с ± 0,5 с, в журнале перечислены незаписанные файлы, в хранилище — прежние версии; подменная задержка записи плейлиста 4 с и `state.toml` 2 с → плейлист записан, `state.toml` не записан, в журнале это отражено.

**ОВ-5 → вариант пользователя: Play Now.** «Загрузить плейлист» заменяет рабочий плейлист и запускает его воспроизведение независимо от прежнего состояния (играет / пауза / стоп). Первым воспроизводится первый трек видимого порядка по действующему ключу сортировки; при Shuffle — первый трек новой перестановки; действуют текущие Repeat и Shuffle. Пока идёт фоновая загрузка (ТЗ-13, ТЗ-47), прежний трек продолжает играть; по её окончании он останавливается и начинается воспроизведение нового плейлиста. Подготовленный следующий трек прежнего плейлиста (gapless) отменяется. При ошибке чтения выбранного файла рабочий плейлист и воспроизведение не меняются, флаг не взводится, окно Error (ОВ-7). Пустой плейлист → стоп, флаг взведён. Mute сохраняется. Приёмка: автотест: играет трек X, загрузить плейлист P (ключ «Название ↑») → до окончания загрузки играет X; после — воспроизводится первый по названию трек P, X в очереди нет; то же из паузы и стопа → воспроизведение началось; нечитаемый файл → плейлист и X без изменений.

**ОВ-6 → а).** Входит в объём. Windows: `WM_QUERYENDSESSION` → немедленно TRUE; `WM_ENDSESSION` (wParam = TRUE) → путь выхода ТЗ-14 выполняется синхронно в обработчике, в пределах ОВ-4, затем возврат (как `aboutToQuit` в Qt). macOS: Cmd+Q, «Завершить» в Dock и выход из сеанса (`applicationShouldTerminate:`) → путь выхода ТЗ-14, завершение после записи; одной замены пункта меню Quit недостаточно. ТЗ-15 дополняется `SIGHUP`; обработчик сигналов только будит цикл событий. ТЗ-14 дополняется: повторный сигнал завершения во время выхода завершает процесс немедленно (файлы целы по ТЗ-18). Исключение к ТЗ-22: на пути выхода UI-поток ожидает писателя в пределах ОВ-4. Реализация — модуль жизненного цикла (У-3); способ перехвата (сабклассинг HWND / скрытое окно; метод делегата через рантайм Objective-C / winit `macos-quit-as-close`) — Часть 3; если на платформе способ не найден — ОВС с описанием потерь, подсказка параметра N их описывает. Основание (источники): winit не передаёт `WM_QUERYENDSESSION`/`WM_ENDSESSION` (https://github.com/rust-windowing/winit/issues/4360); Qt вызывает `aboutToQuit` синхронно в `WM_ENDSESSION`; правила Microsoft (https://learn.microsoft.com/en-us/windows/win32/shutdown/wm-queryendsession, https://learn.microsoft.com/en-us/windows/win32/shutdown/wm-endsession); приложение на Slint теряет настройки при Cmd+Q (https://github.com/qarmin/czkawka/issues/1942); winit PR `macos-quit-as-close` (https://github.com/rust-windowing/winit/pull/4692). Приёмка: Windows-ноутбук: изменить громкость и добавить трек, сразу «Завершение работы» → после загрузки оба изменения сохранены; macOS: то же через Cmd+Q и через «Завершить» в Dock; Linux: `kill -HUP` → файлы записаны; двойной `SIGTERM` при подменной задержке записи 10 с → процесс завершён сразу после второго сигнала, файлы — прежние целые версии.

**ОВ-7 → вариант пользователя: окно сообщений.** Каналы сообщений: (1) окно сообщения — оверлей поверх главного окна и диалога настроек; уровни Info / Warning / Error с разными значками и цветом заголовка; блокирует главное окно по механизму ТЗ-23 до закрытия; воспроизведение и трей работают; Enter — основная кнопка, Esc — закрыть; сообщения, возникшие до первого показа окна, показываются после него; несколько сообщений — очередью по одному; (2) системное уведомление — если главное окно скрыто в трей; окно сообщения показывается при открытии плеера; (3) журнал. Правило: окно — если данные пользователя под угрозой или его явное действие не выполнено; успешное действие, результат которого виден в интерфейсе, сообщения не порождает; остальное — журнал. Строка состояния каналом сообщений не является. Уровень Info в текущем объёме не используется.

Раскладка: ошибка записи `settings.toml`, `state.toml`, `playlist.m3u` → окно Error; ошибка записи файла экспорта и ошибка чтения файла «Загрузить плейлист» → окно Error; `playlist.m3u` повреждён или нечитаем при запуске (ОВ-8) → окно Warning/Error; повреждённый `settings.toml` (ТЗ-7) → окно Warning с путём копии `*.bad`; повреждённый `state.toml`, отдельные недопустимые и неизвестные ключи, ошибка записи на пути выхода → только журнал.

Ошибки записи рабочих файлов показываются в одном окне Error со списком файлов и причиной («нет места на диске», «нет доступа», «файловая система только для чтения», «ошибка ввода-вывода»; текст ОС и путь — в журнал); новая ошибка при открытом окне добавляет файл в список; кнопки «Повторить» и «OK». После первой неудачной записи файла запись этого файла по таймеру N прекращается. «Повторить» выполняет запись всех файлов списка сразу; записанные удаляются из списка, для них запись по таймеру возобновляется; окно закрывается, когда список пуст; при неудаче окно остаётся с обновлённой причиной. На пути выхода выполняется одна попытка записи каждого файла, у которого есть отличия (ОВ-2), независимо от прежних неудач (кроме случая 3 ОВ-8); её ошибка — только в журнал. Дедупликации нет. Ошибка явного действия пользователя (экспорт, «Загрузить плейлист») — отдельное окно на каждую неудачную попытку. По «Сохранить» при ошибке записи диалог закрывается, настройки действуют в памяти, повтор при выходе (ОВ-2). Системные уведомления — платформенный модуль (У-3).

Приёмка: автотест: «нет места» для `state.toml` → одно окно, за следующие 10 мин 0 попыток записи по таймеру; «Повторить» после освобождения места → запись выполнена, окно закрыто, следующее изменение записано по таймеру; без «Повторить» место освобождено → выход → `state.toml` записан; readonly-носитель, изменить громкость и добавить трек → через N с одно окно со списком `state.toml`, `playlist.m3u`; окно скрыто в трей → системное уведомление и окно при открытии плеера; повреждённый `settings.toml` → окно Warning с путём копии после первого показа главного окна. (Внесено как ТЗ-52; ТЗ-20.)

**ОВ-8 → вариант пользователя (три случая).** (1) `playlist.m3u` отсутствует — пустой плейлист в памяти, без сообщений; файл создаётся при первой обычной записи. (2) Файл прочитан, но повреждён (не валидный UTF-8 или содержит строку, которая не пустая, не комментарий `#…` и не абсолютный путь; путь к несуществующему файлу повреждением не считается) — частичного разбора нет: файл при запуске переименовывается в `playlist.m3u.bad` (одна копия, следующая заменяет предыдущую), плейлист пуст, окно Warning с путём копии; если переименовать не удалось — как (3). (3) Файл не читается (ошибка ввода-вывода, нет доступа) или его не удалось переименовать — файл не трогается, плейлист пуст, окно Error; `playlist.m3u` в этом сеансе не записывается ни по таймеру, ни при выходе; воспроизведение и работа с плейлистом в памяти доступны; при следующем запуске — новая попытка чтения. Приёмка: автотест: нет файла → пустой плейлист, 0 записей до первого изменения; файл с невалидным UTF-8 → `playlist.m3u.bad` побайтово равен исходному, `playlist.m3u` отсутствует до первой записи, окно Warning; ошибка чтения → добавить трек, выход → 0 записей `playlist.m3u`, исходный файл не изменён, одно окно Error. Ручной сценарий: каталог настроек на readonly-носителе → плеер запускается, плейлист читается и играет.

**ОВ-9 → б).** Системные диалоги выбора файлов (добавить файлы, добавить каталог, загрузить плейлист, сохранить плейлист, выбор файла темы) не блокируют цикл событий UI: пока диалог открыт, работают трей, отсчёт N и обновление ползунков. Главное окно на это время недоступно по механизму ТЗ-23; повторно открыть выбор файла нельзя. Выбор файла — платформенный модуль (У-3). Если на платформе неблокирующий вызов невозможен, там используется блокирующий, это фиксируется в протоколе приёмки. Приёмка: замер: открыт диалог «Добавить каталог» 30 с → максимальная итерация цикла событий UI ≤ 50 мс, громкость колёсиком трея меняется; ручной сценарий на Linux, Windows, macOS: при открытом выборе файла главное окно не реагирует на щелчки и клавиши, трей работает. (Внесено как ТЗ-53.) Уточнено В-1 (§11): трей — только Linux.

**ОВ-10 → б).** «Удалить текущий трек» и «Очистить плейлист» удаляются из диалога настроек и переносятся в меню главного окна, в котором находятся «Добавить файлы» и «Добавить папку»; выполняются сразу, без подтверждения, по общим правилам команд плейлиста (флаг «плейлист изменён», ТЗ-12; недоступность во время загрузки, ОВ-15). Кнопки очистки кэшей остаются в диалоге как мгновенные действия вне модели копии; на вкладке рядом с ними — постоянный текст: очистка выполняется сразу и не отменяется кнопкой «Отмена». Очистка выполняется вне UI-потока, после неё обновляется показанный размер кэша, сообщений нет. Приёмка: автотест: очистить кэш обложек, затем «Отмена» → кэш пуст, настройки без изменений, 0 записей `settings.toml`; «Очистить плейлист» из меню → плейлист пуст, флаг взведён, через N с одна запись `playlist.m3u`. Ручной сценарий: текст о неотменяемости виден на вкладке кэша без наведения.

**ОВ-11 → а), расширенный.** Нормализация колёсика — модуль платформенного ввода (У-3); пороги и знаки хранятся в модуле как таблица данных «платформа × тип устройства», не в коде. GNOME, KDE, Windows — по эксперименту `wheel_test.md`. macOS до эксперимента — по API платформы: тип устройства по признаку точных дельт, направление с учётом системной инверсии, инерционные события после окончания жеста игнорируются; порог тачпада — значение по умолчанию; пометка «не подтверждено экспериментом»; после эксперимента меняются только данные таблицы. Эксперимент записывает тип дельты, фазу жеста и признак инерции; записи используются как данные автотестов ТЗ-36. Для каждой пары «платформа × источник» (над ползунком, над треем) протокол приёмки фиксирует исход: подтверждено экспериментом / по документации платформы / правило по умолчанию (событие колеса мыши — один щелчок, пиксельные дельты накапливаются до порога, знак по системной настройке) / источника нет (не дефект; глобальный перехват мыши в объём не входит). Если слой Slint не передаёт тип дельты или фазу, модуль получает события ниже Slint — способ определяет Часть 3. Приёмка: автотест на записанных последовательностях GNOME, KDE, Windows; автотест macOS на синтетической последовательности «жест + инерция» → инерционные события не меняют громкость; протокол содержит исход для всех восьми пар. Уточнено В-2…В-5 (§11); признак инерции эксперимент не записывает (`wheel_test.md` §4.6).

**ОВ-12 → а).** Щелчки по заголовку колонки циклически переключают ключ: по возрастанию → по убыванию → без сортировки; щелчок по другой колонке начинает с «по возрастанию». Без сортировки видимый порядок равен исходному, стрелки нет. Снятие ключа меняет состояние (отсчёт N, ключ «нет» в `state.toml`), флаг «плейлист изменён» не взводит, воспроизведение не прерывает; следующий трек — по новому видимому порядку (при Shuffle — ТЗ-45). Если колонка ключа скрыта (решение 2), ключ снимается только после её показа; отдельного пункта меню нет. Приёмка: автотест: три щелчка по «Название» → ключ «↑», «↓», «нет»; после третьего видимый порядок равен исходному, 0 записей `playlist.m3u`, через N с `state.toml` с ключом «нет»; щелчок по «Году» при ключе «Название ↓» → «Год ↑».

**ОВ-13 → б), расширенный.** Текст сравнивается без учёта регистра, после приведения к одной форме Unicode; последовательности цифр внутри текста сравниваются как числа («No. 9» < «No. 10»). Год, номер трека и номер диска сравниваются как числа. Пустые значения — в конце при любом направлении. Вторичные ключи (всегда по возрастанию, независимо от направления главного): Исполнитель → год → альбом → диск → трек; Альбом → диск → трек; Год → альбом → диск → трек; остальные колонки — без вторичных ключей. При полном равенстве — исходный порядок (стабильная сортировка). Колонка «Сейчас играет» не сортируется: щелчок ничего не делает, стрелки нет. Приёмка: автотест на наборе с регистром «beatles»/«Zappa», годами «999»/«2001», дисками 1/2 одного альбома, названиями «No. 9»/«No. 10», одним названием в двух формах Unicode и пустым годом → ожидаемый порядок для каждой колонки в обоих направлениях.

**ОВ-14 → б).** В задаче 02 реализуется только операция ручного изменения порядка в модели (ТЗ-44) с автотестами. Интерфейс (перетаскивание мышью, клавиатура) — отдельная задача; он будет вызывать ту же операцию. Приёмка ТЗ-44 — автотест `drag_reorder_clears_sort_key` на операции модели.

**ОВ-15 → а), для стартовой загрузки и «Загрузить плейлист».** Пока идёт загрузка, недоступны: «Добавить файлы», «Добавить папку», «Загрузить плейлист», «Удалить текущий трек», «Очистить плейлист», «Сохранить плейлист», сортировка по заголовку и перенос файлов в окно; подсказка «Идёт загрузка плейлиста». Во время «Загрузить плейлист» прежний трек играет; пауза, стоп, перемотка, громкость и mute работают; «Далее» и «Назад» недоступны; по окончании загрузки новый плейлист начинает воспроизводиться независимо от состояния, в том числе если во время загрузки нажат «Стоп» (Play Now, ОВ-5). Выход до окончания «Загрузить плейлист» — рабочий плейлист и `playlist.m3u` прежние, флаг не меняется. Приёмка: автотест: подменная загрузка задерживается → каждая перечисленная команда не меняет плейлист и недоступна; после окончания — доступна; «Загрузить плейлист», «Стоп» во время загрузки → после загрузки воспроизводится первый трек нового плейлиста; выход во время «Загрузить плейлист» → 0 записей `playlist.m3u`.

**Уточнение к ОВ-15 (ответ пользователя на вопрос после внесения решений).** До окончания «Загрузить плейлист» рабочим остаётся прежний плейлист; флаг «плейлист изменён», взведённый до команды, продолжает действовать. Прежний плейлист записывается по обычным правилам: при выходе (ТЗ-14) и по истечении отсчёта N во время загрузки (ТЗ-11/ТЗ-12). Загружаемый список не пишется, пока загрузка не завершена. Фразу ОВ-15 «рабочий плейлист и `playlist.m3u` прежние» понимать как «не заменяются загружаемым списком». Приёмка (ТЗ-17): флаг взведён до команды → выход во время загрузки → `playlist.m3u` записан прежним рабочим плейлистом, одна запись; флаг не взведён → 0 записей; флаг взведён, отсчёт N истекает во время загрузки → одна запись прежнего плейлиста.

**ОВ-16 → закрыт решением по ОВ-7.** Повреждённый `settings.toml` — окно Warning, остаётся до закрытия пользователем; отдельная длительность показа не нужна.

**ОВ-17 → б).** В файл экспорта «Сохранить плейлист» записывается видимый порядок таблицы на момент экспорта; перестановка Shuffle не учитывается. Формат: UTF-8, `#EXTM3U`, `#EXTINF` (длительность, «Исполнитель — Название»), абсолютные пути; расширение по умолчанию `.m3u8`. Формат рабочего `playlist.m3u` не меняется. Приёмка: автотест: ключ «Название ↑», Shuffle включён → экспорт → пути в файле в порядке видимой таблицы, у каждого `#EXTINF`; `playlist.m3u` — 0 записей, флаг не изменился.

Решения пользователя по вопросам В-1…В-5 (`wheel_test.md`) — §7.4 (вопросы, варианты) и §8 (решения) `wheel_test.md`; данные — там же, §3–§6. Где применены — §3 (строка «В-1…В-5»).

**В-1 → трей на Windows и macOS — не в объёме задачи 02.** У плеера трей есть только на Linux (`ksni`). Трей на Windows и macOS — отдельная будущая задача. В задаче 02: для пар «Windows × над треем» и «macOS × над треем» исход ТЗ-36 — «источника нет»; правила и ручные сценарии, где участвует трей (колёсико над иконкой, команды трея, «Выход» в трее, сворачивание в трей, системное уведомление при окне, скрытом в трей), действуют и проверяются только на платформах, где у плеера есть трей (сейчас Linux). На Windows и macOS окно в трей не сворачивается; окно сообщения показывается обычным образом.

**В-2 → события winit через `on_winit_window_event`.** Модуль ввода получает события колёсика окна через `slint::winit_030::WinitWindowAccessor::on_winit_window_event` (feature `unstable-winit-030`): тип дельты (`LineDelta`/`PixelDelta`) и фазу жеста. Принадлежность события ползунку громкости определяется событием Slint `scroll-event`: событие winit сопоставляется с ним по значению (×60 для строк) и времени. Без сопоставленного события winit применяется правило по умолчанию на значениях Slint. Нестабильный API изолирован в модуле ввода (ТЗ-54); обновление Slint требует проверки модуля автотестами на записанных последовательностях. (Архитектурное решение для Части 3, ADR обязателен.)

**В-3 → класс устройства — по тому, что сообщает ОС.** Класс события (колесо / тачпад) определяется по тому, что сообщает ОС через winit (тип дельты, дробность значений, фаза). Устройство, которое ОС отдаёт как колесо, обрабатывается как колесо: одно деление — один щелчок, без ограничения скорости, даже если физически это тачпад, эмулирующий колесо. Требование ТЗ-36 «одно движение тачпада не даёт десятков шагов» проверяется на событиях класса «тачпад». Приёмка: записанные последовательности «тачпада» KDE-3 и GNOME-2 обрабатываются как колесо; быстрая прокрутка мышью 10–12 щелчков даёт 10–12 шагов.

**В-4 → тачпад Windows: T = 0,5 строки, K = 5.** Класс «тачпад» на Windows: порог одного шага T = 0,5 строки (60 ед. `WHEEL_DELTA`), накопление со знаком с переносом остатка, не более K = 5 шагов на свайп; граница свайпа — пауза больше 300 мс, после неё остаток сбрасывается. Инерция отдельно не отбрасывается — её ограничивает K. Значения T, K и паузы — данные таблицы модуля ввода (ТЗ-36). Приёмка: записанные свайпы Windows дают: короткий — 1–4 шага, длинный и быстрый — 5; выбросы ≈ 67 строк не дают больше 5 шагов на свайп.

**В-5 → знак трея по хосту.** Для источника «трей» ключ таблицы модуля ввода — хост StatusNotifierItem; знак и единица деления — данные таблицы: KDE Plasma — «вверх» = +, деление 120; GNOME с AppIndicator — «вверх» = −, деление 1. Хост определяется по процессу-владельцу службы `org.kde.StatusNotifierWatcher` на D-Bus (способ подтверждается в Части 3); запасной путь — `XDG_CURRENT_DESKTOP`. Неизвестный хост — знак как у KDE, деление — по величине первого события; исход «правило по умолчанию». Приёмка: записанные последовательности трея KDE-1…3 и GNOME-1, 2 дают одинаковое число шагов того же направления, что и ползунок; текущая инверсия трея на KDE устранена.

**Шаг громкости — подтверждение решения 3.** Шаг 2 % за щелчок одинаков для всех источников, включая трей; отдельного коэффициента для трея нет (решение 3 и НФ-2 без изменений). Различие 0,04 / 0,02 в текущем коде (ревью §3.4) — дефект, а не свойство источника.
