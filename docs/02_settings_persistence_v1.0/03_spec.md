### ADR-1. Владелец и единственный писатель рабочих файлов

**Выполняет:** ТЗ-1, ТЗ-3, ТЗ-22 (запись вне UI-потока), ТЗ-28; НФ-5. Решения 1, 5; ОВС-14 (01_audio_modes).

**Контекст.** Сейчас у `settings.toml` один писатель (`SettingsStore::save`, `src/settings.rs:1142-1148`), но его вызывают семь мест UI-потока синхронно (ревью §4.1: W1–W7), включая запуск (`src/settings.rs:1136-1139`). `playlist.m3u` пишет `save_playlist` в UI-потоке при выходе (`src/app/mod.rs:1575-1577`, `:1727-1729`). ТЗ-3: записи одного файла не перекрываются; каждая — файл целиком из снимка памяти на момент запроса; ни одна часть приложения не пишет отдельный раздел. ТЗ-22: запись — не в UI-потоке. ОВС-14 и ADR-22 (01_audio_modes): движок `settings.toml` и `state.toml` не читает и не пишет.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Синхронная запись в UI-потоке через один объект хранилища (как сейчас, но атомарно) | Нарушает ТЗ-22: `fsync` на медленном носителе останавливает цикл событий на секунды |
| Б | Отдельный поток на каждую запись (`thread::spawn`) | Две записи одного файла могут перекрыться, итог зависит от планировщика — нарушает ТЗ-3 |
| В | Писать из потока движка `apap-engine` | Противоречит ОВС-14 (01_audio_modes) и решению 4 |
| Г | Выделенный поток-писатель, единственный владелец модуля файловой системы для этих файлов; UI отправляет команды с готовыми байтами снимка; у каждого файла один слот ожидающей записи | Записи одного файла последовательны по построению; UI не ждёт диска; проверяется на подменной ФС |

**Критерии:** ТЗ-3 (последовательность и итог = последний снимок); ТЗ-22; ТЗ-14 (выход ждёт писателя не дольше 5 с); ТЗ-50 (тот же писатель работает с `MemStore`, ADR-19).

**Выбор: Г.**

- Поток `apap-persist` — единственный, кто записывает `settings.toml`, `state.toml`, `playlist.m3u`, их копии `*.bad`, переименовывает повреждённый `playlist.m3u` (ТЗ-21, ADR-5) и пишет файл экспорта (ТЗ-13, ADR-17). Доступ к диску — только через модуль файловой системы (ADR-6).
- **Снимок делается в UI-потоке в момент запроса.** `settings.toml` и `state.toml` сериализуются в UI-потоке в детерминированный текст (ADR-2): этот же текст нужен для сравнения с эталоном (ADR-3). `playlist.m3u` — текст из путей исходного порядка в текущем формате (по одному абсолютному пути в строке, `src/playlist.rs:225-240`; ТЗ-13 а: формат не меняется). Экспорт — текст расширенного M3U (ADR-17). Писатель получает только байты и не обращается к памяти UI.
- **Команды писателю:** запись рабочего файла (файл, байты, порядковый номер снимка); экспорт (путь, байты, номер попытки); переименование повреждённого плейлиста; копия `*.bad`; запись на пути выхода с общим сроком. **Ответы:** «записано / ошибка» с номером снимка и классом ошибки (ADR-4) — в канал, который UI разбирает на тике (ADR-20), а на пути выхода ждёт напрямую (ADR-7).
- **Слот ожидающей записи.** Для каждого рабочего файла у писателя не больше одной ожидающей команды: команда, пришедшая, пока файл пишется, заменяет ожидающую, но не прерывает текущую запись. Поэтому записи одного файла идут строго одна за другой, а последней записывается последний запрошенный снимок. Разные файлы пишутся в одном потоке в порядке поступления команд; порядок на пути выхода задаёт ADR-7.
- Эталонный текст, флаг «плейлист изменён» и признак «запись остановлена ошибкой» хранит UI (ADR-3): только UI знает, совпадает ли записанный снимок с текущими значениями.

**Последствия.**

- `SettingsStore::save` и все его вызовы (W1–W7) удаляются; `MusicApp` не обращается к файлам настроек, состояния и плейлиста напрямую.
- Стоимость снимка в UI-потоке — сериализация TOML нескольких килобайт и текст плейлиста (для 5 000 путей — сотни килобайт); оценка времени — замер ТЗ-22 (ADR-20). Если замер покажет превышение бюджета, сериализация плейлиста переносится в писатель с передачей `Arc`-снимка путей; решение принимается по замеру этапа (заход 3).
- Движок по-прежнему пишет только `bp_tests.toml` и `track_marks.toml` (ADR-19 (01_audio_modes)); единый модуль ФС для них — ADR-19.

**Что проверяет выбор.** Автотест ТЗ-3: подменная задержка записи; истечение N во время записи по «Сохранить» и запрос выхода во время отложенной записи → записи каждого файла последовательны, итог равен последнему снимку. Ревью кода: вызовы записи рабочих файлов — только в модуле писателя.

### ADR-2. Разделение `settings.toml` и `state.toml`, DTO, разбор по ключам, `*.bad`

**Выполняет:** ТЗ-2, ТЗ-4, ТЗ-5, ТЗ-6, ТЗ-7 (журнал), ТЗ-8, ТЗ-9; НФ-3, НФ-7. Решения 1, 9, 11; Т-1, Т-2; ОВ-1, ОВ-2; ОВС-15 (01_audio_modes).

**Контекст.**

- Сейчас одна структура `Settings` (`src/settings.rs:729-818`) хранит и настройки, и состояние. Разбор — весь документ или ничего (`toml::from_str(..).unwrap_or_default()`, `:1109`, R-2); у части полей `#[serde(default)]` даёт ноль вместо документированного значения (R-10).
- `columns` и `info_labels` — `HashMap` (`src/settings.rs:751`, `:808`). `toml` сериализует таблицу в порядке обхода отображения, а порядок обхода `std::collections::HashMap` зависит от случайного зерна процесса. Поэтому текст одного и того же значения в двух запусках разный, и сравнение с эталонным текстом (ОВ-2) давало бы отличие при каждом выходе. Порядок обхода `HashMap` — свойство std (документация `std::collections::HashMap`: «iterates in arbitrary order», `RandomState`); проверка поведения `toml` 1.1.4 по исходнику — заход 2.
- 01_audio_modes задаёт `PlaybackDto` и чистую функцию `load_mode_settings(Option<PlaybackDto>)` для раздела `[playback]` (§2.2, §6.27 (01_audio_modes)) и тип `PlaybackState` (§2.2 (01_audio_modes)); файловое представление `PlaybackState` и чтение файлов — задача 02.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Одна `serde`-структура на файл с `#[serde(default = "…")]` у каждого поля (предложение R-10) | Значение неверного типа у одного ключа ломает разбор всего документа — нарушает ТЗ-5; заметки по ключам не получить |
| Б | DTO с полями `Option<toml::Value>` и `#[serde(flatten)] unknown` (как `PlaybackDto` (01_audio_modes)), затем преобразование по полям | Работает, но вложенный типизированный `PlaybackDto` снова делает ошибку типа внутри `[playback]` ошибкой всего файла |
| В | Двухступенчатый разбор: текст → `toml::Table` (ошибка только при синтаксической ошибке TOML = «неразбираемый файл»); затем извлечение каждого ключа по таблице описаний ключей с проверкой и заметкой; раздел `[playback]` — отдельно в `PlaybackDto` (ошибка → заметка и `load_mode_settings` по п. 2 §6.27 (01_audio_modes)) | Ошибка одного ключа влияет только на этот ключ; заметки собираются естественно; `PlaybackDto` (01) используется как есть |

**Критерии:** ТЗ-5 (ключ за ключом, одна сводная запись журнала на файл); ТЗ-6 (неразбираемый = синтаксис); ТЗ-8 (документированные значения); ОВ-2 (детерминированный текст); переиспользование типов 01 без изменений.

**Выбор: В.**

- **Распределение.** `settings.toml` — `SettingsFile`: настройки окна настроек (тема, видимость и порядок колонок, параметры визуализации кроме типа, обложки, кэш, сворачивание в трей, прокрутка к текущему треку, размеры верхней панели, подписи `info_labels`, N) и раздел `[playback]` с `ModeSettings` (01_audio_modes). `state.toml` — `StateFile`: `PlaybackState` (01_audio_modes: активный режим, громкость и mute по режимам), ширины колонок, ключ сортировки, тип визуализации, Repeat, Shuffle, геометрия окна, последний каталог (ТЗ-2, Т-1, Т-2). Перечни ключей и значения по умолчанию — модель данных (§2, заход 2); источник значений по умолчанию — ТЗ-8 и текущие ненулевые значения `impl Default for Settings` (`src/settings.rs:820-853`).
- **Разбор.** `toml::Table` → извлечение по таблице описаний ключей (`KeySpec`: имя, тип, допустимое множество, значение по умолчанию). Отсутствующий ключ или недопустимое значение → значение по умолчанию и `LoadNote`; неизвестный ключ → `LoadNote`, в памяти не хранится и при следующей записи в файл не попадает (ТЗ-5). Все заметки файла — одна запись журнала (ADR-21). Ключи прежнего `settings.toml`, ставшие состоянием, — неизвестные ключи (ТЗ-9, ОВ-1 а). Миграция колонок старого формата (`migrate_legacy_columns`, `src/settings.rs:1153-1190`) удаляется: её ключи (`column_widths`, `column_visibility`) — тоже неизвестные (ОВ-1 а: миграции нет).
- **Сериализация** — только из DTO `SettingsFile` / `StateFile` с фиксированным порядком полей структуры и `BTreeMap` вместо `HashMap`. Одинаковые значения дают одинаковый текст в любом процессе (ОВ-2).
- **Неразбираемый файл** (ТЗ-6). Значения по умолчанию в памяти, эталонный текст пуст (ОВ-2), исходные байты сохраняются в памяти и передаются писателю при его запуске. Писатель сразу записывает их атомарно в `settings.toml.bad` / `state.toml.bad`, заменяя прежнюю копию (НФ-7). Копия появляется раньше первой записи самого файла (ТЗ-6, §5.1 ТЗ). Это не запись `settings.toml`/`state.toml`, поэтому ТЗ-4 и НФ-5 («0 записей при запуске») не нарушены. Путь в окне Warning (ТЗ-7) указывает на уже существующую копию. Если копия не записана, причина идёт в журнал, а в окне Warning путь копии заменяется сообщением «копию сохранить не удалось» (текст — §2, заход 2).
- **Загрузка не пишет** (ТЗ-4): разбор — чистые функции без ввода-вывода; коррекции попадают в файл только при следующей записи, необходимость которой определяет сравнение с эталоном (ADR-3).

**Последствия.**

- `SettingsStore` заменяется парой «действующие настройки + действующее состояние» в UI-потоке (ТЗ-1) и чистыми функциями разбора и сериализации.
- Для `[playback]` до этапа С4 (01_audio_modes), где появляются `ModeSettings` и `PlaybackState`, раздел хранит прежние аудио-поля; сведение — §8 (заход 3).

**Что проверяет выбор.** Автотесты ТЗ-5 (один недопустимый, один отсутствующий, один неизвестный ключ → три значения по умолчанию, одна сводная запись журнала, после выхода неизвестного ключа нет), ТЗ-6, ТЗ-8, ТЗ-9; тест детерминизма: два DTO с одинаковыми значениями, построенные из отображений с разным порядком вставки, дают одинаковый текст; круговой тест «значения → текст → значения» для обоих файлов.

### ADR-3. Моменты записи: эталонный текст, отсчёт N, флаг плейлиста, остановка после ошибки

**Выполняет:** ТЗ-10, ТЗ-11, ТЗ-12, ТЗ-20 (остановка и «Повторить»), ТЗ-33 (смена N), ТЗ-38; НФ-1, НФ-5. Решения 1, 5; У-1; ОВ-2, ОВ-3, ОВ-7.

**Контекст.** Сейчас запись идёт сразу по событию (ревью R-5), геометрия — throttle 2 с (`src/app/ui_manager.rs:73-107`), ширины колонок — дебаунс тиков (`src/app/mod.rs:1617-1630`). У-1 задаёт отсчёт от первого незаписанного изменения без перезапуска; ОВ-2 — запись только при отличии сериализации от эталона; ОВ-3 — программные изменения отсчёт не запускают; ОВ-7 — после ошибки запись файла по отсчёту прекращается до успешного «Повторить».

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Дебаунс: каждое изменение переносит срок | Отвергнуто У-1: непрерывная серия никогда не записывается |
| Б | Признаки «изменено» по полям вместо сравнения текста | Отвергнуто ОВ-2: «изменить и вернуть» давало бы запись |
| В | Срок от первого незаписанного изменения; при истечении — сравнение сериализации с эталоном; срок проверяется на существующем тике 100 мс по инжектируемым часам | Выполняет У-1, ОВ-2; тестируется подменными часами без таймеров Slint |
| Г | Как В, но срок — однократный `slint::Timer` | Тест требует цикла событий Slint; смена N требует перезапуска таймера; выигрыш — точность до 100 мс, требованиями не нужен |

**Критерии:** У-1 и приёмка ТЗ-11 на подменных часах; ОВ-2; ОВ-3; ТЗ-20; тестируемость без Slint (ADR-19).

**Выбор: В.**

- `PersistTracker` (UI-поток) хранит: для `settings.toml` и `state.toml` — эталонный текст и признак «запись остановлена ошибкой»; для `playlist.m3u` — флаг «плейлист изменён» с номером изменения, признак остановки ошибкой и запрет записи на сеанс (случай 3 ОВ-8, ADR-5); общий срок отложенной записи `Option<ClockInstant>`.
- **Часы** — трейт `Clock` и `ClockInstant` из ADR-20 (01_audio_modes); в тестах — `ManualClock` оттуда же.
- **Запуск отсчёта.** Изменение состояния сессии с источником `Origin::User` (ADR-22) или взведение флага плейлиста при отсутствующем сроке ставит срок `now + N`. Последующие изменения срок не сдвигают. Изменение с `Origin::Program` меняет только память.
- **Истечение** проверяется на тике 100 мс (`TICK_INTERVAL_MS`, `src/main.rs:12`): срок снимается. `state.toml` записывается, если сериализация отличается от эталона и запись не остановлена ошибкой. `playlist.m3u` записывается, если флаг взведён, запись не запрещена и не остановлена. Задержка записи после срока — не больше одного тика.
- **Порядок в один момент.** Истечение срока обрабатывается раньше изменений, пришедших в тот же тик. Изменение, пришедшее после снятия срока, ставит новый срок. Так приёмка ТЗ-11 «изменения каждые 5 с с t = 0 → записи в t = 30, 60, …» выполняется точно. В общем случае промежуток между записями непрерывной серии не больше N плюс интервал между изменениями; граница потерь НФ-6 (N от первого незаписанного изменения) выполняется всегда. Это толкование приёмки, а не изменение требования.
- **После ответа писателя.** Успех: эталон := записанный текст; флаг плейлиста снимается, только если после снимка не было новых изменений (сравнение номеров). Ошибка: признак остановки для файла, сообщение (ADR-13); эталон и флаг не меняются (ТЗ-20).
- **«Повторить»** немедленно отправляет снимки всех файлов списка, независимо от срока. Успех снимает остановку файла (ТЗ-20).
- **Смена N** по «Сохранить»: если срок идёт — `min(срок, now + N_new)` (У-1).
- **`settings.toml`** пишется по «Сохранить» с отличиями (ADR-11) и на пути выхода при отличии от эталона (ADR-7). Отсчёт N к нему не относится (ТЗ-10).

**Последствия.** Throttle геометрии, дебаунс-запись ширин колонок и все прочие немедленные записи удаляются (§9 ревью). Значения в памяти меняются сразу; на диск они попадают по правилам этого ADR.

**Что проверяет выбор.** Автотесты ТЗ-11 с `ManualClock` (`state_written_after_n_seconds_once`, серия 10 мин, смена N с 120 на 10 с, «изменить и вернуть» → 0 записей), ТЗ-12 (`playlist_dirty_written_by_timer`, `sort_change_does_not_write_playlist`, ошибка → 0 попыток за 10 мин), ТЗ-20, ТЗ-38.

### ADR-4. Атомарная и долговечная запись на Linux, Windows, macOS

**Выполняет:** ТЗ-18, ТЗ-19, ТЗ-20 (классы ошибок). Решение 1; R-1, R-20.

**Контекст.** Сейчас `settings.toml` пишется `fs::write` поверх файла, ошибки отбрасываются (`src/settings.rs:1142-1148`, R-1); `playlist.m3u` — через временный файл и `rename`, но без `fsync` (`src/playlist.rs:225-240`). Без `fsync` каталога на ext4 после пропадания питания возможен пустой файл (ревью §6, https://lwn.net/Articles/322823/). ТЗ-19 задаёт для Linux «`fsync` временного файла до `rename` и `fsync` каталога после», для Windows и macOS — аналогичные гарантии, определённые здесь.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | `tempfile::NamedTempFile::persist` | Не синхронизирует данные (ревью §6); `tempfile` в рантайм-зависимостях плеера нет |
| Б | Крейт `atomicwrites` (`sync_all` + `rename` + `sync_all` каталога; `MOVEFILE_WRITE_THROUGH` на Windows — ревью §6) | Новая зависимость; классификация ошибок всё равно своя |
| В | `std::fs::rename` + `File::sync_all` | Какой системный вызов использует `std::fs::rename` на Windows в rustc 1.98.1 — не подтверждено: исходники std (`rust-src`) на машине не установлены, а документация std оговаривает, что реализация может меняться. Гарантия `MOVEFILE_WRITE_THROUGH` не задана |
| Г | Собственная последовательность в модуле ФС с явными системными вызовами для каждой ОС | Гарантии не зависят от версии std; новых крейтов нет (`libc`, `windows-sys` уже в `Cargo.lock`) |

**Критерии:** атомарность при сбое на любом шаге (ТЗ-18); долговечность до сообщения об успехе (ТЗ-19); классы ошибок ТЗ-20; без новых крейтов.

**Выбор: Г.** Временный файл — в каталоге целевого файла, с фиксированным именем `<имя>.tmp` (например, `settings.toml.tmp`), открывается с усечением. Писатель один (ADR-1), поэтому одновременно временных файлов одного целевого файла не бывает. Временный файл, оставшийся после сбоя, читатели не открывают (другое имя), а следующая запись его перезаписывает (ТЗ-18).

| Шаг | Linux | macOS | Windows |
|---|---|---|---|
| 1. Каталог | `create_dir_all` | то же | то же |
| 2. Данные | открыть `<имя>.tmp` (`O_CREAT \| O_TRUNC \| O_WRONLY`), `write_all` | то же | то же (`CreateFileW` через `std::fs::File`) |
| 3. Сброс файла | `fsync(fd)` (`File::sync_all`) | `fcntl(fd, F_FULLFSYNC)`; если вызов возвращает ошибку (ФС не поддерживает) — `fsync(fd)` | `FlushFileBuffers` (`File::sync_all`) |
| 4. Замена | `rename(tmp, target)` | `rename(tmp, target)` | `MoveFileExW(tmp, target, MOVEFILE_REPLACE_EXISTING \| MOVEFILE_WRITE_THROUGH)` |
| 5. Сброс каталога | `open(dir, O_RDONLY \| O_DIRECTORY)` + `fsync` | `open(dir, O_RDONLY)` + `fcntl(F_FULLFSYNC)`, при ошибке — `fsync` | нет отдельного шага: `MOVEFILE_WRITE_THROUGH` возвращает управление после фактического перемещения на диске |
| 6. Успех | только после шага 5 | то же | после шага 4 |

Источники: Linux — `rename(2)` атомарен (https://man7.org/linux/man-pages/man2/rename.2.html), `fsync(2)` о каталоге (https://man7.org/linux/man-pages/man2/fsync.2.html); macOS — `fsync(2)` не сбрасывает кэш накопителя, это делает `F_FULLFSYNC` (https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html); Windows — `MoveFileExW`, флаг `MOVEFILE_WRITE_THROUGH`: «The function does not return until the file is actually moved on the disk» (https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw). `ReplaceFileW` отвергнут: при ошибке `ERROR_UNABLE_TO_MOVE_REPLACEMENT` файлы могут остаться под другими именами (https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew). `F_FULLFSYNC` на дескрипторе каталога macOS — **не подтверждено** (отсюда запасной `fsync`); проверка на macOS — ревью кода и ручной сценарий (ТЗ-19).

**Ошибки.** Любая ошибка шагов 1–5 → временный файл удаляется (ошибка удаления — только в журнал), целевой файл не тронут (до шага 4 он не менялся; шаг 4 атомарен). Класс ошибки (ТЗ-20) — по `io::ErrorKind` и коду ОС:

| Класс (текст окна) | `io::ErrorKind` | Linux / macOS | Windows |
|---|---|---|---|
| «нет места на диске» | `StorageFull`, `QuotaExceeded` | `ENOSPC`, `EDQUOT` | `ERROR_DISK_FULL`, `ERROR_HANDLE_DISK_FULL` |
| «нет доступа» | `PermissionDenied` | `EACCES`, `EPERM` | `ERROR_ACCESS_DENIED`, `ERROR_SHARING_VIOLATION`, `ERROR_LOCK_VIOLATION` |
| «файловая система только для чтения» | `ReadOnlyFilesystem` | `EROFS` | `ERROR_WRITE_PROTECT` |
| «ошибка ввода-вывода» | всё остальное, включая ошибку сериализации | — | — |

Варианты `io::ErrorKind::StorageFull`, `QuotaExceeded`, `ReadOnlyFilesystem` есть в стабильном std (стабилизированы в Rust 1.83 по release notes; по исходнику std не проверено). Поэтому классификация сначала смотрит на код ОС (`raw_os_error`), затем на `ErrorKind`. Журнал получает вид ошибки, текст ОС и путь (ТЗ-20).

**Последствия.** Модуль ФС (ADR-6) — единственное место с `cfg(target_os)` для записи. Тот же путь используется для экспорта (ТЗ-18), копий `*.bad` и, по ADR-19, для хранилища движка (`bp_tests.toml`, `track_marks.toml`). Права нового файла — по умолчанию ОС (как сейчас у `fs::write`).

**Что проверяет выбор.** Автотест ТЗ-18: подменная ФС прерывает последовательность на каждом шаге → файл равен прежней или новой версии, оставшийся `*.tmp` не читается и не мешает следующему запуску. Ручной сценарий ТЗ-19 (Linux): `strace -f -e trace=fsync,fdatasync,rename,renameat2` → `fsync` tmp, `rename`, `fsync` каталога. Windows, macOS — ревью кода против таблицы.

### ADR-5. Чтение `playlist.m3u`: три случая ОВ-8

**Выполняет:** ТЗ-21, ТЗ-12 (запрет записи), ТЗ-4 (исключение — переименование). ОВ-8.

**Контекст.** Сейчас `load_track_list` в фоновом потоке (`src/app/mod.rs:373-378`) молча отбрасывает строки, которые не являются абсолютным путём к поддерживаемому файлу (`src/playlist.rs:218-221`), и не различает ошибку чтения; после первого изменения файл перезаписывается (ОВ-8, контекст). ОВ-8 задаёт три случая, частичного разбора нет, переименование в `playlist.m3u.bad` — при запуске.

**Варианты.** А — загрузчик сам переименовывает файл; Б — загрузчик классифицирует, переименование выполняет писатель (ADR-1).

**Критерии:** единственный писатель (ТЗ-3: переименование меняет `playlist.m3u`); чтение вне UI-потока (ТЗ-22, ТЗ-47).

**Выбор: Б.**

- Поток стартовой загрузки (ADR-16) читает байты через модуль ФС и классифицирует:
  - «не найден» → случай 1: пустой плейлист, сообщений нет;
  - другая ошибка чтения → случай 3;
  - байты прочитаны → проверка: валидный UTF-8; каждая строка пустая, комментарий `#…` или абсолютный путь (`Path::is_absolute` платформы). Существование файла по пути не проверяется (ОВ-8). Разделитель строк — `\n`, завершающий `\r` отбрасывается, ведущий BOM UTF-8 игнорируется: это допуски чтения, не новый формат. Нарушение → случай 2.
- Случай 2: загрузчик отдаёт UI результат «повреждён», UI отправляет писателю команду «переименовать `playlist.m3u` → `playlist.m3u.bad` с заменой» (Linux, macOS — `rename`; Windows — `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`; затем сброс каталога, как в ADR-4). Успех → окно Warning с путём копии. Ошибка → случай 3.
- Случай 3: файл не трогается; окно Error; в `PersistTracker` взводится запрет записи `playlist.m3u` на сеанс — ни по отсчёту, ни при выходе (ТЗ-12, ТЗ-14). Плейлист в памяти работает.

**Последствия.** Сообщения о случаях 2 и 3 возникают до первого показа окна или сразу после него и ждут первого показа (ADR-13, ADR-23).

**Что проверяет выбор.** Автотесты ТЗ-21 (три случая на `MemStore`: отсутствует, невалидный UTF-8, ошибка чтения; ошибка переименования → случай 3; «добавить трек, выход» в случае 3 → 0 записей `playlist.m3u`).

### ADR-6. Платформенные модули: граница, трейты, подмены, место `cfg(target_os)`

**Выполняет:** ТЗ-54; основа ТЗ-49, ТЗ-50. У-3; В-1.

**Контекст.** У-3 требует пять модулей (жизненный цикл, файловая система, ввод, системные уведомления, выбор файлов) с единым интерфейсом и подменой; вне них `cfg(target_os)` для этих задач запрещён. Сейчас `cfg(target_os` в `src/` нет (`wheel_test.md` §2), трей `ksni` — безусловная зависимость, а трей нужен только на Linux (В-1). Трей участвует сразу в трёх модулях: причина выхода «Выход» в трее, колёсико над иконкой, уведомление при окне в трее.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Один трейт `Platform` со всеми методами | Нарушает разделение интерфейсов; подмена одного аспекта требует реализации всех |
| Б | Пять трейтов, реализации выбираются `cfg` внутри модуля, подмены — отдельные структуры; трей — внутренний подмодуль платформенного слоя, которым пользуются жизненный цикл, ввод и уведомления | Совпадает с У-3; `cfg` сосредоточен в `src/platform/**` |
| В | Как Б, но трей — шестой публичный модуль | ТЗ-54 называет пять модулей; трей не нужен коду приложения напрямую |

**Критерии:** ТЗ-54 (поиск `cfg(target_os` вне модулей ничего не находит); автотесты на любой ОС; В-1.

**Выбор: Б.**

- Каталог `src/platform/` в библиотеке `music_player_rs`: `lifecycle`, `fs`, `input`, `notify`, `pick` и внутренний `tray` (только `cfg(target_os = "linux")`, `ksni`).
- В каждом модуле: трейт и платформенно-независимые типы — в `mod.rs` без `cfg`; реализации — в файлах по ОС, выбор — `cfg(target_os)` только здесь; подмена — `fake.rs`.
- Подмены компилируются всегда (не под `#[cfg(test)]`): тесты бинарника (`src/app/*`) собирают библиотеку без `cfg(test)` и иначе их не увидят. Это небольшие структуры без зависимостей.
- Платформенно-независимые части модуля ввода — нормализатор колёсика и таблица данных (ADR-8) — чистый код без `cfg`. Он тестируется на записанных последовательностях на любой ОС.
- `PlatformCaps { tray, notifications }` возвращает реализация во время работы; код приложения проверяет возможность, а не ОС (например, сворачивание в трей доступно, только если `tray`).
- Зависимости по ОС объявляются таблицами `[target.'cfg(…)'.dependencies]` в `Cargo.toml`: `ksni`, `zbus` — Linux; `windows-sys` — Windows; `objc2`, `objc2-app-kit`, `objc2-foundation` — macOS. Это не `#[cfg]` в коде.
- Реализации внедряются в приложение как объекты трейтов через `AppDeps` (ADR-19); композиция реальных реализаций — только в `main.rs`.

**Последствия.** `src/tray.rs` переезжает в `src/platform/tray/`; команды трея доходят до приложения через модули жизненного цикла (выход, показать/скрыть) и ввода (колёсико), остальные — общим каналом команд трея. На Windows и macOS трей не создаётся (В-1). Перечень трейтов и сигнатуры — §2 (заход 2).

**Что проверяет выбор.** Ревью кода: `cfg(target_os` встречается только в `src/platform/**` (проверка — `grep -rn 'cfg(target_os' src | grep -v '^src/platform/'` пуст); автотесты ТЗ-14, ТЗ-15, ТЗ-18, ТЗ-20, ТЗ-36, ТЗ-52, ТЗ-53 используют подмены и проходят на любой ОС.

### ADR-7. Жизненный цикл и путь выхода

**Выполняет:** ТЗ-14, ТЗ-15, ТЗ-32, ТЗ-22 (исключение: ожидание писателя на пути выхода), ТЗ-52 п. 1 (выход при открытом окне сообщения); НФ-9. Решения 1, 7; ОВ-4, ОВ-6; В-1; ТЗ-136, §6.28 (01_audio_modes).

**Контекст.**

- Сейчас выход — два места (`close_requested`, `src/app/mod.rs:1566-1584`; «Выход» в трее, `:1725-1735`), сигналов нет (R-4), `panic = "abort"` (`Cargo.toml`, `[profile.release]`).
- 01_audio_modes: UI шлёт `EngineCmd::Shutdown`, ждёт `ShutdownComplete` до 2 с; запись файлов настроек не зависит от этого ответа (ОВС-16, §6.28 п. 2а (01_audio_modes)). Сигналы там предложено обрабатывать задачей `tokio::signal` в рантайме трея (§6.28 (01_audio_modes)).
- winit 0.30.13 не обрабатывает `WM_QUERYENDSESSION`/`WM_ENDSESSION`: в `winit-0.30.13/src` нет ни одного упоминания `ENDSESSION`; то же — https://github.com/rust-windowing/winit/issues/4360.
- Хук `EventLoopBuilderExtWindows::with_msg_hook` вызывается «before dispatching a win32 message» (`winit-0.30.13/src/platform/windows.rs:199-200`), только для сообщений, которые цикл забрал `PeekMessageW` (`platform_impl/windows/event_loop.rs:406-420`). `WM_QUERYENDSESSION` и `WM_ENDSESSION` система **посылает** окну (https://learn.microsoft.com/en-us/windows/win32/shutdown/wm-queryendsession, …/wm-endsession), а посланные сообщения `PeekMessageW` доставляет прямо в оконную процедуру, не возвращая их циклу (https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-peekmessagew). Хук их не увидит.
- Делегат приложения winit 0.30.13 на macOS — класс `WinitApplicationDelegate`, реализует только `applicationDidFinishLaunching:` и `applicationWillTerminate:` (`winit-0.30.13/src/platform_impl/macos/app_state.rs:47-75`). Варианта `macos-quit-as-close` (https://github.com/rust-windowing/winit/pull/4692) в 0.30.13 нет. Замена делегата своим ломает winit: `ApplicationDelegate::get` ожидает делегат своего класса (`app_state.rs:174-182`: `expect` и `panic!`, если делегат другого класса).
- HWND окна Slint доступен без типов `slint::winit_030`: `slint::Window::window_handle()` (`i-slint-core-1.17.1/api.rs:790`) реализует `raw_window_handle::HasWindowHandle` при feature `raw-window-handle-06` (`slint-1.17.1/Cargo.toml:121`).
- Трей у плеера есть только на Linux (В-1); рантайм tokio трея завершается, если хоста StatusNotifierItem нет (`src/tray.rs:149-151`).

**Варианты.**

| Аспект | Варианты | Выбор и основание |
|---|---|---|
| Сигналы (Linux, macOS) | А — задача `tokio::signal` в рантайме трея (§6.28 (01_audio_modes)); Б — отдельный поток `apap-signals` с однопоточным рантаймом tokio (feature `signal`); В — крейт `signal-hook` (новая зависимость); Г — `sigaction` + self-pipe на `libc` | **Б**: на macOS трея нет, а на Linux рантайм трея может завершиться (В-1, `src/tray.rs:149-151`); нового крейта нет; обработчик — обычный поток, а не контекст сигнала |
| Windows: завершение сеанса | А — `with_msg_hook`; Б — сабклассинг HWND окна Slint (`SetWindowSubclass`); В — скрытое верхнеуровневое окно в отдельном потоке | **Б**: А не видит посланные сообщения (см. контекст); В требует межпоточного синхронного вызова пути выхода в UI-поток, пока тот может быть занят; Б выполняет путь выхода прямо в UI-потоке, как требует ТЗ-15 («синхронно в обработчике») |
| macOS: запрос завершения | А — замена пункта меню Quit; Б — свой делегат вместо winit; В — `macos-quit-as-close`; Г — добавить метод `applicationShouldTerminate:` в класс `WinitApplicationDelegate` через рантайм Objective-C (`class_addMethod`); Д — наблюдатель `NSApplicationWillTerminateNotification` | **Г**, запасной путь — **Д**: А недостаточно (ТЗ-15); Б ломает winit; В нет в 0.30.13; Г ловит Cmd+Q, «Завершить» в Dock и выход из сеанса — все они идут через `-[NSApplication terminate:]`, который спрашивает делегат (https://developer.apple.com/documentation/appkit/nsapplicationdelegate/applicationshouldterminate(_:)) |
| Ожидание писателя | А — путь выхода асинхронный, цикл событий продолжает работать; Б — путь выхода синхронный: UI-поток ждёт ответов писателя до общего срока 5 с | **Б**: Windows и macOS требуют, чтобы запись завершилась до возврата из обработчика (ТЗ-15); один путь для всех причин; ТЗ-22 прямо допускает это ожидание |

**Критерии:** единый запрос выхода с причиной (ТЗ-14); порядок записи и одна попытка на файл (ТЗ-14); 5 с на все файлы (НФ-9); повторный запрос из окна или трея игнорируется, повторный сигнал завершает процесс сразу (ТЗ-14); перехват на всех трёх ОС (ТЗ-15); `cfg` только в модуле (ТЗ-54).

**Выбор.**

1. **Единый запрос.** `ExitRequest { reason }`, причины: закрытие окна, «Выход» в трее (только при `PlatformCaps.tray`), `SIGTERM`, `SIGINT`, `SIGHUP`, завершение сеанса Windows, запрос завершения macOS. Модуль жизненного цикла доставляет запрос в UI-поток: закрытие окна — из `on_close_requested` (если сворачивание в трей включено и трей есть — окно скрывается, это не выход); «Выход» в трее — через канал команд трея; сигнал — `slint::invoke_from_event_loop` из `apap-signals`; Windows и macOS — синхронным вызовом из UI-потока (п. 4, 5).
2. **Путь выхода** (`ExitCoordinator`, UI-поток), состояния `Running → Exiting → Done`:
   1. `Exiting`; повторный запрос из окна или трея в этом состоянии игнорируется (ТЗ-14);
   2. открытый диалог закрывается как «Отмена» без вопроса (ТЗ-32), открытое окно сообщения — без вопроса (ТЗ-52);
   3. движку — `EngineCmd::Shutdown` (до этапа С3 (01_audio_modes) — текущий `release_engine`);
   4. писателю — снимки в порядке `playlist.m3u` (если флаг взведён и запись не запрещена случаем 3 ОВ-8), `state.toml`, `settings.toml` (каждый — если сериализация отличается от эталона, ADR-3); по одной попытке на файл независимо от остановки после прежних ошибок (ТЗ-14, ТЗ-20);
   5. UI-поток ждёт ответов писателя до `t_запроса + 5 с` (НФ-9) и в том же ожидании принимает `ShutdownComplete` движка, у которого свой срок 2 с от того же момента (§6.28 (01_audio_modes)). Запись от ответа движка не зависит (ТЗ-136 (01_audio_modes));
   6. по ответам или по истечении срока — одна запись журнала: какие файлы записаны, какие нет и почему; ошибки — только в журнал (ТЗ-14);
   7. `Done`: `slint::quit_event_loop()` либо возврат из синхронного обработчика ОС (п. 4, 5).
3. **Сигналы** (Linux, macOS). Поток `apap-signals` с однопоточным рантаймом tokio слушает `SIGTERM`, `SIGINT`, `SIGHUP` (`tokio::signal::unix::signal`). Первый сигнал → `invoke_from_event_loop(ExitRequest)`. Второй сигнал любого из трёх видов → `std::process::exit` прямо из этого потока, без ожидания UI (ТЗ-14). Файлы при этом целы по ADR-4. Код завершения — 128 + номер сигнала (соглашение POSIX-оболочек; требованиями не задан).
4. **Windows.** После первого показа окна модуль получает HWND через `window_handle()` и ставит `SetWindowSubclass` (comctl32). Процедура сабкласса:
   - `WM_QUERYENDSESSION` → немедленно `TRUE`, путь выхода не начинается (ТЗ-15);
   - `WM_ENDSESSION` с `wParam = TRUE` → синхронный путь выхода (п. 2) в пределах 5 с, затем возврат 0;
   - `wParam = FALSE` и остальные сообщения → `DefSubclassProc`.

   Процедура сабкласса вызывается в UI-потоке во время диспетчеризации. `MusicApp` в этот момент не заимствован: из-за ADR-10 в UI-потоке нет блокирующих модальных циклов, которые держат заимствование. Модальный цикл перемещения окна выполняется внутри `DefWindowProc`, вне нашего кода. Путь выхода всё равно берёт `try_borrow_mut`: при неудаче он пишет в журнал «выход во вложенном цикле сообщений, файлы не записаны» и возвращает управление.
5. **macOS.** После инициализации бэкенда Slint (класс делегата регистрирует winit) модуль добавляет в класс `WinitApplicationDelegate` метод `applicationShouldTerminate:`. Метод выполняет синхронный путь выхода (п. 2) в пределах 5 с и возвращает `NSTerminateNow`. Если `class_addMethod` вернул `NO` (метод уже есть в будущей версии winit), модуль пишет запись в журнал и подписывается на `NSApplicationWillTerminateNotification` с тем же синхронным путём выхода (вариант Д). Поведение на macOS **не подтверждено** запуском: у пользователя нет macOS; проверка — ручной сценарий ТЗ-15 при появлении машины, до этого — ревью кода.
6. **Закрытие последнего окна** и «Выход» в трее (Linux) идут тем же путём; модуль жизненного цикла сообщает ОС об окончании записи там, где ОС этого ждёт (Windows, macOS — возвратом из обработчика).

**Последствия.**

- В `Cargo.toml`: `tokio` + feature `signal`; `slint` + feature `raw-window-handle-06`; `windows-sys` (Windows: `Win32_UI_Shell` для `SetWindowSubclass`, `Win32_Storage_FileSystem` для `MoveFileExW`); `objc2`, `objc2-foundation`, `objc2-app-kit` (macOS) — версии, совпадающие с winit 0.30.13.
- Подсказка параметра N (ТЗ-33) описывает только потери при сбое (ADR-18): способ перехвата найден на всех трёх ОС, ОВС с потерями при завершении сеанса не требуется. Если ручная проверка на macOS это опровергнет, вопрос вернётся в ОВС.
- Отличие от §6.28 (01_audio_modes): сигналы — в своём потоке, а не в рантайме трея; добавлены `SIGHUP`, Windows и macOS. Это замечание для §11 (заход 3).
- `run_event_loop_until_quit().unwrap()` и `ui.show().unwrap()` в `main.rs` (`src/main.rs:70`, `:76`) заменяются обработкой ошибок при переписывании `main` (ADR-23).

**Что проверяет выбор.** Автотесты ТЗ-14, ТЗ-15 с подменным модулем жизненного цикла: каждая причина → тот же путь выхода; подменная задержка записи 10 с → завершение через 5 с ± 0,5 с по `ManualClock`, незаписанные файлы перечислены в журнале; задержки 4 с и 2 с → плейлист записан, `state.toml` нет; повторный запрос из трея → записей не прибавилось; двойной сигнал → немедленное завершение (проверяется на уровне `apap-signals` с подменой функции завершения). Ручные сценарии ТЗ-15: Linux `kill -TERM/-INT/-HUP`, Windows «Завершение работы», macOS Cmd+Q и «Завершить» в Dock.

### ADR-8. Модуль ввода: нормализация колёсика

**Выполняет:** ТЗ-36; НФ-2, НФ-8; часть ТЗ-54 п. 3. Решение 3; ОВ-11; В-2…В-5.

**Контекст.**

- `scroll-event` Slint 1.17.1 теряет тип дельты и фазу (`i-slint-core-1.17.1/items/input_items.rs:193-196`; `wheel_test.md` §2). Поэтому В-2 требует событий winit через `on_winit_window_event`.
- Фильтр окна — один слот в адаптере окна (`i-slint-backend-winit-1.17.1/winitwindowadapter.rs:351`). `on_winit_window_event` записывает его в адаптер, даже если окна winit ещё нет (`lib.rs:1078-1092`). Цикл событий вызывает фильтр синхронно непосредственно перед тем, как Slint обработает то же событие (`event_loop.rs:192-199`), а `MouseWheel` Slint превращает в `MouseEvent::Wheel` с умножением строк на 60 (`event_loop.rs:401-421`).
- `BackendSelector::backend_name("winit")` и `select()` гарантируют бэкенд winit или возвращают ошибку (`i-slint-backend-selector-1.17.1/api.rs:252`, `:265`).
- В замере GNOME-2 «`not-winit`» означало только, что `with_winit_window` не вернул окно за 300 мс таймера зонда (`wheel_test.md` §2.2). На регистрацию фильтра это не влияет: фильтр ставится на адаптер.
- Feature `unstable-winit-030` в `Cargo.toml` плеера нет (`Cargo.toml:21-26`). Модуль `slint::winit_030` реэкспортирует `WinitWindowAccessor`, `EventResult`, `winit` (`slint-1.17.1/lib.rs:631-694`) и в Slint 1.18.0 сохранён (`slint-1.18.0/Cargo.toml:205-208`).
- Трей: ksni отдаёт `scroll(delta, orientation)` (`ksni-0.3.6/src/dbus_interface.rs:104`); плеер ориентацию игнорирует (`src/tray.rs:73`). Знак у KDE и GNOME противоположен (`wheel_test.md` §4.2, В-5).

**Варианты.** Источник событий выбран В-2 (`on_winit_window_event`; варианты а, в `wheel_test.md` §7.4 отвергнуты пользователем). Здесь выбираются способ сопоставления, хранение таблицы и определение хоста трея.

| Аспект | Варианты | Выбор |
|---|---|---|
| Сопоставление winit ↔ `scroll-event` | А — по значению и окну времени (число без источника); Б — по порядку диспетчеризации: фильтр кладёт событие в слот «ожидает пары», `scroll-event` того же события приходит в Rust-обработчик в том же вызове и забирает слот, если значения совпадают (`LineDelta·60` или `PixelDelta` в логических px) | **Б**: связь «то же событие» следует из порядка вызовов (`event_loop.rs:192-199` → `:416`); число для окна времени не нужно |
| Таблица данных | А — константы в коде; Б — файл TOML в составе исходников модуля, включаемый `include_str!` и разбираемый при запуске; В — внешний файл в каталоге настроек | **Б**: данные отделены от кода (ТЗ-36 «таблица данных (не код)»), меняются без изменения кода (НФ-8), не требуют чтения файла пользователя; В добавляет файловый ввод-вывод и проверку пользовательского файла без требования |
| Хост трея | А — `XDG_CURRENT_DESKTOP`; Б — владелец `org.kde.StatusNotifierWatcher` на D-Bus → PID → имя процесса; запасной путь — А | **Б** с запасным А (В-5) |

**Критерии:** В-2…В-5; одинаковый результат над ползунком и треем (ТЗ-36); изоляция нестабильного API (ТЗ-54); автотесты на записанных последовательностях.

**Выбор.**

- **Подключение.** В `Cargo.toml` у `slint` добавляется feature `unstable-winit-030`. `main` выбирает бэкенд `BackendSelector::new().backend_name("winit").select()` до создания окна. Если выбор не удался, приложение продолжает работу на бэкенде по умолчанию, и модуль ввода работает только по правилу по умолчанию на значениях Slint (журнал). Сразу после создания `AppWindow` модуль ввода регистрирует единственный фильтр окна; других пользователей фильтра нет (ТЗ-54).
- **Ползунок.** Фильтр на `WindowEvent::MouseWheel` кладёт событие (тип дельты, значение, фаза, время) в слот «ожидает пары» и возвращает `EventResult::Propagate`. `scroll-event` `TouchArea` ползунка вызывает Rust-обработчик модуля со значениями Slint:
  - есть ожидающее событие с совпадающим значением → нормализатор получает событие winit;
  - нет → правило по умолчанию на значениях Slint (60 px = один щелчок; иначе накопление пикселей по параметрам тачпада по умолчанию, ОВС-2).

  Событие winit, которое не забрал `scroll-event` до следующего события winit или до конца тика, отбрасывается: указатель вне ползунка, громкость не меняется (В-2).
- **Класс устройства** (В-3) — по тому, что сообщает ОС через winit:
  - `LineDelta` с целыми значениями и фазой `Moved` → колесо: `k` делений в событии = `k` щелчков, без ограничения скорости (В-3);
  - `PixelDelta` → тачпад;
  - дробный `LineDelta` → тачпад;
  - на Windows целое значение в пределах 200 мс после дробного — тоже тачпад (правило 1 `wheel_test.md` §5.1: 5 из 2 893 событий тачпада Windows кратны целой строке, §4.5). 200 мс — данные таблицы, а не константа кода.
- **Нормализатор** — чистая структура без `cfg`: состояние тачпада (накопитель со знаком, время последнего события, число шагов в текущем свайпе) и таблица. Для тачпада: накопление со знаком до порога T с переносом остатка, не более K шагов на свайп, граница свайпа — пауза больше заданной, после неё остаток сбрасывается (В-4). Знак — как пришёл: системную инверсию ОС уже применила (`wheel_test.md` §4.5, §5.1 п. 4). Горизонтальные дельты (`delta_x`, ориентация трея `Horizontal`) громкость не меняют (`wheel_test.md` §5.3: данных нет, предложено игнорировать). Выход — `VolumeCmd::Step(щелчки)` (ADR-14).
- **Таблица данных** — `src/platform/input/wheel_table.toml`, разбирается при запуске; ошибка разбора — паника исключена: тест проверяет файл при каждом `cargo test`, а в рантайме при ошибке используется правило по умолчанию с записью в журнал. Ключи и значения:
  - ползунок — «платформа × сеанс × класс устройства»: колесо — 1 деление = 1 щелчок для KDE, GNOME, Windows (подтверждено экспериментом), тачпад Windows — T = 0,5 строки, K = 5, пауза 300 мс (В-4);
  - трей — «хост»: KDE Plasma — знак `+`, деление 120; GNOME с AppIndicator — знак `−`, деление 1 (В-5); неизвестный хост — знак как у KDE, деление — модуль первого события (В-5);
  - платформы, сеансы и классы без данных (KDE X11, GNOME X11, тачпад с точными дельтами на Linux, macOS) — правило по умолчанию; его параметры для тачпада — **отложено до ОВС-2**;
  - у каждой строки — исход для протокола приёмки (ТЗ-36: подтверждено экспериментом / по документации / правило по умолчанию).

  Платформу и сеанс (Wayland / X11 / win32 / appkit) модуль определяет внутри себя (`cfg` и тип дескриптора окна).
- **Трей** (только Linux). При запуске трея модуль в потоке трея определяет хост:
  1. `org.freedesktop.DBus.GetNameOwner("org.kde.StatusNotifierWatcher")` (`zbus-5.19.0/src/fdo/dbus.rs:337`);
  2. `GetConnectionUnixProcessID(владелец)` (`:328`);
  3. имя процесса из `/proc/<pid>/comm`: `plasmashell` → KDE Plasma; `gnome-shell` → GNOME;
  4. иначе `XDG_CURRENT_DESKTOP`;
  5. иначе — неизвестный хост.

  То, что на GNOME владельцем службы является процесс `gnome-shell` (расширение AppIndicator работает внутри него), **не подтверждено** — ручная проверка на GNOME. Событие трея `scroll(delta, Vertical)` → `щелчки = знак_хоста · delta / деление`; остаток накапливается так же, как у колеса; `Horizontal` игнорируется.
- **macOS-инерция:** ТЗ-36 требует игнорировать инерционные события после окончания жеста, а winit 0.30.13 инерцию отдельно не помечает (`winit-0.30.13/src/platform_impl/macos/view.rs:683-691`: `momentumPhase` Began/Ended отображается в те же `Started`/`Ended`, что и фаза пальцев). **Отложено до ОВС-1.**
- **Изоляция.** `slint::winit_030` и `on_winit_window_event` используются только в `src/platform/input/**` (ТЗ-54). При обновлении Slint модуль проверяется автотестами на фикстурах (В-2); перевод записей `tools/wheel_probe/results/` в фикстуры формата `wheel_test.md` §7.2 — план тестов (заход 3).

**Последствия.** Шаг ±0,04 в `ui/top_panel.slint:471-476` и инверсия трея (`src/app/mod.rs:1747`) удаляются: громкость меняет только `VolumeCmd` (ADR-14). Когда придут недостающие замеры (`wheel_test.md` §7.3), меняются только строки таблицы и фикстуры.

**Что проверяет выбор.** Автотесты ТЗ-36: фикстуры GNOME, KDE, Windows; В-3 (KDE-3, GNOME-2 как колесо; 10–12 быстрых щелчков → 10–12 шагов); В-4 (короткий свайп 1–4, длинный и быстрый 5, выбросы ≈ 67 строк ≤ 5); В-5 (трей KDE-1…3, GNOME-1, 2 → те же шаги и направление, что у ползунка); В-2 (`scroll-event` без пары → правило по умолчанию; winit без пары → громкость не меняется); одинаковые последовательности над ползунком и треем → одинаковый результат; тест разбора таблицы. Ревью кода: `winit_030` только в модуле ввода.

### ADR-9. Системные уведомления

**Выполняет:** ТЗ-52 п. 2; часть ТЗ-54 п. 4. ОВ-7; В-1.

**Контекст.** Системное уведомление нужно, только пока главное окно скрыто в трей, а трей есть только на Linux (В-1). В зависимостях нет крейта уведомлений; `zbus` 5.19.0 уже в сборке через `ksni`.

**Варианты.** А — крейт `notify-rust` (новая зависимость); Б — прямой вызов `org.freedesktop.Notifications.Notify` через `zbus` (спецификация: https://specifications.freedesktop.org/notification-spec/latest/); В — подсказка трея (`TrayState.notice`, `src/tray.rs:36-38`) — не системное уведомление.

**Критерии:** без новых зависимостей; работа вне UI-потока; подмена для тестов.

**Выбор: Б.** Трейт `Notifier { fn notify(&self, level, title, body) }`. Linux: вызов `Notify` по сессионной шине в рантайме потока трея (рантайм есть, пока работает трей; без трея окно в трей не скрывается и уведомление не нужно). Windows, macOS: пустая реализация, `PlatformCaps.notifications = false`. Подмена записывает вызовы. Ошибка D-Bus — только журнал; окно сообщения всё равно покажется при открытии плеера (ADR-13).

**Последствия.** `zbus` — прямая зависимость для Linux (версия из `Cargo.lock`).

**Что проверяет выбор.** Автотест ТЗ-52: подменная платформа с треем, окно скрыто, ошибка записи `state.toml` → одно уведомление и окно при открытии; без трея → окно, 0 уведомлений.

### ADR-10. Выбор файлов

**Выполняет:** ТЗ-53; часть ТЗ-54 п. 5; ТЗ-22. ОВ-9; В-1.

**Контекст.** Сейчас `rfd::FileDialog` блокирует цикл событий (`src/app/mod.rs:844-883`, R-13). Асинхронные варианты rfd 0.17.2:

- Linux: xdg-desktop-portal выполняется в отдельном потоке с `pollster` (`rfd-0.17.2/src/backend/xdg_desktop_portal.rs:20-34`); запасной `zenity` — в том же потоке (`:105-106`);
- Windows: диалог в отдельном потоке (`backend/win_cid/file_dialog.rs:15-30`);
- macOS: окно-лист, привязанное к окну, если приложение запущено и окно есть; иначе синхронный запасной путь с сообщением в stderr (`backend/macos/modal_future.rs:79-117`).

Родителя можно задать: `set_parent` принимает `HasWindowHandle` (`file_dialog.rs:96`). Futures rfd не зависят от исполнителя (oneshot-канал), их можно выполнять в `slint::spawn_local` (`i-slint-core-1.17.1/context.rs:181`).

**Варианты.** А — оставить блокирующие (отвергнуто ОВ-9); Б — блокирующий rfd в рабочем потоке (на macOS панель должна создаваться в главном потоке — запасной путь rfd паникует вне главного потока, `modal_future.rs:117`); В — `AsyncFileDialog` + `spawn_local`; Г — собственный выбор файлов в Slint (большой объём UI без требования).

**Критерии:** цикл событий не блокируется (ТЗ-53); главное окно недоступно на время выбора (ТЗ-23); повторно открыть нельзя.

**Выбор: В.** Трейт `FilePicker` с операциями «файлы», «каталог», «открыть плейлист», «сохранить плейлист», «файл темы»; результат — через `spawn_local` в UI-поток. Родитель — окно плеера (`window_handle()`, feature `raw-window-handle-06`, как в ADR-7). На время выбора шлюз `UiGate` держит причину «выбор файла» (ADR-12), поэтому второй выбор не откроется. Если rfd на macOS ушёл в синхронный запасной путь, модуль это не узнаёт; факт фиксируется в протоколе приёмки по ручному сценарию (ТЗ-53). Поведение окна-владельца при диалоге из другого потока на Windows — **не подтверждено**: ручной сценарий ТЗ-53.

**Последствия.** Последний каталог берётся из результата выбора и меняет состояние с `Origin::User` (§5.1 ТЗ: N). Подмена `FilePicker` возвращает заданные пути и умеет «не отвечать» (для проверки недоступности окна).

**Что проверяет выбор.** Замер ТЗ-53 (диалог «Добавить каталог» открыт 30 с → максимальная итерация ≤ 50 мс; на Linux колёсико трея меняет громкость); автотест: при открытом выборе вызов обработчиков меню ничего не меняет; ручные сценарии на Linux, Windows, macOS.

### ADR-11. Модель диалога настроек

**Выполняет:** ТЗ-25, ТЗ-26, ТЗ-27, ТЗ-28, ТЗ-29, ТЗ-30, ТЗ-31 (скрытие колонки), ТЗ-34; §5.2 ТЗ. Решения 2, 6; Т-1, Т-2, Т-4; ОВ-10; ТЗ-137, `ModeSettingsUpdate`, `ApplyKind` (01_audio_modes).

**Контекст.** Сейчас копия — вся `Settings` (`src/app/mod.rs:821`) с белым списком «живых» полей при «Сохранить» (`:1314-1342`, R-12). Запись безусловная (R-6), применение не дифференциальное (R-7), тема коммитится после записи (R-8). Кнопки очистки плейлиста и удаления трека — в диалоге (`:1444-1553`, ОВ-10).

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Копия всей `Settings` + белый список (как сейчас) | R-12: каждое новое поле состояния легко забыть |
| Б | Черновик только параметров диалога; «отличия» — сравнение черновика с действующими значениями по значению; разница → план применения по таблице §5.2 ТЗ (предложение ревью §8) | Состояние сессии в черновик не входит по построению (ТЗ-25) |
| В | Признаки «изменено» на каждом элементе диалога | «Изменить и вернуть» давало бы отличие — нарушает ТЗ-27 |

**Критерии:** ТЗ-25…ТЗ-30; одна запись по «Сохранить» (ТЗ-28); применение только отличий (ТЗ-29); тестируемость без Slint (ADR-19).

**Выбор: Б.**

- **Черновик** `DialogDraft` создаётся при открытии из действующих значений и содержит: настройки окна настроек (вся часть `SettingsFile`, кроме `[playback]`), `ModeSettings` (01_audio_modes), тип визуализации (Т-1), признак «Сбросить ширины» (Т-2). Отдельно от черновика — режим, показанный в диалоге (`shown_mode`, ТЗ-30): он не сравнивается и не сохраняется. Флажка bit-perfect как способа выбора режима нет (Т-4).
- **Отличия** — поэлементное сравнение черновика с действующими значениями. Пока диалог открыт, настройки меняются только им (решение 1), поэтому базой сравнения служат действующие значения, а не снимок при открытии. Тип визуализации и ширины сравниваются с действующим состоянием.
- **Проверка** — `validate(&DialogDraft) -> Vec<Invalid { param, reason }>`: допустимые множества параметров и `buffers_allowed` (01_audio_modes, И-Р22). Кнопка «Сохранить» активна тогда и только тогда, когда отличия есть, а недопустимых значений нет. Подсказка — первый недопустимый параметр и причина (ТЗ-27).
- **«Сохранить»:**
  1. итоговые настройки = действующие с применёнными отличиями;
  2. снимок `settings.toml` → писателю, одна запись (ТЗ-28);
  3. применение по плану, построенному из `SettingsDiff`, по строкам §5.2 ТЗ: тема (данные темы уже прочитаны при выборе в диалоге — ADR-20; повторного чтения нет); колонки (скрытие колонки ключа не меняет ключ и видимый порядок — ТЗ-31); обложки; визуализация; кэш; сворачивание в трей; N (ADR-3); тип визуализации и «Сбросить ширины» → действующее состояние с `Origin::User` (запустит N); опции режимов → `EngineCmd::SetModeSettings(ModeSettingsUpdate { settings, diff: Some(…) })`, если изменился хотя бы один параметр режима (ТЗ-29; способ применения в тракте — `ApplyKind`, §6.18 (01_audio_modes));
  4. диалог закрывается. Ошибка записи придёт позже от писателя и откроет окно Error (ТЗ-20, ТЗ-28); настройки уже действуют.
- **«Отмена» / Esc** уничтожают черновик: ничего не применяется и не записывается (ТЗ-26).
- **Очистка кэшей** — мгновенные действия вне черновика (ТЗ-34): задание в поток `apap-io` (ADR-20), затем пересчёт размера; «Отмена» их не отменяет. Постоянный текст о неотменяемости — в вёрстке вкладки. «Удалить текущий трек» и «Очистить плейлист» убираются из диалога в меню «Файл» (ОВ-10) и подчиняются общим правилам команд плейлиста (ТЗ-12, ТЗ-48).

**Последствия.** До этапов С3, С4 (01_audio_modes) `ModeSettings` и `SetModeSettings` нет: аудио-часть черновика и её применение — по текущему коду с минимальными правками; сведение — §8 (заход 3).

**Что проверяет выбор.** Автотесты ТЗ-25…ТЗ-30, ТЗ-34 на модели диалога без Slint: `save_button_disabled_without_changes`, `dialog_cancel_leaves_settings_and_file_unchanged`, `dialog_save_without_changes_does_not_write`, `dialog_save_applies_only_edited_fields` (счётчики чтений темы, перестроений модели плейлиста, перечислений устройств, команд движка).

### ADR-12. Модальность и общий механизм недоступности главного окна

**Выполняет:** ТЗ-23, ТЗ-24, ТЗ-48 (недоступные команды), ТЗ-52 п. 1, ТЗ-53. Решение 8; ОВ-7, ОВ-9, ОВ-15.

**Контекст.**

- Нативной модальности в Slint/winit нет (R-11: https://github.com/slint-ui/slint/pull/8135, https://github.com/slint-ui/slint/issues/6607).
- Сейчас диалог — оверлей (`ui/settings.slint:47`, фон перехватывает указатель `:220-228`), клавиша V отключена (`ui/app.slint:383-386`). Пункты меню «Визуализация» отключаются при открытом диалоге (`ui/app.slint:65-86`), а «Файл» и «Настройки → Параметры» — нет (`ui/app.slint:35-56`, `:91-95`), повторный выбор «Параметры» пересоздаёт копию (R-11).
- `MenuItem` Slint 1.17.1 имеет свойство `enabled`: «When disabled, the MenuItem can be selected but not activated» (`i-slint-compiler-1.17.1/builtins.slint:1303-1304`). Отключить целиком заголовок меню (`Menu`) свойством нельзя.

**Варианты.** А — отдельное окно диалога + `set_enabled(false)` главного (кроссплатформенного API нет); Б — оверлей + отключение пунктов меню; В — Б + проверка шлюза в каждом обработчике команд главного окна (вариант решения 8 «или его обработчики ничего не делают»).

**Критерии:** указатель, колёсико, клавиатура и меню не достигают главного окна (ТЗ-23); трей работает (ТЗ-24); один механизм для диалога, окна сообщения, выбора файла и загрузки плейлиста.

**Выбор: В.**

- `UiGate` (UI-поток) хранит множество причин блокировки окна {диалог настроек, окно сообщения, выбор файла} и отдельно признак «идёт загрузка плейлиста». Метод `allows(cmd)` отвечает для каждой команды главного окна: при любой причине блокировки окна — ни одна команда главного окна; при загрузке — все, кроме перечня ТЗ-48.
- Slint получает два свойства: «окно заблокировано» и «идёт загрузка». По первому:
  - оверлей с перехватом указателя и колёсика и `FocusScope`, забирающим клавиатуру, поверх содержимого главного окна; диалог настроек и окно сообщения — над ним;
  - `enabled: false` у всех пунктов меню, кроме пунктов самого диалога.

  По второму — `enabled: false` у пунктов ТЗ-48 и подсказка «Идёт загрузка плейлиста».
- Каждый обработчик команды главного окна в Rust сначала спрашивает `UiGate::allows`; при отказе ничего не делает. Это закрывает платформы, где отключённый пункт всё же можно выбрать, и делает ТЗ-23 проверяемым автотестом.
- Повторное открытие диалога — команда главного окна, при открытом диалоге шлюз её не пропускает (черновик не пересоздаётся).
- Команды трея (Linux) идут мимо шлюза (ТЗ-24) и меняют действующее состояние, а не черновик; «Выход» в трее — путь выхода (ADR-7).

**Последствия.** Колёсико над ползунком при блокировке не доходит до `scroll-event` (оверлей), а событие winit без пары отбрасывается (ADR-8). Визуальное отключение пунктов на каждой платформе фиксируется в протоколе ручной приёмки (ТЗ-23).

**Что проверяет выбор.** Автотесты `menu_inactive_while_dialog_open` и то же при открытом окне сообщения и выборе файла: вызов каждого обработчика → 0 изменений плейлиста, настроек, состояния и черновика; ТЗ-48: каждая команда перечня при загрузке ничего не меняет. Ручной сценарий ТЗ-23 на Linux X11, Wayland, Windows, macOS.

### ADR-13. Окно сообщений

**Выполняет:** ТЗ-52, ТЗ-7, ТЗ-13 (окна Error явных действий), ТЗ-20 (окно ошибок записи), ТЗ-21 (окна Warning/Error). ОВ-7, ОВ-16; У-2; В-1.

**Контекст.** Сейчас сообщения идут в строку состояния и подсказку трея (`src/app/mod.rs:1683-1689`, `src/tray.rs:36-38`); ОВ-7 вводит три канала, правило выбора канала и раскладку сообщений. Окно сообщения — оверлей поверх главного окна и диалога настроек.

**Варианты.** А — системное окно сообщения (`rfd::MessageDialog`): не оверлей, отдельное окно ОС, вне механизма ТЗ-23; Б — оверлей Slint с очередью в UI-потоке.

**Критерии:** ТЗ-52 (уровни, очередь по одному, буфер до первого показа, Enter/Esc, блокировка по ТЗ-23); одно сводное окно ошибок записи со списком и «Повторить» (ТЗ-20); уведомление при окне в трее.

**Выбор: Б.**

- `MessageCenter` (UI-поток, без Slint):
  - очередь сообщений `{ уровень, заголовок, текст, кнопки }` и текущее показанное сообщение;
  - признак «главное окно уже показано»;
  - сводная запись ошибок записи рабочих файлов: список `(файл, класс ошибки)`.
- **Правила:**
  - до первого показа главного окна сообщения только копятся (ТЗ-7, ТЗ-52);
  - показывается одно сообщение; следующее — после закрытия текущего;
  - ошибки записи `settings.toml`, `state.toml`, `playlist.m3u` — одна сводная запись в очереди; новая ошибка, пока запись в очереди или на экране, добавляет файл в список или обновляет причину (ТЗ-20);
  - «Повторить» — команда писателю для всех файлов списка (ADR-3); записанные файлы удаляются из списка; пустой список закрывает окно;
  - «OK» закрывает окно, запись по отсчёту для этих файлов остаётся остановленной (ТЗ-20);
  - ошибки явных действий (экспорт, чтение «Загрузить плейлист») — отдельная запись на каждую попытку, без объединения (ТЗ-13, ТЗ-20).
- Пока сообщение на экране, `UiGate` держит причину «окно сообщения» (ADR-12). Enter — основная кнопка, Esc — закрыть.
- **Окно в трее** (Linux, `PlatformCaps.tray`): при появлении сообщения, пока окно скрыто, — одно системное уведомление (ADR-9). Само сообщение остаётся в очереди и показывается, когда окно открывают.
- **Выход** при открытом окне закрывает его без вопроса (ADR-7).
- **Slint:** компонент окна сообщения — последним дочерним элементом `AppWindow`, поверх диалога настроек; уровни Warning и Error различаются значком и цветом заголовка из темы; Info в текущем объёме не используется (ТЗ-52).
- Строка состояния перестаёт быть каналом сообщений (ОВ-7); её прочие показания (например, «Loaded N tracks») — вне объёма этого ADR.

**Последствия.** Подсказка трея с уведомлением о bit-perfect (`BP_NOTICE_TEXT`, `src/tray.rs:20-22`) относится к удаляемому коду bit-perfect (этапы 01_audio_modes) и в этот механизм не переносится.

**Что проверяет выбор.** Автотесты ТЗ-52 (два сообщения до первого показа → по очереди после показа; при окне сообщения обработчики меню ничего не меняют; окно в трее → одно уведомление и окно при открытии; без трея → 0 уведомлений; успешный экспорт → 0 окон; повреждённый `state.toml` → 0 окон; «Выход» в трее при окне Error → окно закрыто, одна попытка записи), ТЗ-20, ТЗ-7. Ручной сценарий: различимость уровней, Enter/Esc.

### ADR-14. Источники громкости и mute в UI

**Выполняет:** ТЗ-35, ТЗ-37, ТЗ-38, ТЗ-39, ТЗ-24 (громкость из трея при диалоге); НФ-2. Решение 3; ТЗ-138…ТЗ-141, ОВС-18…ОВС-20, ADR-23 (01_audio_modes).

**Контекст.**

- Сейчас ползунок меняет громкость в Slint (`ui/top_panel.slint:471-476`: ±0,04, `delta-y > 0` — громче), трей — в Rust (`src/app/mod.rs:1736-1754`: ±0,02, `delta < 0` — громче).
- Ревью §3.4 предполагает разрыв привязки ползунка после перетаскивания.
- `PlaybackState` (01_audio_modes) хранит громкость и mute по режимам; в Строгом режиме громкости нет, mute есть; в Оптимальном при `volume_lock` громкость не меняется (ADR-23 (01_audio_modes)).
- Slint 1.17.1 даёт элемент `Tooltip` (`i-slint-compiler-1.17.1/builtins.slint:2633`) с собственным содержимым. Подсказка следит за наведением на родительский элемент (`TooltipArea`, `:2521-2533`) и скрывается, когда указатель уходит с родителя. Поэтому дотянуться указателем до кнопки внутри подсказки, по-видимому, нельзя — **не подтверждено** запуском.

**Варианты.** А — каждый источник меняет громкость сам (как сейчас); Б — все источники формируют одну команду, правило блокировки и шаг — в одной функции; ползунок получает значение только из Rust.

**Критерии:** одинаковое поведение источников (решение 3, ТЗ-36); ползунок всегда показывает громкость активного режима (ТЗ-35); блокировка без изменения состояния и без запуска N (ТЗ-37).

**Выбор: Б.**

- `VolumeCmd`:
  - `Set(Volume)` — ползунок;
  - `Step(щелчки)` — колёсико над ползунком, колёсико трея (ADR-8), будущие горячие клавиши.
- Одна функция применения к `PlaybackState`:
  - активен Строгий режим или Оптимальный с `volume_lock` → ничего не меняется: ни громкость, ни ползунок, ни состояние; отсчёт N не запускается (ТЗ-37);
  - иначе новая громкость = `clamp(текущая + 0,02 · щелчки, 0, 1)` (НФ-2) или заданное значение; изменение с `Origin::User` (ADR-22) запускает N; движку — `EngineCmd::SetVolume` (01_audio_modes); до этапа С3 (01_audio_modes) — текущий `player.set_volume`.
- **Ползунок** в Slint получает значение только свойством из Rust, которое Rust выставляет после каждого применения команды и после смены активного режима. Перетаскивание вызывает обработчик `Set`, а не пишет громкость в самом Slint. Поэтому значение ползунка не может разойтись с громкостью активного режима (ТЗ-35).
- **Mute.** Переключение любым способом меняет mute активного режима в `PlaybackState` (в Строгом — `strict_muted`) с `Origin::User` → N (ТЗ-38); движку — `SetMuted`. Mute работает и в Строгом режиме, и при фиксации (ТЗ-37).
- **Подсказки** (ТЗ-39) — только текст: «Громкость недоступна в Строгом режиме», «Громкость зафиксирована на 100 % в настройках Оптимального режима». `Tooltip` ставится на обёртку ползунка, которая сама не отключается: показ подсказки у отключённого элемента не подтверждён.
- Источники идут в одну функцию и при открытом диалоге (трей мимо шлюза, ADR-12) и меняют действующее состояние, а не черновик (ТЗ-24).

**Последствия.** Шаг 0,04 и знак в Slint, `WHEEL_VOLUME_STEP` и инверсия трея в `poll_tray` удаляются. Кнопка «перейти к настройке» внутри подсказки не делается (ТЗ-39 допускает «только текст»).

**Что проверяет выбор.** Автотесты `strict_mode_wheel_and_hotkeys_do_not_change_volume`, `optimal_volume_lock_ignores_all_sources` (каждый источник → громкость, состояние и срок N без изменений; mute переключается), ТЗ-38 (mute по режимам переживает перезапуск на `MemStore`); ручной сценарий ТЗ-35 (ползунок после перетаскивания и колёсика трея), ТЗ-39.

### ADR-15. Модель порядка плейлиста

**Выполняет:** ТЗ-40, ТЗ-41, ТЗ-42, ТЗ-43, ТЗ-44, ТЗ-45, ТЗ-46, ТЗ-31, ТЗ-12 (что взводит флаг). Решения 2, 5; ОВ-12, ОВ-13, ОВ-14; ТЗ-142, ОВС-21, ADR-15, §6.21, ТС-6 (01_audio_modes).

**Контекст.**

- Сейчас есть `tracks` (видимый порядок) и `disk_tracks` (исходный), сортировка клонирует каждый `Track` (`src/app/playlist_manager.rs:170`, ревью §7). Результаты сканирования добавляются в конец отсортированного списка (ревью §3.6). Сравнение побайтовое и регистрозависимое (ревью §3.6). Shuffle пересоздаётся с потерей истории (`rebuild_shuffle`).
- 01_audio_modes: `Sequencer` получает видимый порядок срезом `TrackId`, при Shuffle — перестановку видимого порядка (ADR-15, §6.21 (01_audio_modes)).

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Физически переставлять треки при сортировке (как foobar2000, DeaDBeeF — ревью §6) | Противоречит ТЗ-40: сортировка не меняет исходный порядок |
| Б | Два списка `Track` (видимый и исходный) — как сейчас | Двойное хранение тяжёлых `Track`, клоны при сортировке |
| В | Один список строк в исходном порядке со стабильным `TrackId`, видимый порядок — перестановка индексов; ключи сравнения строк вычисляются один раз при загрузке и при обновлении тегов | Без клонов `Track`; сортировка — перестановка индексов; вставка по ключу — бинарный поиск |

**Критерии:** ТЗ-40…ТЗ-46; производительность для 5 000 треков (ТЗ-47, замер); связь с `Sequencer` (01_audio_modes).

**Выбор: В.**

- `Playlist` хранит строки исходного порядка (`TrackId`, трек, ключи сравнения), `Option<SortKey>` и видимый порядок как перестановку индексов.
- **Операции:**
  - сортировка по колонке и снятие ключа — только ключ и видимый порядок (ТЗ-40);
  - цикл щелчков по заголовку «↑ → ↓ → нет», щелчок по другой колонке — «↑» (ТЗ-42); колонка «Сейчас играет» не сортируется; ключ скрытой колонки не снимается до её показа (ТЗ-31);
  - добавление — в конец исходного порядка и на место по ключу в видимом: бинарный поиск с равенством, разрешаемым по исходному индексу, поэтому вставка стабильна (ТЗ-41);
  - удаление, очистка — из обоих порядков;
  - ручное изменение порядка (ТЗ-44) — новый видимый порядок с перемещёнными строками; если ключ есть, исходный порядок := новый видимый, ключ снимается; флаг «плейлист изменён» взводится.
- **Флаг** взводят только добавление, удаление, очистка, загрузка другого плейлиста и ручное изменение порядка; сортировка, снятие ключа, смена текущего трека и обновление тегов — нет (ТЗ-12).
- **Сравнение** (ТЗ-43):
  - текст — без учёта регистра после приведения к одной форме Unicode, последовательности цифр — как числа;
  - год, номер трека, номер диска — числа;
  - пустые значения — в конце при любом направлении;
  - вторичные ключи всегда по возрастанию: Исполнитель → год → альбом → диск → трек; Альбом → диск → трек; Год → альбом → диск → трек;
  - при полном равенстве — исходный порядок (стабильная сортировка).

  Ключи сравнения строки (приведённый текст, разобранные числа) вычисляются при загрузке и при обновлении тегов, а не в компараторе. Способ нормализации Unicode и приведения регистра — **отложено до ОВС-3**.
- **Shuffle** (ТЗ-45). `ShuffleState` хранит перестановку видимого порядка, позицию и множество `TrackId`, сыгранных в текущем проходе. При смене ключа, снятии ключа, добавлении и удалении перестановка строится заново так: сыгранные треки — в прежнем порядке, затем текущий трек, затем несыгранные в случайном порядке (`rand`, уже в зависимостях). Текущий трек и воспроизведение не меняются; каждый трек прохода играет один раз (Repeat Off).
- **«Далее» без текущего трека** — первый трек видимого порядка, при Shuffle — первый в перестановке (ТЗ-46).
- **Связь с `Sequencer`** (01_audio_modes). После каждого изменения видимого порядка или перестановки UI передаёт `Sequencer` новый срез `TrackId` (§6.21 (01_audio_modes)); сортировка, снятие ключа, добавление и удаление — действия пользователя, они закрывают серию пропусков (ТЗ-45). До этапа С8 (01_audio_modes) выбор следующего трека выполняет текущий код на той же модели (§8, заход 3).

**Последствия.** `tracks` / `disk_tracks` / `shuffle_order` заменяются одной моделью. Модель строк таблицы Slint обновляется по видимому порядку точечно (как сейчас инкрементально, `playlist_rows`). Нормализация зависит от ОВС-3.

**Что проверяет выбор.** Автотесты ТЗ-40 (`sort_change_does_not_write_playlist`), ТЗ-41, ТЗ-42, ТЗ-43 (набор «beatles»/«Zappa», «999»/«2001», диски 1/2, «No. 9»/«No. 10», две формы Unicode, пустой год — оба направления), ТЗ-44 (`drag_reorder_clears_sort_key`), ТЗ-45 (12 треков, каждый один раз), ТЗ-46, ТЗ-31.

### ADR-16. Загрузка плейлиста как конечный автомат

**Выполняет:** ТЗ-13 б, ТЗ-17, ТЗ-47, ТЗ-48. Решение 10; ОВ-5, ОВ-15 и уточнение к ОВ-15.

**Контекст.**

- Сейчас стартовая загрузка — поток с каналом (`src/app/mod.rs:373-378`), результат применяется на тике и перезаписывает `tracks`, `disk_tracks`, `known_paths` (`:1658-1687`). Добавленное до окончания загрузки пропадает (R-15).
- «Загрузить плейлист» читает файл и теги синхронно в UI-потоке, сортировку не применяет, флаг не взводит, текущий трек сбрасывает без остановки (R-15).
- В текущем коде и в модели 01_audio_modes нет заранее открытого следующего трека: следующий выбирает `Sequencer` по `Ended` (§6.21 (01_audio_modes)); `gapless` в декодере — свойство одного потока (`src/audio/decoder.rs:266`).

**Варианты.** А — показывать плейлист по частям (отвергнуто решением 10); Б — ставить команды в очередь до окончания загрузки (отвергнуто ОВ-15); В — автомат загрузки с поколением и недоступными командами (ОВ-15 а).

**Критерии:** ТЗ-47 (окно не ждёт загрузки, список показывается целиком и отсортированным); ТЗ-48; ТЗ-17 (рабочий плейлист — прежний до окончания); ТЗ-13 б (Play Now).

**Выбор: В.**

- `LoadState`: `Idle`; `Startup { поколение }`; `Command { поколение, путь }`.
- **Поток загрузки** `apap-playlist` (по одному на загрузку):
  1. читает файл — стартовая загрузка через ADR-5, «Загрузить плейлист» через модуль ФС;
  2. читает теги всех файлов последовательно (`meta::probe_file`);
  3. строит ключи сравнения и видимый порядок по действующему ключу сортировки, переданному при запуске загрузки;
  4. отдаёт результат с поколением.

  Ответ с устаревшим поколением отбрасывается.
- **Пока идёт загрузка:**
  - `UiGate` держит признак загрузки (ADR-12): недоступны «Добавить файлы», «Добавить папку», «Загрузить плейлист», «Удалить текущий трек», «Очистить плейлист», «Сохранить плейлист», сортировка по заголовку, перенос файлов в окно; при `Command` — ещё «Далее» и «Назад»;
  - пауза, стоп, перемотка, громкость и mute работают;
  - виден индикатор;
  - рабочий плейлист — прежний, загружаемый список существует только в потоке загрузки.

  Поэтому отсчёт N и путь выхода пишут прежний плейлист, если флаг был взведён, и ничего — если не был (ТЗ-17).
- **Окончание `Startup`:** плейлист заменяется целиком; флаг не взводится; воспроизведение не начинается.
- **Окончание `Command`** (Play Now, ОВ-5):
  1. плейлист заменяется, флаг взводится (запускает N, если срок не идёт);
  2. прежний трек останавливается;
  3. поколение запросов `Open` увеличивается — ответ движка на запрос прежнего плейлиста будет отброшен (ADR-15 (01_audio_modes));
  4. `Sequencer` получает новый видимый порядок или новую перестановку Shuffle;
  5. запускается первый трек — независимо от того, играло ли, стояло на паузе или было остановлено, в том числе если во время загрузки нажат «Стоп» (ТЗ-48).

  Repeat и Shuffle — действующие, mute сохраняется. Пустой плейлист → стоп, флаг взведён.
- **Ошибка чтения выбранного файла:** плейлист и воспроизведение не меняются, флаг не взводится, окно Error на попытку (ADR-13).
- **«Отмена подготовленного следующего трека»** (ТЗ-13 б) выполняется по построению: заранее открытого следующего трека нет, а запрос, отправленный для прежнего плейлиста, отбрасывается по поколению (шаг 3). Если в будущем появится заранее открытый следующий трек, его отмена должна стоять в этом же шаге — замечание для §11 (заход 3).

**Последствия.** Синхронный `load_track_list` в обработчике меню и `drain_startup_tracks` с перезаписью трёх полей удаляются. Тесты не запускают стартовую загрузку пользователя: поток загрузки создаёт фабрика из `AppDeps` (ADR-19), у подмены загрузка управляется вручную («зависла», «завершилась»).

**Что проверяет выбор.** Автотесты ТЗ-13 б (из «играет», «пауза», «стоп»; нечитаемый файл; пустой плейлист), ТЗ-17 (подменная загрузка «зависает» → выход → 0 записей; флаг взведён/не взведён до команды; N истекает во время загрузки → прежний плейлист), ТЗ-48 (каждая команда недоступна и ничего не меняет). Замер ТЗ-47 (5 000 треков: первый кадр, итерации ≤ 50 мс).

### ADR-17. Экспорт «Сохранить плейлист»

**Выполняет:** ТЗ-13 а, ТЗ-18 (экспорт атомарен), ТЗ-20 (окно на попытку). Решение 5; ОВ-17.

**Контекст.** ОВ-17: видимый порядок без перестановки Shuffle; UTF-8, `#EXTM3U`, `#EXTINF` (длительность, «Исполнитель — Название»), абсолютные пути; расширение по умолчанию `.m3u8`; рабочий `playlist.m3u` и флаг не меняются.

**Варианты.** А — писать в UI-потоке; Б — через писателя (ADR-1) с атомарной записью (ADR-4).

**Выбор: Б.**

- Текст формируется в UI-потоке из видимого порядка: первая строка `#EXTM3U`; для каждого трека — `#EXTINF:<секунды>,<подпись>` и абсолютный путь.
- Секунды — длительность, округлённая до целого; неизвестная длительность — `-1`. Это соглашение расширенного M3U; в RFC 8216 §4.3.2.1 у `#EXTINF` — длительность и необязательный заголовок через запятую (https://www.rfc-editor.org/rfc/rfc8216#section-4.3.2.1).
- Подпись — «Исполнитель — Название» (тире U+2014 с пробелами). Если одно из полей пусто — непустое поле. Если оба пусты — имя файла без расширения.
- Перевод строки `\n`, без BOM.
- Путь выбирается через `FilePicker` (ADR-10) с расширением по умолчанию `.m3u8`. Писатель пишет атомарно в каталоге выбранного файла (ADR-4) и отвечает номером попытки; ошибка — отдельное окно Error (ADR-13). `PersistTracker` экспорт не трогает.

**Что проверяет выбор.** Автотест ТЗ-13 а: ключ «Название ↑», Shuffle включён → пути в файле в видимом порядке, у каждого `#EXTINF`; `playlist.m3u` — 0 записей, флаг не изменился; две ошибки экспорта → два окна; успешный экспорт → 0 окон.

### ADR-18. Защита от сбоя

**Выполняет:** ТЗ-16, ТЗ-33 (текст подсказки); НФ-6. Решение 1; У-1.

**Контекст.** Решение 1: аварийной записи из panic-hook нет; `panic = "abort"` остаётся. Panic-hook при `panic = "abort"` выполняется (ревью §6), но решение 1 его для записи не использует.

**Варианты.** А — аварийная запись в panic-hook (отвергнуто решением 1); Б — без записи при сбое, границы потерь задают отложенная запись (ADR-3) и атомарность (ADR-4).

**Выбор: Б.**

- При сбое программа ничего не пишет. На диске каждый из трёх файлов — последняя успешно записанная версия целиком (ADR-4).
- Теряется:
  - изменения состояния сессии и плейлиста, не попавшие в последнюю отложенную запись: не больше N плюс время записи от первого незаписанного изменения (ADR-3); после неудачной записи файла — всё с момента первой неудачи до успешного «Повторить» (ТЗ-20);
  - открытый черновик диалога целиком.
- Настройки после завершённого «Сохранить» не теряются: запись идёт сразу (ADR-11). Если запись по «Сохранить» не удалась, о ней сообщает окно Error (ТЗ-28).
- **Подсказка параметра N** (ТЗ-33) по смыслу: «Через сколько секунд после первого изменения громкости, режима, колонок, сортировки, окна и плейлиста они сохраняются на диск. При аварийном завершении программы или отключении питания теряются изменения не старше этого интервала. Настройки из этого окна сохраняются сразу по кнопке „Сохранить“». Потерь при завершении сеанса ОС подсказка не описывает: перехват найден на всех платформах (ADR-7). Окончательный текст — модель данных (§2, заход 2).

**Что проверяет выбор.** Автотест ТЗ-16 на `MemStore`: изменить громкость, дождаться отложенной записи, изменить ещё раз, уничтожить приложение без пути выхода → в хранилище первое значение. Ручные сценарии ТЗ-16 (`kill -KILL` после N + 5 с и сразу).

### ADR-19. Изоляция тестов от файлов пользователя и счётчик записей

**Выполняет:** ТЗ-49, ТЗ-50, ТЗ-51 (основа перечня — заход 3). R-16; ТЗ-114 (01_audio_modes); ADR-20, ADR-22 (01_audio_modes).

**Контекст.**

- `MusicApp::new` сейчас сам находит каталог настроек (`config_dir()`, `src/settings.rs:1192-1201`), пишет `settings.toml` при загрузке (`:1136-1139`), запускает трей (`src/app/mod.rs:381`) и поток стартовой загрузки (`:373-378`). Тест `bp_report_marks_volume_issue` (`src/app/bp_report.rs:205-207`) создаёт `MusicApp` и этим перезаписывает настройки пользователя (R-16).
- 01_audio_modes называет `MemStore` фейком хранилища и ссылается на «`MemStore` задачи 02» (ADR-20, ADR-22 (01_audio_modes)); `PersistStore` движка хранит только `bp_tests.toml` и `track_marks.toml`, сигнатура трейта `PersistStore` в 01 не приведена.
- Для тестов `MusicApp` нужен экземпляр `AppWindow`, то есть платформа Slint. Headless-бэкенд в проекте не настроен (AGENTS.md, «Запуск с разными конфигурациями»).

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Тестировать `MusicApp` с `AppWindow` на тестовом бэкенде Slint (`i-slint-backend-testing`) | Новая dev-зависимость; каждый тест строит UI; логика остаётся переплетённой с Slint |
| Б | Логика приложения — в `AppCore` без Slint: действующие настройки и состояние, `PersistTracker`, черновик диалога, `Playlist`, `MessageCenter`, `UiGate`, `ExitCoordinator`, применение `VolumeCmd`. `MusicApp` — тонкая прослойка Slint: привязывает колбэки к командам `AppCore` и переносит изменения `AppCore` в свойства окна. Все внешние зависимости — в `AppDeps` | Автотесты всех строк §5.1 ТЗ выполняются без окна, без устройства и без файлов пользователя |
| В | Подменять только каталог настроек (`XDG_CONFIG_HOME` во временный каталог) | Тесты зависят от окружения и реальной ФС; ТЗ-49 запрещает переменные окружения в автотестах (§4 ТЗ, определение «автотест») |

**Критерии:** ТЗ-49 (ни одного обращения к каталогу пользователя, трею, стартовой загрузке); ТЗ-50 (записи каждого файла считаются); ТЗ-114 (01_audio_modes): без устройства.

**Выбор: Б.**

- `AppDeps` — все внешние зависимости `AppCore`:
  - `fs` — модуль ФС (ADR-6);
  - `paths` — каталог настроек и пути трёх файлов;
  - `lifecycle`, `input`, `notifier`, `picker`;
  - `clock` — `Clock` (01_audio_modes);
  - `journal` (ADR-21);
  - фабрика потока загрузки плейлиста (ADR-16);
  - отправитель команд движка (01_audio_modes).

  Реальные реализации собирает только `main.rs`; `config_dir()` вызывается только там.
- **`MemStore`** — подмена модуля ФС, хранящая файлы в памяти:
  - счётчики по каждому пути: записи, переименования, копии;
  - внедряемые ошибки по пути и шагу последовательности ADR-4;
  - задержки записи по `ManualClock`;
  - «содержимое на диске» для проверки после «сбоя».

  Писатель (ADR-1) в тестах работает с `MemStore` в своём потоке; тесты ждут его ответов детерминированно — через подменные часы и явную синхронизацию, без `sleep`.
- **Единая подмена для 01_audio_modes.** Реальный `PersistStore` движка пишет `bp_tests.toml` и `track_marks.toml` через тот же модуль ФС, а его тестовая реализация — через `MemStore`. Так «`MemStore` задачи 02» из ADR-22 (01_audio_modes) — тот же тип. Сигнатура `PersistStore` (её нет в 01) задаётся в §2 этой спецификации (заход 2) — замечание для §11.
- Подмены жизненного цикла и ввода трей не запускают; файлы тем создаются через модуль ФС, то есть в тестах — в `MemStore`.
- Тест `bp_report_marks_volume_issue` переписывается на `AppCore` с `MemStore`; полный перечень существующих тестов к переписыванию или удалению — §7 (заход 3).

**Последствия.**

- `MusicApp` теряет прямое владение настройками: «ромб» сохраняется, но поля переезжают в `AppCore`, а менеджеры `src/app/*` вызывают его команды. Это самая крупная структурная правка задачи; поэтапный переезд — §8 (заход 3).
- Проверка ТЗ-49: `cargo test` с каталогом настроек только для чтения проходит, каталог не меняется.

**Что проверяет выбор.** Приёмка ТЗ-49 (ручной прогон с каталогом только для чтения); по одному автотесту на каждую строку §5.1 ТЗ на `AppCore` + `MemStore` (ТЗ-50; таблица «строка → тест» — заход 3).

### ADR-20. Ввод-вывод и чтение тегов вне UI-потока

**Выполняет:** ТЗ-22, ТЗ-47, ТЗ-34 (очистка кэшей вне UI), ТЗ-13 (загрузка в фоне); НФ-4. R-13; ТЗ-103 (01_audio_modes).

**Контекст.**

- Сейчас в UI-потоке выполняются: запись настроек и плейлиста; синхронная загрузка плейлиста с зондированием каждого трека; чтение тем при открытии диалога и выборе; обход каталогов кэша каждые 100 мс при открытом диалоге (`src/app/mod.rs:1609-1611`); блокирующие диалоги выбора файлов (R-13).
- Фоновые потоки с каналами и разбором на тике уже есть: сканирование, обложки, полнотрековые визуализации (`drain_scan`, `drain_cover`, `drain_fulltrack`, `src/app/mod.rs:1594-1597`).

**Варианты.** А — по потоку на каждую задачу; Б — фиксированный набор потоков по видам работы с поколениями запросов; В — пул (новая зависимость или своя реализация).

**Критерии:** итерация цикла событий ≤ 50 мс, цель ≤ 16 мс (ТЗ-22, ТЗ-103 (01_audio_modes)); порядок операций одного вида; отбрасывание устаревших результатов.

**Выбор: Б.**

| Операция | Где выполняется |
|---|---|
| Запись `settings.toml`, `state.toml`, `playlist.m3u`, `*.bad`, переименование, экспорт | `apap-persist` (ADR-1) |
| Чтение и разбор плейлиста, теги, сортировка при загрузке | `apap-playlist` (ADR-16) |
| Чтение файла темы при открытии диалога и при выборе темы; подсчёт размера кэшей при открытии диалога и после очистки; очистка кэшей | `apap-io` — один поток с очередью заданий и поколением на вид задания |
| Чтение `settings.toml` и `state.toml` при запуске | `main` до создания окна (ADR-23): в перечне ТЗ-22 этой операции нет; так же решено в §6.2 п. 1 (01_audio_modes) |
| Выбор файлов | асинхронный rfd (ADR-10) |

- Результаты возвращаются по каналам и разбираются на тике 100 мс (как `drain_scan`). Ожидание результата не блокирует UI-поток; исключение — ожидание писателя на пути выхода (ADR-7).
- Данные темы, прочитанные при выборе в диалоге, хранятся в черновике и применяются по «Сохранить» без повторного чтения (ADR-11).
- Обход каталогов кэша на каждом тике удаляется: подсчёт — при открытии диалога и после очистки (ТЗ-22).
- **Замер бюджета.** Опоздание существующего 16-мс таймера `reflow` (`REF_INTERVAL_MS`, `src/main.rs:17`): итерация длиннее 50 мс сдвигает следующий запуск таймера не меньше чем на 34 мс. Метрика сценария — максимум «фактический интервал − 16 мс» плюс 16 мс. Инструментирование цикла событий через `slint::winit_030::CustomApplicationHandler` отвергнуто: эти типы разрешены только в модуле ввода (ТЗ-54). Замер — тест класса `perf` (сценарии ТЗ-22, ТЗ-47, ТЗ-53; заход 3).

**Последствия.** Синхронные `rfd::FileDialog`, `load_track_list` в обработчике меню и `sync_cache_stats_to_ui` на тике удаляются.

**Что проверяет выбор.** Замеры ТЗ-22 (запись при подменной задержке 2 с; диалог при кэше 10 000 файлов; очистка 10 000 файлов; загрузка 5 000 треков) → максимальная итерация ≤ 50 мс; автотест: диалог открыт 10 с → подсчёт размера кэша выполнен 1 раз.

### ADR-21. Журнал

**Выполняет:** ТЗ-5 (одна сводная запись на файл), ТЗ-7, ТЗ-14 (незаписанные файлы), ТЗ-20 (вид ошибки, текст ОС, путь), ТЗ-52 п. 3.

**Контекст.** Журнала как подсистемы нет: используется `eprintln!` в разных местах (например, `src/app/mod.rs:1567`, `:1693`). Автотесты должны считать записи журнала (ТЗ-5: «одна сводная запись», ТЗ-7: «одна запись журнала»). Бинарник на Windows собирается с `windows_subsystem = "windows"` в релизе (`src/main.rs:1`), поэтому stderr релизной сборки на Windows пользователь не видит.

**Варианты.** А — `eprintln!` по месту; Б — трейт `Journal` с реализацией по умолчанию и подменой, считающей записи; В — крейт `log` или `tracing` (новая зависимость).

**Критерии:** тесты считают записи; без новых зависимостей; журнал не используется в аудио-колбэке (AGENTS.md, «Запрет на … логирование в аудио-потоке»).

**Выбор: Б.** `Journal { fn record(&self, rec: JournalRecord) }`. `JournalRecord` — типизированная запись: заметки разбора файла (список `LoadNote` одной записью), ошибка записи (файл, класс, текст ОС, путь), итог пути выхода (записанные и незаписанные файлы) и т. п. Реализация по умолчанию пишет в stderr. Подмена `VecJournal` накапливает записи для тестов. Куда пишет журнал релизная сборка на Windows — **отложено до ОВС-4**.

**Последствия.** `eprintln!` в коде, который трогает задача 02, заменяется вызовами `Journal`. Остальной код — вне объёма.

**Что проверяет выбор.** Автотесты ТЗ-5, ТЗ-7, ТЗ-14, ТЗ-20 проверяют число и содержимое записей `VecJournal`.

### ADR-22. Источник изменения состояния: пользователь или программа

**Выполняет:** ТЗ-11 (отсчёт только от пользовательских изменений), ТЗ-4. ОВ-3; ADR-3.

**Контекст.**

- ОВ-3: отсчёт N запускают изменения из событий ввода и окна после первого показа главного окна. Значения, которые присваивает программа (восстановление геометрии, коррекции загрузки, пересчёт до первого показа), меняют состояние без отсчёта. Событие окна, повторяющее только что выставленное программой значение, изменением не считается.
- Сейчас геометрия опрашивается на тике (`track_window_geometry`, `src/app/ui_manager.rs:73-107`), ширины колонок пересчитываются после изменения ширины окна (`reflow`, `src/app/mod.rs:1637-1654`).
- На Wayland положение окна программе недоступно: `Window::outer_position` всегда возвращает `NotSupportedError` (`winit-0.30.13/src/window.rs:694-699`, `platform_impl/linux/wayland/window/mod.rs:263-265`).

**Варианты.** А — признак «пользовательское» вычисляется по месту в каждом обработчике; Б — каждое изменение состояния проходит через одну функцию с явным `Origin`, а значения, выставленные программой, запоминаются для подавления «эха».

**Критерии:** ОВ-3; приёмка ТЗ-11 «запуск без действий, 10 мин, выход → 0 записей»; «изменение размера окна пользователем → одна запись через N с».

**Выбор: Б.**

- Изменения состояния сессии идут через `AppCore` с `Origin::User` или `Origin::Program`. До первого показа главного окна любое изменение — `Program`.
- Источники `User`: обработчики ввода (ползунки, колёсико, меню, клавиши, заголовки таблицы, трей), выбор каталога в системном диалоге, изменения окна, вызванные пользователем.
- Пересчёт ширин колонок наследует источник изменения размера окна, за которым он следует (§5.1 ТЗ: «включая пересчёт ширин вслед за изменением размера окна пользователем»).
- Программа запоминает значения, которые выставила сама (геометрия при восстановлении, ширины при пересчёте). Показание, равное запомненному значению, изменением не считается («эхо», ОВ-3).
- Положение окна на Wayland не читается, поэтому не меняется: в `state.toml` остаётся прежнее значение.
- Как отличить перемещение или изменение размера окна пользователем от размещения окна оконным менеджером сразу после показа, когда менеджер не выполнил запрошенную программой геометрию, — **отложено до ОВС-5**.

**Что проверяет выбор.** Автотесты ТЗ-11: запуск с полным корректным `state.toml`, подменное окно без действий, 10 мин по `ManualClock`, выход → 0 записей `state.toml`; изменение размера окна с `Origin::User` → одна запись через N с; восстановление геометрии → 0 запусков отсчёта.

### ADR-23. Порядок запуска

**Выполняет:** ТЗ-1 (по одному чтению каждого файла), ТЗ-4, ТЗ-6, ТЗ-7 (сообщение после первого показа), ТЗ-21, ТЗ-47 (окно не ждёт загрузки), ТЗ-52 (сообщения до первого показа). §6.2 п. 1 (01_audio_modes).

**Контекст.** Сейчас `main` создаёт окно, `MusicApp::new` читает и пишет `settings.toml`, запускает трей и загрузку, затем `ui.show().unwrap()` и повторное применение геометрии (`src/main.rs:22-79`). 01_audio_modes требует, чтобы `ModeSettings` и `PlaybackState` были прочитаны до первой итерации цикла событий (§6.2 п. 1 (01_audio_modes)).

**Выбор.** Последовательность `main`:

1. Выбор бэкенда winit (ADR-8).
2. Чтение `settings.toml` и `state.toml` через модуль ФС, по одному разу (ТЗ-1); разбор (ADR-2) без записи (ТЗ-4). Байты неразбираемых файлов сохраняются для копий `*.bad`.
3. Запуск писателя `apap-persist` с эталонными текстами и копиями `*.bad`; писатель сразу пишет копии (ADR-2). Сообщения (Warning о `settings.toml`) и сводные записи журнала ставятся в очередь `MessageCenter` (ADR-13).
4. Создание `AppWindow`; регистрация фильтра ввода (ADR-8); `AppCore` и `MusicApp` с `AppDeps`.
5. Применение настроек к UI и программное восстановление геометрии (`Origin::Program`, ADR-22); `EngineCmd::SetModeSettings { diff: None }`, `SetActiveMode`, `SetVolume`, `SetMuted` (§6.2 п. 4 (01_audio_modes)).
6. Показ окна; ошибка показа — запись журнала и выход с кодом ошибки, без `unwrap`. Повторное применение геометрии после показа (оконная система принимает размер и положение только после создания поверхности, `src/main.rs:71-75`).
7. Признак «окно показано» в `MessageCenter` (очередь начинает показываться) и в `AppCore` (начинается учёт `Origin::User`).
8. Установка перехватов жизненного цикла, которым нужен HWND или зарегистрированный делегат (ADR-7); поток `apap-signals`; трей (Linux).
9. Запуск стартовой загрузки плейлиста (ADR-16, ADR-5): сообщения о случаях 2 и 3 ОВ-8 приходят уже после показа.
10. Цикл событий.

**Последствия.** Порядок шагов 7 и 9 гарантирует, что окно появляется, не дожидаясь загрузки (ТЗ-47), а сообщения, возникшие до показа, показываются после него (ТЗ-52).

**Что проверяет выбор.** Автотесты ТЗ-1 (по одному чтению), ТЗ-4 (0 записей при запуске в трёх вариантах файлов), ТЗ-7 (окно Warning только после показа); замер ТЗ-47 (первый кадр).

### ОВС-1. Инерция тачпада на macOS

- **Контекст.** ТЗ-36 (данные таблицы, macOS): «инерционные события после окончания жеста игнорируются»; ОВ-11 так же. winit 0.30.13 отображает `momentumPhase` Began/Ended в те же `TouchPhase::Started`/`Ended`, что и фазу пальцев, а события середины инерции — в `Moved` (`winit-0.30.13/src/platform_impl/macos/view.rs:683-691`). Отдельного признака инерции нет (`wheel_test.md` §2, §4.6). Последовательность одного жеста с броском выглядит как `Started, Moved…, Ended, Started, Moved…, Ended` — так же, как два жеста подряд. Замеров macOS нет (`wheel_test.md` §6). ADR-8 без решения этого вопроса не выполняет ТЗ-36 для macOS.
- **Варианты.**
  - **а) Локальный монитор событий AppKit.** Модуль ввода (только macOS) ставит `+[NSEvent addLocalMonitorForEventsMatchingMask:handler:]` на `NSEventMaskScrollWheel` (https://developer.apple.com/documentation/appkit/nsevent/addlocalmonitorforevents(matching:handler:)). Обработчик вызывается до отправки события окну, видит `momentumPhase` и возвращает событие без изменений. Модуль отмечает «инерция / не инерция» для ближайшего события winit (сопоставление по порядку, как в ADR-8), и инерционные события громкость не меняют. Нестабильный API winit не нужен; нужны `objc2-app-kit` (уже в дереве на macOS) и `unsafe`-блок. Не подтверждено на macOS — проверка при первом замере на macOS.
  - **б) Эвристика по фазам winit.** Новый `Started` сразу после `Ended` считается началом инерции. Нужен порог «сразу», которого нет ни в ТЗ, ни в эксперименте; быстрый повторный жест неотличим от инерции.
  - **в) Ограничение K на свайп, как на Windows** (В-4), без отбрасывания инерции. **Меняет требование ТЗ-36** для macOS («инерционные события игнорируются» → «инерция ограничена K»). Допустимо только решением пользователя с поправкой ТЗ.
  - **г) Подмена метода `scrollWheel:` класса представления winit** (swizzling). Даёт `NSEvent` напрямую, но вмешивается в класс winit; ломается при изменении winit сильнее, чем а).
- **Рекомендация: а).** Это документированный механизм AppKit, он не трогает winit и даёт ровно тот признак, который требует ТЗ-36. Риск — работа без проверки на оборудовании. На этот случай таблица данных macOS сохраняет пометку «по документации платформы, не подтверждено экспериментом» (ТЗ-36), а автотест на синтетической последовательности «жест + инерция» проверяет логику модуля.

### ОВС-2. Параметры тачпада в правиле по умолчанию

- **Контекст.** ТЗ-36: для платформ, сеансов и классов без данных эксперимента (KDE X11, GNOME X11, тачпад с точными дельтами на Linux, macOS) — «правило по умолчанию: событие колеса мыши — один щелчок, пиксельные дельты накапливаются до порога»; для macOS — «порог тачпада — значение по умолчанию». Числа порога нет ни в ТЗ, ни в решениях. Кроме того, ТЗ-36 п. 2 требует для класса «тачпад»: «одно движение не даёт десятков шагов». Одно накопление до порога без ограничения на свайп даёт на быстром свайпе с инерцией десятки и сотни шагов при любом пороге (`wheel_test.md` §5.2: тачпад Windows без K — 142…703 шага на быстрый свайп). На macOS при варианте а) ОВС-1 инерция отбрасывается, но жест пальцами всё равно может дать много шагов. Перевод пикселей в строки — множитель 60 бэкенда Slint (`i-slint-backend-winit-1.17.1/event_loop.rs:403`).
- **Варианты.**
  - **а) Как тачпад Windows** (В-4): T = 0,5 строки (30 логических px), не более K = 5 шагов на свайп, граница свайпа — пауза больше 300 мс, остаток после неё сбрасывается. Числа — из решения В-4, применённого как значение по умолчанию.
  - **б) T = 1 строка (60 логических px), K = 5, пауза 300 мс** — «щелчок тачпада = щелчок мыши» (вариант а `wheel_test.md` §7.4, В-4). Короткий свайп чаще даёт 0 шагов (`wheel_test.md` §5.2, столбец `T=1, K=5`).
  - **в) Только порог, без K** — буквальное «накопление до порога». Нарушает ТЗ-36 п. 2 на быстрых свайпах.
- **Рекомендация: а).** Одинаковое поведение тачпада на всех платформах без данных и на Windows; числа уже утверждены пользователем (В-4); условие ТЗ-36 п. 2 выполняется. После замеров (`wheel_test.md` §7.3) меняются только строки таблицы (НФ-8).

### ОВС-3. Нормализация Unicode и приведение регистра при сортировке

- **Контекст.** ТЗ-43 (ОВ-13 б, расширенный): текст сравнивается «без учёта регистра, после приведения к одной форме Unicode». Std Rust нормализации Unicode не даёт; `str::to_lowercase` в std есть — это приведение к нижнему регистру по Unicode, не полная свёртка регистра (`ß` остаётся `ß`). В `Cargo.lock` уже есть `icu_normalizer` 2.3.0, транзитивно через `ureq` → `url` → `idna` 1.1.0 → `idna_adapter` 1.2.2 (`Cargo.lock:2201-2208`). Какие features `icu_normalizer` включены в текущем дереве, по `Cargo.lock` не видно (нужна `compiled_data` для встроенных таблиц) — при прямой зависимости features задаются явно. Обоснование ОВ-13 б в ТЗ упоминало «без новых зависимостей», а расширенное решение добавило нормализацию.
- **Варианты.**
  - **а) `icu_normalizer` 2.3 прямой зависимостью** (та же версия, что в `Cargo.lock`), форма NFC; регистр — `str::to_lowercase`. Новых крейтов в `Cargo.lock` нет.
  - **б) Крейт `unicode-normalization`** (NFC) + `str::to_lowercase`. Новый крейт в `Cargo.lock`, зато небольшой API без данных ICU4X.
  - **в) Без нормализации**, только `str::to_lowercase`. **Меняет ТЗ-43** («после приведения к одной форме Unicode»): одно название в составной и разложенной формах сортируется как разные строки.
  - Дополнительно — выбор формы: **NFC** (каноническая эквивалентность: «é» одним символом и «e» + комбинируемый акцент совпадают) или **NFKC** (ещё и совместимая: лигатуры, полноширинные цифры — «１２» как «12»). Приёмка ТЗ-43 требует только «одно название в двух формах Unicode»; NFKC меняет больше, чем требуется.
- **Рекомендация: а), NFC.** Без новых крейтов в сборке; NFC достаточна для приёмки ТЗ-43 и не меняет видимые различия символов. Сравнение цифр как чисел («No. 9» < «No. 10») — собственный компаратор без зависимостей: `natord` в `Cargo.lock` есть только как зависимость сборки `.slint` (`rspolib`).

### ОВС-4. Куда пишет журнал релизная сборка на Windows

- **Контекст.** ТЗ-5, ТЗ-7, ТЗ-14, ТЗ-20 требуют записей журнала, но ТЗ не определяет, где журнал. Сейчас журнал — stderr (`eprintln!`). Релизная сборка на Windows — приложение подсистемы `windows` (`src/main.rs:1`): консоли нет, stderr не виден, а пользователь работает на Windows-ноутбуке. Всё, что пользователь обязан увидеть, уже идёт в окно сообщения (ТЗ-52); журнал — диагностика (например, «какие файлы не записаны при выходе», ТЗ-14).
- **Варианты.**
  - **а) stderr на всех ОС** (как сейчас). На Windows в релизе журнал фактически недоступен; при запуске из консоли или отладочной сборки — виден.
  - **б) Файл журнала в каталоге настроек** (например, `apap.log`), запись в фоновом потоке, ограничение размера с заменой. Новый файл данных и новый путь записи, которых ТЗ не перечисляет (§5.1); нужны числа (предельный размер, число старых файлов), которых нет в ТЗ, — их задаёт пользователь.
  - **в) stderr + `OutputDebugStringW` на Windows.** Журнал виден в отладчике или DebugView без нового файла; обычному пользователю без инструментов не виден.
- **Рекомендация: а).** Не вводит новых файлов и чисел; требования ТЗ к журналу (содержание и число записей) проверяются автотестами через `VecJournal` (ADR-21) независимо от приёмника. Если журнал на Windows нужен пользователю для диагностики, — б) отдельной задачей с числами пользователя.

### ОВС-5. Пользовательское или программное изменение геометрии окна

- **Контекст.** ОВ-3: геометрия, которую восстанавливает программа, отсчёт N не запускает; «событие окна, повторяющее только что выставленное программой значение, изменением не считается»; изменение размера окна пользователем запускает N. Геометрия известна программе только опросом (`window().size()`, `position()`, `is_maximized()`, `is_fullscreen()`; `src/app/ui_manager.rs:73-107`); событий «окно перемещено пользователем» в публичном API Slint нет. Оконный менеджер может разместить окно не там и не того размера, что запросила программа, и сделать это через несколько кадров после показа. Например, на X11 позиция с рамкой и без неё различается; некоторые менеджеры двигают окно при наложении на панели. Такое показание не равно выставленному программой и выглядит как изменение пользователем. Тогда при запуске без действий пользователя через N с записывается `state.toml` — это нарушает приёмку ТЗ-11 «запуск без действий, 10 мин, выход → 0 записей» (на реальной машине; на подменах тест проходит). На Wayland положение не читается вовсе (ADR-22).
- **Варианты.**
  - **а) Первое показание после показа — программное.** Первое показание геометрии после первого показа окна принимается как эхо программной установки, каким бы оно ни было; последующие изменения — пользовательские. Оконный менеджер, который двигает окно позже первого показания, даёт одну лишнюю запись `state.toml` за запуск, с верной геометрией.
  - **б) Положение окна не запускает N.** Изменения положения меняют состояние в памяти и попадают в файл со следующей записью или при выходе; размер, «развёрнуто» и полноэкранный режим запускают N. **Меняет требование** §5.1 ТЗ для положения («геометрия окна — изменение пользователем → N») — только решением пользователя.
  - **в) Период установления после показа.** Изменения в течение заданного времени после первого показа — программные. Нужно число, которого нет в ТЗ и эксперименте; оконный менеджер может уложиться в него не всегда.
  - **г) Признак пользовательского действия от оконной системы** — события winit `Moved`/`Resized` не отличают действие пользователя от действия менеджера (документация `winit::event::WindowEvent`); в Slint этих событий нет. Не решает вопрос.
- **Рекомендация: а).** Не меняет требований и не вводит чисел; худший случай — одна лишняя запись с правильным содержимым за запуск на части оконных менеджеров. Ручной сценарий ТЗ-11 на Linux X11, Linux Wayland, Windows фиксирует фактическое число записей при запуске без действий в протоколе приёмки.

## 11. Замечания для следующей сессии поправок 01_audio_modes

*Заход 3.* Найдено в заходе 1 (сводный список с местами в 01 — в заходе 3):

- §6.28 (01_audio_modes): сигналы обрабатываются в отдельном потоке `apap-signals`, а не в рантайме трея (трея нет на macOS; рантайм трея завершается без хоста StatusNotifierItem); добавлены `SIGHUP`, завершение сеанса Windows, запрос завершения macOS (ADR-7; уже отмечено в ТЗ §8).
- ADR-20, ADR-22 (01_audio_modes): сигнатура трейта `PersistStore` в 01 не задана; `MemStore` — общая подмена модуля ФС задачи 02, через которую работает и `PersistStore` движка (ADR-19).
- ADR-19 (01_audio_modes): `bp_tests.toml` и `track_marks.toml` пишутся «во временный файл, затем `rename`» без `fsync`; при переходе `PersistStore` на модуль ФС задачи 02 они получают ту же долговечную запись (ADR-4) — уточнить текст ADR-19 (01_audio_modes).
- ТЗ-13 б: в модели 01 нет заранее открытого следующего трека; если он появится (gapless между треками), его отмена при «Загрузить плейлист» — в шаге смены поколения `Open` (ADR-16).
