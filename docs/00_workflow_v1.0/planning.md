# Планирование сессии (WF1.0)

Применяется в начале каждой сессии и сразу после регистрации задачи из
чата (`task_intake.md`) — до первой правки. Цикл самого шага —
`execution.md`.

## 1. Режим сессии

По `_STATE_.yaml` (прочитан по правилу начала сессии, `AGENTS.md`):

- **`status: done`** или файла нет → «Новая задача»: источник задачи — §3.
- **`status: in_progress`** → «Продолжение»: открытая сессия доводится до
  закрытия первой. Возьми `task`, `current_step`, `next_action`,
  `whitelist`; сообщи: «Вхожу в режим Продолжения. Текущий шаг:
  `<description current_step>`. Работаю со следующими файлами:
  `<whitelist>`» — и продолжай именно `current_step`, не пересчитывая план.
- Пункт `plan.items` со `status: in_progress` — долгоиграющая работа
  пользователя поверх сессий: сообщи о ней в любом режиме; когда открытой
  сессии нет, её следующий этап и есть задача сессии (§3 (б)).

## 2. Проверка репозитория (до любой правки)

1. `git status --porcelain`. Есть незакоммиченные изменения:
   - «Новая задача» → СТОП: «Репозиторий содержит незакоммиченные
     изменения. Пожалуйста, выберите действие: 1) Сделать WIP-коммит,
     2) Выполнить git stash, 3) Отменить изменения (git reset). Ожидаю
     вашей команды.» Без явного выбора пользователя — не продолжать.
   - «Продолжение» → `python tools/state_tool.py check-whitelist` (чистое
     дерево — норма: шаг прерван после коммита). Зелёный — продолжай; файл
     вне вайтлиста — СТОП: «Внимание! Обнаружено расхождение между Git и
     файлом состояния сессии. Требуется ручное вмешательство.» Ничего не
     менять.
2. `cargo check --quiet`.
   - «Продолжение» с незакоммиченными правками шага — красная сборка
     ожидаема (прерванный шаг): продолжай по `execution.md`, счётчик
     провалов — `fail_counter`.
   - Иначе красный → СТОП: файлы не меняются, пока пользователь не выберет:
     1) диагностика — только чтение; в чат: файл, строка, функция, причина
        и дифф-решение, затем вопрос «Применить?»;
     2) ручной ремонт пользователем — после «готово» повтори проверку.
   - Применение после «Да»: в «Новой задаче» — как задача из чата
     (`task_intake.md`, сессия из одного шага); в «Продолжении» — шагом
     текущей сессии (ID коммита — текущей задачи, причина — в описании
     шага, вайтлист — по `execution.md` §1). Причина вне текущей задачи
     (например, ветка `cfg` другой ОС) — дополнительно B-строка
     `⬜ открыто` для учёта.

## 3. Выбор задачи («Новая задача»)

- **(а) Задача из чата** — уже зарегистрирована по `task_intake.md`
  (B-строка `🔄`).
- **(б) Этап спецификации** — строка ROADMAP со статусом `🔄` с префиксом
  спеки, названной в `description` пункта `plan.items` со
  `status: in_progress` (пункт может вести несколько спек по сквозному
  порядку). Строка `🔄` при `status: done` — брошенная сессия: сообщи
  пользователю и бери её заново. Строки `🔄` нет — первая `⬜` по разделу
  «Сквозной порядок этапов» `ROADMAP.md`, а если он не задан — по порядку
  таблицы спецификации. Не осталось `⬜` — спека (или все спеки пункта)
  готова к закрытию (`spec_closing.md`), сообщи пользователю. Выбранному
  этапу поставь `🔄 выполняется`.

Если в `note` пункта плана есть «ВОПРОС ПОЛЬЗОВАТЕЛЮ» к выбранному этапу —
задай его до декомпозиции и жди ответа; вопросы к другим этапам не
блокируют, но упомяни их при старте.

## 4. Что прочитать из спецификации перед этапом

Только относящееся к этапу:

- строку этапа в таблице «Этапы внедрения» (§8): содержание, ТЗ-N, что
  работает после этапа, что удаляется;
- перечисленные в ней ТЗ-N (с решениями ОВ/ОВС, которые на них
  ссылаются) и ADR-N;
- разделы спеки именно по этим ТЗ/ADR (модель данных, путь сигнала,
  инварианты, алгоритмы, тесты) — по ссылке на раздел, не постранично.

## 5. Микро-декомпозиция

Разбей задачу на шаги `_STATE_.yaml:steps`, соблюдая:

- **Одна сущность на шаг** — запрещены шаги с «и»/«+» («маппинг и UI»,
  «логика и тесты»); ровно одна изолированная подзадача. Исключение —
  закреплённый текст в ТЗ и в коде (`task_intake.md` §5): одна сущность.
- **Локализация** — не более 1–2 файлов кода на шаг; 3–4 — разбить на
  подшаги; смена типа, задевающая больше 2–3 файлов, — через временный
  мост (адаптер старое↔новое), который убирается отдельным шагом очистки.
- **Объём** — одна сущность (тип/функция) со связанными правками;
  ≤ ~5 новых тестов за шаг (остальные — отдельным шагом «тесты для X,
  ч. 2»); ≤ ~5–6 изменяемых функций; ~200 строк диффа. Превышение любого
  порога — сигнал разбить шаг, даже если файл один.
- **DoD на каждом шаге** — техническая проверка в `description`:
  «Добавить поле в Settings. Проверка: cargo check без ошибок».
- **Трассируемость** — какие ТЗ-N/ADR-N/§ шаг выполняет.
- **ЧЕКПОИНТ** — отдельный шаг каждые 2–3 кодовых шага и перед закрытием
  задачи (состав проверок — `execution.md` §3).
- Одна активная задача — одна строка `🔄`; крупный этап переживает
  несколько сессий через `steps`/`current_step`.

## 6. Запись сессии в `_STATE_.yaml`

Поля (схема — `tools/schema/state.schema.json`):

- `status: in_progress`;
- `task.roadmap_id`, `task.title` — ID и название строки ROADMAP;
- `whitelist` — только файлы, которые физически нужно менять для плана;
  `hooks/pre-commit` (`check-whitelist`) блокирует коммит с изменением вне
  списка. `_STATE_.yaml`, `_STATE_.md`, `ROADMAP.md` и
  `docs/acceptance/*/results-*.yaml` проверкой не ограничиваются —
  вносить их не нужно;
- `dod` — критерий готовности всей задачи целиком (не шага);
- `steps[]` — список `{id, description, done}` по правилам §5;
- `current_step` — id шага в работе;
- `next_action` — что делать прямо сейчас, одной фразой;
- `fail_counter: 0`, `fail_counter_max: 3`, `failed_attempts: []`;
- `plan` — состав полей не трогать, кроме точечной правки `note`/`status`
  нужного пункта; поле переживает `status: done`.

Пример (имена и описания условны):

```yaml
status: in_progress
task:
  roadmap_id: AM1.0-8.7
  title: "С7 (01). DSP-корректность"
whitelist:
  - src/audio/dsp.rs
dod: "cargo test audio:: зелёный; TPDF не меняет RMS сигнала тишины"
steps:
  - id: 1
    description: "TpdfDither: структура и LCG-генератор (§6.16, ТЗ-8). Проверка: cargo check"
    done: false
current_step: 1
next_action: "Добавить struct TpdfDither в src/audio/dsp.rs"
fail_counter: 0
fail_counter_max: 3
failed_attempts: []
```

После записи: `python tools/state_tool.py render`, затем
`python tools/state_tool.py check` и `python tools/traceability_tool.py check`
— оба зелёные перед тем, как показывать план пользователю.

## 7. Регистрационный коммит и подтверждение

Отдельный коммит без кода — только `ROADMAP.md` (статус `🔄`, для задачи
из чата — новая B-строка) и `_STATE_.yaml`/`_STATE_.md`
(`chore(state): start <ID> session`). Затем выведи пользователю микро-план
и вайтлист:

> «План микро-сессии сформирован. Вайтлист файлов заблокирован. Готов
> приступить к Шагу 1.»

- **Задача из чата** — код не пишется до подтверждения пользователя;
  после подтверждения — `execution.md`.
- **Этап спецификации** (§3 (б)) — подтверждение не ждётся: выведи план и
  сразу переходи к `execution.md`. Пользователь может остановить или
  поправить план в любой момент.
