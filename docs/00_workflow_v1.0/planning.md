# Планирование сессии (WF1.0)

Применяется в начале каждой сессии (режимы «Продолжение»/«Новая задача») и
сразу после регистрации задачи из чата (`task_intake.md` §7) — до первой
правки кода. Цикл самого шага (вайтлист при правке, верификация, коммит,
откат при 3/3) — в `execution.md`.

## 1. Где живёт состояние

`_STATE_.yaml` — единственный источник состояния микро-сессии. `_STATE_.md`
генерируется из него командой `python tools/state_tool.py render` и руками
не правится (блокирует pre-commit); он для человека, агент его не читает.
Других файлов состояния (`plan-*.md`, `.current-plan.json` и т. п.) не
создавать. Между машинами переносится только git: `git pull` в начале
сессии, коммит и push после каждого завершённого шага.

## 2. Старт сессии

Прочитай `_STATE_.yaml` и определи режим:

- **`status: done`** (или файла нет) → режим «Новая задача»: источник задачи —
  §3 ниже.
- **`status: in_progress`** → режим «Продолжение»: возьми `task`,
  `current_step`, `next_action`, `whitelist`; сообщи пользователю:
  «Вхожу в режим Продолжения. Текущий шаг: `<description current_step>`.
  Работаю со следующими файлами: `<whitelist>`» — и продолжай именно
  `current_step`, не пересчитывая план заново.
- Если в `plan.items` есть пункт со `status: in_progress` — это текущая
  долгоиграющая работа пользователя поверх сессий; сообщи о ней (её активный
  этап — строка `🔄` в `ROADMAP.md`) независимо от режима выше.

Проверка репозитория (до любой правки):

1. `git status --porcelain`. Если есть незакоммиченные изменения:
   - в «Новой задаче» — СТОП: «Репозиторий содержит незакоммиченные
     изменения. Пожалуйста, выберите действие: 1) Сделать WIP-коммит,
     2) Выполнить git stash, 3) Отменить изменения (git reset). Ожидаю
     вашей команды.» Без явного выбора пользователя — не продолжать.
   - в «Продолжении» — сверь список изменённых файлов с `whitelist`; при
     полном совпадении продолжай, при любом расхождении — СТОП: «Внимание!
     Обнаружено расхождение между Git и файлом состояния сессии. Требуется
     ручное вмешательство.» Ничего не менять.
2. `cargo check --quiet`. Красный до начала работы — СТОП, режим «Чтение»:
   предложи диагностику (только чтение: найти причину — файл, строка,
   функция; показать дифф-решение) или ручной ремонт пользователем. На «Да»
   исправление регистрируется как задача из чата: B-строка
   (`task_intake.md`) и сессия из одного шага. Если открыта другая сессия
   («Продолжение»), её `_STATE_.yaml` не перезаписывается: как совместить
   (шаг в текущей сессии с расширением вайтлиста или отдельная сессия
   после неё) — решает пользователь.

## 3. Выбор задачи

- **(а) Задача из чата** — уже зарегистрирована по `task_intake.md`
  (B-строка в ROADMAP).
- **(б) Активный этап спецификации** — строка ROADMAP со статусом `🔄`
  внутри пункта `plan.items` со `status: in_progress`; если такой строки
  нет — первая `⬜` по «сквозному порядку» (раздел ROADMAP, когда для
  нескольких спецификаций задан общий порядок этапов), иначе — первая `⬜`
  по порядку таблицы своей спецификации. Порядок этапов **внутри** одной
  спецификации не меняется; порядок **между** спецификациями может быть
  переопределён только отдельным разделом сквозного порядка в ROADMAP (не
  явочным путём).

## 4. Что прочитать из спецификации перед этапом

Только то, что относится к этапу — не весь документ:

- строку этапа в таблице «Этапы внедрения» (§8 спецификации): содержание,
  ТЗ-N, что работает после этапа, что удаляется;
- перечисленные в ней ТЗ-N (вместе с решениями ОВ/ОВС, которые на них
  ссылаются) и ADR-N;
- разделы спецификации, относящиеся именно к этим ТЗ/ADR: модель данных,
  модель пути сигнала, инварианты, алгоритмы, тесты — по ссылке на раздел,
  не постранично.

Дефект вне текущего этапа, найденный по дороге — не чинить молча: B-строка
со статусом `⬜ открыто` в ROADMAP (`task_intake.md` §8), и дальше по плану
текущего этапа.

## 5. Статус в ROADMAP

Выбранному этапу/багу — статус `🔄 выполняется` точечной правкой одной
строки, не задевая соседние строки таблицы.

## 6. Микро-декомпозиция

Разбей задачу на шаги `_STATE_.yaml:steps`, соблюдая:

- **Одна сущность на шаг** — запрещены шаги с «и»/«+» («маппинг и UI»,
  «логика и тесты»); ровно одна изолированная подзадача.
- **Локализация** — не более 1–2 файлов кода на шаг; если выходит 3–4 —
  разбить на подшаги, при смене типа, задевающей больше 2–3 файлов —
  через временный мост (адаптер старое↔новое), который убирается отдельным
  шагом очистки.
- **Объём** — помимо числа файлов: одна сущность (тип/функция) со
  связанными правками; ≤ ~5 новых тестов за шаг (остальные — отдельным
  шагом «тесты для X, ч. 2»); ≤ ~5–6 изменяемых функций; ~200 строк диффа.
  Превышение любого из порогов — сигнал разбить шаг, даже если файл один.
- **DoD на каждом шаге** — техническая проверка в `description`, например
  «Добавить поле в Settings. Проверка: cargo check без ошибок».
- **Трассируемость** — какие ТЗ-N/ADR-N/§ шаг выполняет.
- **ЧЕКПОИНТ каждые 2–3 кодовых шага** и обязательно перед закрытием этапа
  (полный `cargo test` + `cargo clippy`; детали прогона — `execution.md`).
- В `_STATE_.yaml` держится только одна активная задача — одна строка `🔄`;
  крупный этап переживает несколько сессий через `steps`/`current_step`.

## 7. Запись сессии в `_STATE_.yaml`

Поля (схема — `tools/schema/state.schema.json`):

- `status: in_progress`;
- `task.roadmap_id`, `task.title` — ID и название строки ROADMAP;
- `whitelist` — только файлы, которые физически нужно менять для плана,
  плюс `_STATE_.yaml`/`_STATE_.md` и `ROADMAP.md`, когда их тоже правишь на
  этом шаге; `pre-commit check-whitelist` блокирует всё остальное;
- `dod` — критерий готовности всей задачи целиком (не шага);
- `steps[]` — список `{id, description, done}` по правилам §6;
- `current_step` — id шага в работе;
- `next_action` — что делать прямо сейчас, одной фразой;
- `fail_counter: 0`, `fail_counter_max: 3`, `failed_attempts: []`;
- `plan` — не трогать состав полей, кроме точечной правки `note`/`status`
  нужного пункта; это поле переживает `status: done` и не очищается при
  консервации сессии.

Пример (имена и описания условны):

```yaml
status: in_progress
task:
  roadmap_id: AM1.0-8.7
  title: "С7 (01). DSP-корректность"
whitelist:
  - src/audio/dsp.rs
  - _STATE_.yaml
  - _STATE_.md
dod: "cargo test audio:: зелёный; TPDF не меняет RMS сигнала тишины"
steps:
  - id: 1
    description: "TpdfDither: структура и LCG-генератор (§6.16, ТЗ-8). Проверка: cargo check"
    done: false
current_step: 1
next_action: "Добавить struct TpdfDither в src/audio/dsp.rs"
fail_counter: 0
fail_counter_max: 3
failed_attempts: []
```

После записи: `python tools/state_tool.py render`, затем
`python tools/state_tool.py check` и `python tools/traceability_tool.py check`
— оба зелёные перед тем, как показывать план пользователю.

## 8. Регистрационный коммит и подтверждение

Сделай отдельный коммит без кода — только ROADMAP (статус `🔄`) и файлы
состояния (`_STATE_.yaml`/`_STATE_.md`). Затем выведи пользователю
сформированный микро-план и вайтлист и скажи:

> «План микро-сессии сформирован. Вайтлист файлов заблокирован. Готов
> приступить к Шагу 1.»

- **Задача из чата** (`task_intake.md`) — код не пишется до подтверждения
  пользователя; после подтверждения — `execution.md`.
- **Этап спецификации** по сквозному порядку (`§3 (б)`) — подтверждение не
  ждётся: выведи план и сразу переходи к `execution.md`. Пользователь может
  остановить или поправить план в любой момент.
