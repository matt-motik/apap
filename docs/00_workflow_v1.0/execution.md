# Выполнение шага (WF1.0)

Цикл каждого микро-шага `_STATE_.yaml:steps` — от первой правки текущего
шага до коммита или отката.

## 1. Вайтлист перед правкой

Перед правкой любого файла убедись, что он в `whitelist` `_STATE_.yaml`.
Файла там нет — запись инструментом запрещена; `hooks/pre-commit`
(`check-whitelist`) блокирует коммит с изменением вне списка (файлы
состояния и `ROADMAP.md` не ограничиваются — `planning.md` §6).

Нужен файл вне списка — первым делом не расширение вайтлиста, а разбиение
шага по правилам локализации (`planning.md` §5): перепиши шаги в
`_STATE_.yaml` (подшаги, сквозная перенумерация следующих шагов и ссылок),
внеси только недостающие для подшагов файлы и сообщи об этом пользователю.
Если файл всё равно нужен шире плана — спроси разрешения, не расширяй
вайтлист молча.

## 2. Правка

Правь `current_step`. Без заглушек: `// TODO`, «…остальной код» и подобные
обрывы запрещены; не удаляй существующие функции, если об этом не просили
прямо. В `ui/*.slint` — без пустых `callback`/`property` и без маскировки
нереализованного UI прозрачностью. Правка точечная, окружающий код и
комментарии сохраняются.

Doc-комментарии нового и переписываемого кода — ссылки на ТЗ-N/ADR-N/§
по `AGENTS.md` («Трассируемость», префикс — `architecture.md` §3.1).
Текст, закреплённый в документации (значение константы, формулировка),
правится только по `task_intake.md` §5.

## 3. Верификация

- **каждый шаг** — `cargo check`;
- **шаг, меняющий форматы данных или общие типы** (схемы `settings.toml`/
  state-файла, DTO, поля `Settings`/`SessionState`, публичные
  `enum`/`struct`, сигнатуры, используемые в нескольких модулях) — полный
  `cargo test` сразу же: фильтр по своему модулю не ловит сломанные
  фикстуры в соседних модулях (например, `core/testing.rs`);
- **остальные кодовые шаги** — `cargo check`, по месту допустим
  `cargo test <фильтр>` по затронутому модулю;
- **ЧЕКПОИНТ** (каждые 2–3 кодовых шага и обязательно перед закрытием
  задачи) — полный `cargo test` + `cargo clippy` без новых предупреждений;
- **шаг только по докам/процессу** (без кода) — `python tools/state_tool.py
  check` и `python tools/traceability_tool.py check`.

`cargo clippy` линтит весь крейт: сравнивай не весь вывод, а только
предупреждения по путям файлов текущего вайтлиста (фильтр по пути в тексте
предупреждения или `--message-format=json`). Не держи в контексте два
полных лога («до» и «после»).

## 4. Успех

Проверка по §3 зелёная:

- сбрось `fail_counter` в `0`;
- отметь шаг `done: true`, запиши новые `current_step` и `next_action`;
- `python tools/state_tool.py render`;
- один коммит, включающий код и `_STATE_.yaml` + `_STATE_.md`
  одновременно, и push. Сообщение —
  `<тип>(<область>): <что сделано> (<ID задачи>, step <N>)`, например
  `feat(path): PathPlan::dac filled by planner (AM1.0-B29, step 2)`;
  скобка с ID и шагом обязательна — по ней коммит связывается со строкой
  ROADMAP и шагом `_STATE_.yaml`;
- сообщи пользователю одной строкой, какой шаг завершён и какой текущий —
  без этого переход к следующему шагу не делается.

## 5. Провал

Проверка упала (`cargo`, тест или `hooks/pre-commit`): увеличь
`fail_counter` на 1, запиши краткое описание ошибки. Счётчик сбрасывается
только успехом шага (§4), поэтому «3/3» — три провала одного шага. Пока
счётчик меньше `fail_counter_max` (3) — попробуй ОДИН альтернативный подход
(не повторяй тот же код) и вернись к §3.

При достижении `3/3`:

1. запиши в `failed_attempts` тезисы каждой попытки шага (суть подхода и
   почему не сработал, не сам код);
2. выполни `git checkout -- <файлы вайтлиста из кода>` и удали файлы,
   созданные этим шагом (их нет в последнем коммите; смотри
   `git status --porcelain`, удаляй только свои). Файлы состояния сессии в
   откат не входят — записи в `failed_attempts` сохраняются;
3. закоммить и запушь только `_STATE_.yaml` + `_STATE_.md`
   (`chore(state): <ID> step <N> failed 3/3`) — иначе записи не попадут на
   другую машину;
4. выведи лог ошибки и сообщение: «🚨 Достигнут лимит ошибок (3/3). Зашёл в
   тупик, не могу пройти проверку шага, выполнил откат изменений этого шага
   к последнему коммиту. Опробованные подходы зафиксированы в
   `_STATE_.yaml`. Передаю управление человеку.» — и останови работу.

После вмешательства пользователя: забудь прежнее (неудачное) решение шага,
сбрось `fail_counter` на `0`, перепиши описание `current_step` под указанную
пользователем траекторию и только после этого делай новую попытку.

## 6. Исполнители и контекст

На каждый микро-шаг запускается новый исполнитель (свежий помощник) с чистым
контекстом и самодостаточным заданием: нужные сигнатуры, инварианты,
правила и файлы вайтлиста — прямо в тексте задания, а не ссылкой на историю
диалога. Продолжать того же исполнителя можно только в пределах одного
шага (повтор после сбоя, правка по его отчёту); после коммита шага он не
переиспользуется. Причина: контекст накапливается, и каждый вызов
инструмента оплачивает его заново целиком. Рутинные проверки (прогон
тестов, git-операции) можно поручать дешёвому исполнителю — не самому
дорогому из доступных.

## 7. Остановка для очистки контекста

«Сессия» в этом разделе — текущий разговор с агентом (один контекст от
запуска до очистки), а не сессия `_STATE_.yaml`: закрытие задачи и старт
следующей её не прерывают.

Если в текущем разговоре уже была автоматическая компактизация контекста
(пересказ истории при переполнении) — после коммита ближайшего шага, не
дожидаясь ЧЕКПОИНТа, остановись: убедись, что дерево чистое, шаг
закоммичен и запушен, `_STATE_.yaml` указывает на следующий шаг, ни один
исполнитель не работает, и сообщи пользователю, что пора очистить контекст
и начать новый разговор. Дальше не продолжай без ответа пользователя.

Без компактизации — просто напомни об очистке на ЧЕКПОИНТе или в конце
задачи, не останавливаясь.

Пользователь может отключить эти остановки на весь разговор («работай без
остановок на очистку») и снова включить в нём же; отключение не
переносится в следующие разговоры. При отключённых остановках после
закрытия этапа (`closing.md`) агент сам берёт следующий этап по сквозному
порядку (`planning.md` §3 (б), без ожидания подтверждения); напоминание об
очистке в итоговом отчёте остаётся строкой, не остановкой. Остальные
СТОП-правила (вайтлист, лимит ошибок, расхождение git/состояния) действуют
независимо.

## 8. `hooks/pre-commit`

Коммит проходит пять быстрых проверок:

1. `tools/state_tool.py check` — схема и бизнес-правила `_STATE_.yaml`,
   `_STATE_.md` не разошёлся с `render`;
2. `tools/state_tool.py check-whitelist` — изменённые файлы (`git status`)
   не выходят за `whitelist` сессии (при `status: done` не проверяется);
3. `tools/traceability_tool.py check` — ID, якоря и маркеры статуса между
   спецификациями и `ROADMAP.md`; `task.roadmap_id` открытой сессии —
   существующая не-✅ строка;
4. `tools/acceptance.py check` — валидность пакетов `docs/acceptance/`;
5. `tools/check_rt_imports.py` — запрещённые конструкции в аудио-колбэке
   (`src/audio/render/**`, AM1.0 §7.7).

Пропуск хуков (`--no-verify`) — только по явному согласию пользователя на
конкретный коммит, не по умолчанию.
