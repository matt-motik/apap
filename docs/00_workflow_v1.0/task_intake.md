# Приём задачи из чата (WF1.0)

Применяется к любому запросу из чата: правка кода, документации,
конфигурации или процесса. Не применяется к работе по уже открытой сессии
(«Продолжение», `planning.md` §1) — там задача уже зарегистрирована.

Новая просьба при открытой сессии — не вклинивается в неё: зарегистрируй
B-строку (§2–§4) со статусом `⬜ открыто` и пометкой «отложено до закрытия
сессии `<ID>`» (в ближайший коммит), сообщи пользователю и доведи
открытую сессию до закрытия; затем — `planning.md` §3. Пользователь велит бросить текущую — `planning.md`
§7 (отказ от сессии).

Кода нет до регистрации (`AGENTS.md`, «Любая правка регистрируется»). Для
мелочи сессия — один шаг (`steps` с одним элементом); его проверка — сразу
полный состав ЧЕКПОИНТа (`execution.md` §3), отдельный шаг ЧЕКПОИНТа не
нужен.

## 1. Два пути

- **Путь А — «в рамках спеки».** Правка укладывается в действующие ТЗ и
  спецификацию, не меняет смысл требований. Примеры: опечатка в тексте UI;
  однострочный баг-фикс в уже реализованной функции; добавление недостающего
  вызова синхронизации, который по спеке и так должен был происходить. →
  B-строка (§2–§4), затем сессия (§6).
- **Путь Б — «большое или противоречит спеке».** Новое поведение, которого
  нет в действующей спеке; правка требует новых этапов внедрения (работы
  больше чем на одну сессию); правка меняет смысл существующего требования,
  а не только формулировку. Примеры: добавить новый режим воспроизведения;
  изменить модель данных настроек; переопределить, что считается
  bit-perfect. → СТОП. Сообщи пользователю, что нужен полный цикл по
  `docs/_template/process.md` (промт → ревью → ТЗ → спецификация → этапы в
  ROADMAP). Код не пишется, пока спецификация не утверждена и её этапы не
  внесены в ROADMAP.

Сомневаешься между путями — спроси пользователя, не угадывай молча.

## 2. Префикс и номер

Префикс — спека, которой касается правка (реестр в шапке `ROADMAP.md`);
правки процесса — `WF1.0`. Правка, не описанная ни в одной спеке (подпись
кнопки, косметика UI): спека каталога файла по таблице `architecture.md`
§3.1; для смешанного файла — спека, к функции которой относится правка
(воспроизведение и вывод — `AM1.0`, настройки/состояние/окна сообщений —
`SP1.0`, визуализация — `V5.1`, темы — `T1.0`). Текст, закреплённый в
спеке (§5), — префикс этой спеки, а не каталога файла. Не можешь выбрать —
спроси пользователя.

Номер бери из строки «Следующие свободные номера» в начале таблицы
Баг-раунда `ROADMAP.md` и в той же правке увеличь значение в строке —
следующий агент должен увидеть обновлённый номер. Номера не
переиспользуются.

## 3. Приоритет

- 🔴 **Критический** — паники, утечки памяти, гонки, зависания UI,
  блокирующий I/O, риск для слуха или оборудования.
- 🟡 **Высокий** — нарушение ключевой логики, регрессия аудио-движка.
- 🟢 **Средний** — оптимизация, рефакторинг, новые настройки UI, ошибки
  поведения без влияния на звук.
- 🔵 **Низкий** — косметика: тексты, подписи, опечатки, оформление.

Риск для звука или слуха поднимает приоритет независимо от размера правки
(`AGENTS.md`, «Продукт и приоритеты»).

## 4. Формат B-строки

Колонки — как в таблице Баг-раунда `ROADMAP.md`: `ID | Задача | Приоритет |
Статус | ТЗ`. Статус новой строки — `🔄 выполняется`; `⬜ открыто` — только
для побочных находок, не взятых в работу (`AGENTS.md`, «Любая правка
регистрируется»), и просьб, отложенных до закрытия открытой сессии
(преамбула). Колонка «ТЗ» — ссылка на якорь относящегося раздела
спецификации (правка не описана в спеке — на §8 спеки выбранного
префикса), GitHub-стиль: нижний регистр, пунктуация удаляется, пробелы →
`-` (`## 8. Этапы внедрения` → `#8-этапы-внедрения`).

```
| <Префикс>-B<N> | Что не так и где (файл/функция); откуда задача (запрос пользователя <дата> / найдено на <ID>) | 🟡 Высокий | 🔄 выполняется | [§8 С6](docs/01_audio_modes_v1.0/03_spec.md#8-этапы-внедрения) |
```

После регистрации — `python tools/traceability_tool.py check`; не оставляй
строку, которую он не пропускает.

## 5. Закреплённый в документации текст

Перед правкой текста, константы или имени поищи значение в `docs/` (кроме
`docs/_canceled/`). Если оно зафиксировано в действующей спецификации или
ТЗ:

- просьба пользователя изменить его — разрешение на правку именно этого
  места; сообщи пользователю, где именно оно закреплено;
- измени спецификацию и код одним коммитом; файл спецификации — в вайтлист
  сессии наравне с кодом. «Текст X в ТЗ-N и в коде» — одна сущность, один
  шаг (`planning.md` §5).

Если правка меняет смысл требования, а не только формулировку, — это не
точечная правка: СТОП и вопрос пользователю (возможен путь Б, §1).

Если значения в `docs/` нет — обычная правка; запись в `docs/` в остальных
случаях — только по явному разрешению пользователя.

## 6. Открытие сессии

После регистрации B-строки — `planning.md` §5–7: микро-декомпозиция,
запись `_STATE_.yaml`, регистрационный коммит, подтверждение плана
пользователем.
