# Приём задачи из чата (WF1.0)

Применяется к любому запросу из чата: правка кода, документации, конфигурации
или процесса (`AGENTS.md`, `.claude/`, хуки, `tools/`). Не применяется к
работе по уже открытой сессии `_STATE_.yaml` (режим «Продолжение») — там
задача уже зарегистрирована, см. `planning.md`.

## 1. Кода нет до регистрации

Лёгкого пути без регистрации нет (README §2 п.1). Любая правка — опечатка,
константа, однострочный баг, правка конфига — получает строку
`<Префикс>-B<N>` в `ROADMAP.md` и сессию в `_STATE_.yaml`. Для мелочи сессия
состоит из одного шага (`steps` с одним элементом, `dod` — простая проверка
вроде `cargo check` без ошибок). Пропускать регистрацию запрещено независимо
от размера правки.

## 2. Классификация — два пути

Определи, в каком пути лежит запрос (README §2 п.2):

- **Путь А — «в рамках спеки».** Правка укладывается в действующие ТЗ и
  спецификацию, не меняет смысл требований. Примеры: опечатка в тексте UI;
  однострочный баг-фикс в уже реализованной функции; добавление недостающего
  вызова синхронизации, который по спеке и так должен был происходить. →
  B-строка в ROADMAP, затем сессия и шаги по `planning.md`.
- **Путь Б — «большое или противоречит спеке».** Новое поведение, которого
  нет в действующей спеке; правка затрагивает несколько этапов внедрения;
  правка меняет смысл существующего требования, а не только формулировку.
  Примеры: добавить новый режим воспроизведения; изменить модель данных
  настроек; переопределить, что считается bit-perfect. → СТОП. Сообщи
  пользователю, что нужен полный цикл по `docs/_template/process.md`
  (промт → ревью → ТЗ → спецификация → этапы в ROADMAP). Код не пишется, пока
  спецификация не утверждена и её этапы не внесены в ROADMAP.

Если сомневаешься между путями — спроси пользователя, не угадывай молча.

## 3. Выбор префикса и номера

Префикс — префикс спецификации, которой касается правка (реестр в шапке
`ROADMAP.md`, таблица «Спека → Префикс»). Правки самого процесса (`AGENTS.md`,
`.claude/`, хуки, `tools/`) — всегда `WF1.0`.

Номер бага бери из строки «Следующие свободные номера» в начале таблицы
Баг-раунда `ROADMAP.md` и в этой же правке увеличь
соответствующее значение в строке — следующий агент должен увидеть
обновлённый номер, не прежний.

## 4. Приоритет

Шкала для колонки «Приоритет» B-строки:

- 🔴 **Критический** — паники, утечки памяти, гонки, зависания UI,
  блокирующий I/O, риск для слуха или оборудования.
- 🟡 **Высокий** — нарушение ключевой логики, регрессия аудио-движка.
- 🟢 **Средний** / 🔵 **Низкий** — оптимизация, рефакторинг, новые настройки
  UI.

## 5. Формат B-строки

Колонки — как в действующей таблице Баг-раунда `ROADMAP.md`: `ID | Задача |
Приоритет | Статус | ТЗ`. Новая строка получает статус `🔄 выполняется` (не
`⬜ открыто` — это статус для найденных, но пока не взятых в работу дефектов,
см. §6). Колонка «ТЗ» — ссылка-якорь на относящийся раздел спецификации,
GitHub-стиль: нижний регистр, пунктуация удаляется, пробелы → `-`
(`## 8. Этапы внедрения` → `#8-этапы-внедрения`).

Пример строки:

```
| <Префикс>-B<N> | Что не так и где (файл/функция); откуда задача (запрос пользователя <дата> / найдено на <ID>) | 🟡 Высокий | 🔄 выполняется | [§8 С6](docs/01_audio_modes_v1.0/03_spec.md#8-этапы-внедрения) |
```

После регистрации проверь `python tools/traceability_tool.py check` — он
валидирует ID, якоря и маркеры; не оставляй строку, которую он не пропускает.

## 6. Закреплённый в документации текст

Перед правкой текста, константы или имени поищи значение в `docs/` (кроме
`docs/_canceled/`, который читать запрещено). Если оно зафиксировано в
действующей спецификации или ТЗ:

- просьба пользователя изменить его — разрешение на правку именно этого
  места;
- сообщи пользователю, где именно это закреплено;
- измени спецификацию и код одним коммитом; файл спецификации — в вайтлист
  сессии наравне с кодом.

Если правка меняет смысл требования, а не только формулировку, — это не
точечная правка: СТОП и вопрос пользователю (возможен переход в путь Б, §2).

Если значения в `docs/` нет — обычная правка, пункт 6 не применяется;
запись в `docs/` в остальных случаях — только по явному разрешению
пользователя.

## 7. Открытие сессии

После регистрации B-строки открой сессию в `_STATE_.yaml` по правилам
`planning.md` (микро-декомпозиция, вайтлист, DoD). Сообщи пользователю:

> «Задача зарегистрирована в ROADMAP.md (`<ID>`) и декомпозирована в
> `_STATE_.yaml`. Перехожу к выполнению.»

— отправляй это сообщение только после того, как пользователь подтвердил
план (формулировка подтверждения — в `planning.md`); до подтверждения код не
пишется.

## 8. Побочные находки

Дефект вне текущей задачи, обнаруженный по ходу работы, не чини молча: добавь
B-строку в `ROADMAP.md` со статусом `⬜ открыто` (без открытия сессии для
неё) и продолжай текущую задачу.
