# Закрытие этапа и сессии (WF1.0)

Применяется, когда все шаги текущей задачи в `_STATE_.yaml:steps` отмечены
`done: true` и финальная верификация зелёная — полный `cargo test` +
`cargo clippy` без новых предупреждений (ЧЕКПОИНТ перед закрытием,
`execution.md` §3); для задачи только по докам/процессу (без кода) —
`python tools/state_tool.py check` и `python tools/traceability_tool.py check`.
Регистрация задачи — `task_intake.md`; микро-декомпозиция
и вайтлист — `planning.md`; цикл шага — `execution.md`. Путь ниже для этапа
спецификации (`<Префикс>-8.N`); закрытие бага (`<Префикс>-B<N>`) — §9.

## 1. Статус в ROADMAP

Точечной правкой одной строки (не затирая соседние):

```
✅ сделано в <hash> (ветка <branch>)
```

`<hash>` — короткий хэш коммита, закрывающего последний шаг этапа. Статус
следующего этапа не трогать — он станет `🔄 выполняется` при старте его
сессии (`planning.md` §5). Строка этапа с ✅ остаётся в таблице спеки до её
закрытия (§5). В разделе «Текущий статус проекта» `ROADMAP.md` обнови строку
«Следующая задача — …» (закрытый ID — в список закрытых, следующий — по
сквозному порядку). Всё закрытие (§1–§6) — один коммит
`chore(roadmap): close <ID>`.

## 2. Общие условия §8 спеки

Проверь условия, общие для всех этапов данной спецификации (таблица «Этапы
внедрения», преамбула §8 — например, у AM1.0: `cargo build`/`test`/`clippy`
зелёные, плеер играет в Совместимом режиме, бейдж никогда не показывает
«Bit-perfect» без выполнения ТЗ-52; это пример одной спеки, не общее правило
WF1.0 — источник истины всегда §8 спецификации этапа). Условие, которое
нельзя проверить автоматически — ручная проверка (§3).

## 3. Жизненный цикл ручной проверки

Непроверенная ручная проверка — одна строка в `note` пункта `plan.items` со
`status: in_progress` (формат: `"Ручные проверки за пользователем: <ID> — …"`,
см. пример в `_STATE_.yaml:plan.items`).

- **Подтверждена** (целиком или частично) — в этом же ходе: подтверждённое
  убирается из строки (строка целиком, если не осталось непроверенного),
  `python tools/state_tool.py render`, коммит
  `chore(state): manual check <ID> confirmed <ГГГГ-ММ-ДД>`.
- **Провалена** — строка заменяется багом в ROADMAP (Баг-раунд, `<Префикс>-B<N>`,
  `task_intake.md`).
- **Отказ пользователя от проверки** — строка удаляется, в коммите помечается
  `waived`.

Непроверенная ручная проверка не блокирует закрытие этапа или бага: задача
закрывается, строка остаётся в `note` до подтверждения. Коммиты
подтверждения и отказа — служебные, без B-строки и сессии (`AGENTS.md`,
«Любая правка регистрируется»).

Подтверждения, оставшиеся только в чате, не считаются: между машинами
переносится только git — без коммита факт проверки не существует для
следующей сессии.

## 4. Заметка пункта плана

Обнови `note` соответствующего пункта `plan.items`: какой этап закрыт (ID,
короткое название, хэш), какой следующий по сквозному порядку (строка вида
«СЛЕДУЮЩИЙ (п. N сквозного порядка): …», как в текущих записях). Состав
прочих полей `plan.items` не трогать — только точечная правка `note`/`status`
нужного пункта (`planning.md` §7).

## 5. Закрытие спецификации

Когда закрыт последний этап спецификации (приёмка):

0. Открытые B-строки этой спеки (`<Префикс>-B<N>` со статусом `⬜`/`🔄`)
   покажи пользователю списком: спека закрывается, а они остаются в
   Баг-раунде со своим префиксом, пока пользователь не решит иначе
   (закрыть, отказаться — строка в `archive_bugs.md` с пометкой
   «отклонено <дата>»).

1. Проведи кросс-ОС приёмку: `python tools/acceptance.py run` по пакету
   спецификации (`docs/acceptance/<name>/`) на каждой ОС пакета (Linux —
   десктоп, Windows — ноутбук), результаты — в git. Сам пакет создаётся
   этапом приёмки спеки (утверждён вместе со спекой), результаты пишет
   `tools/acceptance.py` — отдельного разрешения на запись в `docs/` не
   нужно; коммит результатов — служебный
   (`chore(acceptance): <пакет> <ОС> <дата>`). Закрытие только когда
   `python tools/acceptance.py status` показывает прогоны всех ОС. Прогона на
   второй машине нет — строка в `note` пункта плана, спека не закрывается;
   п. 2–4 выполняются на той машине, где прошёл последний прогон, —
   отдельной B-строкой `WF1.0` не регистрируются, это продолжение закрытия
   (коммит `chore(roadmap): close <Префикс>`).
2. Перенеси историю этапов в `_TODO_/history/archive_<Префикс>.md`
   (например, `archive_AM1.0.md`: версии `vX.Y` у разных спек совпадают,
   уникален только префикс; прежние `archive_v0.x.md` не переименовываются). Запрещено
   слепо стирать текст — составь технический паспорт решения: коммиты и
   даты по этапам, применённые формулы, созданные структуры данных, размеры
   буферов/FFT-окон, зашитые Real-Time константы (формат — заголовок,
   таблица «Этап → коммит → дата → детали», раздел «Ключевые структуры и
   константы», раздел «Верификация»; образец — `_TODO_/history/archive_v0.5.md`).
3. В `ROADMAP.md` оставь строку глобального статуса спецификации
   (например, «Спека V5.1 считается полностью выполненной» — см. существующий
   раздел «Текущий статус проекта»); таблицу этапов убери — это
   разрешённое исключение из правила точечной правки `ROADMAP.md`.
   Строки этапов в разделе «Сквозной порядок» остаются (✅), пока не
   закрыты все спеки этого порядка; тогда раздел удаляется целиком.
4. Пункт `plan.items` — `status: done`, только когда закрыты все спеки,
   которые он ведёт; иначе — запись в `note` («закрыта спека <Префикс>»).

## 6. Консервация `_STATE_.yaml`

- `status: done`;
- очисти `task`, `whitelist`, `steps`, `current_step`, `next_action`,
  `failed_attempts` (`fail_counter: 0`);
- `plan` не трогай — поле переживает `status: done` и не очищается;
- выполни `python tools/state_tool.py render`.

## 7. Финальный аудит

`git diff --stat <родитель регистрационного коммита>..HEAD` — все
изменения задачи, включая регистрацию; отчёт в чат до итогового сообщения.

## 8. Итоговый отчёт

- что сделано: изменённые модули и ключевые структуры, какие ТЗ-N/ADR-N
  закрыты;
- какие тесты подтверждают работоспособность (команда и счётчик, например
  «`cargo test` — N lib + M bin зелёные»);
- следующий логический ход — следующий этап по ROADMAP/сквозному порядку;
- если в текущей сессии уже была компактизация контекста — напоминание об
  очистке контекста перед следующей сессией (`execution.md` §7: без
  компактизации достаточно напомнить, не останавливаясь).

Если дальше работа продолжается сама (этап по сквозному порядку при
отключённых остановках, `execution.md` §7) — заверши строкой «Перехожу к
`<следующий ID>`» и начинай `planning.md`. Иначе заверши фразой:

> «Задача полностью завершена, репозиторий чист, файлы состояния
> законсервированы. Готов к новой задаче.»

## 9. Закрытие бага (Баг-раунд)

Для `<Префикс>-B<N>` выполняются §1, §3, §4 и §6–§8; §2 и §5 (общие условия
§8 спеки, архив спецификации) не применимы — у бага нет этапа §8.

- **§1 для бага:** строка с итоговым статусом `✅ сделано в <hash> (ветка
  <branch>)` в том же коммите закрытия **переносится** из раздела «БАГ-РАУНД»
  `ROADMAP.md` в конец таблицы `_TODO_/history/archive_bugs.md` (целиком, без
  сокращения; подробности фикса — по хэшу). Номер `<Префикс>-B<N>` повторно не
  используется (строка «Следующие свободные номера» в шапке Баг-раунда).
- **§3 для бага:** ручные проверки бага (например, GUI-поведение) живут в
  `note` пункта плана так же, как у этапа: `Ручные проверки за пользователем:
  <Префикс>-B<N> — …`.
- **§4 для бага:** в `note` — какой баг закрыт (ID, хэш) и что следующее.

Коммит закрытия — `chore(roadmap): close <Префикс>-B<N>` (файлы: `ROADMAP.md`,
`_TODO_/history/archive_bugs.md`, `_STATE_.yaml`, `_STATE_.md`).
