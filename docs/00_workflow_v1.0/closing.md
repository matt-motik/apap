# Закрытие этапа или бага (WF1.0)

Применяется, когда все шаги задачи в `_STATE_.yaml:steps` отмечены
`done: true` и ЧЕКПОИНТ зелёный (`execution.md` §3; для задачи без кода —
проверки инструментов оттуда же). Закрыт последний
этап спецификации — после этого файла выполняется `spec_closing.md`.

## 1. ROADMAP

**Этап `<Префикс>-8.N`:**

- статус строки — `✅ сделано в <hash> (ветка <branch>)`, где `<hash>` —
  короткий хэш коммита последнего шага с этим ID, менявшего код (не
  ЧЕКПОИНТа; у задачи без кода — последнего шага); строка остаётся в
  таблице спеки до её закрытия;
- статус следующего этапа не трогать — `🔄` он получит при старте своей
  сессии (`planning.md` §3);
- в разделе «Текущий статус проекта» обнови строку «Следующая задача — …»:
  закрытый ID — в список закрытых, следующий — по сквозному порядку
  (сквозной порядок исчерпан — «Следующая задача — нет, закрытие спек
  (`spec_closing.md`)»);
- общие условия §8 спеки: проверь преамбулу таблицы «Этапы внедрения»
  (например, сборка/тесты/clippy зелёные, плеер играет) — источник истины
  всегда §8 спецификации этапа; условие, которое нельзя проверить
  автоматически, — ручная проверка (§2).

Баг, закрываемый этапом («закрывает `<ID>`» в строке этапа), закрывается
тем же коммитом по правилу для бага ниже, с хэшем этапа.

**`known_issue`.** Если закрываемый ID указан как `known_issue` в
`docs/acceptance/*/criteria.yaml`, удали этот ключ тем же коммитом
закрытия (для бага иначе хук не пропустит коммит) и добавь в ручные проверки (§2) «перепрогнать приёмку
`<пакет>`».

**Баг `<Префикс>-B<N>`:** та же строка со статусом
`✅ сделано в <hash> (ветка <branch>)` (`<hash>` — как для этапа) переносится целиком из Баг-раунда в
конец таблицы `_TODO_/history/archive_bugs.md` (без сокращения; подробности
фикса — по хэшу). Строка «Следующая задача — …» и статусы этапов не
трогаются.

Для бага (не этапа) этот перенос и консервация `_STATE_.yaml` (§4) автоматизированы:
`python tools/state_tool.py close-bug <ID1> <hash1> [<ID2> <hash2> ...]`
(несколько пар — сессия на несколько B-строк) делает перенос строки(строк)
и §4 сразу, печатает остаток `note` (§3) и готовую команду коммита (§5);
строка должна быть `🔄 выполняется`. §2 (ручные проверки) и §6 (аудит,
отчёт) инструмент не делает — их выполняет агент.

## 2. Ручные проверки

Ручная проверка нужна, когда результат виден или слышен только в
запущенном плеере (окно, звук, устройство) и не покрыт тестом, а также для
условий §8 спеки, которые нельзя проверить автоматически. Не нужна для
правки текста, которую целиком показывает дифф. Для `WF1.0` — поведение
хука или инструмента, которое здесь не проверить (другая ОС). Непроверенная
ручная проверка не блокирует закрытие: задача закрывается, а проверка живёт строкой в `note` пункта
`plan.items` со `status: in_progress` (если такого пункта нет — пункта
«Ручные проверки за пользователем» со `status: todo`; нет и его — создай
с новым `id`) — формат
`"Ручные проверки за пользователем: <ID> — …"` (пример — в
`_STATE_.yaml:plan.items`).

- **Подтверждена** (целиком или частично) — в этом же ходе: подтверждённое
  убирается из строки (строка целиком, если не осталось непроверенного),
  `python tools/state_tool.py render`, коммит
  `chore(state): manual check <ID> confirmed <ГГГГ-ММ-ДД>`.
- **Провалена** — строка убирается, в ROADMAP — B-строка `⬜ открыто`
  (`task_intake.md` §4), коммит `chore(state): manual check <ID> failed
  <ГГГГ-ММ-ДД>`.
- **Отказ пользователя от проверки** — строка удаляется, в коммите
  `waived` вместо `confirmed`.

## 3. Заметка пункта плана

`note` хранит только открытое; закрытое видно по ROADMAP и архивам.
Убери строки `note`, которые закрыла задача, включая «СЛЕДУЮЩИЙ …»:
следующий этап задают сквозной порядок и строка «Следующая задача» ROADMAP
(§1).

Прочие поля `plan` не трогать (`planning.md` §6).

## 4. Консервация `_STATE_.yaml`

- `status: done`;
- очисти `task`, `whitelist`, `dod`, `steps`, `current_step`, `next_action`,
  `failed_attempts` (`fail_counter: 0`); `plan` не трогай;
- `python tools/state_tool.py render`.

## 5. Коммит закрытия

§1–§4 — один коммит `chore(roadmap): close <ID>` (файлы: `ROADMAP.md`,
`_STATE_.yaml`, `_STATE_.md`, для бага — `_TODO_/history/archive_bugs.md`),
затем push. Один — потому что хук требует для открытой сессии существующую не-✅
строку (`execution.md` §8). Сессия на несколько B-строк
(`planning.md` §5) закрывает их все этим же коммитом:
`chore(roadmap): close <ID1> and <ID2>`.

## 6. Аудит и итоговый отчёт

`git diff --stat <родитель регистрационного коммита>..HEAD` — все
изменения задачи, включая регистрацию; отчёт в чат, затем:

- что сделано: изменённые модули и ключевые структуры, какие ТЗ-N/ADR-N
  закрыты;
- какие тесты подтверждают работоспособность (команда и счётчик, например
  «`cargo test` — N lib + M bin зелёные»);
- следующий ход — следующий этап по ROADMAP/сквозному порядку;
- если в разговоре уже была компактизация контекста — напоминание об
  очистке перед следующим разговором (`execution.md` §7).

Если работа продолжается сама (этап по сквозному порядку при отключённых
остановках, `execution.md` §7) — заверши строкой «Перехожу к
`<следующий ID>`» и начинай `planning.md`. Иначе заверши фразой:

> «Задача полностью завершена, репозиторий чист, файлы состояния
> законсервированы. Готов к новой задаче.»
