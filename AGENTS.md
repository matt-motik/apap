# AGENTS.md

> СТРОГОЕ ПРАВИЛО НАЧАЛА СЕССИИ: Первым действием всегда читай `_STATE_.yaml` (не `_STATE_.md` — это сгенерированное представление для человека с тем же содержимым).
> Если в `_STATE_.yaml` зафиксирован незавершённый шаг -> переходи в режим "Продолжение".
> Если состояние `done` или файл отсутствует -> переходи в режим "Новая задача".
> Если в поле `plan:` `_STATE_.yaml` есть пункт со `status: in_progress` (в `_STATE_.md` — `[>]`) -> это текущая работа пользователя: сообщи о ней и продолжай её (активный этап — строка `🔄` в `ROADMAP.md`).

## Артефакты и правила доступа к ним

Воркфлоу построен строго вокруг следующих артефактов. Нарушение правил доступа к ним является критической ошибкой:

- `_STATE_.yaml` — Состояние текущей сессии. Твоя единственная точка входа (читаешь и правишь только его). Вся оперативная информация, шаги и контекст живут ТОЛЬКО здесь. Создание любых других файлов состояния (например, `plan-*.md` или `.current-plan.json`) СТРОГО ЗАПРЕЩЕНО.
  - `_STATE_.md` **генерируется** из него командой `python tools/state_tool.py render` (ручная правка `.md` блокируется pre-commit) и предназначен для человека; агент его не читает. **Везде ниже, где сказано «прочитай / сверь с `_STATE_.md`», читай соответствующие поля `_STATE_.yaml`; где сказано «запиши / перезапиши `_STATE_.md`» (в т.ч. шаблон Шага 0), правь поля `_STATE_.yaml` (схема — `tools/schema/state.schema.json`) и выполни `render`.** Многошаговый план поверх задач — поле `plan:` в `_STATE_.yaml`.
  - Пользователь работает на двух машинах (Windows-ноутбук и Linux-десктоп); между ними переносится **только git** — память агента и задачи сессии не переносятся. Поэтому план, точка остановки и отложенные находки фиксируются в `_STATE_.yaml` / `ROADMAP.md` и пушатся; в начале сессии — `git pull` и чтение `_STATE_.yaml`.
- `ROADMAP.md` — Единый технический бэклог проекта. Задачи = этапы внедрения из спецификаций в `docs/` (см. Регламент §3). Изменяется точечно и строго по согласованию с `_STATE_.md`. Порядок этапов менять запрещено.
- `docs/` — Действующая документация (ТЗ, спецификации) в папках задач `docs/NN_имя_vX.Y/`. Изменяется ТОЛЬКО по явному разрешению пользователя (Регламент §2). Структура и навигация — `docs/README.md`.
  - **Действующая документация аудио-тракта — `docs/01_audio_modes_v1.0/`** (`02_tz.md` — требования ТЗ-N; `03_spec.md` — ADR-N, модель, алгоритмы, план тестов, этапы С0…С11). При противоречии с любым другим документом или с правилами ниже о стиле кода действует она.
  - `docs/_template/` — шаблон и порядок работы для новой задачи (`prompt_template.md`, `process.md`).
  - `docs/acceptance/` — пакеты кросс-ОС приёмки для `tools/acceptance.py`.
- `docs/_canceled/` — Архив устаревшей и заменённой документации (прежние спеки `A2.0`, `A3.0`, `AP5.0`, ревью к ним, отработанный инбокс `_TODO_/done/`). **Не является источником требований.** ТЕБЕ ЗАПРЕЩЕНО читать этот каталог без прямой просьбы пользователя (чтение заблокировано в `.claude/settings.json`). Старые коды в комментариях кода (`ТЗ A3.0 §7.3` и т. п.) — это историческая пометка; соответствие кодов и путей — таблица в `docs/README.md`.
- `_DRAFTS_/` — Личная папка пользователя. ТЕБЕ ЗАПРЕЩЕНО читать, открывать, изменять, перемещать файлы из неё или ссылаться на них. Игнорируй её существование.
- `_TODO_/history/` — Архивы завершённых этапов (`archive_vX.Y.md`, технический паспорт решения — Регламент §4). Других подкаталогов в `_TODO_/` нет: инбокс упразднён, новые задачи приходят из чата (раздел «Интерактивный режим»).
- `examples/` — Справочные примеры кода и решений. ТЕБЕ ЗАПРЕЩЕНО мутировать, изменять или перезаписывать файлы в этом каталоге. Доступ только на чтение (`read`).


Шаг 0: Инициализация и состояние

1. Прочитай файл `_STATE_.yaml`.
2. Определи режим работы по следующим правилам:

   - **РЕЖИМ "ПРОДОЛЖЕНИЕ"** (Если в файле есть незавершённые шаги `[ ]` или статус не равен `done`):
     - Считай из файла: `активная задача`, `current_step`, `следующий ход` и `изменяемые файлы`.
     - Выведи пользователю текстовое подтверждение: *"Вхожу в режим Продолжения. Текущий шаг: [название]. Работаю со следующими файлами: [список]"*.
     - Переходи строго к выполнению указанного `current_step`, не пересчитывая план заново.

   - **РЕЖИМ "НОВАЯ ЗАДАЧА"** (Если файл отсутствует, пустой или его состояние `done`):
     - Создай (или полностью перезапиши) `_STATE_.md` строго по следующему шаблону:

```markdown
# Текущая микро-сессия

- **Задача из ROADMAP:** [ID и название задачи, например AM1.0-8.0 — С0. Основа приёмки]
- **Вайтлист файлов в работе (Изменяемые файлы):**
  - [Путь к файлу 1]
- **Критерий успеха (Definition of Done):** [Четкий технический критерий, например: тесты проходят, компиляция ок]

## Итерационный трекер
[ ] Шаг 1: [Описание микро-шага]

- **Текущий шаг (current_step):** Шаг 1
- **Следующий ход:** [Что делать прямо сейчас]
- **Счетчик безуспешных компиляций:** 0/3
- **Состояние:** in_progress
```

     - Заполни в шаблоне только базовые поля, если задача уже известна, либо оставь плейсхолдеры до завершения Шагов 1–3.


## Делегирование субагентам

- На каждый микро-шаг `_STATE_.yaml` запускается **новый** субагент с чистым контекстом и коротким самодостаточным заданием (нужные сигнатуры, инварианты, правила и файлы вайтлиста — в тексте задания). Продолжать того же агента можно только в пределах одного шага (сбой по лимиту, правка по его отчёту); после коммита шага агент не переиспользуется. Причина: контекст накапливается, и каждый вызов инструмента повторно оплачивает его целиком.
- Если смена типа затрагивает больше 2–3 файлов, шаг разбивается через временный мост (адаптер «старое ↔ новое»), чтобы каждый подшаг компилировался сам; мост удаляется на шаге очистки.

## Лёгкий путь (тривиальные правки)

Если задача — точечный фикс, затрагивающий **ровно 1 файл** и **не требующий** новой функциональности (опечатка, константа, однострочный баг, комментарий), полный цикл Шаг 0–5 можно сократить:

1. `git status --porcelain` — репозиторий должен быть чистым (иначе действует общее правило Шага 1).
2. Внеси правку.
3. `cargo check` (и `cargo test <относящийся_фильтр>`, если правка затрагивает покрытую тестом логику).
4. Коммит с понятным сообщением. `_STATE_.md`/`ROADMAP.md` трогать не обязательно.

Если в процессе выясняется, что правка требует больше 1 файла или превращается в несколько логических шагов — прекрати лёгкий путь и перейди к полному воркфлоу (Шаг 0–5).

Шаг 1: Аудит Репозитория (Безопасность)

1. Выполни команду `git status --porcelain`.
2. На основе результатов определи чистоту репозитория и режим сессии:

   - **Если репозиторий "ГРЯЗНЫЙ" (есть незакоммиченные изменения):**
     - Выполни `git diff --stat` и выведи отчет о текущих изменениях в чат.
     - **В режиме "Новая задача":** СТОП. Запрещено вносить изменения. Выведи в чат сообщение: 
       *"Репозиторий содержит незакоммиченные изменения. Пожалуйста, выберите действие: 1) Сделать WIP-коммит, 2) Выполнить git stash, 3) Отменить изменения (git reset). Ожидаю вашей команды."* Не продолжай работу без явного ответа пользователя.
     - **В режиме "Продолжение":** Сверь список фактически изменённых файлов из `git status` со списком в разделе `Вайтлист файлов в работе` в `_STATE_.md`.
       - *Если файлы СТРОГО СОВПАДАЮТ:* Продолжай работу.
       - *Если есть любые расхождения (лишние или недостающие файлы):* СРОЧНЫЙ СТОП. Выведи в чат ошибку: *"Внимание! Обнаружено расхождение между Git и файлом состояния сессии. Требуется ручное вмешательство."* Ничего не изменяй в репозитории.

   - **Если репозиторий "ЧИСТЫЙ":** Продолжай работу.

3. Выполни базовую проверку компиляции проекта командой `cargo check --quiet`.
   - **Если компиляция успешна:** Переходи к Шагу 2.
   - **Если компиляция упала с ошибкой (`Error`):** СТОП. Вносить изменения в код запрещено. Перейди в интерактивный режим диагностики и выведи в чат сообщение:
     
     *"🚨 Обнаружена ошибка компиляции проекта ДО начала работы. 
     Я сохраняю режим 'Чтение' (Read-only) и не буду менять файлы без команды. 
     
     Пожалуйста, выберите действие:
     1) [Диагностика] — Попросить меня проанализировать логи и код, чтобы найти причину поломки.
     2) [Ручной ремонт] — Вы исправите ошибку самостоятельно и введёте 'готово' для повторной проверки."*

4. **Воркфлоу Режима Диагностики** (Активируется ТОЛЬКО если пользователь выбрал вариант 1):
   - Изучи лог ошибки `cargo check`. Найди проблемный файл и строку.
   - Прочитай этот участок кода (используй строго инструмент `read`, инструмент `write/patch` ЗАПРЕЩЕН).
   - Выведи пользователю краткий и понятный технический отчет:
     - **Локализация:** Файл, строка, какая функция сломана.
     - **Причина:** Почему упало (например: не совпадает тип, пропущен аргумент, мёртвая зависимость).
     - **Готовое решение:** Покажи в чате кусок кода (дифф), который исправит проблему.
   - Заверши отчет вопросом: 
     *"Я могу применить это исправление автоматически? Ответь: 'Да' (для авто-применения) или 'Нет' (если исправишь сам)."*
   - **Если пользователь ответил 'Да':** Примени конкретный дифф, выполни `cargo check` повторно. Если компиляция стала зелёной -> приведи `_STATE_.md` к начальному виду и иди на Шаг 2. Если снова упало -> СТОП, вернись к выбору ручного ремонта.


Шаг 2: Выбор задачи

1. Инбокса нет. Источники задач: (а) активный этап в `ROADMAP.md` (строка со статусом `🔄`), (б) задача, поставленная пользователем в чате (раздел «Интерактивный режим»).
2. Если в разделе «План» `_STATE_.md` есть пункт `[>]` — работай в его рамках: возьми из `ROADMAP.md` строку `🔄` этого плана; если её нет — первую `⬜` по сквозному порядку из `ROADMAP.md`, если он задан, иначе по порядку таблицы (порядок этапов менять запрещено).
3. Прочитай из спецификации всё, что относится к этапу:
   - строку этапа в таблице «Этапы внедрения» (`03_spec.md` §8) — содержание, ТЗ-N, что работает после этапа, что удаляется;
   - перечисленные в ней требования ТЗ-N (`02_tz.md` §4, вместе с решениями ОВ/ОВС, которые на них ссылаются) и ADR-N (`03_spec.md` §1);
   - все разделы `03_spec.md`, относящиеся к этим ТЗ-N и ADR-N: модель данных §2 и модель пути сигнала §3, инварианты §5, алгоритмы §6, тесты §7.
   Одной строки этапа и текста ТЗ/ADR для реализации недостаточно. Разделы, не относящиеся к этапу, не читай.
4. Найденные по ходу работы дефекты вне текущего этапа не чини молча: зарегистрируй строкой в `ROADMAP.md` (Баг-раунд) и продолжай этап.


Шаг 3: Планирование (Микро-декомпозиция)

1. Возьми активную задачу (из `_STATE_.md` или по Шагу 2).
2. Поставь этой задаче в `ROADMAP.md` статус `🔄 выполняется` (используй точечный `patch/diff`, не затирай соседние строки).
3. Разбей задачу на атомарные микро-шаги в `_STATE_.md`, строго следуя **Правилам микро-декомпозиции**:

   - **Правило "Один шаг — одна сущность":** Запрещено создавать шаги, содержащие союзы "И", "МАППИНГ + UI", "ЛОГИКА И ТЕСТЫ". Один шаг должен решать ровно одну изолированную подзадачу (например: только добавить структуру в `settings.rs`, только пробросить колбэк в `ui_manager.rs`, только написать один юнит-тест).
   - **Правило локализации:** Один микро-шаг должен затрагивать **не более 1–2 файлов** кода. Если для шага требуется изменить 4 файла — разбей этот шаг на два или три независимых подшага.
   - **Правило явного Definition of Done (DoD):** Каждый шаг в итерационном трекере должен содержать четкий технический критерий проверки (например: `[ ] Шаг 1: Добавить поле в Settings. Проверка: cargo check без ошибок`, `[ ] Шаг 2: Написать тест test_bit_perfect. Проверка: cargo test test_bit_perfect зелёный`).
   - **Правило трассируемости шага:** в описании шага указывай ТЗ-N / ADR-N / §, которые он выполняет (например: `Шаг 2: SampleBlock (§2.1, ADR-03, ТЗ-4)`).
   - **Правило иерархии:** `ROADMAP.md` = этапы спецификации (один этап = одна задача, ID `<Префикс>-<§>.<N>`, см. Регламент §3). `_STATE_.md` = микро-шаги ТЕКУЩЕГО этапа (один шаг = одна сущность, ≤1–2 файла). Если этап слишком велик для одной сессии — это нормально: микро-шаги переживают сессии в `_STATE_.yaml`. В `_STATE_.md` держится только ОДНА активная задача — строка `🔄` в `ROADMAP.md`.

4. Полностью сформируй и запиши обновленный `_STATE_.md` по утвержденному шаблону из Шага 0.
5. Строго заполни поле `Вайтлист файлов в работе (Изменяемые файлы)`. Внеси туда только те файлы, которые физически необходимо мутировать для выполнения составленного плана.
6. Выведи сформированный микро-план и вайтлист файлов в чат пользователю и напиши:
   *"План микро-сессии сформирован. Вайтлист файлов заблокирован. Готов приступить к Шагу 1."*


Шаг 4: Цикл Выполнения (Итерационный кодинг)

Выполняй каждый микро-шаг плана строго по одной итерации за раз, следуя алгоритму:

1. **Проверка Вайтлиста:** Перед изменением любого файла убедись, что он внесен в `Вайтлист файлов в работе` в `_STATE_.md`. 
   - *СТРОГОЕ ТАБУ:* Если файла нет в вайтлисте, тебе ЗАПРЕЩЕНО использовать к нему инструменты записи (`write/patch`). Если файл критически необходим — сначала остановись и запроси у пользователя разрешение на расширение вайтлиста.
   - *Сначала — разбиение:* потребность добавить файлы в вайтлист (или выйти за 1–2 файла шага) — сигнал, что шаг слишком крупный. Прежде чем просить расширение, проверь, нельзя ли разбить шаг на подшаги по Правилу локализации (Шаг 3), при необходимости через временный мост (раздел «Делегирование субагентам»). Перепиши план в `_STATE_.yaml` (подшаги, сквозная перенумерация последующих шагов и ссылок на них) и только недостающие для подшагов файлы внеси в вайтлист, сообщив об этом пользователю.

2. **Внесение изменений:** Напиши или измени код для текущего `current_step`.
   - *Запрет на заглушки:* Категорически запрещено писать `// TODO`, `// ... остальной код`,  удалять существующие функции, если об этом не просили прямо,а также оставлять пустые callback/property в файлах `ui/*.slint` или скрывать нереализованный UI через прозрачность. Если меняешь файл (Rust или Slint) — пиши код полностью от начала до конца, сохраняя окружающий контекст и комментарии.
   - *Ссылки в коде:* новый и переписываемый код аудио-тракта ссылается в doc-комментариях на требования действующей документации: `ТЗ-N`, `ADR-N`, `§X.Y` (например, `/// Сброс ring за O(1) (ТЗ-99, ADR-13, §6.16).`). Ссылки на коды `A2.0`/`A3.0`/`AP5.0` в новый код не добавляются; старые пометки удаляются вместе с заменяемым кодом.

3. **Верификация (Сборка и Тесты):**
   - `cargo check` — выполняй **после каждого микро-шага** (проверка компиляции и типов, дёшево по времени и токенам).
   - `cargo clippy` и `cargo test` — полный прогон **не обязателен на каждом шаге**. Гоняй их раз в 2-3 микро-шага и обязательно перед финальным коммитом задачи (Шаг 5). Для одиночного шага, где это уместно, можно ограничиться `cargo test <фильтр>` по конкретному затронутому модулю вместо полного набора.
   - `cargo clippy` линтит весь крейт, а не отдельные файлы — сравнивай вывод не построчно целиком, а фильтруй по путям файлов из текущего вайтлиста (`cargo clippy --message-format=json | ...` или простой grep по пути в тексте предупреждения). Не держи в контексте полный лог дважды («до» и «после») — сверяй только строки, относящиеся к изменённым файлам.

4. **Обработка РЕЗУЛЬТАТОВ верификации:**

   - **СЦЕНАРИЙ А: УСПЕХ (Все проверки зеленые):**
     - Сбрось `Счетчик безуспешных компиляций` в `_STATE_.md` на `0/3`.
     - Отмечай шаг выполненным `[x]` в итерационном трекере.

## Стиль кода, SOLID и инженерные правила

Ты обязан писать код, соответствующий уровню **Staff System Engineer**, строго соблюдая архитектурную парадигму SOLID и специфику высокоточного аудио-движка:

> Правила этого раздела действуют, пока не противоречат `docs/01_audio_modes_v1.0/`. В частности, п. 4 «Синхронизация Bit-perfect» и «Режим Mixed» описывают прежнюю модель настроек; для кода аудио-тракта действуют модель режимов ADR-04, ТЗ-8 (дизеринг) и матрица режимов `02_tz.md` §5.

### 1. Архитектурные принципы SOLID в Rust-реализации

* **S (Single Responsibility / Единственная ответственность):** 
  Каждый модуль в `src/audio/` и каждый менеджер в `src/app/` решает только одну задачу. Логика декодирования (Symphonia), логика трансформации потока (Ресемплинг/Дизеринг) и логика вывода (Cpal) должны быть строго изолированы друг от друга. Потребители получают данные только через направленный `AppEvent-feed`.
* **O/D (Open-Closed & Dependency Inversion / Открытость к расширению и Инверсия зависимостей):** 
  Прямая зависимость от конкретных системных бэкендов (ALSA, WASAPI, ASIO) запрещена. Все взаимодействия с оборудованием и алгоритмами ресемплинга осуществляются через трейты (`AudioHost`, `AudioSource`). Поддержка нового режима вывода (например, WASAPI Exclusive) или нового алгоритма апсемплинга должна происходить путем создания новой структуры, реализующей существующий трейт, без изменения логики ядра `Player`.
* **I (Interface Segregation / Разделение интерфейсов):** 
  Трейты должны быть точечными. Поведение разделено на обязательный стриминг кадров и опциональные возможности (например, методы `seek()` или `duration()` в `AudioSource` имеют безопасные дефолтные реализации, избавляя DSD-декодеры от избыточного кода).

### 2. Безопасность памяти, типов и защита звукового тракта (No Clipping)

* **Абсолютное табу на `unwrap()` и скрытые паники:** 
  В коде аудио-движка вызовы `.unwrap()` **СТРОГО ЗАПРЕЩЕНЫ**. Используй `?`, `let-else` или консервативный `expect()`. Любая паника в монопольном режиме намертво вешает аудио-подсистему ОС.
* **Запрет на небезопасное приведение типов (Предотвращение цифровых щелчков):** 
  При масштабировании сэмплов или изменении разрядности (например, при расчете громкости или подготовке кадров) запрещено использовать оператор `as`, способный вызвать бесшумное переполнение и искажение сигнала. Используй строго `.clamp()` и безопасные методы преобразования с контролем границ (`try_into()`, `from_sample()`).
* **Бережная работа с Borrow Checker:** 
  Запрещено использовать `.clone()` на тяжелые объекты (`Track`, `Vec`, `Settings`) ради обхода ограничений времени жизни. Передавай данные по ссылкам `&`, управляй разделяемыми ресурсами через атомики и связку `Arc<Mutex>` / `Arc<RwLock>` только на границах потоков.

### 3. Потоковый аудио-DSP код реального времени (Hard Real-Time Constraints)

* **0 аллокаций в горячем цикле:** 
  Аудио-колбэки `cpal` и внутренние циклы ресемплеров/анализаторов должны работать с нулевым выделением памяти в куче (`Vec`, `Box`, `String`). Все буферы (включая DoP-контейнеры и FFT-окна) должны быть аллоцированы заранее при инициализации структур.
* **Запрет на блокировки и логирование в аудио-потоке:** 
  Внутри колбэков вывода звука запрещено использовать любые длительные блокирующие примитивы (`Mutex` не должен удерживаться), а также любые макросы логирования (`println!`, `eprintln!`, `tracing::*`). Сбой тайминга в аудио-потоке из-за вывода в консоль — это критическая ошибка (Drop-out/Заикание).

### 4. Инкапсуляция "Ромба" и аудиофильская синхронизация Slint UI

* **Инкапсуляция состояния:** 
  Все мутируемые поля состояния приложения инкапсулированы внутри `src/app/mod.rs`. Подмодули расширяют логику через `impl MusicApp` и общаются через видимость `pub(super)`.
* **Синхронизация Bit-perfect режима:** 
  Если в настройках активирован режим `bit_perfect`, код синхронизации интерфейса в `ui_manager.rs` обязан принудительно блокировать (`set_enabled(false)`) программные ползунки громкости, баланса и эквалайзера в Slint, переводя тракт в режим Direct Output (100% громкости на ЦАП без пересчета сэмплов). 
* **Режим Mixed:** 
  В обычном режиме (Mixed) громкость считается в точности 32/64-bit float с обязательным применением треугольного дизеринга (TPDF) перед выводом. 
  *КРИТИЧЕСКИЙ ГАЙДЛАЙН ДЛЯ DSP:* Запрещено использовать блокирующий или медленный `rand::thread_rng()` внутри аудио-колбэка для генерации TPDF. Шум должен вычисляться через сверхбыстрый безалокационный генератор (например, простой линейный конгруэнтный генератор LCG / PRNG, сдвиговый регистр LFSR или предвычисленный массив/LUT-таблицу), чтобы гарантировать соблюдение Hard Real-Time ограничений.

- `app/*` — «Ромб-декомпозиция»: методы `MusicApp` разнесены по `impl`-блокам в подмодулях. Все поля остаются в `mod.rs`, подмодули вызывают методы друг друга через `pub(super)`.

### Как связывается Slint

- `build.rs` компилирует `ui/app.slint` → генерирует структуру `AppWindow` в Rust (`slint::include_modules!()` в `src/app/mod.rs`).
- `AppWindow` содержит `in-property`, `callback` и т.д.; Rust подписывается через `ui.on_<callback>(...)` и читает/пишет через `ui.set_<prop>(...)` / `ui.get_<prop>()`.
- Slint-файлы импортируют друг друга через `import { Name } from "file.slint";`. `app.slint` — точка входа, остальные — компоненты.
- Стиль UI задан в `build.rs` (`fluent`).

### Единый экземпляр настроек (SettingsStore)

- `MusicApp` — единственный мутирующий владелец `SettingsStore`; читает с диска один раз при старте (`SettingsStore::load()`).
- Остальные модули (cover, output) получают `Settings` явно по ссылке через параметры (`CoverConfig::from_settings(&Settings)`); глобального снапшота конфига нет.

## Features

Собственных Cargo features нет (в Cargo.toml `[features]` отсутствует).

Зависимости подключают свои features:
- `slint` 1.17 — `std, compat-1-2, backend-winit-x11, renderer-winit-skia` (X11-бэкенд, Skia GPU-рендер; требует g++ и libstdc++-dev в системе); build-dependency: `slint-build` 1.17.
- `symphonia` 0.6 — кодеки: `flac, wav, aiff, pcm, mp3, ogg, aac, alac, isomp4, vorbis, adpcm`.
- `tokio` 1.53 — `rt, macros, sync` (только для `mpsc` в tray).
- Аудио/визуализация: `cpal` 0.18 (вывод), `rustfft` 6.4 (БПФ), `rtrb` 0.4 (кольцевой буфер), `clru` 0.6 (LRU-кэш изображений).
- Данные/интеграции: `rfd` 0.17 (диалоги файлов/папок), `ureq` 2 + `tls` (HTTP для обложек), `serde`/`serde_json`/`toml` (сериализация), `dirs` 6, `walkdir` 2 (сканирование библиотеки), `rand` 0.8 (shuffle), `image` 0.25 + `png` (рендер обложек/кэш).
- Трей: `ksni` 0.3.6 (StatusNotifier).

## Запуск с разными конфигурациями

- Обычный запуск: `cargo run`.
- Трей требует StatusNotifier-хост (KDE/GNOME AppIndicator). Если хоста нет, трей молча не появляется — приложение продолжает работать.
- Эмуляции бэкенда/winit в коде нет. Для headless-тестирования Slint предоставляет тестовый бэкенд, но в проекте он не настроен.
