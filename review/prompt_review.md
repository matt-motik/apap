## Что проверять

### 1. Real-time аудио-поток

- Нет аллокаций и освобождений памяти в аудио-колбэке: Vec, Box, String, а также drop последней ссылки Arc. Нет системных вызовов.
- Нет блокирующих примитивов (Mutex, RwLock, Condvar) и логирования на пути аудио-данных.
- Обмен UI ↔ аудио идёт через lock-free структуры (rtrb / RingBuffer) и атомики.
- Нет паник в колбэке: индексация, assert, unwrap/expect, арифметическое переполнение.
- Промежуточный формат данных (например, ring на f32) не теряет бит там, где режим требует bit-perfect (32-bit int PCM, DoP).

### 2. Slint и UI-поток

- Slint UI отвечает только за отображение. Декодирование, DSP, открытие файлов и устройства выполняются в фоновых потоках. В UI-потоке нет блокирующего I/O.
- Корректное использование slint::ComponentHandle, as_weak()/upgrade(), upgrade_in_event_loop: без утечек, циклов ссылок и deadlock'ов.
- Свойства обновляются только при реальном изменении значения, без лишних перерасчётов layout на каждом тике.

### 3. Идиоматичный Rust и безопасность

- Нет unwrap/expect в продакшн-коде. Ошибки типизированы (enum), а не String, если от вида ошибки зависит поведение.
- unsafe при FFI с драйверами обоснован и изолирован.
- Корректное владение и времена жизни; нет .clone() тяжёлых объектов ради обхода borrow checker.

## Требования к режимам воспроизведения

Три автоматических режима. Для каждого проверь соответствие кода требованиям.

### Режим 1. Совместимый — «Играем всегда»

- Цель: воспроизведение не прерывается из-за других приложений.
- Доступ: Shared / non-exclusive.
- Поведение: плеер передаёт системному аудиосерверу максимально качественный поток, который способен сформировать.
- Граница гарантии: дальнейшие преобразования PipeWire / Windows Audio / CoreAudio — вне зоны ответственности плеера, но UI должен честно об этом сообщать.
- Принцип: совместимость и непрерывность важнее bit-perfect («нажал Play — играет», как в AIMP/Winamp).

### Режим 2. Оптимальный — «Лучшее из возможного»

- Доступ: монопольный / Exclusive.
- Поведение: источник передаётся без преобразований, если устройство его поддерживает. Частота, разрядность и число каналов выбираются по реальным возможностям устройства.
- Fallback: если формат не поддерживается, выполняется качественный ресемплинг / конвертация в поддерживаемый формат. При несовпадении числа каналов — корректный downmix, а не отбрасывание каналов.
- Примеры:
  - FLAC 24/192 → ЦАП 24/192 → вывод без SRC;
  - FLAC 24/192 → ЦАП max 24/96 → 24/96 после качественного SRC;
  - DSD512 → ЦАП max DSD256 → поддерживаемый путь либо преобразование (см. решение пользователя 6).
- Принцип: музыка играет всегда, плеер сам делает лучший вывод, доступный устройству. Это best possible quality, а не «bit-perfect любой ценой».

### Режим 3. Строгий — «Только лучшее»

- Доступ: монопольный / Exclusive.
- Поведение: исходный поток передаётся без преобразований.
- Запрещено: ресемплинг, смена разрядности, изменение числа каналов, громкость, дизеринг, эквалайзер и любые другие преобразования.
- При несовместимости (формат / sample rate / число каналов / DSD-режим / exclusive недоступен):
  1. текущий трек не воспроизводится;
  2. пользователь получает понятное сообщение о причине;
  3. плеер автоматически переходит к следующему треку плейлиста;
  4. следующий трек проверяется по тем же правилам.
- Несовместимость не останавливает плейлист. Принцип: «не нарушать bit-perfect, но продолжать воспроизведение там, где это возможно».
- Краевые случаи, которые обязательно проверить:
  - весь плейлист несовместим при Repeat All — не должно быть бесконечного цикла;
  - Repeat One — пропуск ведёт к следующему треку, а не к тому же;
  - пропало устройство — это остановка с ошибкой, а не пропуск трека;
  - серия пропусков не замораживает UI и не спамит уведомлениями;
  - несовместимость по возможности определяется заранее по метаданным, без захвата устройства.

### Общие правила режимов

- DSD-фолбэк зафиксирован: Native → DoP → PCM. Порядок менять нельзя, отдельные пути можно только отключать.
  - В режиме 1 (Shared) Native и DoP недоступны: системный микшер разрушает DoP-маркеры. DSD воспроизводится только через PCM.
  - В режиме 3 путь PCM запрещён, переход Native → DoP разрешён (DoP bit-perfect).
- Платформы: проверь, достижим ли exclusive на каждой ОС (ALSA hw:, WASAPI exclusive, CoreAudio hog mode). Если нет, режимы 2 и 3 должны честно сообщать об этом, а не молча работать в shared.

## Бейдж проверки bit-perfect

> Требования этого раздела уточнены решениями пользователя 5, 10 и 11 (review/01_review.md): бейдж bit-perfect и кнопка-бейдж «Тест» — отдельные элементы; побитовая сверка выполняется только по запросу; в Совместимом режиме у бейджа нейтральное состояние «Shared». При противоречии действуют решения.

В статус-баре должен быть бейдж, который показывает, что сигнал действительно bit-perfect, а не только что bit-perfect «включён в настройках».

Требования:

- Бейдж отражает фактическое состояние тракта, а не значение флага в настройках. Зелёный только при подтверждении, никогда по умолчанию или по предположению.
- Минимум три состояния, различимые не только цветом:
  - «Bit-perfect ✓ (подтверждено)» — все проверки пройдены;
  - «Bit-perfect ? (не подтверждено)» — программный тракт плеера чистый, но часть проверок невозможна на этой платформе или устройстве;
  - «Не bit-perfect» — с короткой причиной: известное преобразование (ресемплинг, громкость ≠ 100 %, дизеринг, DSD→PCM, смена разрядности, downmix).
- В Shared-режиме бейдж не может подняться выше «Bit-perfect ? (не подтверждено)»: плеер не контролирует системный микшер. «Не bit-perfect» ставится только при известном преобразовании.
- Что должно проверяться:
  - статически: выбранный формат устройства совпадает с источником по частоте, разрядности и каналам; нет ресемплинга, громкости, дизеринга, EQ; доступ exclusive;
  - по факту открытого потока: реальные параметры, которые принял драйвер (для ALSA — фактические hw_params устройства, а не запрошенные); отсутствие системного микшера на пути;
  - в рантайме, только в тракте, где преобразований быть не должно: контрольная проверка, что сэмплы на выходе колбэка побитово совпадают с декодированными (для DoP — после распаковки). Например, лёгкий хеш/CRC блоков на стороне worker и колбэка без аллокаций и блокировок, либо периодическая выборочная проверка. Оцени, как сделать это без нарушения real-time ограничений.
- Граница гарантии: бейдж не может подтвердить, что происходит внутри ЦАП или драйвера после точки передачи. Это должно быть честно указано в подсказке или отчёте.
- В режиме 1 бейдж показывает, что плеер отдал системе, и явно сообщает, что дальнейшие преобразования вне контроля плеера.
- Обновление бейджа не нагружает UI: пересчёт только при изменении состояния, чтение атомиков без блокировок.
- Если в коде уже есть бейдж или отчёт bit-perfect, проверь его на честность: может ли он быть зелёным при усечении разрядности, при громкости < 100 %, при shared-доступе или при DSD→PCM.

### Окно «Путь сигнала» (открывается по нажатию на бейдж)

Нажатие на бейдж открывает окно, где понятным языком показан весь путь сигнала от файла до ЦАП и все преобразования на нём. Цель — дать пользователю основания для решения: изменить тонкие настройки плеера, изменить настройки ОС или задуматься о смене оборудования.

Путь показывается как цепочка этапов:

1. Источник: контейнер, кодек, частота, разрядность, каналы, DSD-частота; для lossy-форматов — явная пометка, что bit-perfect возможен только относительно декодированного потока.
2. Декодер: декодирование без потерь или с потерями.
3. Обработка в плеере: ресемплинг (алгоритм, из какой частоты в какую), смена разрядности (расширение или усечение), дизеринг, громкость, эквалайзер, downmix, DSD→PCM, упаковка DoP (как транспорт без потерь).
4. Вывод: API и режим доступа (ALSA hw:, PipeWire, WASAPI Shared/Exclusive, CoreAudio), фактические параметры, принятые драйвером.
5. Уровень ОС: системный микшер и его частота/формат (например, частота графа PipeWire или формат общего режима Windows), если их можно определить. Если нельзя — честная пометка «не контролируется плеером, возможно преобразование».
6. Устройство/ЦАП: за границей гарантии плеера; показывается только то, что известно о принятом формате.

Для каждого этапа окно показывает:

- статус: «без изменений» / «преобразование без потерь» / «преобразование с потерями» / «неизвестно». Статус различим не только цветом;
- что именно изменилось (например, «192 кГц → 96 кГц, SRC Sinc»);
- почему: какая настройка плеера, ограничение устройства или политика ОС вызвала преобразование;
- достоверность: факт подтверждён (прочитан у драйвера или проверен в рантайме) или только предполагается.

Рекомендации в окне разделены на три типа:

- тонкие настройки плеера: что можно изменить в рамках текущего режима, с кнопкой перехода прямо к нужной настройке;
- настройки ОС: что изменить в системе (например, разрешённые частоты PipeWire, разрешение монопольного режима и формат устройства в Windows), с кратким пояснением;
- оборудование: если ограничение аппаратное (устройство не поддерживает нужную частоту, разрядность, число каналов или DSD-путь), так и сказать, указав, какие характеристики устройства нужны для bit-perfect на этом материале.

Правила для рекомендаций:

- рекомендации не противоречат текущему режиму. Если bit-perfect достижим только в другом режиме, окно говорит об этом явно и предлагает сменить режим, а не менять настройку, запрещённую режимом;
- в режиме 1 окно явно показывает, где заканчивается ответственность плеера и какие преобразования может выполнить ОС;
- в режиме 3 для пропущенных треков окно показывает, какой этап сделал трек несовместимым и что изменить, чтобы он воспроизводился.

Прочее:

- окно обновляется при смене трека, устройства или настроек, без пересчёта на каждом тике;
- данные для окна берутся из готового снимка состояния тракта, окно не выполняет I/O и не обращается к устройству;
- отчёт можно скопировать текстом (для форума, поддержки или сравнения до/после).

## Критерии оценки

1. Баги и логические ошибки — уязвимости, краевые случаи, утечки ресурсов.
2. Производительность — узкие места, лишние перерисовки/запросы, неоптимальные алгоритмы (в том числе DSD→PCM на DSD256/512).
3. Читаемость и архитектура — чистота кода, SOLID/DRY, понятность имён.
4. Тестируемость — насколько легко покрыть код тестами; какие тесты нужны для режимов, бейджа и окна «Путь сигнала».

   - приоритет: P0 — риск для слуха/оборудования, паника, ложное заявление о bit-perfect; P1 — нарушение логики режима; P2 — качество и производительность;
   - обоснование: ссылка на R-N или пометка «новое требование»;
   - критерий приёмки: автоматический тест, замер с числовым порогом или ручной сценарий с шагами и ожидаемым результатом. Формулировки вроде «качественный», «быстро», «корректно» без числа или сценария недопустимы;
   - зависимости от других требований, если есть.
5. **Матрица режимов:** таблица «параметр × режим: зафиксирован / настраивается / недоступен» для всех параметров тракта. Противоречивых сочетаний в ней быть не должно.
6. **Нефункциональные требования:** RT-бюджет (аллокации, блокировки, время колбэка), CPU-бюджеты, отзывчивость UI. Где числа не заданы пользователем или ревью — не придумывай их, вынеси в открытые вопросы.
7. **Покрытие находок:** таблица R-1…R-28 → ТЗ-N. Каждая находка либо покрыта требованием, либо помечена «не включено» с причиной. Непокрытых находок быть не должно.
8. **Порядок внедрения по приоритетам:** какие группы требований реализуются первыми (сначала P0) и какие зависимости это определяют. Без привязки к конкретной реализации.
9. **Открытые вопросы:** всё, что требует решения пользователя, с вариантами и рекомендацией.

### Часть 3. Спецификация (как это должно быть сделано)

#### Входные данные

- Основа — утверждённое ТЗ (review/02_tz.md). Спецификация выполняет требования ТЗ-N и не вводит новых требований; если требование невозможно выполнить, это фиксируется в открытых вопросах, а не обходится.
- review/01_review.md — справочно: находки R-N, решения пользователя и предложения ревью как варианты для ADR.
- Решения пользователя имеют приоритет над предложениями ревью и над требованиями этого промта.
- Модель данных: типы Rust для режимов, опций каждого режима, типизированных ошибок несовместимости, состояний бейджа.
- Модель пути сигнала: тип этапа, статус преобразования, причина, достоверность факта и тип рекомендации (плеер / ОС / оборудование), чтобы окно строилось из данных, а не из разрозненных флагов.
- Архитектура потоков: кто владеет устройством, декодером, ring; как события доходят до UI.
- Алгоритмы: выбор формата и устройства по режиму, DSD-цепочка, логика пропуска треков, проверки bit-perfect.
- Инварианты, которые обеспечиваются типами, и те, что проверяются в рантайме.
- План тестов: конкретные тесты с названиями и ожидаемым результатом.
- Этапы внедрения: порядок, при котором проект остаётся в рабочем состоянии после каждого этапа.
- Открытые вопросы: всё, что требует решения пользователя, с вариантами и рекомендацией.
- Архитектурные решения в формате ADR: для каждого ключевого выбора (архитектура потоков, формат ring, модель режимов, модель пути сигнала, способ рантайм-проверки, SRC, DSD→PCM) — рассмотренные варианты (включая предложения из ревью), критерии выбора, выбранный вариант и последствия. Каждое решение ссылается на требования ТЗ-N, которые оно выполняет.
