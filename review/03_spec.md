Правила документа:

- Спецификация выполняет требования ТЗ-N и не вводит новых требований. Если требование нельзя выполнить выбранной реализацией, это фиксируется в «Открытых вопросах» (§9), а не обходится.

- Обозначения: **ТЗ-N** — требование ТЗ; **R-N** — находка ревью; **ОВ-N** — решение по открытому вопросу (§10 ТЗ); **решение N** — решение пользователя из `01_review.md`.

## 1. Архитектурные решения (ADR)

Формат каждого ADR: **Контекст** → **Выполняет** (ТЗ-N) → **Варианты** (включая предложения ревью) → **Критерии** → **Решение** → **Последствия**.

### ADR-01. Архитектура потоков: поток движка

**Контекст.** Сейчас `Player` принадлежит `MusicApp` (`Rc<RefCell<…>>`), и все его операции выполняются в event-loop Slint. Среди них открытие файла с построением seek-индекса, перечисление ALSA-устройств, сборка потока, `join` воркера (R-4). Добавляются операции, которые по природе ждут: резервирование через D-Bus (до 5 с, ОВ-34), обнаружение устройств, автоматический повторный захват.

**Выполняет:** ТЗ-103, ТЗ-104, ТЗ-91, ТЗ-45, ТЗ-51, ТЗ-102, ТЗ-126.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Оставить `Player` в UI-потоке, вынести в фон только отдельные операции | Каждую новую блокирующую операцию придётся выносить заново. Состояние движка разрывается между потоками. Нарушает ТЗ-103 по построению |
| Б | Отдельный поток движка владеет всем управлением аудио; UI общается командами и событиями (предложение ревью R-4, §6.6) | Одна точка владения устройством и сессией. UI не может заблокироваться на движке |
| В | Движок как async-актор на tokio (tokio уже есть для трея) | Блокирующие вызовы alsa-lib и symphonia всё равно пришлось бы уводить в `spawn_blocking`. Тянет runtime в аудио-подсистему без выигрыша |
| Г | Слить управление с потоком декодирования | Поток декодирования живёт один трек. Замок и `DeviceClaim` живут дольше трека (ТЗ-43). Слияние смешивает времена жизни |

**Критерии:** итерация UI ≤ 50 мс (ОВ-23); одна точка владения устройством (решение 3); тестируемость без UI (ТЗ-114); нет новой runtime-зависимости.

**Решение: Б.** Поток `apap-engine` владеет замком и `DeviceClaim`, кэшем устройств, планировщиком пути, текущей сессией воспроизведения, хранилищем результатов «Теста» и снимком пути сигнала. UI посылает `EngineCmd` через неблокирующий `Sender`. Движок отвечает `EngineEvent` (ADR-02). Длительные ожидания внутри движка (ответ на `RequestRelease`, открытие декодера) не блокируют цикл движка: они выполняются в служебных потоках, а результат приходит во входящую очередь движка как внутреннее сообщение (`EngineMsg::Internal`). Схема потоков — §4.

**Последствия.**

- `MusicApp` больше не держит `Player`. Он держит `EngineHandle { tx: Sender<EngineMsg>, … }` и зеркальное UI-состояние (`UiAudioState`), которое обновляется только событиями.
- Устраняется цикл сильных ссылок R-20. `MusicApp` хранит `Weak<AppWindow>`. Выход проходит через `EngineCmd::Shutdown` и ожидание `EngineEvent::ShutdownComplete` с таймаутом в `run_event_loop_until_quit` (ТЗ-45).
- Все проверки времени (5 с резервирования, 10 с повторного захвата, 1 с сообщения о потере устройства) выполняет движок по инжектируемым часам (ADR-20).

### ADR-02. Доставка событий в UI и обновление свойств

**Контекст.** Бейдж и окно «Путь сигнала» должны пересчитываться только по событию (ТЗ-60, ТЗ-83). Свойства Slint должны записываться только при изменении (ТЗ-106). Сообщение о потере устройства должно появиться не позднее 1 с (ОВ-24). Сейчас отчёт пересобирается каждые 100 мс (R-22).

**Выполняет:** ТЗ-60, ТЗ-83, ТЗ-106, ТЗ-56, ТЗ-51 (срок 1 с), ТЗ-79.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | `slint::invoke_from_event_loop` с замыканием, которое несёт событие и `Weak<AppWindow>` (ревью §6.6) | Замыкание должно быть `Send`. Доступ к `MusicApp` (`Rc`) из него невозможен без thread-local |
| Б | Очередь `EngineEvent` (mpsc), которую UI разбирает на существующем тике 100 мс | Просто. Задержка до 100 мс — в пределах ОВ-24. Лишние пробуждения при пустой очереди |
| В | Очередь (mpsc) + пробуждение через `invoke_from_event_loop` пустым `Send`-замыканием, которое вызывает разбор очереди через thread-local `Weak<RefCell<MusicApp>>`; тик разбирает очередь как страховка | Задержка — одна итерация event-loop. Пустая очередь стоит одного `try_recv` |

**Критерии:** задержка события ≤ 1 с; ноль пересчётов при пустой очереди; нет доступа к `Rc` из чужого потока.

**Решение: В.** Движок пишет события через трейт `EventSink`. Рабочая реализация кладёт событие в `std::sync::mpsc` и, если флаг `wake_pending` был сброшен, вызывает `slint::invoke_from_event_loop(drain_engine_events)`. Функция разбора в UI-потоке выбирает все события, применяет их к `UiAudioState` и пишет в Slint только изменившиеся поля. Сравнение идёт с последним записанным значением: у каждого поля в `UiAudioState` есть копия «записано в UI». Тестовая реализация `EventSink` складывает события в `Vec`.

Каждый снимок пути и каждый вердикт несут `generation: u64` сессии. UI отбрасывает события с поколением меньше текущего (ТЗ-56: после неудачного открытия параметры предыдущего трека не показываются).

**Последствия.** Окно «Путь сигнала» получает готовый `Arc<SignalPath>` и `DynamicPathState` (§3) и не выполняет I/O (ТЗ-79). Модели списков окна обновляются через `VecModel::set_row_data`, а не пересоздаются (ТЗ-106).

### ADR-03. Формат ring и единственная точка квантования

**Контекст.** Сейчас между декодером и колбэком передаётся только `f32` (`AudioSource::next_frames -> &[f32]`, `RingBuffer<f32>`). 32-битный PCM теряет 8 младших бит (R-3). Квантование `×32767` несимметрично нормировке symphonia `/32768` (R-3). Громкость и дизеринг применяются в колбэке по флагам, а не по факту преобразований (§7 п. 22 ревью).

**Выполняет:** ТЗ-4, ТЗ-5, ТЗ-6, ТЗ-7, ТЗ-8, ТЗ-17, ТЗ-41, ТЗ-98, ТЗ-112.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Только `f32` (текущее) | Не переносит 32-битный целый PCM. Отвергнут (R-3) |
| Б | Только `f64` | Точен для всех целых ≤ 32 бит. Память и пропускная способность ×2: 384 кГц × 2 кан × 10 с = 61 МБ на ring |
| В | Только `i32`; пути с DSP квантуются в `i32` в декодере, громкость — в колбэке | Двойное квантование на путях с DSP. Дизеринг нужен в двух местах, иначе ТЗ-8 не выполняется последовательно |
| Г | Типизированный ring: `ExactI32` (целые, выравнивание влево) для путей без DSP и `F32` для путей с DSP; квантование только в колбэке (ревью §5 п. 1, §7 п. 4: «два типа ring») | Bit-exact там, где нужен. Одна точка квантования и дизеринга. Тип ring выбирается при открытии и не меняется до конца сессии |

**Критерии:** bit-exact для 16/24/32 бит (ТЗ-4, ТЗ-5); одна точка квантования, дизеринг только при переквантовании (ТЗ-8); громкость меняется без переоткрытия потока (ТЗ-41, ОВ-5); память ≤ текущей.

**Решение: Г.**

- `RingPayload::ExactI32 { valid_bits }` — сэмпл исходной разрядности, выровненный по старшему биту `i32` (для 16 бит: `s << 16`). Младшие `32 − valid_bits` бит равны нулю. Используется для PCM без SRC, downmix и DSD→PCM: passthrough, zero-padding, моно → 2 канала, усечение в Оптимальном режиме, а также для полезной нагрузки DoP (ADR-12). Lossy-источники (MP3, AAC, Vorbis) тоже идут через `ExactI32` с `valid_bits = 24`: декодер округляет свой float-выход до 24-битных целых без дизеринга, и это часть этапа «Декодер» (ОВ-36, §6.10).
- `RingPayload::F32` — результат DSP в нормировке `[−1, 1)`. Используется, если в плане есть SRC, downmix или DSD→PCM. Это выход обработки в потоке декодирования, а не выход декодера: декодер `F32`-блоков не выдаёт (§2.1).
- Колбэк — единственная точка, где значения приводятся к формату точки передачи. Громкость — атомик в `SessionShared`. Дизеринг TPDF применяется тогда и только тогда, когда колбэк переквантовывает: громкость ≠ 100 % при целом выходе, `F32`-полезная нагрузка при целом выходе, `valid_bits` больше разрядности выхода (усечение). При выходе `F32` (Совместимый режим) дизеринг не применяется: сокращения разрядности нет.
- Стадия `AtomicGain` читает `gain_bits` и `muted` **один раз за период**, до цикла по сэмплам, и выбирает одну из трёх ветвей на весь период:
  - `GainState::Unity` (`gain_bits == 1.0f32.to_bits()`) и не mute — `ExactI32` передаётся **в целочисленном виде без изменений**: те же сдвиги, что у `NoGain`, без перевода во float и без дизеринга. Для `F32`-нагрузки — квантование без умножения (дизеринг — по правилу выше, потому что `F32` уже результат DSP);
  - `GainState::Scaled` — `ExactI32` переводится в `f64` (точно для любых 32-битных целых), умножается на коэффициент, затем TPDF и квантование. `F32`-нагрузка умножается в `f32`;
  - `GainState::Muted` — на выход идут нули формата (у DoP стадии усиления нет, ADR-12).

  Громкость 100 % движок записывает в атомик как точное `1.0f32`, без вычислений, поэтому сравнение по битам однозначно. Итог: в Оптимальном режиме при громкости 100 % выход побитово равен исходному потоку, в том числе для 32-битного источника (ТЗ-5, И-Р19).
- Перевод формата без обработки — сдвиги: `S32_LE` — копия; `S24_LE` — `>> 8` (арифметический, даёт знаковое расширение, ОВ-32); `S24_3LE` — три младших байта от `>> 8`; `S16_LE` — `>> 16`; `F32` — `s as f32 / 2³¹` (точно при `valid_bits ≤ 24`). Правильность этих сдвигов обеспечивает инвариант «младшие биты нулевые» (§5.1, И-Т7).
- Масштаб при квантовании `F32 → N бит` симметричен нормировке декодера: `round(x · 2^(N−1))` с ограничением `[MIN, MAX]` (ТЗ-7, ТЗ-17).

**Последствия.**

- `AudioSource::next_frames` заменяется на `fn next_block(&mut self) -> Result<Option<SampleBlock<'_>>, FileError>`, где `SampleBlock` — `ExactI32` / `DsdBytes` (§2.1). Декодер PCM читает `AudioBuffer<i32>` symphonia без промежуточного `f32` (FLAC и ALAC уже отдают значения, сдвинутые влево до 32 бит). Lossy-декодер читает `AudioBuffer<f32>` symphonia и округляет в `ExactI32 { valid_bits: 24 }` (ОВ-36).
- Колбэк мономорфизируется по паре «тип полезной нагрузки × формат выхода» и по стадии усиления (ADR-06, §2.9). Ветвления по формату внутри цикла по сэмплам нет.
- Изменение громкости в Оптимальном режиме не переоткрывает поток. Движок пересобирает только снимок пути (добавляет или убирает этапы «громкость» и «дизеринг») с новым поколением.
- Решение касается только аудио-тракта. Визуализатор получает свой tap (ADR-18).

### ADR-04. Модель режимов и настроек

**Контекст.** Поведение сейчас задают девять независимых настроек (`ExclusiveMode`, `FallbackPolicy`, `ResamplerMode`, `FallbackRatePolicy`, `ClockFamily`, `fixed_rate`, `bit_perfect`, `ResamplerDither`, `DsdMode`). Противоречия представимы и исправляются авто-коррекцией (`resampler_fixed_fallback_guard`, R-10, §3 и §7 п. 1–3 ревью).

**Выполняет:** ТЗ-18, ТЗ-19, ТЗ-20, ТЗ-34, ТЗ-41, ТЗ-93, ТЗ-94, ТЗ-95, ТЗ-96, ТЗ-97, ТЗ-124, матрица §5 ТЗ.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Оставить флаги, добавить валидацию сочетаний | Противоречия остаются представимыми; валидация — та же авто-коррекция. Нарушает ТЗ-94 |
| Б | `enum PlaybackMode { Compatible(Opts), Optimal(Opts), Strict(Opts) }` с опциями внутри варианта (ревью §7 п. 1–2) | Противоречия непредставимы. Но при переключении режима опции неактивных режимов теряются, если хранить только активный вариант |
| В | Б + отдельное хранение опций всех трёх режимов: `ModeSettings { active, compatible, optimal, strict }` (ревью §7 п. 2, «Хранение `ModeSettings`») | Противоречия непредставимы. Значения каждого режима сохраняются при переключении (ТЗ-93) |

**Критерии:** противоречивое сочетание нельзя выразить ни в UI, ни в файле (ТЗ-94); значения режимов переживают переключение и перезапуск (ТЗ-93, ТЗ-19); параметры, зафиксированные режимом, видны с текущим значением (ТЗ-95).

**Решение: В.**

- В каждой структуре опций есть только поля, которые матрица §5 помечает «Н» для этого режима (§2.2). У Строгого режима — только устройство и размер буфера.
- Файловый формат отделён от доменного типа. `ModeSettingsDto` (serde) содержит `#[serde(flatten)] unknown: BTreeMap<String, toml::Value>` в каждом разделе. Преобразование `ModeSettingsDto → ModeSettings` записывает в журнал и отбрасывает неизвестные ключи (ТЗ-94). Недопустимое значение известного ключа заменяется значением по умолчанию с записью в журнал; этого прямо требует ТЗ-34 для ремодуляции. Значения других режимов не меняются.
- Доступность параметров определяется одной статической таблицей `PARAMS: &[ParamDescriptor]` с функцией `availability(ParamId, ModeKind) -> Availability` (§2.2). Таблица — единственный источник матрицы §5 ТЗ. Её читают диалог настроек (ТЗ-95), фильтр рекомендаций (ТЗ-82) и автотест «таблица = матрица §5».
- Действующая политика тракта — `PathPolicy<'a>`: ссылка на опции активного режима плюс режим. Её получает каждое открытие трека. Поэтому применённые при старте и при сохранении политики совпадают по построению (ТЗ-19, R-10).
- Миграции нет (ОВ-27). Файл без `[playback] schema = 2` или с нераспознанным разделом даёт `ModeSettings::default()` (Совместимый режим) и одну запись в журнал (ТЗ-97, ТЗ-124).

**Последствия.** Удаляются `ExclusiveMode`, `FallbackPolicy`, `ResamplerMode`, `FallbackRatePolicy`, `ClockFamily`, `bit_perfect`, `DsdMode`, `TargetBitDepth`, `TargetSampleRate`, значение `Triangular` в дизеринге (ТЗ-96), функция `resampler_fixed_fallback_guard` и её тест (ТЗ-94).

### ADR-05. Модель пути сигнала: план и снимок

**Контекст.** `StreamDesc` хранит запрошенные параметры, строковую причину DSD и один слот `fallback` (R-15, R-16, §7 п. 6–8 ревью). Окно строится эвристикой по флагам (R-22). Несовместимость в Строгом режиме нужно определять до открытия потока (ТЗ-38), а для пропущенного трека показывать, какой этап его заблокировал (ТЗ-80).

**Выполняет:** ТЗ-38, ТЗ-52, ТЗ-56, ТЗ-57, ТЗ-70…ТЗ-84; правила планировщика по режимам — ТЗ-13, ТЗ-21…ТЗ-29, ТЗ-31…ТЗ-33, ТЗ-35…ТЗ-37, ТЗ-39 (сами правила — в «Алгоритмах»).

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Расширить `StreamDesc` флагами | Причины продолжают вытеснять друг друга. Добавление эквалайзера требует правок бейджа, окна и рекомендаций. Нарушает ТЗ-72, ТЗ-73 |
| Б | `SignalPathSnapshot { stages: Vec<Stage>, … }` после открытия (ревью §7 п. 6) | Честный снимок открытого потока. Нет модели для предпроверки и пропущенного трека |
| В | Две фазы: `PathPlan` (чистая функция метаданных, возможностей устройства и политики, до открытия) → `SignalPath` (план плюс факты драйвера и ОС, после открытия). Обработка — список `Transform` с дескриптором | Один и тот же план служит предпроверке, открытию, окну пропущенного трека и бейджу |

**Критерии:** все преобразования перечислены (ТЗ-72); предпроверка без открытия потока (ТЗ-38); добавление вида обработки затрагивает только его описание (ТЗ-73); данные окна готовы заранее (ТЗ-79).

**Решение: В.** Модель — §3. Ключевые свойства:

- `plan(&SourceFormat, &DeviceCaps, PathPolicy) -> Result<PathPlan, Blocked>` — чистая функция без I/O. `Blocked` несёт `Incompatibility` и этап, на котором план остановился (ТЗ-80).
- `SignalPath::from_opened(plan, OpenedFacts)` дополняет план фактами: принятые драйвером параметры с достоверностью, уровень ОС, резервирование. Если фактическая частота отличается от запрошенной, путь строится по ADR-07: в Оптимальном режиме — перепланирование с SRC в фактическую частоту, в Строгом — пропуск (ТЗ-30, ТЗ-113).
- Этапов всегда шесть, порядок фиксирован (ТЗ-70). Состав этапа «Обработка» — `SmallVec<[Transform; 6]>`. Логика бейджа, окна и рекомендаций обращается к преобразованию только через методы дескриптора `TransformKind` (§3.3). Эквалайзер — новый вариант плюс ветки в дескрипторе.
- Снимок неизменяем (`Arc<SignalPath>`). Меняющиеся во время воспроизведения величины (underrun, ошибки декодирования, MD5, состояние «Теста») хранятся отдельно в `DynamicPathState` (§3.5) и приходят событиями при изменении.

**Последствия.** Удаляются `StreamDesc`, `FallbackReason`, `bp_report.rs` с `positives` и итогом `flag && reasons.is_empty()` (§7 п. 6–8 ревью). Копирование отчёта текстом (ТЗ-84) — `impl Display for PathReport`, который строится из снимка.

### ADR-06. Бейдж, «Тест» и замок — три независимых автомата

**Контекст.** Решение 5 разделяет ответственность: режим — политика тракта; замок — владение устройством; бейдж — есть ли преобразования; «Тест» — подтверждено ли проверкой. Решение 11 добавляет нейтральное состояние «Shared». Сейчас бейдж собран из трёх bool (`bp-active`, `dsd-not-bp`, `bp-resample`) и отражает флаг настроек (R-1).

**Выполняет:** ТЗ-41, ТЗ-42, ТЗ-43, ТЗ-44, ТЗ-45, ТЗ-46, ТЗ-50, ТЗ-52…ТЗ-58, ТЗ-59 (клик по бейджу в любом состоянии открывает окно), ТЗ-60…ТЗ-62, ТЗ-121 (подсказка состояния `Held`), ТЗ-125.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Единый бейдж с тремя состояниями `Confirmed / Unconfirmed / NotBitPerfect` и постоянной рантайм-проверкой (ревью R-1, §6.1) | Отменён поправками к ревью (решения 5, 10, 11) |
| Б | Один общий автомат «режим × замок × бейдж × тест» | Экспоненциальное число состояний; нарушает разделение ответственности решения 5 |
| В | Три автомата: `LockState` (в движке), `BadgeState` (чистая функция снимка), `TestBadge` (из хранилища результатов и текущего теста) | Каждый автомат тестируется отдельно. Связи между ними — только через явные входы функций |

**Решение: В.**

- **Бейдж** — `fn verdict(path: &SignalPath, gain: GainState, test: Option<&TestRecord>) -> BadgeState`. Для Shared и Exclusive возвращаемые подтипы разные (`SharedBadge`, `ExclusiveBadge`, §2.5), поэтому «Bit-perfect» в Совместимом режиме непредставим (ТЗ-54). `ExclusiveBadge::BitPerfect` нельзя построить вне модуля вердикта: конструктор приватный и требует `DriverFormat::Confirmed`, совпавшего с запрошенным (ТЗ-52, ОВ-14).
- **Порядок причин** «Не bit-perfect» (ТЗ-53 отдаёт его Части 3): тест не пройден → параметры драйвера не подтверждены → DSD→PCM → ресемплинг → downmix → усечение разрядности → 32-бит → float → mute → громкость → дизеринг. Обоснование: сначала то, что опровергает остальной анализ (провал теста, неподтверждённые факты); затем структурные преобразования в порядке тракта; затем пользовательские регуляторы. Дизеринг последний: он всегда следствие другой причины. Признак «+N» — число остальных причин.
- **«Тест»** — `TestBadge` строится из `TestRecord` для текущего `ConfigKey` и состояния текущего теста. Доступность — `fn test_availability(&BadgeState, ModeKind) -> TestAvailability`: активен, если бейдж `BitPerfect` или единственная причина — `TestFailed` (ОВ-20); иначе неактивен с блокером (ТЗ-61, ТЗ-62).
- **Замок** — `LockState` принадлежит движку (§2.6). Переходы происходят только по событиям из ТЗ-42 (шесть событий захвата), по открытию замка, смене режима или устройства, выходу, потере устройства. Play, пауза, стоп и смена трека входами автомата не являются: их у функции перехода нет (ТЗ-43, ТЗ-125).
- **Усиление** в колбэке задаётся типом стадии: `NoGain` (Строгий режим, DoP) или `AtomicGain` (Совместимый и Оптимальный, PCM). Колбэк Строгого режима не содержит кода громкости (ТЗ-41). `AtomicGain` проверяет состояние усиления один раз на период. При `GainState::Unity` без mute она передаёт `ExactI32` в целочисленном виде без изменений, то есть ведёт себя как `NoGain` (ADR-03, И-Р19). Поэтому вердикт `BitPerfect` в Оптимальном режиме при громкости 100 % соответствует фактическому выходу, а не только отсутствию этапа «громкость» в снимке.

**Последствия.** В Slint передаются `badge-kind` (enum Slint), `badge-text`, `badge-more`, `test-kind`, `test-text`, `test-enabled`, `lock-kind`, `lock-text` вместо трёх bool (§7 п. 9 ревью). Различимость без цвета (ТЗ-55, ТЗ-61) обеспечивает пара «значок + текст» для каждого варианта enum.

### ADR-07. Бэкенды вывода

**Контекст.** В cpal 0.18 WASAPI открывается только Shared, hog mode для CoreAudio нет. ALSA задаёт частоту через `ValueOr::Nearest` без сверки, `S24_3LE` не поддерживается, фактические `hw_params` не читаются (ревью §0, §3 «Платформы»). Решение 8 требует собственного ALSA-вывода для Exclusive. Классификация устройств сейчас идёт по подстрокам имён (§7 п. 18).

**Выполняет:** ТЗ-21, ТЗ-30, ТЗ-43, ТЗ-48, ТЗ-49, ТЗ-109…ТЗ-113, ТЗ-122, ТЗ-127.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | cpal для всего, доработки через форк | Форк cpal — постоянная стоимость сопровождения. `hw_params_current` и удержание PCM между потоками в модель cpal не вписываются |
| Б | Собственный ALSA-вывод на крейте `alsa` (безопасная обёртка alsa-lib, уже в дереве через cpal) для Exclusive; cpal — для Shared на всех ОС | Полный контроль над PCM, форматами и `hw_params`. cpal остаётся там, где его возможностей хватает |
| В | Сырой FFI к alsa-lib | `unsafe` без выигрыша относительно Б |

**Критерии:** Exclusive с резервированием, фактическими `hw_params`, `S24_3LE` и сменой частоты без закрытия PCM (решение 8); доступность режимов по возможностям бэкенда (ТЗ-109); тесты без устройства (ТЗ-114); минимум `unsafe`.

**Решение: Б.** Трейты и типы — §2.3, §2.9.

- `trait SharedBackend` — перечисление Shared-выходов и открытие Shared-потока. Реализация: `CpalSharedBackend`. На Linux он показывает только выходы аудиосервера (`default`, `pipewire`, `pulse`). Флаг выхода задаёт бэкенд, а не эвристика по имени в общем коде.
- `trait ExclusiveBackend` — `capabilities()`, перечисление аппаратных устройств, `acquire(DeviceId) -> Result<DeviceClaim, CaptureFailure>`, `configure(&mut DeviceClaim, StreamFormat) -> Result<DriverFormat, ConfigureError>`, `start(&mut DeviceClaim, Render) -> Result<StreamHandle, …>`. Реализация: `AlsaExclusiveBackend` (только Linux). На Windows и macOS реализации нет, и `BackendCaps::exclusive == false` (ТЗ-109, ТЗ-110).
- `DeviceClaim` владеет резервированием (ADR-08) и открытым PCM (`alsa::PCM`). Он существует от захвата до освобождения и не зависит от Play, паузы, стопа и смены трека (ТЗ-43). Возможности устройства (частоты, форматы, каналы) определяются на захваченном PCM через `HwParams::any` и `test_*`, без повторного открытия.
- Смена частоты: `drop` → `hw_free` → `hw_params(new)` → `prepare` на том же PCM (ТЗ-49). Если драйвер отказывает без закрытия, PCM закрывается и переоткрывается под удержанием резервирования. Отказ повторного открытия — `CaptureFailure::LostOnReopen`, замок переходит в «не удалось захватить», Shared-выход не открывается (ТЗ-49, решение 4).
- После `hw_params` бэкенд однократно читает `hw_params_current()` (формат, частота, каналы) вне колбэка и возвращает `DriverFormat::Confirmed` или `DriverFormat::Unreadable` (ТЗ-113, ОВ-14).
- Поток вывода `apap-alsa-out` создаётся на время воспроизведения. PCM **перемещается** в поток (`alsa::PCM: Send`), поток возвращает его как результат `JoinHandle::join`, и `StreamHandle::stop` кладёт PCM обратно в `DeviceClaim` без закрытия (§6.7). Вариант со scoped-потоком отвергнут: `std::thread::scope` блокирует вызывающий поток до конца воспроизведения, и тогда понадобился бы ещё один служебный поток на сессию без выигрыша. Цикл потока: `avail_update` → `render(&mut period_buf)` (это и есть аудио-колбэк) → `writei`, с ожиданием через `wait`. Системные вызовы (`writei`, `wait`) принадлежат циклу драйвера, а не функции `render` (ТЗ-98).
- Форматы Exclusive: `S16_LE`, `S24_3LE`, `S24_LE`, `S32_LE` (ОВ-32). Enum `ExclusiveSampleFormat` исчерпывающий, `unreachable!` не нужен (R-27, ТЗ-101).

**Последствия.** Появляется изолированный платформенный модуль `audio/backend/alsa_exclusive.rs` (cfg Linux) и общий `audio/backend/mod.rs` с трейтами. `unsafe` не требуется: крейт `alsa` безопасный. Если в «Алгоритмах» понадобится `unsafe` (например, для RT-приоритета потока), он будет изолирован и обоснован.

### ADR-08. Резервирование `org.freedesktop.ReserveDevice1`

**Контекст.** Эксперимент (`pw_reserve_test.md`, шаги 0–5) и решение 2: `hw:` открывается только после получения резервирования; оно удерживается всё время захвата и снимается после закрытия PCM. Чужие `RequestRelease` при закрытом замке отклоняются. Ожидание ответа владельца — 5 с (ОВ-34). Приоритет 0, имя «APAP» (ОВ-33). Нет сессионной шины — ОВ-35.

**Выполняет:** ТЗ-45, ТЗ-46, ТЗ-47, ТЗ-48, ТЗ-117, ТЗ-118, ТЗ-119, ТЗ-120, ТЗ-121, ТЗ-122, ТЗ-123.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | `zbus` (чистый Rust, уже в дереве через ksni), блокирующий API и экспорт объекта | Нет C-зависимости. Входящие вызовы обслуживает внутренний исполнитель zbus |
| Б | `dbus` (обёртка libdbus) | Новая C-зависимость, ручной цикл обработки сообщений |
| В | Вызывать `pw-reserve` как внешний процесс | Зависимость от утилиты PipeWire. Нельзя отклонять `RequestRelease` по состоянию замка |

**Решение: А.** Трейт `ReservationService` (§2.3) с реализацией `DbusReservation` и тестовой `FakeReservation`.

1. `RequestName("org.freedesktop.ReserveDevice1.AudioN", DO_NOT_QUEUE)` **без флага `ALLOW_REPLACEMENT`**. Всё время, пока плеер владеет именем, замок закрыт (или идёт захват). Без `ALLOW_REPLACEMENT` шина сама отклоняет чужие `RequestName(REPLACE_EXISTING)`, поэтому имя нельзя отобрать даже в обход вызова `RequestRelease` (ТЗ-118).
2. Если имя занято: вызвать у владельца `/org/freedesktop/ReserveDevice1/AudioN` метод `RequestRelease(priority = 0)` с таймаутом 5 с. Если он вернул `true`, повторить `RequestName` с флагами `REPLACE_EXISTING | DO_NOT_QUEUE`, по-прежнему без `ALLOW_REPLACEMENT`. Точная последовательность — §6.6.
3. Экспортировать объект с методом `RequestRelease(i32) -> bool`, который возвращает `false`, пока замок закрыт, и свойствами `ApplicationName = "APAP"`, `ApplicationDeviceName = <имя устройства>`, `Priority = 0`.
4. **Потеря имени.** Служба подписана на сигнал `NameLost` для своего имени. Если имя всё же потеряно (перезапуск шины, внешний `ReleaseName`, ошибка брокера), служба сразу посылает движку `InternalMsg::ReservationLost`. Движок в том же проходе цикла останавливает поток вывода и **немедленно закрывает PCM**, не дожидаясь конца трека, и переводит замок в `Failed(CaptureFailure::ReservationLost)`. Держать `hw:` без резервирования — это ровно сценарий R-29 (И-Р20).
5. **Открытие `hw:` после резервирования.** Прежний владелец (WirePlumber) может закрывать PCM асинхронно уже после ответа `true`. Поэтому `EBUSY` при открытии повторяется каждые 50 мс, но не дольше 1 с по инжектируемым часам (ADR-20); всё это время замок показывает «захват…». Если за 1 с открыть не удалось — `ReleaseName` и `CaptureFailure::BusyOutsideProtocol` (ТЗ-122). Другие коды ошибок не повторяются: `DriverRefused { errno }`.
6. Освобождение: закрыть PCM, затем `ReleaseName`. Порядок обеспечен порядком полей `DeviceClaim` (PCM объявлен раньше резервирования) и явным `Drop` (§5.2, И-Р1).
7. Аварийное завершение: соединение D-Bus закрывается вместе с процессом, шина освобождает имя (ТЗ-120; проверяется ручным сценарием ТЗ-120).

Ожидание (п. 2) идёт в потоке исполнителя zbus. Движок получает `EngineMsg::Internal(ReservationDone)` и всё это время показывает `LockState::Acquiring` (ТЗ-119).

Отсутствие сессионной шины (ОВ-35): трейт `AudioServerProbe` проверяет наличие сокетов `$XDG_RUNTIME_DIR/pipewire-0` и `$XDG_RUNTIME_DIR/pulse/native` (попытка `connect`). Нет шины и нет сервера — `Reservation::Unavailable`, `hw:` открывается, этап «Вывод» показывает предупреждение. Нет шины, сервер есть — `CaptureFailure::NoSessionBus`.

**Последствия.** `zbus` становится прямой зависимостью с `cfg(target_os = "linux")`. Отдельный поток исполнителя zbus живёт, пока есть хотя бы одно резервирование.

### ADR-09. Рантайм-проверка «Тест»

**Контекст.** Решение 10: побитовая сверка только по кнопке «Тест», на играющей музыке, до конца трека, но не дольше 30 с (ОВ-17). Нагрузка на колбэк — не более 10 % (ОВ-22). Underrun даёт «не завершён» (ОВ-16). Нужно сравнить исходный поток декодера с тем, что колбэк записал в точку передачи, после снятия zero-padding и распаковки DoP (ТЗ-63).

**Выполняет:** ТЗ-63, ТЗ-64, ТЗ-65, ТЗ-66, ТЗ-67.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | CRC32C/xxh3 блоков по N кадров на обеих сторонах, сверка в фоне (ревью §5 п. 7) | Колбэк получает данные периодами, не совпадающими с блоками. Нужна потоковая хеш-функция с состоянием между вызовами. Вероятность ложного ✓ ненулевая (2⁻³² для CRC32C) |
| Б | Выборочная проверка каждого K-го блока (ревью §5 п. 7, «альтернатива») | Пропускает ошибки в непроверенных блоках. Для ✓ по всему треку непригодна |
| В | Постоянная сверка | Отменена решением 10 |
| Г | Зеркалирование: колбэк копирует записанные слова в SPSC-ring зеркала (memcpy), декодер копирует эталон в SPSC-ring эталона; поток `apap-verify` выравнивает данные по номеру кадра, снимает формат и сравнивает побитово | Колбэк делает только копирование уже горячих данных. Сравнение точное: ложный ✓ исключён. Выравнивание по абсолютному номеру кадра, а не по блокам |

**Критерии:** ложный ✓ недопустим (ТЗ-63, P0); ≤ 10 % времени колбэка; 0 аллокаций в колбэке (ТЗ-64); проверяется именно точка передачи.

**Решение: Г.**

- Зеркало и эталон — SPSC-ring (`rtrb`) ёмкостью 2 с потока. Они создаются при старте теста в потоке движка, вне колбэка. Колбэк получает producer зеркала через lock-free слот (`TestSlot`, §2.9): атомарный указатель, который движок устанавливает, а колбэк забирает `swap`-ом один раз. Освобождает слот всегда движок после остановки теста.
- Колбэк пишет в зеркало `(frame_index, записанные байты периода)`, только пока `test_active`. Если места нет, он ставит `mirror_overflow` и не пишет. Итог теста тогда — «не завершён».
- Декодер во время теста пишет в эталон `ExactI32`-полезную нагрузку с номерами кадров (для DoP — DSD-байты до упаковки).
- `apap-verify` для каждого кадра восстанавливает исходное значение из выходного формата: `S16` — `<< 16`; `S24_3LE`/`S24_LE` — `<< 8`; `S32` — как есть; DoP — проверка маркера и чередования, затем 16 бит нагрузки. Ненулевые младшие биты там, где по `valid_bits` должен быть zero-padding, — несовпадение. Первое несовпадение — ✕ с позицией (ТЗ-63).
- Underrun, overflow, seek, смена трека, режима или устройства, открытие замка — «не завершён» (?) без ✕ (ТЗ-65, ТЗ-67). Пауза приостанавливает тест: время теста считается по кадрам, прошедшим проверку.
- Результат сохраняется по `ConfigKey` (ADR-19, ТЗ-66).

**Последствия.** Граница проверки — буфер, отданный драйверу (ТЗ-78): окно пишет об этом явно. Нагрузка измеряется бенчмарком из плана тестов (второй заход).

### ADR-10. SRC

**Контекст.** Текущий windowed-sinc не масштабирует срез при понижении частоты (алиасинг), вычисляет `sin()` на каждый тап и отбрасывает кадры сверх 8192 (R-7, R-13). Требования: уровень «высокое» — алиасинг ≤ −100 дБ, неравномерность ≤ 0.1 дБ, граница полосы 20 кГц / 0.45·fs_out; два уровня качества (ОВ-8); ≤ 15 % ядра при 384 кГц (ОВ-22); все кадры пакета до 65 535 обрабатываются (ТЗ-11); задержка фильтра — известная константа (ТЗ-11).

**Выполняет:** ТЗ-11, ТЗ-14, ТЗ-27, ТЗ-30, ТЗ-99 (SRC вне колбэка).

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Исправить текущий sinc (масштаб среза, окно) | Остаётся `sin()` на каждый тап; CPU-бюджет недостижим |
| Б | Собственный полифазный FIR: окно Кайзера, рациональное отношение L/M, таблица фаз строится при открытии (ревью R-13, §5 п. 3) | Полный контроль над порогами и задержкой. Все используемые отношения рациональные (семейства 44.1k/48k) |
| В | Крейт `rubato` за трейтом (ревью R-13, «вариант») | Готовый код. Пороги и групповую задержку для наших отношений пришлось бы подтверждать замерами; задержка зависит от внутренних буферов крейта |
| Г | libsoxr через FFI | Эталонное качество, но C-зависимость и сборка на Windows |

**Критерии:** пороги ТЗ-14 измеримы автотестом; задержка — константа конфигурации; нет аллокаций после открытия; нет новых зависимостей.

**Решение: Б.** Трейт `SampleRateConverter` (§2.9) позволяет позже подключить вариант В или Г без изменения декодера. Конвертер держит курсор внутри входного пакета и забирает кадры частями: входной пакет любого размера обрабатывается полностью (ТЗ-11). Таблицы `PolyphaseTable` кэшируются в движке по ключу `(fs_in, fs_out, SrcQuality)` как `Arc` и строятся при открытии вне RT. Параметры окна и число тапов для двух уровней — в «Алгоритмах». Пороги уровня «стандарт» утверждаются после замеров CPU (ОВ-8, ОВ-22).

**Последствия.** SRC работает в потоке декодирования на `f32` и выдаёт `RingPayload::F32`. Функция `latency_frames()` входит в `SampleRateConverter` и учитывается в позиции воспроизведения и в тестах ТЗ-11.

### ADR-11. DSD→PCM

**Контекст.** Сейчас это CIC 4-го порядка, две ступени ×8: около −12.5 дБ на 20 кГц, `i128` на бит, аллокации `Vec` на группу (R-21). Частоты по ОВ-9: DSD64 → 88.2 кГц; DSD128/256/512 → 176.4 кГц или ниже по устройству. Бюджет DSD512 — ≤ 25 % ядра (ОВ-22). Пороги качества задаются после выбора алгоритма (ОВ-9).

**Выполняет:** ТЗ-15, ТЗ-16, ТЗ-23, ТЗ-31, ТЗ-33.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Оставить CIC, исправить аллокации | Спад АЧХ и слабое подавление шума остаются |
| Б | CIC + компенсирующий FIR | Лучше А, но подавление внеполосного шума ограничено порядком CIC; вычисления по битам остаются |
| В | Многоступенчатый FIR: первая ступень — свёртка по байтовым LUT (ревью R-21, §5 п. 4), затем полуполосные ступени ×2 на `f32` | Первая ступень — одно сложение на байт вместо восьми операций на бит. АЧХ и подавление задаются проектированием фильтров |

**Решение: В.**

- Ступень 1: FIR длиной `8·K` бит; для каждой из `K` позиций байта предвычислена таблица из 256 частичных сумм (`f32`). Децимация до 352.8 кГц: DSD64 ÷8, DSD128 ÷16, DSD256 ÷32, DSD512 ÷64.
- Ступени 2…n: полуполосные FIR ÷2 до целевой частоты `dsd_pcm_rate(dsd, &caps)`: 176.4 кГц; для DSD64 — 88.2 кГц; ниже, если устройство или сервер не принимает (ТЗ-16).
- `dsd_pcm_rate` — единственная функция расчёта частоты. Её вызывают и планировщик, и декодер (И-Р11, R-18).
- Все буферы выделяются при открытии декодера. Выход — `RingPayload::F32`, разрядность выхода определяет колбэк (float в Совместимом, наибольшая разрядность устройства в Оптимальном, ОВ-9).

**Последствия.** Длины фильтров и пороги (неравномерность до 20 кГц, подавление 20–40 кГц) предлагаются в «Алгоритмах» и выносятся на утверждение в «Открытые вопросы» до приёмки ТЗ-15.

### ADR-12. DoP: где ставятся маркеры

**Контекст.** Сейчас пауза, seek и underrun дают `0` без маркеров, ЦАП выходит из DSD (R-14). `DoPFramer.leftover` не сбрасывается при seek (R-24). DoP допустим только в Exclusive (ТЗ-1, R-2).

**Выполняет:** ТЗ-1, ТЗ-2, ТЗ-3, ТЗ-39, ТЗ-108.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Декодер формирует готовые DoP-слова, колбэк на паузе генерирует тишину со своей фазой (ревью R-14) | После паузы следующее слово из ring может повторить маркер, уже выданный тишиной, — разрыв фазы |
| Б | Декодер кладёт в ring только 16 бит DSD-нагрузки на канал (`ExactI32`, биты 23..8); маркер ставит колбэк по своему счётчику фазы для каждого слова — и для данных, и для тишины | Фаза непрерывна по построению: её хранит только колбэк |

**Решение: Б.** Колбэк DoP (`DopRender`, §2.9) ставит в биты 31..24 маркер `0x05`/`0xFA` по счётчику фазы, который меняется на каждом кадре независимо от источника данных. Нет данных — нагрузка `0x6969`. DoP-маршрут строится только из `DeviceClaim` (И-Т3): в Shared DoP непредставим. Упаковщик нагрузки в декодере сбрасывается по поколению seek (ADR-13). Визуализатор при DoP не получает tap: у `DopRender` нет стадии tap (ТЗ-108).

**Последствия.** Выходные форматы DoP — только 24-битные контейнеры: `S24_3LE`, `S24_LE`, `S32_LE` (`DopOutFormat`). `S16_LE` для DoP непредставим.

### ADR-13. Seek, пауза и сброс ring

**Контекст.** Сейчас колбэк дренирует ring циклом `pop()` до подтверждения seek, это O(n) (R-8). Декодер публикует `seek_done` и сразу пишет, а колбэк в том же вызове сначала дренирует ring — начало после seek съедается (R-24). При паузе недописанный хвост теряется (R-6).

**Выполняет:** ТЗ-9, ТЗ-10, ТЗ-99, ТЗ-2.

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | O(1)-сброс в колбэке `read_chunk(slots).commit_all()` без смены протокола (ревью §6.3, «минимальный вариант») | O(1), но гонка R-24 остаётся |
| Б | Новая пара ring на каждый seek, передача consumer колбэку через lock-free слот (ревью §6.3) | Старый ring нужно освобождать вне RT; сложнее без выигрыша |
| В | Двухфазное рукопожатие: движок увеличивает `seek_requested`; колбэк, увидев новое поколение, сбрасывает ring за O(1) и публикует `seek_acked`; декодер пишет данные нового поколения только после `seek_acked` (первая редакция этого ADR) | O(1) в колбэке, но гонка остаётся (см. ниже). Отвергнут |
| Г | Трёхфазное рукопожатие: колбэк сбрасывает ring только после того, как декодер подтвердил остановку записи | Сброс гарантированно позже последней записи старого поколения и раньше первой записи нового. O(1) в колбэке |

**Почему двухфазная схема допускала старые данные после сброса.** Декодер — единственный producer. Он проверяет `seek_requested` между операциями, а не атомарно вместе с каждой записью. Возможен такой порядок:

1. Декодер прочитал `seek_requested = N−1`, декодировал пакет старой позиции и начал `write_chunk`.
2. Движок записал `seek_requested = N`.
3. Колбэк увидел N, сбросил ring (`commit_all` потребителя) и опубликовал `seek_acked = N`.
4. Декодер закончил `commit` пакета старой позиции: эти слоты лежат в ring уже **после** сброса. Иначе `PendingTail` старого поколения дописывается на следующей итерации.
5. Декодер увидел N и `seek_acked = N`, выполнил seek и записал данные позиции F следом за старыми.

Колбэк проигрывает сначала хвост старой позиции, потом F. Это нарушает ТЗ-10: первые сэмплы после seek должны начинаться ровно с F. Сброс в двухфазной схеме упорядочен относительно подтверждения, но не относительно последней записи декодера.

**Решение: Г.** Три фазы; поля — `SessionShared` (§2.9), алгоритм — §6.16.

1. **Запрос.** Движок записывает `seek_target_frame`, затем увеличивает `seek_requested = N` (Release).
2. **Остановка декодера.** Декодер проверяет `seek_requested` перед каждой записью в ring. Увидев N, он прекращает запись, отбрасывает `PendingTail`, выполняет seek в демультиплексоре и декодере, сбрасывает состояние SRC, DSD-фильтра и упаковщика DoP. Затем публикует `decoder_stopped = N` (Release). Все его прежние `commit` упорядочены раньше этой записи.
3. **Сброс в колбэке.** Колбэк, увидев `seek_requested > seek_acked`, сразу выдаёт тишину (для DoP — DoP-тишину) и не считает underrun. Ring он не трогает, пока `decoder_stopped != seek_requested`. Когда `decoder_stopped == seek_requested` (Acquire), колбэк видит все коммиты старого поколения, сбрасывает ring за O(1) и публикует `seek_acked = N` (Release).
4. **Возобновление.** Декодер пишет данные поколения N только после `seek_acked == N` (Acquire).

Серия seek подряд: если за время фазы 2 или 3 движок увеличил `seek_requested` до N+1, декодер повторяет фазу 2 для N+1: читает новый `seek_target_frame`, снова выполняет seek, публикует `decoder_stopped = N+1`. Колбэк подтверждает только совпадение `decoder_stopped == seek_requested`, поэтому промежуточное поколение N никогда не подтверждается. Цель seek декодер читает так: `seek_requested` (Acquire) → `seek_target_frame` → повторная проверка `seek_requested`; если значение изменилось — повтор. Рукопожатие выполняется и на паузе: поток вывода работает всегда, пока жива сессия (ТЗ-43).

`commit_all` у `rtrb` для типов без `Drop` (`i32`, `f32`) не обходит элементы: это O(1). Пауза: колбэк выдаёт тишину (для DoP — DoP-тишину), ring не трогает. Декодер при заполненном ring ждёт и хранит недописанный хвост (`PendingTail`); хвост сбрасывается только при seek и stop (ТЗ-9). Колбэк считает underrun, только если `playing`, не ждёт seek и не достигнут конец потока (ТЗ-68).

**Последствия.** Время колбэка не зависит от заполненности ring (ТЗ-99).

### ADR-14. Типизированные ошибки и реакции

**Контекст.** Ошибки на границах `open`/`choose_output` — `String` (§7 п. 19). I/O-ошибка превращается в EOF, `spawn` → `.ok()` (R-17). ТЗ-86 требует пять классов с разной реакцией.

**Выполняет:** ТЗ-24, ТЗ-32, ТЗ-36, ТЗ-46, ТЗ-51, ТЗ-86, ТЗ-87, ТЗ-88, ТЗ-92 (класс `BadFile`), ТЗ-100 (колбэк только пишет код сбоя), ТЗ-102, ТЗ-127.

**Варианты:** А — `String` с разбором текста (отвергнут); Б — `Box<dyn Error>` с downcast (класс не выражен в типе); В — enum на каждой границе + функция классификации (ревью §7 п. 19).

**Решение: В.** Типы — §2.4. Реакция — чистая функция `fn reaction(class: ErrorClass, mode: ModeKind, device: DeviceChoiceKind) -> Reaction` с исчерпывающим `match`:

| Класс | Совместимый | Оптимальный | Строгий |
|---|---|---|---|
| `Incompatible` | непредставим (планировщик Совместимого режима не возвращает `Incompatibility`) | непредставим | `Skip` |
| `CaptureFailed` | непредставим | `LockFailed` | `LockFailed` |
| `DeviceLost` | `FollowSystemDefault` при «системном по умолчанию», иначе `StopWithError` | `StopWithError` + `LockFailed(DeviceDisconnected)` + точка повторного захвата | то же |
| `BadFile` | `Skip` | `Skip` | `Skip` |
| `ReadError` | `Skip` | `Skip` | `Skip` |
| `Internal` (отказ запуска потока) | `StopWithError` | `StopWithError` | `StopWithError` |

**Последствия.** Колбэк и поток ошибок cpal сообщают о сбое только через атомик `SessionShared::fault` (код `StreamFault`), без логирования и блокировок (ТЗ-102). Движок опрашивает его в своём цикле (≤ 50 мс) и кроме того следит за «сердцебиением» колбэка: если счётчик вызовов не растёт дольше 500 мс при `playing`, это `StreamFault::Stalled`. Так срок ОВ-24 (1 с) выполняется, даже если бэкенд не вызвал колбэк ошибки (R-5).

### ADR-15. Последовательность треков и серия пропусков

**Выполняет:** ТЗ-36, ТЗ-38, ТЗ-85, ТЗ-89, ТЗ-90, ТЗ-91.

**Контекст.** Пропуск, Repeat All без бесконечного цикла, Repeat One ведёт к следующему, одно уведомление на серию, UI не замерзает (ТЗ-36, ТЗ-85, ТЗ-89…ТЗ-91). Плейлист принадлежит `MusicApp` («ромб»).

**Варианты.**

| # | Вариант | Оценка |
|---|---|---|
| А | Очередью владеет движок; UI отправляет копию плейлиста при каждом изменении | Дублирование состояния между потоками; копия тяжёлого списка (`Track`) при каждом изменении |
| Б | Чистая структура `Sequencer` + `SkipSeries` в UI-потоке; движок получает от UI `Open { track_ref }`, делает предпроверку и открытие, отвечает `Opened` / `Skipped` / `Failed` | Каждый шаг UI — O(1) без I/O. Плейлист остаётся на месте. Логика тестируется без UI и без устройства |

**Решение: Б.** `Sequencer::next_after(current, cause: AdvanceCause) -> Option<TrackRef>` учитывает Repeat, Shuffle и то, что пропуск при Repeat One ведёт к следующему треку (ТЗ-90). `SkipSeries` хранит множество `TrackId`, проверенных с начала серии, и счётчик для уведомления. Любой успешно начатый трек или действие пользователя закрывает серию (термин «серия пропусков»). Стоп во время серии — UI перестаёт отправлять `Open`; ответ на уже отправленный `Open` отбрасывается по поколению команды (ТЗ-91).

**Последствия.** `TrackId` — стабильный идентификатор строки плейлиста, не индекс: плейлист может меняться во время серии.

### ADR-16. Обнаружение и кэш устройств

**Выполняет:** ТЗ-105, ТЗ-126, ТЗ-127.

**Контекст.** Сейчас устройства перечисляются при каждом открытии трека с открытием всех PCM (R-4). ТЗ-105 требует кэш и обнаружение подключения/отключения на Linux (для ТЗ-126 и ТЗ-127).

**Варианты:** А — `udev`-монитор (новая зависимость libudev); Б — inotify на `/dev/snd` (видит узлы, но не смену карты за тем же номером); В — опрос `/proc/asound/cards` раз в 1 с в отдельном потоке с сравнением списка `(номер, id, имя)`.

**Решение: В.** Поток `apap-devwatch` (Linux) раз в 1 с читает `/proc/asound/cards` (несколько сотен байт) и при изменении посылает движку `EngineMsg::Internal(DevicesChanged)`. Движок перечисляет устройства один раз и обновляет `DeviceCatalog`. Задержка обнаружения ≤ 1 с укладывается в 10 с ТЗ-126. На Windows и macOS обновление — по команде «Обновить» и по событиям ошибки потока. Shared-выходы на Linux (серверные узлы) перечисляются через cpal вместе с тем же событием.

**Последствия.** Трейт `DeviceWatcher` с тестовой реализацией, которая генерирует события вручную (ТЗ-105, ТЗ-114).

### ADR-17. MD5 FLAC

**Выполняет:** ТЗ-69, ТЗ-75.

**Контекст.** `verify = false` (`decoder.rs:267`, R-28). Решение 10 и ОВ-15: проверка во всех режимах, вне колбэка; при несовпадении — отметка, уведомление, постоянная пометка трека; бейдж не меняется.

**Варианты:** А — встроенная проверка symphonia (`DecoderOptions { verify: true }`, результат в `finalize().verify_ok`); Б — собственный MD5 по декодированному потоку (новая зависимость `md-5`, повтор логики упаковки сэмплов FLAC).

**Решение: А.** Доступность проверена по исходникам symphonia 0.6.1 (§6.24). Поток декодирования создаёт FLAC-декодер с `AudioDecoderOptions::default().verify(true)`. Структура помечена `#[non_exhaustive]`, поэтому литерал структуры недоступен; тип называется `AudioDecoderOptions`, а не `DecoderOptions`. По естественному концу поток вызывает `AudioDecoder::finalize()` и читает `FinalizeResult::verify_ok: Option<bool>`, затем публикует `Md5Status`. Если была перемотка, результат — `NotChecked(Seeked)` независимо от ответа symphonia: `FlacDecoder::reset()` не сбрасывает накопитель MD5. Нулевой MD5 в STREAMINFO symphonia превращает в отсутствие `verification_check` в параметрах кодека; это `Absent`. Пометки хранятся в `track_marks.toml` (ADR-19).

### ADR-18. Визуализатор

**Выполняет:** ТЗ-107, ТЗ-108.

**Контекст.** Tap снимается у производителя до ring, поэтому спектр опережает звук на глубину буфера (R-19). DoP-слова попадают в анализатор как PCM (R-14). Требования: расхождение ≤ 50 мс (ОВ-25); при DoP — «недоступно при DoP».

**Варианты:** А — tap в колбэке (ревью R-19); Б — tap у производителя с меткой кадра и задержкой отображения на глубину ring (ревью R-19, «либо»).

**Решение: А.** Колбэк PCM-маршрута, пока `viz_tap_active`, копирует выданные кадры в `f32` в отдельный SPSC-ring визуализатора. Если места нет, кадры не пишутся (визуализатор может терять кадры, звук — нет). У `DopRender` стадии tap нет (ТЗ-108). Вариант Б отвергнут: задержка отображения на глубину ring зависит от заполненности и неточна после seek и underrun.

**Последствия.** Стоимость tap входит в бюджет колбэка ТЗ-99 и измеряется вместе с ним.

Запись выполняется вне UI-потока: во временный файл, затем `rename`. Нет файла `settings.toml` — `ModeSettings::default()` (Совместимый режим, ТЗ-124). Результаты теста по давности не устаревают (ОВ-18): дата хранится только для показа.

### ADR-20. Тестируемость: зависимости движка через трейты

**Выполняет:** ТЗ-114, ТЗ-115, ТЗ-116.

**Контекст.** Env-gated тесты `open_*` не исполняются; `open_auto_falls_back_once_on_exclusive_failure` логически сломан (R-26). ТЗ-114 требует тестов логики режимов, пропуска, замка, бейджа и окна без устройства.

**Решение.** Движок параметризован набором зависимостей:

```rust
/// Все внешние зависимости движка. В тестах каждая подменяется фейком.
pub struct EngineDeps {
    pub shared: Box<dyn SharedBackend>,
    pub exclusive: Option<Box<dyn ExclusiveBackend>>, // None на Windows/macOS
    pub reservation: Box<dyn ReservationService>,
    pub server_probe: Box<dyn AudioServerProbe>,
    pub os_probe: Box<dyn OsLevelProbe>,
    pub watcher: Box<dyn DeviceWatcher>,
    pub sources: Box<dyn SourceOpener>,   // открытие файлов и предпроверка
    pub clock: Box<dyn Clock>,            // монотонное время, управляемое в тестах
    pub store: Box<dyn PersistStore>,     // настройки, результаты «Теста», пометки
    pub events: Box<dyn EventSink>,
    pub spawner: Box<dyn ThreadSpawner>,  // отказ запуска потока подменяется (ТЗ-88)
}
```

Фейки: `FakeSharedBackend`, `FakeExclusiveBackend` (заданные возможности; счётчики захватов, открытий, освобождений; внедряемые отказы и расхождение `hw_params`), `FakeReservation` (ответы «разрешить / отказать / молчать N с»; порядок вызовов), `FakeServerProbe`, `FakeOsProbe`, `FakeDeviceWatcher`, `ManualClock`, `FakeSource` (заданный `SourceFormat` и поток-счётчик), `MemStore`, `VecSink`, `FailingSpawner`. Колбэк тестируется напрямую: фейковый бэкенд вызывает `render` с буфером нужного формата.

**Последствия.** Все тесты из перечня §7 ревью переводятся на фейки (ТЗ-115). Таблица «ячейка матрицы сценариев → тест» (ТЗ-116) — в «Плане тестов».

### ADR-21. Уровень ОС в пути сигнала

**Выполняет:** ТЗ-25, ТЗ-77.

**Контекст.** Этап «Уровень ОС» показывает системный микшер и его частоту/формат, если их можно определить, иначе «не контролируется плеером» (ТЗ-77). Сейчас этап пуст.

**Решение.** Трейт `OsLevelProbe` вызывается движком один раз при открытии Shared-потока, вне UI и с таймаутом 500 мс:

- Linux: чтение `clock.rate` / `clock.force-rate` из метаданных PipeWire (`pw-metadata -n settings`). Способ зафиксирован как предположение ревью (§5 п. 8). Если он недоступен, результат — `OsLevel::Unknown`. Проверка способа — в «Открытых вопросах».
- Windows: формат общего режима — `default_output_config()` cpal для WASAPI Shared (это mix format).
- macOS: номинальная частота устройства через cpal, достоверность «предполагается».
- Exclusive: `OsLevel::NotInvolved` без опроса.

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum DsdRate { Dsd64, Dsd128, Dsd256, Dsd512 }

/// Разрядность PCM-источника (1..=32).
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug)]
pub struct BitDepth(NonZeroU8);

/// Кодек и признак потерь (ТЗ-74).
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum Codec { Flac, Alac, Wav, Aiff, Mp3, Aac, Vorbis, Adpcm, Dsf, Dff, Other }

/// Факты об источнике, полученные из открытого файла (не из тегов плейлиста, ТЗ-74).
#[derive(Clone, PartialEq, Debug)]
pub struct SourceFormat {
    pub container: Container,
    pub codec: Codec,
    /// true для MP3/AAC/Vorbis: bit-perfect только относительно декодированного потока.
    pub lossy: bool,
    pub rate: SampleRate,
    pub layout: ChannelLayout,
    pub kind: SourceKind,
}

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum SourceKind {
    /// PCM с известной разрядностью (lossless). Для lossy (MP3/AAC/Vorbis)
    /// bits = 24: выход декодера, округлённый до 24-битных целых (ОВ-36).
    Pcm { bits: BitDepth },
    /// DSD; `rate` в `SourceFormat` — частота DSD-битов на канал.
    Dsd { dsd: DsdRate },
}

/// Блок, который декодер отдаёт тракту (заменяет `next_frames -> &[f32]`).
/// Варианта с float нет: все PCM-декодеры, включая lossy, отдают целые (ОВ-36).
pub enum SampleBlock<'a> {
    /// Целые исходной разрядности, выровненные влево; младшие 32−valid_bits бит = 0.
    /// Lossless: значения файла без изменений. Lossy (MP3/AAC/Vorbis): float-выход
    /// symphonia, округлённый до 24 бит без дизеринга, valid_bits = 24 (§6.10).
    ExactI32 { data: &'a [i32], valid_bits: BitDepth },
    /// DSD-байты, чередование по каналам, как в контейнере после нормализации.
    DsdBytes { data: &'a [u8] },
}

/// Формат сэмпла в точке передачи. Исчерпывающий (R-27, ТЗ-101).
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum OutputSampleFormat { S16Le, S24_3Le, S24Le, S32Le, F32 }

/// Подмножество форматов Exclusive на Linux (ОВ-32).
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum ExclusiveSampleFormat { S16Le, S24_3Le, S24Le, S32Le }

/// Форматы, допустимые для DoP: только 24-битное поле и шире (ADR-12).
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum DopOutFormat { S24_3Le, S24Le, S32Le }

impl OutputSampleFormat {
    /// Число значащих бит поля (16, 24, 24, 32; для F32 — 24 бита мантиссы).
    pub const fn field_bits(self) -> u8;
}

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub struct StreamFormat {
    pub rate: SampleRate,
    pub sample: OutputSampleFormat,
    pub channels: NonZeroU8,
}

### 4.2. Владение ресурсами

| Ресурс | Владелец | Кто ещё обращается | Механизм |
|---|---|---|---|
| `ModeSettings` (истина) | UI (`MusicApp`) | движок — копия | `EngineCmd::SetModeSettings` при каждом изменении и при старте (ТЗ-19) |
| `LockState`, `DeviceClaim` (резервирование + PCM) | движок | поток вывода — PCM на время воспроизведения | PCM заимствуется или перемещается в `apap-alsa-out` и возвращается при `stop` без закрытия (ADR-07) |
| `DeviceCatalog` | движок | UI — `Arc`-копия | событие `Devices` |
| Декодер, SRC, DSD→PCM, MD5 | `apap-decode` | — | создаётся на сессию, завершается по `stop`/поколению |
| Producer ring | `apap-decode` | — | SPSC `rtrb` |
| Consumer ring, счётчик фазы DoP, TPDF-генератор | колбэк (RT) | — | принадлежат `PcmRender`/`DopRender` |
| `SessionShared` | движок (`Arc`) | decode, RT — клоны `Arc` | только атомики; последний `Arc` освобождает движок после остановки потока вывода (И-Р7) |
| Зеркало и эталон «Теста» | движок создаёт, `apap-verify` читает | RT — producer зеркала через `TestSlot` | SPSC; освобождение — движок после остановки теста |
| Tap визуализатора | анализатор (consumer) | RT — producer | SPSC, пишется только при `viz_tap_active` |
| `Arc<SignalPath>` | движок создаёт | UI читает | событие `Opened`/`BadgeChanged` с поколением |
| Файлы `settings.toml`, `bp_tests.toml`, `track_marks.toml` | движок (`PersistStore`) | — | атомарная запись вне UI (ADR-19) |

### 4.3. Жизненный цикл операций

- **Open** (`EngineCmd::Open`). Движок читает заголовок файла через `SourceOpener::probe` (только заголовок, без seek-индекса) → `plan()`. Ошибка плана — `Skipped` без открытия потока (ТЗ-38). Затем Exclusive: `configure` на `DeviceClaim` → чтение `DriverFormat` → при расхождении перепланирование (Оптимальный) или `Skipped` (Строгий). Затем создаются ring и `SessionShared`, запускается `apap-decode`; он полностью открывает декодер (seek-индекс лениво) и сообщает `SessionReady` или `FileError`. После `SessionReady` запускается поток вывода и строится `SignalPath` → `Opened`. Прежний снимок недействителен с момента начала `Open`: UI показывает «нет потока» до `Opened` (ТЗ-56).
- **Pause/Play.** Меняется только атомик `playing`. Устройство и поток вывода остаются (ТЗ-43); колбэк выдаёт тишину, для DoP — DoP-тишину.
- **Seek.** Трёхфазное рукопожатие поколений (ADR-13, §6.16); движок сбрасывает MD5 в `NotChecked(Seeked)` и прерывает «Тест».
- **Смена трека той же частоты.** Поток вывода останавливается, PCM остаётся в `DeviceClaim`, новая сессия запускается на нём же. Если частота другая — сначала `configure` (ТЗ-49).
- **Громкость и mute.** Меняется атомик; движок пересобирает `SignalPath` (новое поколение, те же факты) и вердикт (ТЗ-60).
- **Потеря устройства.** Атомик `fault` или остановившийся `heartbeat` → движок в течение ≤ 1 с (цикл 20 мс + порог 500 мс) останавливает сессию. Затем `reaction()`: в Exclusive закрывает PCM, снимает резервирование, `LockState::Failed(DeviceDisconnected)`, сохраняет `ReacquirePoint`; `DevicesChanged` с тем же устройством → повторный захват и пауза на позиции (ТЗ-126). В Совместимом режиме с «системным по умолчанию» — переоткрытие на новом устройстве по умолчанию с той же позиции (ТЗ-127).
- **Выход.** UI отправляет `Shutdown`, ждёт `ShutdownComplete` до 2 с и завершает event loop. Движок останавливает тест, сессию и поток вывода, закрывает PCM, снимает резервирование, записывает хранилище (ТЗ-45). Сигналы `SIGTERM`/`SIGINT` переводятся в тот же путь через обработчик, который вызывает выход из event loop.
